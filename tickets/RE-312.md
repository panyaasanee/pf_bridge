### คำถาม (สองข้อ ตอบข้อไหนก่อนก็ปลดงานได้)
**Q1 — ไคลเอนต์มีทางรับ (inbound) สำหรับแปด id นี้หรือไม่ และมันเรียกอะไรต่อ**
สำหรับแต่ละ id: `0x37B1` `PartyInviteVital` · `0x2466` `PartyCmdVital` · `0xB9E9` `Community_RequestBeFriendVital` · `0x98A1` `Community_RemoveFriendVital` · `0x6E12` `Community_SendMailVital` · `0xAF60` `Community_GetMailContentVital` · `0x8183` `Community_DeleteMailVital` · `0x3700` `TradeInviteVital` —
ไคลเอนต์ลงทะเบียน id นั้นไว้ใน **ตารางส่งต่อขาเข้า** ด้วยหรือไม่ (คือมีเส้นทางที่ deserialize คลาสนี้ *จากสาย* แล้วส่งให้ฟังก์ชัน UI) หรือ id นี้เป็นขาออกอย่างเดียว?
ถ้ามี: `handler_va` ที่ `external/PF_PROTOCOL_REGISTRY.tsv` ให้ไว้ **ถูกเรียกจากลูปรับแพ็กเก็ตจริงหรือไม่** และฟังก์ชันแรกที่มันเรียกต่อ (ชื่อ/VA) คืออะไร

**Q2 — ถ้าไม่ใช่ id เดิม แล้วเซิร์ฟเวอร์ต้องตอบด้วยคลาสไหน**
สำหรับ `PartyInviteVital` อย่างเดียวก็พอเป็นตัวอย่างตัดสิน: ฟังก์ชันที่ประกอบและ **ส่ง** `0x37B1` ในไคลเอนต์ (เส้นทางกดปุ่ม "ชวนเข้าปาร์ตี้") หลังส่งแล้วมันรอ id ใด — มี state/ตัวจับเวลา/callback ที่ผูกกับ id ปลายทางตัวไหน

### ทำไมคำถามนี้ ไม่ใช่คำถามที่ตอบแล้ว (`grep` แล้ว: เจอ/ไม่เจอ ตาม `AGENTS.md` §7 — คำต่อคำจากเจ้าของใบ)
- `external/PF_SERIALIZER_FIELDS.tsv`: **เจอ** — `PartyInviteVital` 6 แถว (W 3 / R 3) · `PartyCmdVital` 4 (W 2 / R 2) · `TradeInviteVital` 6 (W 3 / R 3) · และ **ไม่เจอ** ศูนย์แถวสำหรับห้าคลาส `Community_*`
  🔴 **แถว W กับ R ของคลาสเดียวกันเหมือนกันทุกฟิลด์** ⇒ นั่นคือ serializer เขียน/อ่าน **คลาสเดียวกัน** ไม่ใช่ "ขาส่ง vs ขาตอบ" ⇒ ตารางนี้ **ไม่ตอบ** ว่าเซิร์ฟเวอร์ต้องตอบอะไรกลับ นี่คือช่องว่างที่ใบนี้ขอ
- `external/PF_PROTOCOL_REGISTRY.tsv`: **เจอ** ทั้งแปดคลาส มีคอลัมน์ `handler_va` ให้แล้ว (`PartyInviteVital` serializer `0x00664550` handler `0x0062EA70` vtable `0x00F34958` · `Community_RequestBeFriendVital` serializer `0x00642C40` handler `0x00645BF0` vtable `0x00F35C58`) แต่ **ไม่มีที่ไหนบอกว่า handler นั้นถูกเรียกจากลูปรับแพ็กเก็ตหรือเป็นแค่ vtable slot ที่ไม่มีผู้เรียก** — คำว่า "handler" ในตารางเป็นชื่อคอลัมน์ ไม่ใช่ผลการวัดว่ามีคนเรียก
- `external/00_SEARCH_HERE_FIRST.md`: ค้นแล้ว ไม่มีหัวข้อที่ครอบสำมะโนทางรับของสามตระกูลนี้

### เกณฑ์ผ่าน (ตอบแบบไหนถึงนับว่าตอบ)
1. ต่อหนึ่ง id: `INBOUND_YES <VA ของผู้เรียก> <ชื่อ/VA ฟังก์ชันถัดไป>` หรือ `INBOUND_NO` พร้อมหลักฐานว่า **ไม่มี** ผู้เรียกในอิมเมจ (ไม่ใช่ "หาไม่เจอ")
2. ตอบครบทั้งแปดได้ดีที่สุด · **ตอบแค่ `PartyInviteVital` ตัวเดียวก็ปลดงานรอบหนึ่งได้แล้ว** (สาย LANE-UI จะเขียนผู้ตอบตัวแรกให้คลาสนั้นทันทีในรอบที่ผลกลับมา ตามกฎ NOW "RE ตอบแล้ว → ใบสร้าง+GT รอบเดียวกัน")
3. ผลลบมีค่าเท่าผลบวก: `INBOUND_NO` ทั้งแปด = คำตอบว่า **ห้าม**ตอบด้วย id เดิม และสาย LANE-UI จะปิดแถวนี้แล้วย้ายแรงไปแถวอื่น แทนที่จะเดา

### ทำไมต้องเป็น RE ไม่ใช่ "ลองส่งดู"
เดา opcode แล้วส่งไบต์ออก = สิ่งที่ทำให้ไคลเอนต์ปิดตัวมาแล้ว (ใบ `1744`, `/warp x y`) · ซีมที่รอบนี้เพิ่งวางลง (`ui_dispatch.py`) ทำให้การส่งเป็นไปได้ **เชิงโครงสร้าง** เป็นครั้งแรก ⇒ ความเสี่ยงของการเดาเพิ่งเปลี่ยนจาก "เป็นไปไม่ได้" เป็น "เป็นไปได้" ในรอบนี้เอง นั่นคือเหตุผลที่ใบนี้ต้องมาก่อนบรรทัดโค้ดที่ประกอบเฟรมบรรทัดแรก
