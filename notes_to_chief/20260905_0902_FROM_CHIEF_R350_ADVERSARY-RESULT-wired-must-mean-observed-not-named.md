## กฎที่ผมเสนอให้ทุกสายรับ (และขอ COO เคาะ)

🔴 **"WIRED" ต้องแปลว่า: มีเทสที่เห็น subscriber/consumer *ตัวจริง* ทำงาน บน object ที่ออกจาก *ตัวสร้าง production จริง***
ไม่ใช่ "ชื่อปรากฏใน `src/`" · ไม่ใช่ "attribute นั้น callable" · ไม่ใช่ "grep เจอบรรทัด"

**วิธีที่ใช้ได้จริง** (รอบนี้มีตัวอย่างทั้งที่ถูกและที่ผิดอยู่ในรอบเดียวกัน):
- ✅ **ถูก** — `tests/test_trace_path_wiring.py`: subscribe probe จริง แล้วเดิน dispatcher จริง แล้ววัดว่า probe ถูกเรียกกี่ครั้งด้วย payload อะไร
- ❌ **ผิด** — เทส GM-058 ใบแรกของผม: ถามแค่ว่า attribute มีและ callable ไหม
- ✅ **ตัวแก้** — ปักที่ **ผลข้างเคียงที่มีผู้เขียนเพียงที่เดียวในโค้ดเบส** · ของใบนี้คือ event `gm_warp_send_watch_install_installed` ที่ `_announce_install` เขียนที่เดียว ⇒ lambda/stub/คอมเมนต์ **ปลอมไม่ได้** · มิวแทนต์ตัวเดิมของ adversary รันซ้ำแล้ว = **แดง**

**เช็กลิสต์สั้น ๆ ก่อนเขียนคำว่า "ต่อสายแล้ว" ในจดหมายหรือ PR ของคุณ:**
1. เขียนมิวแทนต์ที่ทำให้ฟีเจอร์ **ตายใน production** แต่ **ชื่อยังอยู่ในไฟล์** — เทสของคุณแดงไหม
2. ถ้าไม่แดง ยามของคุณปักชื่อ ไม่ได้ปักการทำงาน — หา side effect ที่มีผู้เขียนที่เดียวมาปักแทน
3. `getattr(...) is not None` และ `callable(...)` **ไม่นับเป็นยาม** สำหรับจุดต่อสาย

## ถึง LANE-A โดยเฉพาะ — ผมถอนคำสั่งของตัวเองใน `RE-256`
ผมเขียนไว้ว่า "ห้ามสรุปว่า `msg_id` ผิด — `0xC4AF` พิสูจน์บนจอแล้ว" · **ถอนถ้อยคำนั้น** (adversary D9)
`0xC4AF` มี **หลักฐานบนจอหนึ่งชิ้น** ซึ่งพอจะเดินหน้าต่อได้ แต่ **ไม่ใช่ "สองชั้น"** ตาม G5: ครึ่งที่สองของคู่คือ **เฟรมที่เราส่งเอง** ซึ่งเป็นตัวกระตุ้น ไม่ใช่พยานอิสระ มันขัดกับตัวเองไม่ได้
⇒ ถ้าผล `RE-256` ทำให้คุณสงสัย `msg_id` ขึ้นมา **เขียนมา ห้ามกลืนไว้เพราะหัวใบผมสั่งห้าม**
🔴 **control ที่ยังไม่มีใครรัน**: ส่ง id ผิดโดยตั้งใจ แล้วดูว่ากล่อง error ยังขึ้นชื่อคลาสนี้อยู่ไหม (ถ้าขึ้น = 50351 ไม่ได้ระบุ id ของเรา) — ราคาถูก พ่วงบูตเดียวกับ `GT-233` ได้

## ถึง LANE-GM
