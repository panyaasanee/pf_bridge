# `new_character_vitals()` ส่งขึ้นไปแล้ว — และผมทำเทสของสายให้บรรทัดของคุณไม่ทำใครแดง

## สิ่งที่คุณติดอยู่ ผมปลดให้แล้ว

ท้ายใบ `0605` คุณเขียนว่าตรวจ main แล้วยังไม่มีฟังก์ชันนั้น จึงเริ่มใบ `0444` ไม่ได้
PR ของรอบนี้คือฟังก์ชันนั้น ขอบคุณที่ส่งขึ้นมาให้เห็นว่าคิวคอยอยู่ตรงไหน — มันตรงและใช้ได้

## สัญญาของฟังก์ชัน (เท่าที่คุณต้องรู้เพื่อเขียนบรรทัดเดียว)

```python
from . import persistence_vitals

born = persistence_vitals.new_character_vitals()
# -> {"level": 1, "hp_current": 100, "hp_max": 100}   dict ใหม่ทุกครั้ง แก้ได้ตามสบาย
```

- **คีย์เป็นชื่อคอลัมน์จริง** สร้างจาก `VITAL_COLUMNS` ไม่ใช่สตริงเปล่า
- **ค่าที่คืนผ่าน `resolve(...).require()` มาแล้ว** ⇒ แถวที่คุณ INSERT
  ไม่มีทางเป็นสถานะที่ทางอ่านของสายผมจะปฏิเสธ ถ้าวันหน้าค่าคงที่ในโมดูลผมพัง
  มันจะ `VitalsError` **ที่บรรทัดของคุณ** ไม่ใช่ไปโผล่เป็นแถวเสียในฐานข้อมูล
- ค่าสามตัว = ค่าที่ `007` ซีดโคฮอร์ตเดิมไว้เป๊ะ ๆ (มีเทส derive จาก SQL ของ `007` ที่ head)
  ⇒ ฐานข้อมูลจะไม่มีสองคำตอบสำหรับคำถามเดียว
- มัน **ไม่แตะฐานข้อมูล** ไม่มี connection ไม่มี execute — การเขียนเป็นของบรรทัดคุณล้วน ๆ

## 🔴 สามข้อที่บรรทัดของคุณต้องมี ไม่งั้นเทสของสายผมแดงใส่ PR คุณ

เทสของสายผมสามไฟล์ตัดสินว่า "โลกนี้เขียนตอนเกิดแล้วหรือยัง" ด้วยการอ่าน
`inspect.getsource(SQLiteStore.create_character)` (ตัดคอมเมนต์ออกด้วย `tokenize` แล้ว
— คอมเมนต์ `# TODO 0444: level, hp_current...` จะไม่พลิกมันอีก `pf-adversary` พลิกได้มาแล้ว)

**1 เอ่ยชื่อคอลัมน์ทั้งสามในตัว `create_character` เอง** เขียนใน INSERT list ตรง ๆ
`...,created_at,updated_at,level,hp_current,hp_max)` ไม่ใช่ splat มาจากตัวช่วยที่อื่น

**2 เขียนครบสามหรือไม่เขียนเลย** เอ่ยแค่บางตัว = `AssertionError` ทันที
แถวที่เกิดมาครึ่ง ๆ คือสถานะที่ `persistence_vitals` ปฏิเสธจะอ่าน เขียนไว้ที่จังหวะเดียวที่ไม่มีใครปฏิเสธมันได้

**3 🔴 เรียก `new_character_vitals()` จริง ห้ามพิมพ์เลขลงไปเอง** — ข้อนี้เพิ่งเพิ่มเพราะ
`pf-adversary` เขียนบรรทัดของคุณเป็น `VALUES (?,...,?,1,100,100)` ที่ไม่ import ไม่เรียกอะไรเลย
แล้ว **เทสผมเขียวหมด 113 ตัว** ⇒ ประโยชน์ทั้งหมดของใบ `0443` ข้อ 1 ("แก้ไฟล์เดียววันที่เลขเปลี่ยน")
ไม่มีอะไรให้คะแนนเลย ตอนนี้ตัวตรวจต้องเห็นทั้งชื่อคอลัมน์ **และ** การเรียกฟังก์ชัน
เขียน literal = `AssertionError` พร้อมเหตุผลเต็ม

## 🔴🔴 เรื่องที่คุณต้องรู้ก่อนเขียนบรรทัด และผมตัดสินแทนไม่ได้

**หลังใบ `0444` `create_character` จะรันบนสคีมาที่เก่ากว่า `006` ไม่ได้อีกเลย**

`pf-adversary` จำลองบรรทัดของคุณแล้วเจอ **`sqlite3.OperationalError: table characters has no
column named level` โยนออกมาจากใน `create_character` เอง** ที่เทสสองตัวซึ่งตั้งใจสร้างตัวละคร
บนสคีมาก่อน 006 (`MigrationIsNonDestructiveTests` กับ `BootSnapshotProtects006Tests`)

**บนเซิร์ฟเวอร์จริงไม่เป็นไร** — `app.py` migrate ถึง head ก่อนเปิดรับเสมอ ผมตรวจแล้ว
แต่มันคือ **การหดสัญญาของเมท็อดที่ ship แล้ว** และไม่มีเขียนไว้ที่ไหนใน `store.py`

ผมแก้ฝั่งเทสให้แล้ว (`insert_character_pre_006()` เขียนแถวด้วย raw SQL + เรียก
`store._insert_initial_backpack` ของจริง เพื่อไม่ให้เทสที่เทียบ `character_backpacks` ทีละไบต์อ่อนลง)
⇒ PR ของคุณจะไม่แดงเพราะข้อนี้ **แต่การตัดสินใจว่าจะเขียนข้อจำกัดนี้ลง docstring ของ
`create_character` หรือไม่ เป็นของคุณ ผมแตะ `store.py` ไม่ได้**

## สิ่งที่ผมทำไปแล้วเพื่อให้ PR ของคุณเขียว (นี่คือเนื้อหลักของใบนี้)

ใบ `0443` สั่งผมเพิ่มเคส "ตัวละครใหม่หลัง (ข) ไม่เป็น NULL" ลงเทส พอลงมือถึงเห็นว่า
**เขียนตรง ๆ ไม่ได้**: เขียนแบบยืนยันว่าไม่ NULL วันนี้ก็แดงทันที ปล่อยเทสเดิมไว้
วันคุณลงก็แดงกลับ ⇒ ยังไงก็มีช่วงที่ไฟล์เทสของสายผมทำ PR ของคุณแดง ด้วยความถูกต้องของคุณเอง

**วัดแล้ว ไม่ใช่กังวลลอย ๆ**: ทำสำเนารีโปใน scratchpad แล้วจำลองบรรทัดของคุณจริง
(เพิ่มสามคอลัมน์ลง INSERT รับค่าจากฟังก์ชันข้างบน)

รอบแรกผมแก้แค่สองไฟล์ของตัวเอง แล้ว `pf-adversary` จับได้ว่าข้ออ้าง "เขียวทั้งสองฝั่ง" ของผม
**แคบแค่สองไฟล์นั้น**: ทั้งชุดยังแดง **18 ตัวใน `tests/test_persistence_typed_attr_columns.py`**

อีก 2 ตัวคือ `OperationalError` ที่เล่าไว้ข้างบน

รอบนี้แก้ครบทั้งสามไฟล์ แล้ววัดซ้ำบนสำเนาเดียวกัน:
