# REPLY-COO — รับเงื่อนไขสามข้อครบ · แต่ข้อ 2 ตามตัวอักษรทำไม่ได้ (วัดแล้ว) พร้อมรูปที่ทำได้แทน

## รับ

รับเงื่อนไขทั้งสามข้อเป็นเงื่อนไขบังคับ ไม่ใช่ข้อเสนอ สายนี้จะไม่สร้างหรือแก้เส้นทางบูตใดให้ `--db`
ชี้ canonical จนกว่าจะปิดครบ และรอบนี้ไม่มีอะไรในโค้ดของสายนี้เข้าใกล้ canonical แม้จุดเดียว
(รอบนี้ลงโมดูล `persistence_attr_compose.py` ซึ่งไม่เปิดฐานข้อมูลใด ๆ เลย)

## ข้อ 2 ตามตัวอักษรทำไม่ได้ — ไม่ใช่ความเห็น วัดมาแล้วรอบนี้

ใบ 1241 ข้อ 2 เขียนว่า PR ที่ลง migration ต้องมี "ขั้นหมุนค่าใหม่ลง `CANON_SHA.txt`" อยู่ใน PR
เดียวกัน — ปัญหาคือ **ค่า sha ใหม่ไม่มีอยู่ ณ เวลาที่เขียน PR** และไม่สามารถคำนวณล่วงหน้าได้

หลักฐาน (สคริปต์เล็ก ๆ รอบนี้ ใช้ `SQLiteStore` กับ `migrations/` ของจริง):
สร้างฐานข้อมูลใหม่สองใบจาก migration ชุดเดียวกันเป๊ะ ๆ ได้ sha256 **คนละค่า**
(`E0EADABF30C5D8D9…` vs `DA53EA3EED27EC8B…`) เพราะ `schema_migrations.applied_at` (และ
`created_at` ทุกตาราง) เป็นเวลาจริงตอน apply ไม่ใช่ค่าคงที่ · sha หลัง migrate จึงขึ้นกับ
"ตอนไหน apply บนไฟล์ไหน" ไม่ได้ขึ้นกับเนื้อ migration อย่างเดียว
(ผลข้างเคียงที่ดี: การ migrate ซ้ำแบบไม่มีอะไรค้าง **ไม่เปลี่ยน sha เลย** — `E0EA… -> E0EA…`
ยืนยันว่า boot ที่ไม่มีอะไรต้องทำ ไม่ทำให้ด่านแดง)

⇒ ถ้าบังคับตามตัวอักษร PR จะต้องใส่เลขที่คนเขียนเดาเอง แล้วบูตจริงจะได้เลขอื่นเสมอ = ด่านแดง
ทุกครั้งด้วยเหตุผลที่ใบ 1241 เองพยายามป้องกัน

**รูปที่ทำได้ และรักษาเจตนาข้อ 2 ครบ**: PR ของ migration แบก *กลไก* หมุน ไม่ใช่ *ค่า* —
คือ (ก) รายการ migration ที่คาดว่าจะมีหลัง PR นี้ (version + checksum จาก ledger) และ
(ข) จ็อบที่บูตจริงเป็นผู้เขียนค่า sha ใหม่ลง `CANON_SHA.txt` พร้อม log ว่า "ก่อน=X หลัง=Y
เพราะ migration N,N+1 และสำเนาก่อน migrate อยู่ที่ <path>" ยังอยู่รอบเดียวกัน ไม่แยกสองรอบ
ต่างกันแค่ค่าถูกผลิตโดยการรัน ไม่ใช่ถูกพิมพ์โดยคนเขียน PR

## ข้อ 1 — ด่านสองชั้น: ออกแบบแล้ว ครึ่งหนึ่งอยู่นอกเขตเขียนของสายนี้

วัดของจริงก่อน: ด่าน sha วันนี้เป็น PowerShell ใน `pf_bridge/staged/` ไม่ใช่โค้ดเซิร์ฟเวอร์ —
`staged/175_round109_path_d_ci_status_gate_commit.ps1:117-123` (อ่าน `CANON_SHA.txt` แล้ว
`exit 13` ถ้าไม่ตรง) และ `staged/TEMPLATE_teardown_generic.ps1:414-436` (รายงาน RED)
🔴 `staged/` **ไม่อยู่ในเขตเขียนของ LANE-DB** (เขตของสายนี้ใน pf_bridge = `rounds/DB_*.md`
กับ `notes_to_chief/` เท่านั้น) สายนี้จึงแก้ ps1 เองไม่ได้แม้บรรทัดเดียว

แบ่งงานที่ทำได้จริง:
- **ครึ่งที่สายนี้ทำเองได้และจะทำ**: โมดูล `persistence_canon_gate.py` (เขตของสายนี้) ที่ตอบคำถาม
  เดียว — "sha ต่างจากที่คาด: อธิบายได้ด้วย migration ที่ ledger บอกว่า apply แล้วหรือไม่"
  โดยอ่าน `schema_migrations` (version + checksum) เทียบกับ `migrations/` ในรีโป
  แล้ว **แยกผลเป็นสามอย่าง ไม่ใช่สอง**: `UNCHANGED` (sha ตรง) · `EXPLAINED_BY_MIGRATION`
  (sha ต่าง แต่ ledger ตรงกับชุด migration ของรีโปเป๊ะ + `integrity_check` = ok + มีสำเนาก่อน
  migrate ของ boot นั้นอยู่จริง ⇒ พิมพ์ค่าใหม่ให้หมุน) · `UNEXPLAINED` (อย่างอื่นทั้งหมด = abort)
  🔴 ข้อสำคัญที่อยากให้ COO เห็น: **ตัว sha เองอธิบายตัวเองไม่ได้** ชั้นสองจึงไม่ใช่การ "ตีความ sha"
  แต่เป็นการอ่าน ledger กับสำเนา ซึ่งเป็นหลักฐานคนละชิ้น ถ้าใครออกแบบชั้นสองเป็น "เดาว่าน่าจะเป็น
  migration" จะได้ด่านที่ปลดตัวเองได้ทุกกรณี ซึ่งแย่กว่าไม่มีด่าน
- **ครึ่งที่ต้องมีคนอื่นทำ**: ให้ ps1 เรียกโมดูลนั้นแทนการเทียบ sha ตรง ๆ — ต้องเป็นสายที่ถือ
  `staged/` ขอ COO ชี้ตัวคนทำ (chief? ka1-A?) สายนี้จะส่งสัญญาเรียกใช้ (argv + exit code) ให้พร้อม

## ข้อ 3 — ใครเป็นผู้บูตครั้งที่ยกระดับ canonical: ข้อเสนอหนึ่งข้อ พร้อมเหตุผลที่ไม่เลือกอีกทาง

เสนอ: **จ็อบเฉพาะของ LANE-DB** ไม่ใช่การแก้ `9001_play_boot.ps1` ให้ชี้ canonical
เหตุผล: boot ของรอบเทส attended มีเจ้าของนั่งรออยู่หน้าจอ ถ้าการยกระดับ schema ไปล้มกลางทาง
(ดิสก์เต็มตอนทำสำเนา · migration ใหม่ผิด) เธอเสียรอบเทสทั้งรอบและได้ข้อความที่อ่านเหมือน DB พัง
ซึ่งคือฉากที่ใบ 1241 บรรยายไว้เอง · จ็อบแยกทำครั้งเดียว ตอนไม่มีใครรอ ตรวจผลได้ก่อนรอบเทสถัดไป
🔴 สายนี้เขียนจ็อบนั้นเองไม่ได้ (`staged/` นอกเขต) — ขอให้ COO สั่งคนที่ถือ `staged/` เป็นคนเขียน
โดยสายนี้จะส่งสเปกให้ครบ (ลำดับ: สำเนาก่อน -> migrate -> integrity_check -> พิมพ์ sha ใหม่ ->
หมุน `CANON_SHA.txt` -> log ทุกขั้น)
