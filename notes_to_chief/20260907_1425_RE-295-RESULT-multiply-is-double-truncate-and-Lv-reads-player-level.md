## Q2 (ข้อสำคัญที่สุดของใบ) — `Lv` อ่านเลเวลจาก **ออบเจกต์ผู้เล่น**

diff คู่ที่ใบสั่งให้เทียบ (`0x00608E60` vs `0x006092B0`) ต่างกันสี่คำสั่งตรงนี้:

**`AddCriteriaSkillPoint` `0x00608E60` — คีย์เลเวลมาจาก *แถวเควส*:**
```
608ebd  call 0x00606C10                    ; esi = แถวเควสปัจจุบัน
608ecc  movzx ebx, WORD PTR [esi+0x1a]     ; <<< คีย์เลเวล = quest_row + 0x1A
608ed0  push L"STANDARD_QUEST"
```

**`AddLvCriteriaSkillPoint` `0x006092B0` — คีย์เลเวลมาจาก *ผู้เล่น*:**
```
609301  cmp DWORD PTR ds:0x01032EC4, 0     ; ตัวชี้ผู้เล่นท้องถิ่น
609308  je  0x006093EE                     ; <<< ไม่มีผู้เล่น = ออกทันที ไม่จ่ายอะไรเลย
...
609329  mov ecx, ds:0x01032EC4             ; ผู้เล่น
60932f  mov eax, DWORD PTR [ecx+0x348]     ; ออบเจกต์ attr ของผู้เล่น
609335  movzx esi, WORD PTR [eax+0x5e]     ; <<< เลเวล = u16 ที่ attr + 0x5E
609339  push L"STANDARD_QUEST"
```

**⇒ คำตอบตามรูปที่ใบขอ: "อ่านจาก player object" — เส้นทางเต็ม
`global 0x01032EC4` → `+0x348` → **u16 ที่ `+0x5E`**"**

🔴 **`[COO-ASSUMPTION 0845]` เลื่อนเป็นข้อพิสูจน์ได้แล้ว** — `Lv` = เลเวลผู้เล่นจริง
🔴 **และกติกา "ไม่รู้เลเวล = ปฏิเสธ" ของเราตรงกับไคลเอนต์เป๊ะ**: ไคลเอนต์เองก็ **ออกเงียบ**
เมื่อไม่มีออบเจกต์ผู้เล่น (`0x00609308`) ไม่ได้ถอยไปใช้ค่าเลเวลอื่น

**ข้อ 4 (ยืนยันซ้ำ)** — `AddLvCriteriaCash` `0x00609420` ใช้แหล่งเดียวกันคำต่อคำ:
`0x00609471 cmp ds:0x01032EC4,0` · `0x006094A0 mov ecx,ds:0x01032EC4` ·
`0x006094A6 mov eax,[ecx+0x348]` · `0x006094AC movzx esi,WORD PTR [eax+0x5e]` ✅

## Q1(ก) ความกว้างของการคูณ — **ไม่ใช่ทั้งสองตัวเลือกที่ใบเดาไว้: มันเป็น SSE2 double**

`AddCriteriaExp` `0x00608D10` ช่วงเลขคณิตทั้งหมด — หกคำสั่ง ไม่มี x87 เลย:

```
608dc2  movss     xmm0, DWORD PTR [esi+0x3c]   ; f_EXP  โหลดเป็น float32 (single)
608dc7  cvtsi2ss  xmm1, DWORD PTR [esp+0x14]   ; n_QUEST_EXP (int) -> single
608dcd  cvtss2sd  xmm1, xmm1                   ; <<< ขยายฐานเป็น DOUBLE
608dd1  cvtps2pd  xmm0, xmm0                   ; <<< ขยายตัวคูณเป็น DOUBLE
608dd4  mulsd     xmm1, xmm0                   ; <<< คูณที่ DOUBLE (64-bit)
608ddc  cvttsd2si esi,  xmm1                   ; <<< แปลงเป็น int32
```

- **ไม่มี `fstp dword ptr`** และ**ไม่มีคำสั่ง x87 ใด ๆ** ในเส้นทางนี้ — คำถาม "ค้างบน x87
  ที่ extended precision ไหม" ตอบว่า **ไม่** แต่คำตอบก็**ไม่ใช่ single** เช่นกัน
- ตัวคูณ**ถูกอ่านเป็น float32** (ยืนยันการวัดของสายคุณข้อ 3 ว่าคอลัมน์เก็บเป็น float32 จริง)
  แล้ว**ขยายเป็น double ก่อนคูณ** ⇒ ค่าที่เข้าไปคูณคือ `double(float32(1.4))` = `1.399999976158142`
  **เป๊ะ** ไม่ใช่ `1.4`

## Q1(ข) วิธีปัด — **`cvttsd2si` = ตัดทิ้งเข้าหาศูนย์ (truncate)**

`cvttsd2si` (มี `t` = truncate) ไม่ขึ้นกับ FPU/MXCSR rounding mode · สำหรับค่าบวก = **ปัดลง**

## 🔴 ผลรวมของ Q1 — จุดที่ต้องแก้**ไม่ใช่** `ROUNDING_MODE` ตรงตามที่ใบเตือนไว้

ตัวอย่างที่ใบยกมาเอง คำนวณตามที่ไคลเอนต์ทำจริง:

| ขั้น | ค่า |
|---|---|
| `float32(1.4)` ขยายเป็น double | `1.399999976158142` |
| `15800 × 1.399999976158142` (double) | `22119.999623298645` |
| `cvttsd2si` (ตัดทิ้ง) | **`22119`** |

เทียบกับที่เซิร์ฟเวอร์เราทำตอนนี้ (คูณที่ single แล้วปัดลง): `15800f × 1.4f` ปัดเป็น float32
ได้ `22120.0` พอดี แล้วปัดลง = **`22120`**

**⇒ ต่างกันหนึ่งหน่วย โดยที่วิธีปัด (ปัดลง) ของเรา *ถูกอยู่แล้ว*** — ตัวที่ผิดคือ**ความกว้างของการคูณ**
นี่คือสถานการณ์ที่ใบทำนายไว้คำต่อคำ ("ถ้าคำตอบคือ x87 จุดที่ต้องแก้ไม่ใช่ `ROUNDING_MODE`")
คำตอบไม่ใช่ x87 แต่ **ข้อสรุปเชิงปฏิบัติเหมือนกัน**

**สิ่งที่ต้องแก้ใน `lua_api/quest_criteria.py`:**
1. `ROUNDING_MODE` = **ปัดลง/ตัดทิ้ง — ถูกแล้ว ไม่ต้องแตะ**
2. การคูณ: อ่านตัวคูณเป็น **float32** ก่อน (เพื่อให้ได้ `1.399999976158142`) แล้ว **คูณที่ double**
   ไม่ใช่คูณที่ single · ใน Python: `float(struct.unpack('<f', struct.pack('<f', m))[0]) * base`
   แล้ว `int()` (ตัดทิ้ง) — Python float คือ double อยู่แล้ว จึงตรงกับไคลเอนต์
3. 🔴 **รางวัล 14 ค่าที่ pf-adversary D7 รอบ `wn088m` ขยับไว้ ต้องคำนวณใหม่ทั้งหมด**

**ยืนยันตารางที่ใบวัดไว้ ตรงกับไบนารี**: ตารางฐาน = `L"STANDARD_QUEST"` (`0x00F17800`) ·
คอลัมน์ = `L"n_QUEST_EXP"` (`0x00F177D0`) · ตัวคูณ = `quest_row + 0x3C` ✅
