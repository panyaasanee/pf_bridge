# ③ ปม `TriggerCastSkillVital` — วัดแล้วว่า "วิธีที่ใช้อยู่มองไม่เห็น" ไม่ใช่ "ของไม่มี"

**ผู้เขียน:** ผู้ช่วย (cloud · อ่านอิมเมจผ่าน mount แบบอ่านอย่างเดียว) · **ถึง:** chief (cc) และ Panya
**ต่อจาก:** `20260824_0055_GT050-RESULT-CLEARNRESULT-CLOSED-TRIGGER-DIRECTION-UNRESOLVED.md`
**สถานะ:** ไม่ได้ปิดปม — แต่เปลี่ยนสถานะปมจาก "หาไม่เจอ" เป็น **"พิสูจน์แล้วว่าวิธีนี้หาไม่เจอแม้กับของที่รู้คำตอบอยู่แล้ว"**

---

## สิ่งที่ทำ

GT-050 จบด้วยประโยคซื่อสัตย์ว่าไม่พบสายที่ `TriggerCastSkillVital` วิ่งเข้า outbound submit `0x005DD800`
คำถามที่ยังไม่มีใครถามคือ: **ถ้าเอาข้อความที่ *รู้แน่* ว่าไคลเอนต์ส่งเอง มาผ่านวิธีเดียวกัน วิธีนี้จะเจอไหม**

ตัวควบคุมที่ใช้: **`PickupTerrainThing`** — GT-046 พิสูจน์แล้วว่าไคลเอนต์สร้างที่ `0x006B0639`
และเข้าคิวส่งออกที่ `0x006B0653` (จุดจุดชนวน `WM_LBUTTONDOWN 0x201`)

## ผลการวัด

**ยืนยันด้วยไบต์เองก่อน** — VA `0x006B0653`, file offset `0x002AFA53`, bytes `e8 a8d1f2ff` = `E8 call 0x005DD800`
⇒ ตัวควบคุมมี **direct edge** เข้า submit จริง · ทั้งอิมเมจมี direct `E8/E9` เข้า `0x005DD800` ทั้งหมด **277 จุด**
(ตรงกับเลข 277 ที่ GT-050 รายงาน — re-derive อิสระผ่าน)

แล้วลองสองวิธีที่จะ "เดินย้อนจากตัวข้อความไปหาจุดส่ง":

| วิธีค้น | ครอบคลุมกี่ข้อความ | ตัวควบคุมถูกพบไหม |
|---|---:|---|
| หา **vtable literal** ภายใน 0x200 ไบต์ก่อนจุดเรียก submit | 23 / 502 (4.6%) | 🔴 **ไม่พบ** |
| หา **id_global literal** ภายใน 0x200 ไบต์ก่อนจุดเรียก submit | 5 / 519 (1.0%) | 🔴 **ไม่พบ** |

**ทั้งสองวิธีพลาดตัวควบคุมที่เรารู้คำตอบอยู่แล้ว**

### ทำไมถึงพลาด — เห็นถึงระดับไบต์

ไบต์รอบจุดสร้างของตัวควบคุม (VA `0x006B0610`–`0x006B0660`):

```
6a 00                 push 0
68 0C A9 F0 00        push 0x00F0A90C        <- ไม่ใช่ vtable ไม่ใช่ id_global
b9 94 13 03 01        mov  ecx, 0x01031394
e8 52 89 F3 FF        call 0x005E8F90        <- สร้างวัตถุ
...
e8 a8 d1 f2 ff        call 0x005DD800        <- ส่งออก
```

- vtable ของมัน `0x00F3005C` — **ไม่ปรากฏในหน้าต่างนี้เลย**
- id_global ของมัน `0x0108202C` — **ไม่ปรากฏเช่นกัน**

⇒ **จุดสร้างของข้อความไม่ได้อ้าง identity ของข้อความด้วยตัวมันเอง** วัตถุถูกสร้างผ่านตัวสร้างที่รับ literal อื่น
ดังนั้นการเดินย้อนจาก vtable/id_global ไปหาจุดส่ง **โครงสร้างมันไปไม่ถึงอยู่แล้ว** ไม่ใช่เรื่องหน้าต่างสั้นไปหรือกวาดไม่ครบ

### สมมติฐานที่ผู้ช่วยตั้งแล้วฆ่าทิ้งเอง

เห็น literal `0x00F0A90C` (ตัวควบคุม) กับ `0x00F0A8D0` (ที่ pool factory ของ `TriggerCastSkillVital` push)
ห่างกัน `0x3C` พอดี → ตั้งสมมติฐานว่าเป็น **ตารางตัวระบุชนิดข้อความ** ถ้าจริงจะปิดปมได้ทันที
**ฆ่าทิ้งแล้ว:** `0x00F0A8D0` ถูก push **683 จุด** และ `0x00F0A90C` **1,276 จุด** ทั่วอิมเมจ
ทั่วไปเกินกว่าจะเป็นตัวระบุรายข้อความ (น่าจะเป็น RTTI/exception record หรือ literal ร่วมของ MSVC)
⇒ **สมมติฐานตาย จดไว้เพื่อไม่ให้ใครเดินซ้ำ**

## 🔴 ข้อสรุปที่ใช้ได้จริง

1. **การที่ `TriggerCastSkillVital` ไม่โผล่ในสำมะโน outbound = ไม่มีข้อมูล ไม่ใช่หลักฐาน**
   สำมะโนเดียวกันก็พลาดข้อความที่เรารู้ว่าเป็น outbound ⇒ ผลลบนี้ไม่นับเป็นน้ำหนักไปทางฝั่ง inbound แม้แต่นิดเดียว
2. GT-050 ที่ปฏิเสธจะให้คำตัดสิน **ถูกต้องแล้ว** — ตอนนี้มีตัวเลขรองรับ ไม่ใช่แค่ความระมัดระวัง
3. 🔴 **ห้ามใครรันสำมะโน direct-call แบบเดิมซ้ำแล้วคาดหวังคำตอบอื่น** — เพดานถูกวัดแล้ว
4. **เกณฑ์รับรองวิธีใหม่ (บังคับ):** วิธีไหนก็ตามที่จะใช้ตอบเรื่องทิศทาง **ต้องพิสูจน์กับ `PickupTerrainThing` ก่อน**
   ถ้าวิธีนั้นบอกไม่ได้ว่า `PickupTerrainThing` เป็น outbound = วิธีนั้นใช้ตอบเรื่อง `TriggerCastSkillVital` ไม่ได้
