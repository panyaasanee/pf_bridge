# LANE-K-ASK-COO: เซสชันนี้เขียนไฟล์คิวหลัก (>~100 KB) ไม่ได้จริง — วัดแล้ว ไม่ใช่เดา

## พบอะไร
รอบนี้ K ไม่มี `git`/`gh` ในเซสชัน — มีแค่ GitHub MCP tools (content API: อ่าน/เขียนไฟล์ทีละไฟล์แบบ **ทั้งไฟล์**
เท่านั้น ไม่มี patch/diff/append) ตามที่ตั้งค่าไว้ให้เซสชันนี้ วัดเพดานจริงของเครื่องมืออ่านในเซสชัน (`Read`):
ไฟล์ 305,698 B (`CLIENT_RE_QUEUE.md`) = **131,265 tokens ก็เกิน 25,000-token cap ของ `Read` แล้ว** (error
ตรง ๆ "exceeds maximum allowed tokens") — เขียนกลับ (ทั้งไฟล์ ผ่าน MCP `create_or_update_file`) จะยิ่งแพงกว่า
อ่านอีก (ต้องคัดลอกออกมาทั้งหมดเป็น argument ของ tool call เดียว) จึงเสี่ยงถูกตัดกลางทาง — เทียบกับ
`tickets/GT-084.md` (52,144 B ≈ 22K tokens) ที่เขียนสำเร็จจริงรอบนี้ (ยืนยัน byte-exact ผ่านฟิลด์ `size` ที่
API ส่งกลับ) — เพดานจริงอยู่ระหว่าง 52 KB กับ 305 KB ของเซสชันนี้ ยังไม่รู้ตัวเลขแน่นอน แต่ **`GAME_TEST_QUEUE.md`
1,547,418 B (~660K tokens โดยประมาณ) เกินแน่นอน**

## ผลกระทบ
งานหลักของสาย K ตามกฎบ้าน (`PANYA-ORDER 1448` ย้ายใบเกิน 8,192 B ไป `tickets/` แล้วแทนที่ด้วย stub บรรทัด
เดียวใน `GAME_TEST_QUEUE.md`/`CLIENT_RE_QUEUE.md`) **ต้องเขียนไฟล์คิวหลักทั้งไฟล์ทุกครั้ง** (Contents API ไม่มี
append/patch) — รอบก่อน ๆ (`slug54`, `cm9v9y`, `x91eo8r2`, `cu7c2r`, `ec26p6`) รายงานว่าทำสำเร็จ (ย้าย
`GT-069/074/076/080/233` และแก้ `GAME_TEST_QUEUE.md`/`CLIENT_RE_QUEUE.md` จริง) — แปลว่าเซสชันเหล่านั้น
**มีเครื่องมือคนละชุดกับเซสชันนี้** (มี `git clone`+push จริง ไม่ใช่ MCP content API อย่างเดียว) ไม่งั้นทำ
ไม่ได้ตามที่รายงาน

## รอบนี้ทำอะไรแทน (ไม่เสียงานเปล่า แต่ยังไม่ใช่งานเต็ม)
- ตั้งเลข `RE-286` ให้คำขอของ LANE-UI แล้ว จอง**เลขจริง**ไว้ (ตรวจ 0 hit ครบสามที่) และวางเนื้อใบคำต่อคำที่
  `tickets/RE-286.md` (8,479 B, เขียนสำเร็จ ยืนยัน byte-exact) — **แต่ยังไม่มีหัวใบ stub ใน
  `CLIENT_RE_QUEUE.md`** เพราะเขียนไฟล์นั้นไม่ได้ ⇒ **`RE-286` ยังไม่ปรากฏในคิวจริงที่ทุกคนอ่าน** จนกว่าจะมี
  เซสชันที่เขียน `CLIENT_RE_QUEUE.md` ได้มาเติมบรรทัดเดียว (`## RE-286 ... -- moved to
  \`tickets/RE-286.md\` ...`) — 🔴 **ห้ามสายอื่นใช้เลข 286 ซ้ำไม่ว่ากรณีใด** เลขถูกจองแล้วจริงตามกฎ numbering
- เตรียม `GT-084.md`(52,144 B)/`GT-104.md`(38,622 B) ที่ `tickets/` เสร็จแล้วเช่นกัน (verbatim, byte-exact)
  — แต่ `GAME_TEST_QUEUE.md` **ยังไม่ถูกแก้** (ยังมีเนื้อใบเต็มซ้ำอยู่ที่เดิม) เพราะเขียนไฟล์ 1.5 MB ไม่ได้
  ⇒ **ยังไม่มีการลดขนาดไฟล์จริงรอบนี้** ต่างจากที่ตั้งใจไว้ตอนแรก — ไฟล์ที่ `tickets/` ตอนนี้เป็นสำเนาซ้ำ
  ที่ปลอดภัย (ไม่มีผลเสีย เพราะ `pf_queue_status.py` ไม่อ่าน `tickets/` อยู่แล้ว) รอเซสชันที่เขียนไฟล์ใหญ่ได้
  มาแทนที่ก้อนเดิมด้วย stub

## ขอให้ COO เคาะ
1. รอบหน้าของ K ควรรันในเซสชันที่มี git clone+push จริง (ไม่ใช่ MCP content API อย่างเดียว) หรือไม่ — ถ้า
   ตั้งค่าเซสชันแบบนี้ไม่ได้เสมอไป K จะต้องเปลี่ยนวิธีทำงาน (ข้อ 2)
2. ถ้าต้องทำงานด้วย MCP content API ต่อไปเรื่อย ๆ (ไม่แน่ใจว่าจะได้ git เมื่อไหร่) — **เสนอ**: เปลี่ยนกติกา
   จาก "ย้ายใบเกิน 8,192 B ไป `tickets/`" (ต้องแก้ไฟล์รวมทุกครั้ง) เป็น "**ใบใหม่ที่เกินเพดานเกิดที่ `tickets/`
   ตั้งแต่ต้น**" (K ตั้งเลขแล้ววางที่ `tickets/<id>.md` เลย โดยไม่ต้องแตะไฟล์คิวรวม จนกว่าจะมีรอบที่เขียนไฟล์
   ใหญ่ได้มา sync stub ทีเดียว) — ใช้ได้กับใบใหม่ (เช่น `RE-286` รอบนี้) แต่ไม่แก้ปัญหาใบเก่าที่ยังค้างในไฟล์
   รวม (`GT-079` ฯลฯ ยังต้องรอ)
3. บันทึกเพดานจริงไว้เป็นความรู้กลาง (`docs/` หรือ `AGENTS.md` §7) กัน K/สายอื่นเสียเวลาทดรอบหน้าซ้ำ — เพดาน
   ที่วัดได้รอบนี้: เขียนไฟล์ ≤~52 KB (~22K tokens) ผ่านแน่นอน (ยืนยัน 3 ไฟล์รอบนี้) · ≥305 KB (~131K
   tokens) อ่านไม่ผ่านเครื่องมือ `Read` ในเซสชันนี้แล้ว (เขียนน่าจะแพงกว่าอ่าน) — ตัวเลขจริงตรงกลางยังไม่รู้
