## ทำไมต้องมีฉบับนี้

จดหมายผลข้อ 6.1 บอกว่า *"ถ้าสถานะภายในตรงเงื่อนไข `0x33` ไคลเอนต์จะ ACK เองทันทีโดยไม่มีหน้าต่าง"* แล้วติด nonclaim 3 ว่ายังไม่ได้ถอดว่า `0x005F9F60` ทดสอบอะไร
**ถ้า LANE-A เขียนเซิร์ฟเวอร์โดยสมมติว่าต้องมีคนกด OK เสมอ จะเจอเคส "บางครั้งวาปทันที บางครั้งรอกด" แล้วไล่หาสาเหตุไม่เจอ** — จึงเดินต่อจนได้โครงสร้างของประตูนั้นมา

## สิ่งที่วัดเพิ่มได้

### 1. `0x005F9DE0` และ `0x005F9F60` เป็นคู่ เขียน/อ่าน ของ **ทะเบียนวัตถุฝั่งไคลเอนต์** ตัวเดียวกัน

- ทั้งคู่ทำงานบนอ็อบเจ็กต์ `[0x01032EC4] + 0x130` · โครงสร้างจริงคือ map ที่ `this + 0xA0` (`0x005F9F6B: lea esi,[ecx+0xA0]`)
- `0x005F9F60(&key)` = **lookup**: สร้างคีย์แล้วเรียก `0x005F8400` (find) · คืน `al` = เจอ/ไม่เจอ และเติมค่าที่ผู้เรียกอ่านต่อที่ `key+0x14`
- `0x005F9DE0(k, a2, a3)` = **insert**: ประกอบเรคคอร์ดสามช่อง (`+0x18` = `k`, `+0x28` = `a2`, `+0x30` = `a3`) แล้วเรียก `0x005F9C70`

### 2. ผู้เขียนทะเบียนนี้ **คือ handler ของไวทัลขาเข้า** — crosswalk กับรีจิสทรีของบ้านเราเอง

สำมะโนผู้เรียก `0x005F9DE0` ครบ **11 จุด** แล้วหาฟังก์ชันครอบ แล้วเทียบกับคอลัมน์ `handler_va` ของ `external/PF_PROTOCOL_REGISTRY.tsv`:

| ฟังก์ชันครอบ | ชื่อในรีจิสทรี | คีย์ที่เขียน |
|---|---|---|
| `0x005E4060` | **`GSCN_RunTimeProtocolRes`** | `0x3E` · `0x3F` |
| `0x005F1D50` | **`GSCN_GetGameWorldData`** | `0x48` · `0x49` |
| **`0x005F2190`** | **`TeleportCheckVital`** | **`0x51`** |
| `0x0073D440` | **`CWebGMVital_GSGC`** | `0x62` |
| `0x0044E890` · `0x00450610` · `0x005DE000` · `0x00617130` | (ไม่ใช่ handler ที่จดทะเบียน) | `0x12` · `0x48` · `0x36` |

⇒ **คีย์เป็นเลขประจำ "ชนิดของสิ่งที่ไคลเอนต์กำลังถืออยู่" ไม่ใช่ค่าสุ่ม** และ `TeleportCheckVital` เป็นผู้เขียนคีย์ `0x51` เอง (เฉพาะกรณี confirm 22 ตามจดหมายผลข้อ 6.2)

### 3. เลขคีย์มาจากตารางชนิดวัตถุที่ประกอบไว้ตอนบูต

`0x00418050` เป็นฟังก์ชันลงทะเบียนชนิดวัตถุ: วนสร้างทีละชนิดด้วยรูปเดิมซ้ำ ๆ —
`push <ขนาด>` → `0x0088D020` (จองหน่วยความจำ) → `mov dword [esp+0x18], <เลขชนิด>` → ctor เฉพาะชนิด → `0x005FB420` → `0x005FB800` (ลงทะเบียน)

```
0x00418B97  mov dword [esp+0x18], 0x32   ; ctor 0x00729F80
0x00418BCD  mov dword [esp+0x18], 0x33   ; ctor 0x0072A5C0   <<< คีย์ที่ประตูของเราถาม
0x00418C03  mov dword [esp+0x18], 0x34   ; ...
```

🔴 **ctor ของชนิด `0x33` คือ `0x0072A5C0` ซึ่งอยู่ในโมดูลเดียวกับโค้ดเดินเรือทั้งหมด** (`0x0072FE50` ตัวโหลด `SAILING_RESULT` ที่ `RE-270` พินไว้ · `0x007321C0` confirm เข้า instance · `0x00734D50` confirm เกาะกิลด์ · `0x00737060` ตัวแจก event ของหน้าต่างแล่นเรือ) ⇒ **ชนิด `0x33` เป็นวัตถุของระบบเดินเรือ**

### 4. ประตูทั้งสองบานของ handler อ่านใหม่ได้ว่า

```
0x005F21FE  คีย์ 0x33  -> ถ้า "มีอยู่" และค่าที่มันเก็บ == marker id ของเฟรมนี้
0x005F2219      => ตอบกลับทันที (ไวทัลเดิม เลขเดิม) แล้วออก — ไม่มีหน้าต่าง ไม่รอผู้เล่น
0x005F225D  คีย์ 0x24  -> ถ้า "มีอยู่" (และไบต์ประกอบ != 0)
0x005F2273      => ออกเงียบ — ไม่เปิดหน้าต่าง และ ไม่ตอบอะไรเลย
                 มิฉะนั้น -> เส้นทางปกติ: เปิด confirm 21/22 แล้วรอปุ่ม
```

## ผลต่อโค้ดที่ LANE-A จะเขียน (นี่คือเหตุผลเดียวของจดหมายฉบับนี้)

1. **เซิร์ฟเวอร์ต้องยอมรับ ACK ที่มาถึงเร็วผิดปกติ** (ไม่มีเวลาให้มนุษย์กด) — อย่าใส่ตรรกะ "ถ้า ACK มาเร็วกว่า N ms = โกง"
2. **เซิร์ฟเวอร์ต้องยอมรับกรณีที่ ACK ไม่มาเลย** — ทั้งกรณีผู้เล่นกด Cancel (จดหมายผลข้อ 5) และกรณีประตู `0x24` ปิดเงียบ ⇒ ต้องมี timeout หรือปล่อยค้างได้อย่างปลอดภัย **ห้ามล็อกสถานะผู้เล่นไว้รอ**
3. **ห้ามส่งเฟรมเดิมซ้ำเพื่อ "กระตุ้น"** ถ้ายังไม่ได้คำตอบ — เข้าเส้นทางประตูแรกได้ ทำให้ผู้เล่นถูกวาปโดยไม่ได้กด

## nonclaims (ห้ามตัดออก)

1. **ไม่อ้างว่ารู้ว่าชนิด `0x33` และ `0x24` "ชื่ออะไร"** — วัดได้แค่ว่าเป็นเลขชนิดในทะเบียนที่ `0x00418050` ประกอบ และ ctor ของ `0x33` คือ `0x0072A5C0` ซึ่งอยู่ในช่วงที่อยู่ของโมดูลเดินเรือ · **"อยู่ในช่วงที่อยู่เดียวกัน" ไม่ใช่ crosswalk field** — ห้ามสรุปว่าเป็นวัตถุตัวไหนโดยเฉพาะ
2. **ไม่ได้ยืนยันว่า `0x00418050` เป็นแหล่งเดียวที่เขียนเลขชนิดเหล่านี้** — พบว่ามันเขียน `0x32/0x33/0x34/…` ต่อเนื่องกัน ยังไม่ได้ไล่ทั้งฟังก์ชัน (ยาวกว่า `0x0C00` ไบต์)
3. **ไม่ได้ถอดว่าอะไรเป็นคนใส่ค่า marker id ลงในเรคคอร์ดของชนิด `0x33`** — รู้แค่ว่า handler อ่านมันที่ `key+0x14` แล้วเทียบ · ผู้เรียก `0x005F9DE0` ทั้ง 11 จุดส่ง `(k, 0, 0)` คือไม่มี payload ⇒ **ต้องมีผู้เขียนอีกทางที่ยังไม่พบ**
4. **ไม่ได้ตรวจผู้เรียก `0x005F9F60` ทั้ง 126 จุด** — ดูเฉพาะสองจุดในใบนี้
5. ผลนี้ **ไม่เปลี่ยน** คำตอบสามข้อของใบ และ **ไม่เปลี่ยน** สถานะ PASS
6. static ล้วน · ไม่เปิดเกม · ไม่แตะ `GameClient\` `SERVER\` `external\` `gamedata\` หรือคิวใด ๆ
7. อิมเมจเดิม sha256 `9627211412ac60d50ad189ce5a629443ce928ec23a9f8d219dfb2b157028b623` (ก่อน = หลัง)
