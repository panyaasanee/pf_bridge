# ใบ `0444` (เสียบสามคอลัมน์ใน INSERT ของ `create_character`) ทำให้เทสแดง 35 ตัว และมี **สอง** ข้อเป็นบั๊กจริง — ต้องเข้าหลัง PR รอบนี้

🔴 **ใบนี้ถูกแก้ตัวเลขสองครั้ง อ่านฉบับนี้เท่านั้น** ฉบับก่อน ๆ เขียน 15 แล้ว 33 ผิดทั้งคู่
pf-adversary รอบสามชี้ว่า 33 = 15 + 18 คือการบวกเลขจากต้นไม้สองสถานะแล้วแปะกับสถานะที่สาม
**35 คือตัวที่ re-derive ได้** วัดบน `6d470eb6` (= `main` ก่อน PR รอบนี้) พร้อม control

ที่มาของ 35 แบบ re-derive ได้: control บน `6d470eb6` = 0 failed · เสียบจุด = 35 failed
แยกเป็น **18** (`test_persistence_typed_attr_columns.py` — ไฟล์ที่ฉบับแรกของผมไม่ได้เปิดดูเลย)
+ **12** (`test_persistence_vitals_seed_007.py`) + **5** (`test_persistence_vitals.py`)
รอบนี้แก้ครบทั้ง 35 ตัวแล้ว และวัดใหม่ทั้งชุดทั้งสองสถานะ

## เรื่องที่ต้องอ่านก่อนเสียบ: 2 ใน 18 ตัวนั้นไม่ใช่ fixture มันคือ precondition ที่ยังไม่มีใครเขียนไว้
พอ INSERT ของ `create_character` มีชื่อสามคอลัมน์ของ `006` **เมท็อดนี้ต้องการสคีมา 006 ทันที**
ฐานข้อมูลที่ยังอยู่ที่ 005 จะได้:
```
sqlite3.OperationalError: table characters has no column named level
  จาก src/pirateforce_foundation/store.py:234
```
ซึ่งคือ error ดิบไร้ชื่อ แบบเดียวกับที่ `persistence_vitals.verify_schema` มีอยู่เพื่อกำจัด
เทสสองตัวที่สร้าง DB 005 พร้อมแถวจริง (`MigrationIsNonDestructiveTests` และ
`BootSnapshotProtects006Tests`) ตายแบบนี้ตรง ๆ

**สิ่งที่ผมทำให้แล้ว** — `new_character_vitals()` รับ `db` เป็นพารามิเตอร์เสริม
ถ้าส่ง connection มาด้วย มันจะเรียก `verify_schema(db)` ก่อน แล้วโยน `SchemaDriftError`
ที่ **บอกชื่อคอลัมน์ที่ขาด** แทน error ดิบจาก INSERT
⇒ ขอให้เขียนจุดเสียบเป็น `new_character_vitals(db)` **ไม่ใช่** `new_character_vitals()`
เทสสองตัวที่พิสูจน์เรื่องนี้อยู่ใน `tests/test_persistence_vitals.py` แล้ว

รายชื่อที่วัดได้ทั้งหมด (ก่อนรอบนี้แก้ · จำลองจุดเสียบแล้วรัน `pytest tests/` ทั้งชุด):
`tests/test_persistence_typed_attr_columns.py` — 18 ตัว (2 ตัวข้างบน + 16 ตัว fixture)
`tests/test_persistence_vitals_seed_007.py` — 12 ตัว · `tests/test_persistence_vitals.py` — 5 ตัว

## รอบนี้แก้ให้แล้ว ฝั่งเทสของผมเอง ไม่ได้แตะ `store.py` แม้บรรทัดเดียว
- `_unseed()` (`tests/test_persistence_vitals.py`) และ `_make()` (ไฟล์ `007`) ล้างสามคอลัมน์เป็น
  NULL อย่างชัดแจ้งหลังสร้างตัวละคร ⇒ fixture ไม่ผูกกับพฤติกรรมของ `create_character` อีกต่อไป
- สองเทสใน `SeedsACohortNotADatabaseTests` เปลี่ยนเป็น **สองสถานะ**: ผ่านทั้งก่อนและหลังใบ `0444`
  และแดงเฉพาะ "สถานะที่สาม" — ตัวละครเกิดมาถือค่าที่ไม่ใช่ทั้งค่าว่างและไม่ใช่ค่าเดียวกับ `007`
  (รวมถึงแถวที่ถือแค่บางคอลัมน์ ซึ่งคือรูปครึ่งคู่ที่ `007` อุตส่าห์กันไว้)
- เพิ่มเทสที่ **จำลองจุดเสียบของคุณวันนี้** ผ่าน `write_typed_attributes` เพื่อให้สาขา "หลังเสียบ"
  ถูกตรวจตั้งแต่ตอนนี้ ไม่ใช่รอไปตรวจวันที่ PR ของคุณลง

## สิ่งที่ขอ
1. **ให้ PR ของรอบนี้เข้า `main` ก่อนใบ `0444`** ถ้าใบ `0444` เข้าก่อน `main` จะแดง 35 ตัวทันที
   ถ้าลำดับกลับกันไปแล้ว ไม่ต้องแก้เทสเอง — บอกผมมาในใบ ผมออกรอบแก้ให้ในรอบถัดไป
2. ตอนเสียบ ขอให้เรียก `persistence_vitals.new_character_vitals(db)` (ส่ง connection ด้วย
   ตามหัวข้อ precondition ข้างบน) แล้ว bind ค่าจาก dict ที่ได้
   **อย่าเขียนเลข 1/100/100 ลงใน `store.py` ตรง ๆ** เหตุผลคือวันที่ RE ตอบว่าค่าจริงของเกมเดิม
   คือเท่าไร (ยัง OPEN ตามป้าย TRANSCRIBED) จะได้แก้ที่เดียว และเลขของตัวละครใหม่จะไม่มีวัน
   แยกจากเลขที่ `007` เขียนให้ตัวละครเก่า — ซึ่งเป็นเหตุผลทั้งหมดที่ฟังก์ชันนี้มีอยู่
3. `new_character_vitals()` คืน dict คีย์เป็น **ชื่อคอลัมน์** และตรวจค่าตัวเองก่อนคืน
   ถ้าวันหนึ่งค่าไม่ผ่านกฎของโมดูล มันจะ raise `VitalsError` ตรงจังหวะสร้างตัวละคร
   ไม่ใช่เขียนแถวที่ `read_character_vitals` จะปฏิเสธไปตลอดชีวิตตัวละครนั้น
   ⇒ จุดเสียบไม่ต้องดักอะไรเพิ่ม แต่ควรรู้ว่ามันโยนได้

## ที่ไม่ได้อ้าง
- ไม่ได้อ้างว่าใบ `0444` ลงแล้ว หรือลงแล้วจะทำงานถูก — ผมจำลองเอง แล้วคืนสภาพ `store.py` เดิม
  ก่อน commit (`diff` กับสำเนาก่อนรอบยืนยันว่าเหมือนกันทุกไบต์ เหลือเฉพาะสี่ไฟล์ในเขตเขียน)
- หลักฐานสุดท้าย วัดทั้งชุด ไม่ใช่สองไฟล์: **ไม่มีจุดเสียบ 6924 passed / มีจุดเสียบจำลอง
  6924 passed** (ก่อนแก้ มีจุดเสียบ = 18 failed)
- ไม่ได้อ้างว่า M4 ปลดล็อกครบ ตามข้อ 5 ของใบ `0443`: ยังจริงเฉพาะตัวละครที่มีอยู่ตอน `007` รัน
  จนกว่าใบ `0444` จะขึ้น `main`
