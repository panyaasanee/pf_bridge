# LANE-B REPLY — PANYA-ORDER: ตีความ field ของสนามมอนสเตอร์ — วัดได้ 3 ข้อ, สมมติฐาน 1 ข้อ, ไม่รู้ 1 ข้อ

งานนี้ทำแบบ static/read-only ตามที่สั่ง ไม่เปิดเกม อ่าน `gamedata/scene/*/*.placements.tsv` (อ่านอย่างเดียว
ไม่แก้) เทียบกับตารางที่สาย B มีอยู่แล้ว: `field_mob_tables.py`/`field_mob_tables_bg0015.py`
(placement -> MOBS จริง) และ `field_mob_ai_tables.py` (ai_wander/ai_combat -> n_AGGRO/n_OFFESIVE จริง)
สคริปต์ที่ใช้เป็นเพียงสคริปต์ตรวจสอบ ไม่ได้ commit ไว้ในโค้ด (ยังไม่ใช่ของ production)

## ข้อ 1 (คำถามสาย B ข้อ 1) — f32_4/f32_5 ไม่ใช่ "รัศมี aggro" — วัดได้ (negative)

`field_mob_ai_tables.py` (scene bg0001 เท่านั้น — ไม่มีตารางแบบนี้สำหรับฉากอื่นในสาย B ตอนนี้) มี
`n_AGGRO`/`n_OFFESIVE` จริงต่อ `ai_wander` id: id `11` -> aggro `1200`, offensive `1` · id `16` -> aggro `0`,
offensive `0` เทียบกับ `field_mob_tables.HOSTILE_PLACEMENTS` (bg0001) ที่มีทั้ง 2 ai_wander นี้จริง แล้ว join
กับ tsv ของ bg0001 ตาม `placement_index`:

| placement | ai_wander (aggro จริง) | f32_4 | f32_5 |
|---:|---|---:|---:|
| 12,30,33,60,95,103,105,107,109 | 16 (aggro=0) | 500.0 | 800.0 |
| 58,63 | 11 (aggro=1200) | 500.0 | 800.0 |
| 59 | 16 (aggro=0) | **1000.0** | **1500.0** |
| 132 | 11 (aggro=1200) | **3.0** | 800.0 |

11 จาก 13 placement มี f32_4/f32_5 เท่ากันเป๊ะ (500/800) ไม่ว่า aggro จริงจะเป็น 0 หรือ 1200 — **ถ้า f32_4/f32_5
คือรัศมี aggro จริง ค่าที่ aggro ต่างกัน (0 vs 1200) ควรทำให้ f32 ต่างกันด้วย แต่ไม่ต่าง** สรุป: f32_4/f32_5
**ไม่ใช่**ตัวเดียวกับ `n_AGGRO` ของตาราง AI ที่สายนี้รู้อยู่แล้ว (เป็นคนละฟิลด์กันจริง ไม่ใช่แค่คนละหน่วย) —
2 ค่าผิดปกติ (placement 59, 132) ยังไม่มีคำอธิบาย ทิ้งไว้เป็นข้อสังเกต ไม่ใช่ผลสรุป

## ข้อ 2 (คำถามสาย B ข้อ 3) — กลุ่ม "101+" ไม่ใช่มอนสเตอร์เป็นส่วนใหญ่ — วัดได้ (Bg0015)

ใช้ `field_mob_tables_bg0015.HOSTILE_PLACEMENTS` (มาจากตาราง MOBS จริง ไม่ใช่การเดา) เป็น ground truth
เทียบกับเลขชุดจาก `set_names` ใน tsv ของ Bg0015 (91 placements ทั้งฉาก):

- ชุด **1..N** (76 placements): เป็นมอนสเตอร์จริง (อยู่ใน `HOSTILE_PLACEMENTS`) **16/76 (21%)**
- ชุด **101+** (15 placements): เป็นมอนสเตอร์จริง **1/15 (7%)**
- `u16_0`: กลุ่ม 101+ เป็น **0 ทั้ง 15/15** ส่วนกลุ่ม 1..N ผสม 1 (53 ตัว) / 0 (23 ตัว) — แยกกันชัดเจน 100%
  สำหรับกลุ่ม 101+ แต่**ยังไม่รู้ว่า `u16_0=0` แปลว่าอะไร** (ไม่ใช่แค่ "ไม่ใช่มอนสเตอร์" เพราะกลุ่ม 1..N เองก็มี
  `u16_0=0` อยู่ 23 ตัว)

สรุป: สนับสนุนสมมติฐานของ Panya ที่ว่ากลุ่ม 101+ เป็นอะไรบางอย่างที่ **ไม่ใช่มอนสเตอร์เป็นส่วนใหญ่** จริง
(อัตราต่างกันชัด 21% vs 7%) แต่**ยังพิสูจน์ไม่ได้ว่าเป็น "NPC บริการ/บอส/จุดเกิดผู้เล่น" ตัวไหน** — มีแค่
สัญญาณว่าเป็นคนละประเภทกับกลุ่ม 1..N [สมมติฐาน: 101+ = ไม่ใช่มอนสเตอร์ - รอ COO/Panya ยืนยัน]

## ข้อ 3 (คำถามสาย B ข้อ 1) — u16_1/u16_3 = "จำนวนตัวต่อชุด" — สมมติฐาน ได้รับการสนับสนุนบางส่วน ไม่ผ่านทั้งหมด

ทดสอบตรง ๆ: `u16_1` เท่ากับจำนวน placement ที่ใช้ `set_names` เดียวกันจริงหรือไม่ (Bg0015 ทั้งฉาก 51 ชุด) —
**ตรง 40/51 ชุด, ไม่ตรง 11/51 ชุด** (ตัวอย่างที่ไม่ตรง: `MOBSET_20` มี 4 จุดแต่ `u16_1` สลับ 2/3,
`MOBSET_29` มี 2 จุดแต่ `u16_1=4` ทุกจุด) สรุป: เป็นสมมติฐานที่ **สนับสนุนบางส่วน (78%)** ไม่ใช่กฎตายตัว —
อาจเป็น "จำนวนตัวที่ตั้งใจ" (design intent) ที่ไม่ตรงกับจำนวนจุดที่วางจริงเสมอ (คนออกแบบวางเกินหรือขาด) แต่
นี่คือการเดา ไม่ใช่ข้อสรุป [สมมติฐาน - รอ COO/Panya ยืนยัน]

## ข้อ 4 (คำถามสาย B ข้อ 2) — definition payload (b5/b15/u32@11) เทียบ level/rank/spawn-rate — ไม่รู้

สายนี้ไม่มีเครื่องมืออ่าน raw payload 16 ไบต์ของ definition (`.npc` header) ที่ join กับ per-monster level/rank
ได้โดยตรงใน `src/` ตอนนี้ — `field_mob_tables_bg0015.py`/`field_mob_ai_tables.py` มีแค่ field ระดับ
placement/AI-row (level, rank, ai_wander, ai_combat, n_AGGRO ฯลฯ) ที่ join จากตาราง MOBS ไม่ใช่จาก definition
payload ที่ Panya ถอดไว้ (b0/b5/b6-10/u32@11/b15) การจะตอบข้อนี้ให้วัดได้จริง ต้อง (ก) มีตัว parser
definition-payload ที่ join `set_names`/template name เข้ากับ `n_ID`/`n_LEVEL_MIN`/`n_RANK` ของ MOBS ต่อฉาก
และ (ข) เทียบค่า b5/b15/u32@11 กับ level/rank ที่ได้ — เครื่องมือนี้ไม่มีในเขตของสาย B วันนี้ **ไม่เดา**
คำถามนี้ยังตอบไม่ได้จากของที่มี — เปิดใบให้สาย C ด้านล่าง
