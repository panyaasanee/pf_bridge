## 1. คำตอบ

**`0x005F38B2` — `call eax` โดยที่ `eax = [vtable + 0x1C]`** อยู่ในลูปกระจายงานที่ `0x005F3840`

8B 11         mov edx, [ecx]        ; vtable
8B 42 1C      mov eax, [edx+0x1C]   ; slot +0x1C = inbound handler

## 3. ทำไมรอบก่อน ๆ หาไม่เจอ (เหตุผลเชิงวิธี ไม่ใช่เชิงโชค)

**3.1 ไบนารีนี้ไม่มีคำสั่ง `call dword ptr [reg+disp]` เลยแม้แต่คำสั่งเดียว** — วัดแล้วทั้ง `.text`:

| รูปแบบ call | จำนวน |
|---|---|
| `call <imm32>` | 22,378 |
| `call dword ptr [<abs>]` (IAT) | 7,341 |
| `call edx` | 2,969 |
| `call eax` | 2,113 |
| `call ebp/esi/ebx/edi/ecx` | 1,790 |
| `call dword ptr [reg + disp]` | **0** |

⇒ ทุก virtual call ในเกมนี้เป็นรูป `mov r,[vtbl+slot]` แล้ว `call r` การค้นด้วย `FF 5x xx` จึงคืนศูนย์เสมอ ไม่ว่า slot ไหน

**3.2 การถอดรหัสแบบเชิงเส้น (linear) จาก `.text` base เพี้ยนในไบนารีนี้** เพราะมีข้อมูลปนใน `.text` เมื่อสแกน slot +0x1C:

- linear จาก `.text` base → เจอ **96** จุด และ **ไม่เจอ** `0x005F38B2` เลย (ทั้งช่วง 0x005D0000–0x00610000 ให้ผลศูนย์ ซึ่งเป็นผลลวง)
- สแกนแบบยึดขอบฟังก์ชัน (ตัด `.text` ที่ช่วง `CC CC` แล้วถอดรหัสจากต้นฟังก์ชันแต่ละก้อน; 46,191 ก้อน) → เจอ **468** จุด รวม `0x005F38B2`

⇒ ผลลบจาก linear disassembler ในไบนารีนี้ **ใช้เป็นหลักฐานไม่ได้จริง ๆ** ตามกฎที่วางไว้ ผมเกือบรายงานผลลบนั้นออกไป แต่ตรวจซ้ำด้วยวิธีที่สองก่อนจึงจับได้ เครื่องมือที่แก้แล้วส่งมาด้วยในรอบนี้ (ข้อ 6)

## 4. ความหมายของ slot ที่เพิ่มขึ้นจากรอบนี้

| slot | ความหมาย | หลักฐาน |
|---|---|---|
| +0x08 | stub ร่วม `0x00401B20` | เดิม |
| +0x10 | id getter | เดิม + ใช้จริงที่ 0x005F3F03 |
| +0x14 | factory/pool | เดิม |
| +0x18 | serializer (stream, direction) | เรียกจริงที่ `0x005F3F40` |
| +0x1C | inbound handler | เรียกจริงที่ `0x005F38B2` |
| **+0x20** | **ด่านตรวจก่อน handle คืน bool** | เรียกจริงที่ `0x005F388C` |

**เรื่องที่ต้องระวัง (BUILD_IMPACT ข้อ 1 ด้านล่าง)**: ถ้า slot +0x20 ของ vital ตัวใดคืน 0 ลูปจะ `xor al,al; ret 4` ทันที — คือ **ทิ้ง sub-vital ที่เหลือทั้งเฟรม** ไม่ใช่ข้ามแค่ตัวเดียว

   และ `0x005F2190` ถูกอ้างอิงจาก `.rdata 0x00F0D688` **ที่เดียว** ⇒ ถูกเรียกแบบ virtual ล้วน สอดคล้องกับข้อ 1
2. **`0x005E3260` + `0x005E2E00` = "หา vital instance จาก u16 id"** — จุดยึดใหม่ที่ใช้ซ้ำได้ (`0x005E3260` มีผู้เรียก 4 จุด, `0x005E2E00` 6 จุด)

4. **ตัวจองหน่วยความจำแบบพูล `0x005DD460` / `0x0044AF00`** รับ `("file", 0)` ซึ่งเป็นอาร์กิวเมนต์ `__FILE__`/`__LINE__` ของ `PcRecycleBlock` (สตริง `source\shareproj\essential\PcRecycleBlock.h` อยู่ติดกันที่ 0xF0A8E0) — **ไม่ใช่ชื่อคลาส** ใครเห็น `push 0xF0A90C` อย่าอ่านเป็นชื่อ vital
5. โค้ดจัดการเฟรมมาจากไฟล์ `..\..\ShareCode\NetCode\VitalDataBase.cpp` (สตริง log ที่ 0xF30DD4) — ยืนยันว่าเป็นโค้ดที่ client กับ server ใช้ร่วมกัน

## 7. NONCLAIM — สิ่งที่ยัง**ไม่ได้**พิสูจน์ในรอบนี้

1. **ยังไม่รู้ว่าใครเรียก slot +0x1C ของ VitalData ตัวนอกสุด** (ตัวที่เป็นทั้งเฟรม) รอบนี้ปิดเฉพาะชั้นในคือการกระจายไปยัง sub-vital แต่ละตัว ผู้เรียกชั้นนอกยังเปิดอยู่ — จาก census 468 จุด ผู้ต้องสงสัยที่ยังไม่ตัดออกคือ `0x005E0270` (มี 6 จุดในฟังก์ชันเดียว), `0x005F1810`, `0x005C7D90`
   - ตัดออกแล้วด้วยการอ่านโค้ดจริง: `0x005F4FC0` (เป็น event dispatch ไปที่ `[0x1093198]+0x180`) และ `0x005FA590` (เป็น tick loop ส่ง float = deltaTime)
2. ยังไม่ได้ไล่ว่า slot +0x20 ของ vital แต่ละตัวคืนค่าอะไรบ้าง จึงยังบอกไม่ได้ว่ามี vital ตัวไหนที่ทำให้ทั้งเฟรมถูกทิ้งได้จริงในทางปฏิบัติ
3. ชื่อคลาสจาก RTTI type descriptor **อ่านแบบ static ไม่ได้** ในไบนารีนี้ (`0x0103177C`, `0x01033484`, `0x0102D954` อยู่ในส่วนที่ไม่ได้เก็บค่าเริ่มต้นในไฟล์) — ยืนยันซ้ำจากรอบก่อน
4. `0xEA7E` ที่พบเป็นค่าคงที่ใน `0x0044BC70` ผมเห็นว่าเขียนลง `[obj+0x30]` แต่ **ไม่อ้างว่า** เป็น vital id — ยังไม่มี crosswalk รองรับ

## 8. BUILD_IMPACT

1. 🔴 **เซิร์ฟเวอร์ต้องระวังลำดับใน batch**: ถ้าเราส่ง sub-vital ที่ client ตอบ `false` จาก slot +0x20 ลูก vital **ที่เหลือทั้งหมดในเฟรมเดียวกันจะไม่ถูกประมวลผล** และ handler ตัวนอกคืน false ⇒ อาการที่ผู้เล่นเห็นคือ "บางอย่างหาย" แบบสุ่มโดยไม่มี error ควรวาง vital ที่มีเงื่อนไขไว้ท้ายเฟรม หรือแยกเฟรม
2. 🟡 เฟรมขาเข้าเป็น **batch**: header คือ u16 count (tag 0x12) แล้วตามด้วยชุด `[u16 id (tag 0x12)][u8 (tag 0x0B)][ตัว vital]` ต่อกัน — ใครเขียน encoder ฝั่งเซิร์ฟเวอร์ต้องใส่ count และ u8 ตัวนี้ให้ครบ ไม่ใช่ส่ง vital เดี่ยว ๆ
3. 🟡 u8 ที่อ่านหลัง id ถูกเทียบกับ `[obj+0x10]`; ถ้าไม่ตรง client จะ log `0xE0000031` แต่ **ยังเดินต่อ** — เป็น warning ไม่ใช่ error ใช้เป็นสัญญาณดีบักได้
4. 🟢 การค้นหา virtual call ในไบนารีนี้ต้องใช้รูป `mov r,[vtbl+slot]; call r` เท่านั้น และต้องสแกนแบบยึดขอบฟังก์ชัน — เครื่องมือเดิมที่ใช้ linear จะพลาดประมาณ 80% ของจุดเรียก
