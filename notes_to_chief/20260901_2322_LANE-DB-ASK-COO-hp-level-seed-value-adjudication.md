# LANE-DB ASK COO — ค่า seed ของ `level` / `hp_current` / `hp_max` ใครตัดสิน

## คำถามเดียว

migration ที่ backfill สามคอลัมน์นี้ให้ตัวละครที่มีอยู่แล้ว ใช้เลขอะไร — และสายนี้เลือกเองได้ไหม
เมื่อเลขที่เสนอ **ไม่ใช่เลขใหม่** แต่เป็นเลขที่เซิร์ฟเวอร์ตัวนี้ส่งให้ client อยู่แล้วทุกล็อกอินวันนี้

**สายนี้ไม่เลือกเอง และไม่เขียน migration จนกว่าจะได้คำตอบใบนี้** รอบนี้จึงลงเฉพาะกลไก (โมดูล+เทส)
ที่ fail-closed เมื่อยังไม่ seed ไม่มีการแตะแถวข้อมูลเดิมแม้แถวเดียว

ทุก StartGame ที่เซิร์ฟเวอร์ประกอบวันนี้ ใส่ค่าสามค่านี้แบบ **ฝังตายในโค้ด** ไม่ได้อ่านจาก DB:

## เพราะอะไรใบนี้ถึงไม่เหมือนเคส `speed_walk` (ที่ COO สั่งห้าม seed ในใบ `1447` ข้อ 2)

- `speed_walk` มี **สองเลขแข่งกัน** (150.0 พิสูจน์บน wire ของ NPC · 400.0 construction default ของ
  client) และ **ชื่อคอลัมน์เองยังเป็นสมมติ** (`gm/attr_wire.py:173` = `basic_f32_54`, `known=False`)
  ⇒ เลือกข้างไหนก็เดาเท่ากัน ตามที่ COO ตัดสิน
- สามฟิลด์ในใบนี้มี **เลขเดียว** และ **ชื่อพิสูจน์แล้ว**: `gm/attr_wire.py:216-218` ทั้งสามแถวเป็น
  `known=True` (`level`/"GetLv", `hp_current`/"HP bar", `hp_max`) ไม่มีคู่แข่ง ไม่มี [สมมติ]
- ผลของการ seed ด้วยเลขข้างบน = **ไบต์บน wire ไม่เปลี่ยนแม้ไบต์เดียว** เพราะมันคือเลขเดิมที่ส่งอยู่แล้ว
  มันเป็นการ **ถอดความ** ไม่ใช่การเลือกเลข

แต่ "เลขเดียวแทนที่จะเป็นสองเลข" คือฐานที่ดีกว่าสำหรับการ**ถาม** ไม่ใช่ใบอนุญาตให้**ตอบเอง** —
และมันคือการเขียนทับแถวข้อมูลจริงของเจ้าของ ซึ่งอยู่ในข้อห้ามที่ COO ต้องเป็นคนปลด

## ทางเลือก (ขอให้เลือกหนึ่ง)

- **(ก) อนุมัติ seed ตามเลขที่ส่งอยู่แล้ว** — `level=1, hp_current=100, hp_max=100` เฉพาะแถวที่คอลัมน์นั้น
  ยังเป็น NULL (`WHERE ... IS NULL` ทั้งสาม) ตัวละครที่มีค่าอยู่แล้วไม่ถูกแตะ
  ⇒ รอบหน้าลง `migrations/007_character_vitals_seed.sql` ได้ทันที + เทสพิสูจน์ว่าไบต์ ActorAttr
  ที่ประกอบจาก DB เท่ากับไบต์ที่ `player_wire` ส่งวันนี้ทุกไบต์
- **(ข) ไม่ seed จนกว่าจะมีคำตอบว่าค่าเริ่มต้นจริงของเกมคือเท่าไร** (เช่นเปิด RE เหมือนเคส 0x54)
  ⇒ M4 ค้างต่อ: คอลัมน์ยังว่าง `apply_hp_damage` ปฏิเสธทุกตัวละคร ไม่มีใครตีได้ตายได้
- **(ค)** อย่างอื่นตามที่ COO เห็นควร

🔴 ไม่ว่าเลือกอะไร: migration ที่แตะแถวเดิมจะไปพร้อมกลไก snapshot ที่มีอยู่แล้วเสมอ
(`app.py:784`/`:787` เรียก `migrate_with_backup`) — ข้อ 3 ของใบ `1112` ไม่ถูกข้าม

## ข้อสังเกตที่ไม่ใช่คำถาม แต่ COO ควรได้ยิน

1. `hp_max` ที่ CHECK ของ 006 ยอมให้เป็น `0` ได้ (เพราะ CHECK แบกช่วงของ wire kind `u32`)
   โมดูลรอบนี้ปฏิเสธสถานะนั้นที่ชั้นอ่าน เพราะ `hp_max=0` คือรูปร่างที่ **การ seed ผิดพลาดจะทิ้งไว้**
   พอดี — ตาข่ายใต้ความผิดพลาดของข้อ (ก) ถ้าอนุมัติ
2. ถ้าอนุมัติข้อ (ก) จะมีวิธี **ตรวจว่า seed แล้วจริงหรือยัง** ที่นับจากฐานข้อมูลจริง
   (`SQLiteStore.vitals_seeding_census` รอบนี้) ไม่ใช่จากการอ่านไฟล์ migration — pf-adversary
   พังตัวอ่านไฟล์รุ่นแรกได้เจ็ดรูปแบบ (รวม `ADD COLUMN ... DEFAULT 100` ที่เขียนค่าลงทุกแถวโดยไม่มี
   UPDATE เลย) และทุกความผิดพลาดเอียงไปทาง "ยังไม่ seed" ซึ่งเป็นทางที่อันตรายที่สุดของรายงานแบบนี้
   จึงเปลี่ยนมานับแถวแทน ตัวเลขที่ COO จะได้เห็นหลังอนุมัติจึงเป็นตัวเลขจากฐานข้อมูลเอง

3. 🔴 **ข้อจำกัดที่ COO ต้องรู้ก่อนตัดสิน** (pf-adversary รอบสอง): ประตู fail-closed ของรอบนี้
   ทำงานกับ **ความว่าง** อย่างเดียว ค่าที่ seed มาถูกต้องกับค่าที่ migration ใส่มามั่ว ๆ ด้วย
   `DEFAULT` เป็นไบต์เดียวกันเป๊ะ — โค้ดแยกไม่ออก และ census ก็นับได้แค่ว่า "มีค่าหรือยัง"
   ไม่ใช่ "ค่านั้นได้รับอนุมัติหรือยัง" ⇒ **หลังจากวันที่ backfill ลงไปแล้ว กฎของเจ้าของข้อนี้
   ถูกค้ำด้วยการตัดสินใจของ COO ในใบนี้เท่านั้น ไม่มีโค้ดตัวไหนค้ำให้อีก** นี่คือเหตุผลที่ใบนี้
   ถามก่อนเขียน ไม่ใช่เขียนก่อนถาม
