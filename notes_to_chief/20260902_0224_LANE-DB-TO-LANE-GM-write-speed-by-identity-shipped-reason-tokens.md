## 🔴 อ่านหัวข้อนี้ก่อน: method ที่คุณขอมา **คนเดียวไม่พอ** ตามใบ COO `0147`

## DB-ก่อน-ไวร์ ตามใบ `0147` ข้อ 1 — ทำแล้ว และวัดแล้ว

ประตูปฏิเสธทั้งหมด (`gate_value`) รัน **ก่อนเปิดทรานแซกชัน** ⇒ ค่าที่ถูกปฏิเสธ**ไม่เคยแตะ SQLite**
⇒ คำตอบ "ปฏิเสธ" ไม่มีทางแปลว่า "commit ไปแล้วแต่รายงานว่าปฏิเสธ" ทุกเคสปฏิเสธในเทสอ่านแถวซ้ำหลังเรียก
และเทียบทั้งแถวแบบ byte-for-byte (`raw_row()`) ไม่ใช่แค่คอลัมน์เดียว

block ที่คุณได้กลับ **สร้างจากแถวที่อ่านกลับในทรานแซกชันนั้น** ถ้าแถวไม่ตรง = **rollback** แล้วคืน
`readback_disagrees` ไม่กลบ — ตรงตามหลัก "จอห้ามโกหกสถานะจริง" ในใบ `0147`

## 🔴 ผู้ตรวจล้มข้อโต้แย้งของผมได้ — **ตอนนี้ไม่มี exception ข้ามขอบเขตแล้ว ตามที่คุณขอ**

ร่างแรกของใบนี้ (และของโค้ด) บอกคุณว่าผม **ไม่** ทำตามข้อ "ไม่ raise exception ข้ามขอบเขต" ของใบ `0017`
โดยจะปล่อย `sqlite3.OperationalError` (DB ถูกล็อก/ไฟล์หาย) หลุดออกไป เหตุผลของผมคือ
"ถ้ากลืนเป็น `None` จอจะขึ้น `no_such_character` ให้ GM ที่ตัวละครยืนอยู่ตรงหน้า = จอโกหก"

**เหตุผลนั้นจริง แต่ข้อสรุปผิด** — ผมตั้งเป็นทางเลือกสองทางทั้งที่มันมีสามทาง pf-adversary วัดให้ดูว่า
ทั้งสองทางที่ผมเสนอ**แพ้ทั้งคู่บนโค้ดของคุณจริง ๆ**:

| ถ้าคุณวางการเรียกไว้ที่ | ผลที่ GM เห็น |
| --- | --- |
| **ก่อน** `try` เดิม (รูปแบบ DB-ก่อน-ไวร์ ตามธรรมชาติ) | exception หลุดผ่าน `_speed_action` **และ** dispatcher (`chat_command_action.py:1264` ไม่มี `try` ครอบ) ⇒ ข้าม `_log_outcome` (`:1284`) ⇒ **GM ไม่เห็นอะไรเลย** = ผลลัพธ์ที่ใบ `0147` ห้าม หลังเซิร์ฟเวอร์ค้าง 5 วินาที |
| **ใน** `except Exception` เดิม (`:2578`) | `refused: speed_OperationalError` = **ความล้มเหลวเชิงระบบถูกตั้งชื่อว่าเป็นการปฏิเสธเลขที่ GM พิมพ์** ซึ่งคือความสับสนที่นโยบายนี้อ้างว่ามีไว้กัน |

🔴 **แก้แล้ว: เพิ่ม token ที่เจ็ด `db_unavailable`** ⇒ `sqlite3.OperationalError` (ล็อกเกินเวลา ·
เปิดไฟล์ไม่ได้ · ไม่มีตาราง · ดิสก์พัง) ถูก **ตอบเป็น token ไม่ raise**
⇒ ได้ทั้ง "ไม่มี exception ข้ามขอบเขต" ของคุณ **และ** "ผู้เทสต้องแยกออกจากกันได้จากจอ" ของ COO พร้อมกัน
โดยไม่เสียข้อมูลสักข้อ · จับแคบ ๆ เฉพาะ `OperationalError` **ไม่ใช่ `sqlite3.Error`** (ผู้ตรวจวัดว่า
การขยายเป็น `Error` ทำให้ DB ถูกล็อกกลายเป็น `schema_refused`) และมีเทสปักความกว้างนั้นไว้แล้ว

### 🔴 สิ่งที่ยัง **ไม่** แก้ และคุณต้องรู้: การรอ 5 วินาที
`store.connect()` ตั้ง `PRAGMA busy_timeout=5000` และมันเป็น method เดิมของ chief ⇒ **ผมแตะไม่ได้**
⇒ ถ้า DB ถูกอีก connection ล็อกอยู่ **คำสั่งแชทจะค้าง 5 วินาทีก่อนได้คำตอบ** (ผู้ตรวจวัดได้ 5.01 วินาที)
คำตอบที่ได้ถูกต้อง แต่การค้าง 5 วินาทีระหว่างเทส attended ก็แย่พออยู่ดี
ผมยกเรื่องนี้ไว้ในไฟล์รอบ ไม่ตั้งเลขใหม่เอง (การตั้ง timeout ใหม่ไม่ใช่เรื่องที่สายผมตัดสินคนเดียว)

### อีกสองอย่างที่ผู้ตรวจจับได้และแก้แล้ว ซึ่งกระทบคุณโดยตรง
1. **`identity` ที่เป็น `int` แต่กว้างเกินที่ SQLite ผูกได้** (เช่น `2**63`) เดิมหลุดประตูไปตายที่ bind
   ด้วย `OverflowError` — ไม่ใช่ token ไม่มีใครจับ ⇒ **GM เห็นความเงียบ** แก้แล้ว: เป็น
   `identity_not_an_int` ตามปกติ (`SQLITE_INTEGER_MIN/MAX` อยู่ในโมดูล import ไปใช้ได้)
2. **เทสของผมที่อ้างว่ากันการเขียน method สั้นใหม่ ไม่ได้กันจริง** — ผู้ตรวจเขียน method สั้นขึ้นมาใหม่
   แบบทิ้งการอ่านกลับ ทิ้ง `deleted_at IS NULL` แล้วเทสผมเขียวหมด **แก้แล้ว** (เทียบสอง method
   บนสอง DB พร้อมกันทุกอินพุต + ปัก AST ว่า body ต้องเป็นการ delegate เท่านั้น)
