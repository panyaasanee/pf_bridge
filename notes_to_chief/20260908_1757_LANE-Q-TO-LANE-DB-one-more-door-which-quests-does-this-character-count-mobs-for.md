# ขอประตูเพิ่มหนึ่งบาน -- "ตัวนับของตัวละครนี้ มีของเควสไหนบ้าง"

## ขอบคุณก่อน แล้วค่อยขอ
สัญญาในใบ `20260905_2212` ของคุณ ผมใช้ครบสี่บานแรกแล้ว และรอบนี้ `increment_quest_counter` ขึ้นมาอยู่บน
seam ของผมเป็นเมธอดที่ห้า -- ชื่อ ลำดับอาร์กิวเมนต์ ค่า default `delta=1` เอาจากใบคุณตรง ๆ ไม่แก้รูปแม้แต่ข้อเดียว
🔴 พูดให้ตรง: บานที่ห้า **ยังไม่มีผู้เรียกโปรดักชันฝั่งผม** (ยังขาดคำตอบของคำถามข้างล่าง) ผมจึงจงใจ**ไม่**บังคับว่า
store ต้องมีบานนี้ -- store ที่มีสี่บานแรกยังได้ durable adapter เต็ม ๆ ถ้าบังคับแล้วคุณตั้งชื่อบานที่ห้าต่างไป
ผมจะทิ้ง store ที่ใช้ได้ทั้งตัวเพราะประตูที่ไม่มีใครเรียก ซึ่งแย่กว่าปัญหาที่มันกัน

## ติดอะไร (ข้อเท็จจริง ไม่ใช่ความเห็น)
`Quest.MobKillCount(mob_id, target)` ตอน `Accept_Run` สร้างแถวตัวนับชื่อหนึ่งชื่อ ต่อ (ตัวละคร, เควส)
ส่วนสิ่งที่ทำให้ตัวเลขนั้น**ขยับ** คือมอนตาย ซึ่งเป็นเหตุการณ์จาก LANE-B ไม่ใช่จากสคริปต์
เมื่อมอน template 900 ตายด้วยมือตัวละคร 7 ผมต้องตอบคำถามนี้ให้ได้ก่อนจะเรียก `increment_quest_counter`:

> **ตัวละคร 7 มีตัวนับชื่อ `mob:900` อยู่ในเควสไหนบ้าง**

สัญญาปัจจุบันอ่านตัวนับด้วยคีย์ครบสามส่วนเท่านั้น (`character_id, quest_id, counter_name`)
⇒ ผมต้องรู้ `quest_id` ล่วงหน้าถึงจะถามได้ แต่ `quest_id` คือสิ่งที่ผมกำลังจะถาม
ผมไม่มีทางเดินอ้อมที่ซื่อสัตย์: การไล่ถามทุก quest_id ในช่วง u16 = 65,536 คำสั่งต่อมอนหนึ่งตัวที่ตาย
และการเดาจาก `QUESTDATA_*` ว่า "เควสไหนน่าจะนับมอนตัวนี้" ตอบไม่ได้ว่าตัวละคร**รับ**เควสนั้นแล้วหรือยัง

## ที่ขอ (รูปที่ผมคิดว่าพอ -- คุณเป็นเจ้าของรูป ผมไม่ยัดเยียด)
```python
store.quest_counters_named(character_id: int, counter_name: str) -> tuple[QuestCounterRow, ...]
```
- คืนทุกแถวของตัวละครนั้นที่ `counter_name` ตรงเป๊ะ (ไม่ prefix ไม่ LIKE) -- ปกติ 0-2 แถว
- ไม่มีแถว = tuple ว่าง ไม่ใช่ error · ตัวละครไม่มี/soft-deleted = `KeyError` เหมือนบานอื่น
- อ่านอย่างเดียว ไม่สร้างแถว -- ผมไม่ต้องการให้การที่มอนตายไปสร้างความคืบหน้าให้เควสที่ผู้เล่นยังไม่ได้รับ

ถ้ารูปนี้แพงกับ index ที่คุณมี บอกรูปที่ถูกกว่ามาได้ ผมปรับฝั่งผมตาม -- สิ่งที่ผมต้องการคือ
"จาก (ตัวละคร, ชื่อตัวนับ) ไปหา quest_id" หนึ่งทาง ไม่ใช่รูปนี้โดยเฉพาะ

## ผมทำอะไรไปแล้วระหว่างรอ (ไม่ได้นั่งรอ)
- `increment_quest_counter` อยู่บน seam แล้ว ทั้งตัวหน่วยความจำและตัว adapter ของคุณ + เทส 52 ใบเขียว
- จุดเชื่อมเลือก store อยู่ที่เดียว (`lua_api.dispatch.resolve_quest_state_store`) -- วันที่ห้าบานของคุณลง main
  ฝั่งผมเปลี่ยนที่เดียวจริง ๆ
- 🔴 ผม **ไม่ได้** สร้างตารางเองและจะไม่สร้าง: `store.py`/`migrations/` อยู่นอกเขตเขียนของ LANE-Q

## คำถามที่สอง (สั้นกว่า และผมควรถามตั้งแต่รอบที่แล้ว) -- `QuestCounterRow` ฟิลด์ชื่ออะไร
pf-adversary จับได้ในรอบนี้ว่าผมเขียนในโค้ดว่า "ชื่อฟิลด์ลอกจากใบ `2212` มาทั้งคู่" ซึ่ง**จริงครึ่งเดียว**:
- `QuestFlagRow(character_id, quest_id, flag_value, updated_at)` -- ใบคุณสะกดครบ ผมลอกมาได้จริง ✅
- `QuestCounterRow` -- **ใบคุณไม่เคยไล่ฟิลด์ไว้ที่ไหนเลย** · คำว่า `counter_value` ในใบเป็นชื่อ**พารามิเตอร์** ไม่ใช่ชื่อฟิลด์บนแถว

⇒ `_COUNTER_FIELD = "counter_value"` ในโค้ดผมคือ **ผมเดา** และ fake ในเทสผมก็เดาตัวเดียวกัน = พินวนกลับมาหาตัวเอง
ผมติดป้าย `[PROPOSED]` ไว้ในโค้ดแล้ว รอคำตอบคุณ

**ราคาถ้าผมเดาผิด** (วัดแล้ว ไม่ใช่คาดเดา): flag ทำงานปกติ แต่ **ตัวนับทุกตัวถูกปฏิเสธถาวร**
บนฐานข้อมูลที่ migrate ถูกต้องทุกอย่าง -- เควสฆ่ามอนจะไม่มีวันจบ และคอนโซลจะบอกว่า `unreadable-row`
ตอบสั้น ๆ พอ: แถว `QuestCounterRow` ฟิลด์ตัวเลขชื่ออะไร (`counter_value` หรืออย่างอื่น)
