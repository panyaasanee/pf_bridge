# ต้นเหตุ — ไม่ใช่บั๊ก เป็นการออกแบบที่พึ่งความสามารถที่ไม่มีอยู่จริง

โปรโตคอลรอบของทุกสายเขียนไว้ตรง ๆ สองบรรทัดนี้:

- ต้นรอบ: *"ไม่มี PR ค้าง -> **เปิด draft PR ยึดล็อก**ก่อนทำงาน"* ⇒ **ธง draft = ตัวล็อกรอบ**
- จบรอบ: *"push ให้ครบ -> **เอา draft ออก** -> แก้หัวข้อ PR ... แล้วปล่อยให้ workflow merge"*

และ `merge-claude-pr.yml` ปฏิเสธ PR ที่เป็น draft ตรง ๆ (`[ "$DRAFT" = "false" ] || continue`)

⇒ **ทั้งระบบวางอยู่บนขั้นตอน "เอา draft ออก" ซึ่งเอเจนต์ทำไม่ได้เลยสักทาง** วัดซ้ำแล้วสามสายสามคืน:

| ทาง | ผลจริง |
|---|---|
| GraphQL `markPullRequestReadyForReview` | proxy ปฏิเสธ: *"This GraphQL query is not enabled for this session -- only the pinned set of PR-review operations is served"* |
| REST `PATCH /pulls/{n}` `{"draft": false}` | คืน `200` แต่ค่า `draft` ไม่เปลี่ยน — **GitHub REST ไม่รองรับการปลด draft ผ่านฟิลด์นี้จริง ๆ** ไม่ใช่เรื่องสิทธิ์ |

**นี่ไม่ใช่ความผิดของสายไหน** ทุกสายทำถูกตามโปรโตคอลแล้ว โปรโตคอลเองต่างหากที่สั่งให้ทำสิ่งที่ทำไม่ได้
(สาย A ถึงขั้นลองทางที่สาม — ปิด PR แล้วเปิดใหม่ — ซึ่งผิดกฎอีกข้อ แล้วรีบแก้กลับเอง นั่นคืออาการของคนที่ถูกบีบให้หาทางออกที่ไม่มี)

# คำตัดสินของเจ้าของ: เปลี่ยนตัวล็อกจาก "ธง draft" เป็น "เครื่องหมายในเนื้อ PR"

ใช้เฉพาะการกระทำที่**พิสูจน์แล้วว่าเอเจนต์ทำได้จริง** (สาย A ทำสำเร็จรอบนี้: แก้ title และ body ผ่าน REST
แล้ว GET กลับมายืนยันได้)

1. **เปิด PR แบบไม่ใช่ draft ตั้งแต่แรก** หัวข้อขึ้นต้น `[LANE-x] WIP round claim <id>`
2. **ตัวล็อกคือคำว่า `WIP` ในหัวข้อ** — ต้นรอบสายมองหา PR ของตัวเองที่หัวข้อมี `WIP` แทนที่จะดูธง draft
3. **ตัวกันไม่ให้ merge กลางรอบคือ marker ในเนื้อ** — `PF-AUTOMERGE: v4` **ใส่ตอนจบรอบเท่านั้น**
   ไม่ใช่ตอนเปิด (workflow ปฏิเสธ PR ที่ไม่มี marker อยู่แล้ว จึงปลอดภัยระหว่างรอบ)
4. **จบรอบ = PATCH title (ตัด `WIP` ออก) + PATCH body (ใส่ marker)** — สองอย่างนี้ REST ทำได้จริง
5. เงื่อนไข draft ใน `merge-claude-pr.yml` เก็บไว้เหมือนเดิมได้ ไม่ต้องแตะ — จะไม่มี PR draft อีกต่อไป

**ผลที่ต้องได้: ไม่มีขั้นตอนไหนในรอบปกติที่ต้องใช้มือมนุษย์อีกเลย**
