## 🔴 อันตรายที่แท้จริง ไม่ใช่แค่งานซ้ำ

ไฟล์ `migrations/008_character_speed_walk_seed.sql` สองตัว **path เดียวกัน คำสั่ง SQL เหมือนกันเป๊ะ
แต่หัวไฟล์ต่างกัน ⇒ sha256 ต่างกัน**

```
theirs (บน main)  ae9e73dea7365109bfbac142881cfdda6555ecbff3c14b4dc7e4b2580087083e
mine              edc99635553fa897f673b323679b354437139684eddc26dbe7a9ae47cf2f9eed
```

`store.migrate()` เก็บ **checksum** ลง `schema_migrations` และปฏิเสธ boot ด้วย
`migration checksum mismatch` ถ้าไบต์ของ version เดิมเปลี่ยน ⇒ ถ้าเครื่องเจ้าของ apply ของเขาไปแล้ว
แล้ววันหลังไฟล์ผมทับ **canonical DB ของเจ้าของ boot ไม่ขึ้น** นี่คือเคสที่กฎ "ย้อนไม่ได้" ห้ามไว้ตรง ๆ

ที่กันไว้ตอนนี้: PR #558 เป็น `dirty` (ชนที่ path เดียวกัน) workflow จึง merge ไม่ได้เอง

ทั้งสองรอบจึงผ่านการ์ดไปทั้งคู่ **การ์ดที่ดูแค่ PR มองไม่เห็นเซสชันที่ยังไม่ push**
เสนอสองทาง ให้คุณเลือกหรือปฏิเสธทั้งคู่: (ก) หมุด claim ต้นรอบใน `pf_bridge` ที่ push ทันทีก่อนทำงาน
(สาย B ใช้ `LANE-B round claim` อยู่แล้ว เห็นในล็อก main) · (ข) การ์ดที่เช็ค branch `claude/*`
ที่มี commit ของสายเดียวกันในช่วง N นาที ไม่ใช่แค่ PR
