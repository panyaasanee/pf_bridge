## หลักออกแบบที่เคาะ (ผูกกับลำดับระบบ COO `1846`: ข้อ 1 quest-flag = Q · ข้อ 3 `MobAppear` = A)
1. **โลกใบเดียว** (registry ต่อฉากของ A ที่มีอยู่) — มอน/ดรอป/บอส/HP/นับฆ่า อยู่ในโลกร่วม ทุกคนเห็นสถานะเดียวกัน · **ห้ามมีโลกที่สอง**
2. **ฟิลเตอร์การมองเห็นต่อผู้เล่น** ตอนประกอบ census/appear ให้แต่ละ session: ส่งตัวละครนี้ให้คนนี้ไหม = (ไม่ผูกเควส และ `n_MOB_APPEAR=1`) **หรือ** (สถานะเควสของคนนั้นเข้าเงื่อนไข `s_QUEST_BEGIN`/`s_QUEST_END`) **หรือ** (มีธง `MobAppear(true)` ของคนนั้นและยังไม่ถูก `false`)
3. **`Player.MobAppear(id, true/false)` = ติ๊ก/ดับธงในบันทึกของผู้เล่นคนนั้น** — ไม่สร้าง/ลบตัวละครในโลกร่วม (ตัวอย่างที่เจ้าของเข้าใจแล้ว: เชลยที่ ก รับเควสโผล่เฉพาะจอ ก · ข ไม่เห็น · ก ส่งเควสแล้วหายเฉพาะจอ ก ไม่กระพริบบนจอ ข)
4. **กฎตัดสินง่าย ๆ**: **rank 0 = ธงต่อผู้เล่น · rank>0 = ลงโลกร่วมจริง** (มอน/บอสที่ผูกเควส 24 แถว ต้องมี HP ร่วม) — ใช้กฎเดียวกับ hostility (`n_RANK`/`n_AI_COMBAT`) ไม่ต้องมีรายชื่อมือ
5. ต้องมี: ตารางสถานะเควสต่อตัวละคร (Q ข้อ 1 ที่เริ่มแล้ว) + เฟรมโผล่/หายกลางเซสชันต่อ session (A — เฟรม "หาย" มีอยู่แล้วจากมอนตาย/ย้ายฉาก) · **ออกแบบฟิลเตอร์ก่อนแตะ `MobAppear`** ห้ามทำ MobAppear เป็น spawn ลงโลกแล้วค่อยแก้ทีหลัง
6. ขอบเขต: ข้อ 2 ใช้ 3 คอลัมน์นั้นตัดสินทีละแถว ไม่ต้องเดา · ถ้าเจอแถวที่ 3 คอลัมน์ขัดกับสคริปต์ ให้เขียนถึง COO ไม่ตัดสินเอง

## ผู้สมัครเพิ่มให้ RE-155 (ใบ 2142/2150) — จากข้อสังเกตเดียวกัน
- client มีตาราง MOBS อยู่ในเครื่อง (CONSTDATA เป็นไฟล์ client) และ server เราส่ง template id = `n_ID` ในเฟรมอยู่แล้ว · ถ้า client เปิดตารางตัวเองด้วย n_ID ที่เราส่ง มันต้องรู้ว่า Fighting Fish (rank 1) เป็นมอน แต่สีก็ยังผิด ⇒ **client ไม่ได้เปิดตารางด้วยช่องที่เราส่ง หรือใช้คอลัมน์อื่นเป็น key** · แถวหุ่นต้องมีผู้สมัคร: "ช่องไหนใน NPCAttr คือ key ที่ client ใช้เปิดตาราง" — สลับค่า n_ID ระหว่างต้นแบบ NPC/มอน ในแต่ละช่องที่เป็นไปได้ (`template`, `n_ID_MODEL`, `s_ID_MODEL_CLASS`, ช่องที่ยังไม่ระบุความหมาย) ทีละช่อง
- ไม่ใช่เบาะแสเรื่อง "ปล่อยแบบร่วม vs ต่อ session" — client ไม่รู้ว่า server ตัดสินแบบไหน มันได้เฟรมโผล่แบบเดียวกัน (เจ้าของถาม ka1-A ตอบไว้แล้ว)
