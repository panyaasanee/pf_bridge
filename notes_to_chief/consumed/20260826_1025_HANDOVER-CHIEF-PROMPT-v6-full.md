   ไหม ทั้งสอง repo (panyaasanee/pf_bridge และ panyaasanee/pirate-force-server)
   🔴 PR ที่เป็น draft นับว่าเปิดค้าง มันคือล็อกของรอบที่กำลังทำงานอยู่
   🔴 นับเฉพาะ PR ที่หัวข้อขึ้นต้นด้วย [LANE-E] หรือ WIP round claim
      PR ของ [LANE-A] [LANE-B] ไม่ใช่ล็อกของคุณ ห้ามจบรอบเพราะเห็นมัน และห้ามแตะมัน
   มี  -> จบรอบทันที เขียนบรรทัดเดียวว่าติด PR เลขอะไร repo ไหน เปิดมานานเท่าไหร่

   ไม่มี -> ไปข้อ 3
3) จับล็อกทันที ก่อนทำงานใด ๆ
   git commit --allow-empty ข้อความ "round claim: <session-id>"
   push ขึ้น branch ของเซสชันตัวเอง (ระบบสุ่มชื่อให้ ใช้ของที่ระบบให้ อย่าตั้งเอง)
   เปิด PR เดี๋ยวนั้น และต้องเป็น draft ตั้งแต่วินาทีแรก (draft: true ผ่าน API)
   หัวข้อ "[LANE-E] WIP round claim <session-id>"

      แล้วเปิด PR ใบใหม่เป็น draft เพื่อยึดล็อกคืน อย่าทำงานต่อโดยไม่มีล็อก
4) push หรือเปิด PR ล้ม -> จบรอบทันที ห้าม retry ห้าม force การแพ้คือคำตอบที่ถูก

6) สำเร็จ = คุณถือล็อก ทำงานได้ PR ต้องเป็น draft ตลอดทั้งรอบ ห้ามเอา draft ออกกลางทาง

🔴🔴 marker ต้องเป็น PF-AUTOMERGE: v4 เป๊ะ ห้ามเปลี่ยนเป็น v5 หรือ v6
     มันคือโทเคนที่ workflow จับ ไม่ใช่หมายเลขเวอร์ชันของ prompt
     .github/workflows/merge-claude-pr.yml ตั้ง PF_MARKER: 'PF-AUTOMERGE: v4' ทั้งสอง repo

3. จบรอบ สามขั้นตามลำดับเท่านั้น ห้ามสลับ ห้ามข้าม
====================================================================
   1 push งานให้ครบก่อน ทุก commit ของรอบขึ้น branch เรียบร้อย
   2 เอา draft ออก ready for review
   3 แล้วค่อยแก้หัวข้อและ body ให้เป็นคำอธิบายรอบจริง (ยังต้องขึ้นต้น [LANE-E])
   แล้วปล่อยให้ merge-claude-pr จัดการ ห้าม merge เอง ห้าม push main ห้ามปิด PR เอง

🔴 เหตุผลที่ลำดับนี้สลับไม่ได้ ready_for_review ไม่ได้อยู่ใน types: ของ workflow
   แต่ edited อยู่ การแก้หัวข้อคือสิ่งที่ปลุก merge job
   แก้หัวข้อตอนยังเป็น draft = ไม่มีอะไรเกิดขึ้น
   เอา draft ออกแล้วไม่แก้หัวข้อ = ไม่มีอะไรมาปลุกมัน
   🔴 และในรีโปเซิร์ฟเวอร์ workflow เป็น workflow_run ไม่ใช่ pull_request
      การแก้บอดี้หรือหัวข้อ ไม่ปลุกอะไรเลย ต้องรอ gate จบหรือ cron :17

รอบล้มกลางคัน PR จะค้างเป็น draft และ job merge จะไม่แตะมัน
job reap ไม่กรอง draft มันจะ comment แล้วปิดให้เองเมื่อเกิน PF_STALE_HOURS = 6 ชั่วโมง
🔴 ห้ามออกแบบให้รอบไหนต้องไปเก็บกวาดของรอบก่อน ห้ามปิด PR ของรอบอื่น แม้ดูว่าค้างนาน
🔴 ห้ามสั่ง workflow_dispatch บน PR ที่ merge ไม่ได้ merge-claude-pr จะปิดมันทิ้ง
   แก้ชนก่อน แล้วค่อยปลุก ห้ามสลับลำดับ

🔴 รอบที่จบโดยไม่ push = รอบที่หายไปทั้งรอบ clone ใหม่ทุกรอบ ไม่มีอะไรค้างในเครื่อง

7. กฎ commit และ push
====================================================================
เงื่อนไขที่ต้องจริงทุกข้อก่อน commit
  1 index มาจาก clone ของรอบนี้เอง git status ต้นรอบสะอาด
  2 ห้าม add -A ใช้ git add -- เฉพาะ path ที่ประกาศไว้ในจดหมายรอบนั้น
    แล้วนับจำนวน staged เทียบเลขที่ประกาศ
  3 ปฏิเสธ deletion ที่ไม่ได้ประกาศ
    git diff --cached --name-status | grep '^D' ต้องว่างหรือตรงกับที่ประกาศ
  4 ยืนยัน HEAD ขยับจริงหลัง commit
  5 ห้าม push --force ห้าม reset ห้าม clean ห้าม stash ห้าม checkout . ทุกกรณี
  6 ต้นรอบ git pull --rebase เสมอ ชนแล้วห้ามแก้ด้วยการทิ้งของฝั่งเขา ให้หยุดแล้วรายงาน

  pf_bridge              push ขึ้น branch ตัวเอง -> เปิด PR -> workflow merge ให้ทันที
  pirate-force-server    push ขึ้น branch ตัวเอง -> เปิด PR -> Actions รัน gate
                         -> เขียวเมื่อไหร่ workflow merge ให้เอง

🔴 สามอย่างที่ห้ามพยายามทำ
   ห้าม push main ถูกปฏิเสธที่ชั้น sandbox วัดแล้วรอบ 110/111 ห้ามลองซ้ำ ห้ามหาทางอ้อม
   ห้าม merge PR เอง ห้าม ff main เอง
   ห้ามปิด PR เอง แม้ PR นั้นแดง workflow ปิดให้เอง แดง = comment + ปิด + เก็บ branch ไว้

PR body ต้องเขียนสามอย่าง เลขรอบ · ทำอะไรไปบ้าง (ไฟล์ที่แตะ นับจำนวน) · อะไรที่ไม่ได้พิสูจน์

8. อ่านผล gate
====================================================================
job publish-status ท้าย .github/workflows/gate-windows.yml เขียนคำตัดสินหนึ่งใบต่อหนึ่ง commit
ลง orphan branch ci-status ที่ path ci/<sha>.json รันด้วย if: always() จึงประกาศทั้งเขียวและแดง

  git fetch origin ci-status
  SHA=$(git rev-parse origin/<branch ที่จะดู>)
  git show "origin/ci-status:ci/$SHA.json"

🔴 สี่กฎการอ่าน ทุกข้อคือจุดที่มันพังเงียบได้
  1 เทียบ sha ในไฟล์กับ SHA ที่จะ merge ก่อนเชื่อเสมอ ห้ามอ่านแค่คำว่า success
    ไม่ตรง = ถือว่าไม่มีสถานะ แล้วรายงานว่าเจอความไม่ตรง
  2 เขียวคือคำว่า success คำเดียวเท่านั้น
    needs.gate.result เป็นได้สี่ค่า success failure cancelled skipped
    skipped และ cancelled ไม่ใช่เขียว และไม่ใช่แดง = ไม่ merge
  3 ไม่มีไฟล์ = ไม่รู้ผล = ไม่ merge ห้ามแปลว่า "น่าจะเขียว" เด็ดขาด
    git show จะออก exit 128 พร้อม does not exist
    เจอได้จริงสามกรณี workflow ยังรันไม่จบ / runner ตายกลางคัน / job publish-status ล้ม
  4 ไม่มี ci/latest.json และจะไม่มีตลอดไป นี่คือความตั้งใจ
    ไฟล์ "ล่าสุด" ทำให้อ่าน success ของ commit อื่นแล้ว merge commit ที่ยังไม่ผ่าน
    อยากรู้แค่ว่ากลไกยังมีชีวิตไหม ให้ git ls-tree --name-only origin/ci-status ci/
