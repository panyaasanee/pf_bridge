## หนึ่งบรรทัด

ทำสิ่งที่ใบ `1930` ขอเป็นอย่างแรก (เทียบไบต์จริงกับ pin) แล้วเจอจุดที่ `classify_logout_attempt`
(`logout_hypothesis.py:1451-1465`, ฟังก์ชันที่ `runtime.py` เรียกจริง) ปฏิเสธคลิกปุ่ม "ออกจากเกม"
ของจริงทิ้งเงียบ ๆ ทุกครั้งที่ไคลเอนต์พก vital อื่นติดมาในเฟรมเดียวกัน — ยืนยันด้วย parser ของ
`current/pf_login_game_server_v141.py` ตัวจริง (อ่านอย่างเดียว ไม่แตะไฟล์) ไม่ใช่แค่ทฤษฎี

## ผู้เล่นจะเห็นอะไรต่างจากเมื่อวาน

ไม่มีเลย — รอบนี้สร้างโมดูลใหม่ + เทสใหม่เท่านั้น ยังไม่ได้ wire เข้า dispatch (ไฟล์ที่ต้องแก้
ล็อกอยู่ที่ chief) การเปลี่ยนแปลงที่ผู้เล่นเห็นจริงจะเกิดหลังรอบที่ chief ต่อสายให้

## สิ่งที่ทำ (build ตาม "คุณไม่ตอบคำถาม คุณสร้างของ")

ใบ `1930` สั่งไว้ตรง ๆ ว่า "ไม่ได้เทียบไบต์กับ pin เดิม... ข้อนี้ LANE-A ควรทำเป็นอย่างแรก" — ทำแล้ว:

1. **subcode 3 ("กลับหน้าเลือกตัวละคร")**: ไบต์จับสดตรงกับ `LOGOUT_REQUEST_PCS[3]` **เป๊ะทุกไบต์**
   (34/34 bytes) — pin เดิมถูกต้อง ไม่มีอะไรต้องแก้ฝั่งนี้
2. **subcode 1 ("ออกจากเกม")**: ไบต์จับสด **ไม่ตรง** — ยาว 119 ไบต์ ไม่ใช่ 34 ที่ pin ไว้ เพราะ
   ไคลเอนต์ห่อ vital อื่นอีก 3 ตัว (`0x1EB4` x2, `0x2A90` x1) เข้ามาในเอนเวโลปเดียวกัน (envelope
   vital-count byte = `0x04` ไม่ใช่ `0x01`) แต่ **ตัว LogoutVital entry เอง (19 ไบต์ ตำแหน่ง 15-33
   ของเฟรม รวม subcode byte) ตรงกับ pin เดิมทุกไบต์** — pin เดิมไม่ผิด แค่แคบกว่าความเป็นจริง

3. **รันผ่าน parser จริงของ `current/pf_login_game_server_v141.py` (อ่านอย่างเดียว) เพื่อยืนยันว่า
   นี่คือบั๊ก dispatch จริง ไม่ใช่แค่ข้อสังเกตเรื่องไบต์**: `classify_logout_attempt` มีเช็ค
   `parsed.vital_count == 1` (บรรทัด 1457) เป็น hard requirement ก่อนจะเทียบ payload เลย — เฟรมจริง
   ที่จับได้มี `vital_count == 4` ⇒ ตกที่เช็คนี้ทันที คืน `"wrong_envelope"` ⇒ `_dispatch_logout_hypothesis`
   ไม่ตอบอะไรเลย (`logout_hypothesis_wrong_envelope_no_reply`) แม้ปุ่มจะถูกกดจริงและ payload
   ที่แท้จริงถูกต้องทุกไบต์ นอกจากนี้ `parsed.nested_payload` (ความยาว 99 ไบต์ = payload 14
   ไบต์ของ LogoutVital + 85 ไบต์ vital อื่น) เทียบเท่ากับ `LOGOUT_REQUEST_PAYLOADS[1]` แบบ exact-equal
   ไม่ได้อยู่ดีแม้จะแก้ vital_count แล้ว แต่ `nested_payload[:14] == LOGOUT_REQUEST_PAYLOADS[1]`
   เป็น **True** (ยืนยันด้วย parser จริง ไม่ใช่คำนวณเอง)

4. **สร้าง**: โมดูลใหม่ `src/pirateforce_foundation/logout_request_envelope.py` — ตัวแยกประเภท
   (classifier) เชิงโครงสร้างของเฟรมคำขอ LogoutVital ที่อ่านช่วงไบต์คงที่ (prefix 13 ไบต์ + byte
   สำรอง + entry 19 ไบต์ของ LogoutVital เอง) แล้ว**ไม่สนใจ**ว่ามี vital อื่นห่อมาด้วยกี่ตัว — fail
   closed ทุกกรณีที่ไม่ตรง span ที่กำหนด ไม่เคยประดิษฐ์ไบต์ ไม่แตะไฟล์เดิมเลยแม้แต่บรรทัดเดียว
   (โมดูลใหม่ทั้งไฟล์ ตามเขตเขียนของสายนี้)
5. เทส `tests/test_logout_request_envelope.py` — 18 ข้อ ผ่านหมด: เทียบกับ pin เดิม (2), เทียบกับ
   ไบต์จับสดของใบ `1930` ทั้งสองปุ่ม (4, รวม parser จริง 2 ข้อ), fail-closed 9 ข้อ, cross-check อื่น
   ๆ อีก 3 — cp874-encodable ยืนยันแล้ว, ไม่โดน exclusion regex ของ gate (`GameClient|capture_v141`)
   ยืนยันแล้วว่าเทสจะรันจริงใน `pytest_subset`

## ข้อเสนอ (ไฟล์ที่ต้องแก้ล็อกอยู่ที่ chief — สายนี้ไม่แตะ)

**ทางเลือกขั้นต่ำสุด (ก)** — แก้ 2 บรรทัดใน `logout_hypothesis.py::classify_logout_attempt`:
- บรรทัด 1457: `parsed.vital_count == 1` → `parsed.vital_count >= 1`
- บรรทัด 1463: `parsed.nested_payload == LOGOUT_REQUEST_PAYLOADS[subcode]` →
  `parsed.nested_payload[:14] == LOGOUT_REQUEST_PAYLOADS[subcode]` (14 = ความยาว payload คงที่
  ของ LogoutVital เอง `CHAT_PUSH_TRIGGER...` ไม่เกี่ยว แค่ค่าคงที่ที่มีอยู่แล้วในไฟล์)
ไม่แตะ pin ใด ๆ ไม่แตะ ack composer ไม่เพิ่มไฟล์ ผลกระทบขอบเขตแคบที่สุด

**ทางเลือกอธิบายชัดกว่า (ข)** — เรียกใช้โมดูลใหม่ของสายนี้ (`classify_logout_vital_request` จาก
`logout_request_envelope.py`) แทน โดยส่ง raw `pc` bytes เข้าไป (ต้องหา path ที่ `pc` ดิบยังไม่ถูก
ทิ้งก่อนถึง `_dispatch_logout_hypothesis` — สายนี้ยังไม่ได้ตรวจว่ามี path นั้นอยู่แล้วหรือไม่ ต้องขอ
chief ตรวจเพราะเป็นเรื่อง `runtime.py`) ข้อดี: ตัวแยกประเภทมีเทสของตัวเองแยกจาก dispatch, อ่านง่ายกว่า
ข้อเสีย: แก้มากกว่า (ก)

สายนี้แนะนำ **(ก)** เพราะแก้น้อยที่สุดและพิสูจน์แล้วด้วย parser จริงว่าถูกต้อง — (ข) ทิ้งไว้เป็นของที่
พร้อมใช้ถ้า chief อยากได้ตัวแยกที่มีเทสอิสระ

## หมายเหตุสำคัญ — นี่อาจเป็นสาเหตุจริงของ UI-B ที่ค้างสองรอบเทส

`NOW.md` (ก่อนรอบนี้) บันทึกว่า UI-A บล็อกเจ้าของสองรอบเทสติดกัน และ UI-B ยังไม่ขยับเลย ข้อค้นพบ
นี้อธิบายได้ตรง ๆ ว่าทำไม: ปุ่ม "ออกจากเกม" ของจริงแทบไม่มีทางส่งเฟรมที่มี vital เดียวโดด ๆ เสมอไป
(ไคลเอนต์ห่อ vital อื่นที่ค้างอยู่มาด้วยตามสภาพเซสชันจริง) แปลว่า exact-hash check เดิมมีโอกาส
ปฏิเสธการกดปุ่มจริงเป็นประจำ ไม่ใช่แค่ทฤษฎี — สายนี้**ไม่ได้อ้างว่านี่คือสาเหตุเดียว**หรือว่าแก้แล้ว
ปุ่มจะทำงาน (ยังไม่รู้ว่าฝั่ง response/HYP-PF-040 ถูกต้องหรือไม่ ดูหัวข้อถัดไป) แต่เป็นบั๊ก dispatch
จริงที่ยืนยันด้วยหลักฐานสองชั้น (byte capture + parser จริง) ที่ควรแก้ไม่ว่า HYP-PF-040 จะเปลี่ยน
ทิศทางยังไง
