## ✅ 1. ข้ออ้าง re-derive ของ A4 — **ผ่านแบบแข็งที่สุดเท่าที่จะผ่านได้**

คัด `pf_extract_protocol.py` ไปรันในไดเรกทอรีเปล่านอกโฟลเดอร์ส่งมอบ ชี้ที่อิมเมจตัวเดิม แล้วเทียบ sha256:


**ไบต์ต่อไบต์เหมือนกันทั้งสามไฟล์** · รันจบใน <40 วินาที · `image_sha256` ก่อน-หลังตรงกัน
และที่สำคัญกว่า: **ตรวจแล้วว่าไม่มี mapping ชื่อ→VA แบบ hardcode แม้แต่ตัวเดียว** (นับได้ 0)

⇒ **A4 ไม่ใช่การเล่นซ้ำคำตอบที่จำไว้ มันสกัดจากอิมเมจจริงทุกครั้ง**

## 🟡 2. การ์ด mutation — ผ่านบางส่วน **มีช่องหนึ่งที่พิสูจน์ไม่ได้**

**ผ่าน:** `validate_parser_regressions()` และ `validate_schema_mutation_regressions()` รันแล้วไม่ error
⇒ มันปฏิเสธการกลายพันธุ์ **ความยาว** ของ tag `0x26` (A2) และ `0x1F` (A3) ได้จริงตามที่โฆษณา

🔴 **ไม่ผ่าน/พิสูจน์ไม่ได้:** ผมกลายพันธุ์ **`field_offset`** ของ `TargetPosVital:W:1` จาก `+0x14` เป็น `+0x99`
แล้วเรียก `build_schemas()` — **มันยอมรับตารางที่ผิดโดยไม่บ่นเลย** สร้าง schema ออกมาปกติ

ผมพยายามรันชั้น capture ต่อเพื่อดูว่ามันจะจับได้ตอน parse ไหม **แต่รันไม่ได้จากที่นี่**:
```
ERROR: fresh capture path set differs from input inventory
```
เพราะ `PF_INPUT_INVENTORY.tsv` ปักพาธแบบ Windows ไว้ ส่วนผมเข้าถึงผ่าน mount แบบ Linux
(ตัวการ์ดนี้ **ถูกต้องแล้ว** — มันกันไม่ให้ใครเอาคลังอื่นมาสวม แต่มันทำให้ผมตรวจต่อไม่ได้)

**⇒ ข้อสรุปที่ซื่อตรง: มีการทุจริตหนึ่งชนิด (offset ผิด) ที่ยังไม่มีใครพิสูจน์ว่าระบบจับได้**
มันอาจถูกจับตอน parse จริงก็ได้ — แต่ **ยังไม่มีหลักฐาน** และ "ยังไม่พิสูจน์" ห้ามอ่านว่า "ปลอดภัย"

🔴 **ขอให้ Codex เพิ่มการ์ดหนึ่งตัว** (มันรันบน Windows ได้ ผมทำแทนไม่ได้):
กลายพันธุ์ `field_offset` ของข้อความที่สถานะ `VALIDATED` แล้ว **บังคับว่าผลตรวจ capture ต้องรายงาน mismatch > 0**
ถ้าไม่แดง = การ์ดไม่ครอบคลุมชนิดนี้ ต้องแก้
