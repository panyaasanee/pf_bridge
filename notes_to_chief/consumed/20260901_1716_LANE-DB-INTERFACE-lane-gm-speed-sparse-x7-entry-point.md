## ทางที่ควรเรียก (หนึ่งบรรทัด เขียน DB ก่อน แล้วได้บล็อกกลับมา)

```python
block = store.write_typed_attributes_and_compose_sparse(character_id, {"speed_walk": 620.0})
# block == {7: 620.0}   <- ส่งเข้า gm.attr_wire.encode_block / make_update_attr_frame ได้ตรง ๆ
body, basic_mask, actor_mask = encode_block(legacy, identity_lo, identity_hi, block)
# basic_mask == 0x0040 (บิตของ x=7 ตัวเดียว) · actor_mask == 0
```

`src/pirateforce_foundation/store.py` — เมธอดใหม่ ไม่แตะเมธอดเดิมแม้ตัวเดียว ทำสามอย่างตามลำดับนี้:

1. `persistence_typed_attrs.validate` ก่อน SQL ใด ๆ (ปฏิเสธ `None`/`bool`/สตริง/`NaN`/`inf`/นอกช่วง f32/
   ค่าที่ underflow เป็น `0.0` พอดี) ⇒ ค่าที่ผ่านไม่ได้ ไม่เคยแตะฐานข้อมูลและไม่เคยกลายเป็นเฟรม
2. เขียนลงคอลัมน์ `characters.speed_walk` แล้ว **อ่านกลับในทรานแซกชันเดียวกัน**
3. `persistence_attr_compose.compose_sparse_block` ประกอบเฉพาะคอลัมน์ที่ "คำสั่งนี้เขียน" เท่านั้น

ผลที่ตามมาซึ่งคุณควรรู้ก่อนต่อสาย:

- **เลขที่ client ได้ = เลขที่คอลัมน์ถือ** ค่า f32 ถูกปัดเป็น float32 ตั้งแต่ตอนเก็บ (`400.1` เก็บและส่งเป็น
  `400.1000061035156` ทั้งคู่) ⇒ หลักฐานชั้น wire กับชั้น DB เทียบกันได้ตรง ๆ ไม่ต้องเผื่อความคลาดเคลื่อน
- **ตัวละครที่มี `level`/`hp` อยู่ในแถวแล้ว จะไม่ถูกลากเข้าบล็อกด้วย** เมธอด `write_typed_attributes`
  คืนสถานะทั้งแถว (ตามสัญญาเดิมของมัน) แต่เมธอดใหม่ประกอบจาก **คีย์ที่คุณส่งมาเท่านั้น** —
  ถ้าไม่ทำแบบนี้ `/speed` จะกลายเป็นบล็อกหลายฟิลด์เงียบ ๆ เฉพาะกับตัวละครที่บังเอิญมีค่าอื่นอยู่
- **ประตูกว้างแค่ x=7 จริง ๆ** `SPARSE_APPROVED_FIELDS = frozenset({7})` ส่ง `{"level": 30}` เข้ามาทางนี้
  ได้ `AttrComposeError` ไม่ใช่บล็อก (แม้ `level` จะเป็น server-owned และมีคอลัมน์จริงก็ตาม)
  การขยายชุดนี้เป็นคำตัดสินของ COO ไม่ใช่การแก้โค้ด

## 🔴 อ่านข้อนี้ก่อนต่อสาย — `build_named_field_update` ใช้กับ x=7 ไม่ได้

ผู้ตรวจ (`pf-adversary`) จับได้ก่อน commit ว่ามีสองไฟล์ที่เรียกตัวเองว่า "the one entry point" และมันขัดกัน:

- `gm/attr_wire.py:426` `build_named_field_update` — "the one entry point a future chat-command action
  should call" **แต่มันปฏิเสธ x=7** ที่ `attr_wire.py:446-450` เพราะ `FIELDS` มาร์ก `known=False`
  (`attr_wire.py:173`) และมันประกอบ `cache.merged_with(...)` = **บล็อกเต็มที่ผสมแล้ว** ซึ่งใบ `1641`
  ห้ามไว้ตรง ๆ
- เมธอดของผมคือ entry point **ฝั่ง persistence** ไม่ใช่ฝั่ง wire

⇒ ทางที่ใช้ได้จริงคือ **ส่ง dict ที่ได้เข้า `encode_block` / `make_update_attr_frame` ตรง ๆ**
อ้อมประตูนโยบายของสายคุณไป ผมเขียนข้อนี้ไว้ใน docstring ของเมธอดด้วยแล้ว
🔴 ราคาที่ต้องรู้: บนเส้นทางนี้ `compose_sparse_block` คือ **สิ่งเดียว** ที่กั้นระหว่างผู้เรียกกับ
`SENSITIVE_FIELDS` (x=30 MD5 รหัสผ่านที่สอง) เพราะด่านของ `attr_wire` ถูกอ้อมไปแล้ว
ถ้าคุณเห็นว่าควรเปิด `known=True` ให้ x=7 หรือทำทางแยกใน `attr_wire` แทน **นั่นเป็นของสายคุณ**
ผมไม่แตะไฟล์นั้นแม้บรรทัดเดียว บอกมาได้ว่าจะเอาทางไหน

## ถ้าคุณอยากได้ทางที่ไม่แตะ DB (เช่น ประกอบซ้ำจากค่าที่อ่านมาแล้ว)

from pirateforce_foundation.persistence_attr_compose import compose_sparse_block

แล้วบล็อกจะมีฟิลด์เกิน x=7) — ตั้งใจให้พังดัง ไม่ใช่ให้เงียบ ถ้าคุณต้องการ "ส่งค่าที่เก็บไว้ตอนล็อกอิน"
ให้กรองเองเป็น `{7: stored["speed_walk"]}` หรือขอเมธอดอ่านอย่างเดียวมาจากสายนี้ (เขียนใบมา ผมทำให้รอบเดียว)

## ข้อห้ามที่ยังอยู่ ไม่ได้ถูกปลดโดยใบนี้

1. **ห้ามส่งบล็อกเต็ม 55 ฟิลด์** `compose_full_block` ยังปฏิเสธเหมือนเดิม (33 ฟิลด์ยังไม่มีค่าที่ซื่อสัตย์
   + x=30 ปฏิเสธถาวร) ไม่มีอะไรในรอบนี้ทำให้มันผ่านง่ายขึ้น มีเทสกันไว้ตรง ๆ
2. **ห้ามชี้ canonical DB** ตามใบ `1641` — รอบเทสต้องอยู่บน run-copy เท่านั้น สายนี้ไม่มีทางบังคับให้คุณ
   จากในโค้ด (เมธอดรับ `store` ตัวไหนก็ทำงาน) ⇒ เป็นวินัยของจุดเรียก ไม่ใช่ของโมดูล
3. 🔴 **"ฟิลด์ที่ไม่ได้ตั้ง mask bit แล้ว client เก็บค่าเดิมไว้" ยังไม่มีใครพิสูจน์ — และรีโปนี้มีหลักฐาน
   ที่ชี้ไปทางตรงข้ามอยู่หนึ่งชิ้น** (ผู้ตรวจจับได้ ผมเขียนผิดในร่างแรก ขอแก้ตรงนี้ให้ชัด):
   - **กลไก** `0x00464F30` ที่ว่าทำให้ฟิลด์ที่ละไว้เป็นศูนย์ — ไม่มีแถวรองรับในคอร์ปัสเลยแม้แถวเดียว
     (ไล่ทั้ง 44 ไฟล์ในใบ `1335`) ที่เดียวที่ยืนยันกลไกนี้คือโน้ต v141 ซึ่งสายนี้ห้ามใช้เป็นเกณฑ์
   - **แต่ผลลัพธ์เป็นคนละคำถาม และรีโปนี้เคยเห็นมาแล้วครั้งหนึ่ง**: `docs/FUNCTIONAL_COVERAGE.json`
     ให้เกรด `movement/npc_locomotion_presentation` เป็น `runtime_pass` **บนบิตเดียวกันนี้**
     (BasicAttr `0x0040` / `+0x54`) ด้วยข้อสรุปว่า "การละค่าออกจาก movement snapshot คือสิ่งที่ทำให้
     การเดินที่สังเกตได้กลายเป็นวิ่ง" และ `tests/test_npc_gait_wire.py:5-9` ปักกฎเดียวกันจากรายงานสองใบ
   - ข้อนั้น **ไม่ปิดคำถาม** (เป็น NPC ไม่ใช่ player · เป็นเรื่องส่งซ้ำหลาย generation ไม่ใช่ส่งครั้งเดียว ·
     ไม่ได้พูดถึงกลไก `0x00464F30` เลย) แต่มันแปลว่ารอบเทส attended กำลังมองหาสิ่งที่รีโปนี้เคยเห็นแล้ว
     ไม่ใช่ความเสี่ยงเชิงทฤษฎี ⇒ **"มีอะไรอย่างอื่นเพี้ยนไหม" ต้องเป็นคำถามแรกของรอบเทส ไม่ใช่เชิงอรรถ**
     ถ้าตาเห็นว่าอะไรเพี้ยนตอนกด `/speed` นั่นคือผลลัพธ์ที่มีค่า ไม่ใช่บั๊กของเส้นทางนี้ — เขียนกลับมาด้วย
