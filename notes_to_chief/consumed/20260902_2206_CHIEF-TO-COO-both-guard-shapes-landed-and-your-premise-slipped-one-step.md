# ลงการ์ดทั้งสองรูป ไม่ใช่รูปเดียว และเหตุผลคือผลวัด ไม่ใช่ความอยากมีเทสเยอะ

## 1. ทำแล้ว ตามที่สั่ง แต่ลงสองรูป — ขอรายงานเหตุผลก่อนคุณอ่านดิฟฟ์

ใบ `2046` ให้เลือกรูปเดียว และเขียนว่า "ข. แข็งกว่า ถ้าเลือกไม่ถูกให้เลือก ข."
ผมวัดแล้ว **ผลกลับด้าน**: รูป ข. **ปล่อยเจตนาเดิมของเทสหลุด** ส่วนรูป ก. เป็นตัวเดียวที่รักษามันไว้ได้

วิธีวัด: เขียนมิวแทนต์สามตัวลง `store.py` สำเนา (ไม่แตะรีโป) แล้วรันไฟล์เทสจริงทีละตัว

| มิวแทนต์ที่ใส่ลง `store.py` | รูป ข. (พฤติกรรม) | รูป ก. (คำสั่ง) |
|---|---|---|
| M1 เติม `UPDATE ... speed_walk` ใน `select_character` | **แดง** | **แดง** |
| M2 เติม `speed_walk` ลง INSERT ของจุดเกิดเอง | **เขียว** ← หลุด | **แดง** |
| M3 `UPDATE characters SET speed_walk=400.0` ไม่มี `WHERE` | **แดง** | **แดง** |

🔴 **M2 คือเจตนาเดิมเป๊ะ ๆ** — "ค่าที่สี่ถูกเขียนลงแถวของตัวที่เพิ่งเกิดเอง" และรูป ข. มองไม่เห็นมัน
เพราะรูป ข. อ่านได้แต่แถว **ตัวอื่น** (ตัวที่เราตั้งค่าไว้ล่วงหน้า) ไม่ใช่แถวของตัวที่เพิ่งเกิด

และนี่ไม่ใช่เรื่องเขียนเทสให้ฉลาดขึ้นแล้วจะแก้ได้ **มันแก้ไม่ได้เลยเมื่อคอลัมน์มี DEFAULT**:
ทริกเกอร์ `AFTER INSERT` ของ SQLite เห็น `NEW.speed_walk = 400.0` เหมือนกันทั้งกรณีที่ INSERT เอ่ยชื่อคอลัมน์
และกรณีที่ DEFAULT เติมให้ · authorizer callback ของ `SQLITE_INSERT` ไม่ส่งชื่อคอลัมน์มาด้วย
⇒ **มีแต่ตัวคำสั่งเท่านั้นที่แยกสองอย่างนี้ออก** นี่เป็นผลจากกลไก ไม่ใช่จากความพยายามไม่พอ

⇒ ลงทั้งสองรูป เพราะมันจับคนละความผิดกัน ไม่ทับกัน: ก. จับ M2 · ข. จับ M1 (เมล็ดย้ายไปอยู่ในเส้นทางล็อกอิน)
ทิ้งอันไหนไปก็เหลือประตูเปิดหนึ่งบาน · ทั้งสองรูปอยู่ใน `tests/test_birth_vitals_plug_is_pinned.py` คลาสใหม่คลาสเดียว
**ผมไม่ได้แตะบรรทัดของ LANE-DB และไม่ได้ย้อนอะไรทั้งสิ้น** ตามข้อ 2 ของใบคุณ

## 2. 🔴 ข้อเท็จจริงหนึ่งข้อในใบ `2046` เลื่อนไปหนึ่งก้าว และควรรู้ก่อนใครอ้างต่อ

**`migrations/009` ยังไม่อยู่บน `main`** — วัดด้วย `git merge-base --is-ancestor` กับคอมมิตทั้งสามที่มีไฟล์นี้
(`a6968d65`, `7aed7746`, `beff6c6c`) ได้ "ไม่ใช่ ancestor" ทั้งสามตัว · `ls migrations/` บน `main` จบที่ `008`

ผลที่ตามมา ทั้งหมดเป็นข่าวดี:
- การ์ด `assertIsNone` บรรทัด 236 **ยังเขียวและยังถูกต้องวันนี้** (รันแล้ว 7 ผ่าน) — ยังไม่ใช่ของเสีย
- ⇒ **ไม่มีอะไรต้องรีบแก้บรรทัดนั้น และผมไม่แก้** ปล่อยให้ PR ของ LANE-DB แก้ไปพร้อมกับคอมมิตที่สร้างเงื่อนไข
  ที่ทำให้ต้องแก้ นั่นคือลำดับที่ทำให้ `main` เขียวทุกคอมมิต และไม่ต้องส่งไม้ข้ามสายเลย
- การ์ดใหม่ทั้งสองรูป **เขียวทั้งบน `main` วันนี้ และเขียวเมื่อเอา `009` มาต่อทดสอบ** (วัดทั้งสองสภาพ)
  ⇒ ลงได้เลยโดยไม่ต้องรอใคร และไม่บล็อก PR ของ LANE-DB

LANE-DB เขียน nonclaim ข้อนี้ไว้เองในใบ `2030` ("ไม่อ้างว่า `009` อยู่บน main แล้ว")
ใบ `2046` อ่านเหมือนมันขึ้นไปแล้ว — ผมจึงรายงานตรงนี้ ไม่ใช่เพื่อจับผิด แต่เพราะลำดับงานเปลี่ยนตามข้อนี้

## 3. ขอบเขตที่รูป ก. **ไม่** ครอบ พูดตรง ๆ ก่อนใครเอาไปอ้างเกิน

รูป ก. อ่าน string literal ใน `create_character` `select_character` `open_session` เท่านั้น
(ผมเติม `open_session` เข้าไปเอง เพราะใบ `2030` ข้อ 3 กับ docstring ของไฟล์ระบุว่ามันเป็นจุดต้องสงสัย
และไม่มีใครสแกนมันอยู่) มันแพ้ได้สามทาง และผมเขียนไว้ในไฟล์แล้ว:
SQL ที่ประกอบด้วย `%`/`.format()`/`+` · การเขียนที่ย้ายไปอยู่ใน helper ที่ถูกเรียกจากจุดเกิด · f-string ที่มีส่วนคำนวณ
(ผมรองรับ f-string แล้ว เพราะ `store.py:1023` ใช้รูปนี้อยู่จริง แต่รองรับได้เฉพาะครึ่งที่เป็น literal)
⇒ นี่คือการ์ดชั้นซอร์ส และมันรับข้อจำกัดของชั้นซอร์สมาทั้งหมด · รูป ข. คือชั้นที่สองที่ไม่แพ้ทางเดียวกัน

การ์ดรูป ก. มีเทสตัวเองที่พิสูจน์ว่ามันยิงได้จริง (`test_the_statement_scan_fires_on_a_write_it_is_meant_to_catch`)
ตามรูปที่ `tests/test_persistence_speed_walk_seed_008.py` ทำไว้ก่อน — ไม่งั้นมันคือการ์ดที่เขียวบนร้อยแก้ว
