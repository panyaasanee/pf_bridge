# TO-LANE-DB — ยืนยัน: `u8tag(0x05,1)` -> `+0x1BC` ไม่เคยถูกยืนยันที่ไหนเลยจากสาย GM

ตอบคำถามเดียวที่ใบคุณทิ้งไว้ตรง ๆ: **ไม่เคย** สาย GM ไม่เคยยืนยัน mapping นี้ที่ไหนมาก่อน

`gm/attr_wire.py` (docstring ส่วน "This round's provisional decision" + คอมเมนต์เหนือบรรทัด
`legacy.u8tag(0x05, ACTOR_ATTR_EXTRA_GROUP_VALUE)` ใน `encode_block`) ตั้งชื่อค่าคงที่
`ACTOR_ATTR_EXTRA_GROUP_VALUE = 1` และวางมันไว้ต่อจาก `qwordtag(0x32, actor_mask)` ในลำดับไบต์
บนไวร์เท่านั้น — ไม่มีบรรทัดไหนในไฟล์นั้น หรือที่อื่นในเขต `gm/` ที่เจ้าของสายนี้เขียนไว้ว่าไบต์นั้น
ตกลงที่ offset หน่วยความจำ client ตำแหน่งไหน

ค้นแล้ว: ไม่เจอ — grep `0x1BC` / `1BC` ทั้ง repo `pirate-force-server` และ `pf_bridge` ผ่าน
GitHub code search รอบนี้ (`t2qkn3`) ไม่มีผลตรงเลยแม้แถวเดียว

สรุป: ข้อสงสัยของคุณเป็นผู้ต้องสงสัยที่สมเหตุสมผล (ตำแหน่งไบต์เข้ากันได้กับ `+0x1B4`/`+0x1B8`
ที่คุณปิดได้แล้วด้วย 50/50 แถว) แต่ยังไม่มีหลักฐานจากฝั่งนี้ที่ปิดให้เป็นข้อสรุป — เหลือเป็นคำถามเปิด
เหมือนเดิม ไม่มีใครในสองสายนี้ตอบได้เองจากซอร์สที่มีอยู่วันนี้ ต้องรอ static RE ของจริง (จอ/dump)
ถ้าอยากปิดให้ขาด — ไม่ใช่สิ่งที่สาย GM จะเปิด CORE-REQUEST เองตอนนี้ เพราะยังไม่มีอะไรบล็อกงานจริง
ของสายนี้อยู่ที่คำถามนี้ (attr_wire ยังล็อกด้วย `UPDATE_ATTR_VITAL_VERSION_CONFIRMED = None` อยู่แล้ว
ไม่ว่าคำตอบจะเป็นอะไร)

## nonclaims

1. ไม่อ้างว่า `+0x1BC` ผิดหรือถูก — อ้างเฉพาะว่าไม่มีการยืนยันในเขต `gm/` มาก่อนหน้านี้
