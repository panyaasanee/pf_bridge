# RE-292 RESULT — คู่แรก `0B xx` = **`vital_version`** ของซองจดหมาย · presence = **คู่ที่สอง**

ADDRESSEE: LANE-GM — เจ้าของใบ/ผู้บริโภคผล · cc: chief, COO, LANE-UI, LANE-DB, LANE-A
ผู้ทำ: RE runner บนเครื่องสะพาน (static, read-only) · รอบ `RE-RUNNER-20260907_1100-OWNER-ORDERED-FULL-SWEEP`

## สถานะ: **PASS / BOUNDED-POSITIVE** — ตอบครบทั้งสองครึ่งของคำถามเดียวของใบ

## คำตอบสองบรรทัด

1. **คู่แรก `0B 00` = `vital_version`** — ฟิลด์ของ **ซองจดหมายชั้นวิทัลทั่วไป** ไม่ใช่ของคลาส
   เขียนที่ `0x005F3993` จาก `vital_object + 0x10` · ฝั่งรับอ่านที่ `0x005F3EF4` แล้ว
   **เทียบเท่ากันเป๊ะ** กับ `+0x10` ของตัวเอง ที่ `0x005F3EFC/0x005F3F01` · ไม่ตรง = โยน error
   `0xE0000031` ทิ้งทั้งเฟรม
2. **presence = คู่ที่สอง `0B 01`** — เขียนโดย serializer ของคลาสเองที่ `0x00729E37`
   จากเงื่อนไข `[this+0x14] != 0`

⇒ pin `RE-088` อ่านคู่แรกเป็น presence จึงสรุปว่า "ไม่มี body" ทั้งที่เหลืออีก 24 ไบต์
**decoder ไม่ผิดเรื่อง layout ของคลาส — มันเริ่มนับผิดตำแหน่งหนึ่งฟิลด์**

## หลักฐาน — โครงซองจดหมายของ *ทุก* วิทัล (ตัวเขียน `0x005F3956`-`0x005F39A2`)

```
5f3956  mov ecx,[ebx+8]        ; อ็อบเจ็กต์วิทัล
5f3959  mov edx,[ecx]          ; vtable
5f395b  mov eax,[edx+0x10]     ; slot +0x10 = GetClassId()
5f395e  call eax
5f3963  push 0x2               ; ขนาด 2
5f396e  push 0x12              ; TAG 0x12 = u16
5f3972  call 0x89a600          ; << เขียน u16 class id  = ไบต์ "E9 51" ที่ capture อ้างอิง
...
5f3986  mov esi,[ebx+8]
5f3989  push 0x1               ; ขนาด 1
5f398b  lea eax,[esi+0x10]     ; << ต้นทาง = vital_object + 0x10
5f398f  push 0xb               ; TAG 0x0B
5f3993  call 0x89a600          ; << เขียน vital_version  = คู่แรก 0B 00
5f3998  mov edx,[esi]
5f399a  mov eax,[edx+0x18]     ; slot +0x18 = serializer ของคลาส (= 0x00729E10)
5f399d  push 0x1               ; flag = write
5f399f  push ebp               ; stream
5f39a2  call eax               ; << ตัวคลาสเริ่มเขียนตรงนี้ = คู่ที่สองเป็นต้นไป
```

ตัวอ่านคู่ของมัน (`0x005F3EE3`-`0x005F3F40`) พิสูจน์ว่าเป็น version ไม่ใช่ presence:

```
5f3ee9  push 0xb
5f3ef0  mov BYTE [ebp-0x31],0x0    ; ค่าตั้งต้น 0
5f3ef4  call 0x89a640              ; อ่าน u8
5f3efc  cmp cl,BYTE PTR [esi+0x10] ; << เทียบเท่ากันเป๊ะกับของตัวเอง
5f3f01  je  0x5f3f39               ; ตรง -> เดินต่อ
        ...ไม่ตรง -> สร้างข้อความ error 0xE0000031 (สตริง 0x00F30DD4)...
5f3f39  mov eax,[esi]
5f3f3b  mov edx,[eax+0x18]         ; แล้วค่อยเรียก serializer ของคลาส
5f3f40  call edx
```

**presence ไม่มีวันถูก `cmp` กับฟิลด์ของตัวเอง** — พฤติกรรม "เท่ากันเป๊ะ ไม่งั้นทิ้งเฟรม"
คือนิยามของ version ไม่ใช่ของ presence

🔴 **VA คู่นี้ (`0x005F3EFC` / `0x005F3F01`) คือ VA เดียวกับที่ `RE-256` ปักไว้แล้ว**
ตอนตอบ `AddSurveyData` ว่า "`vital_version` ของคลาสนี้ต้องเป็น 0 แบบ exact equality"
⇒ ใบนี้ยืนยันซ้ำจากอีกคลาสหนึ่ง และเลื่อนสถานะของข้อค้นพบนั้นจาก "ของคลาสเดียว"
เป็น **"ของซองจดหมายชั้นวิทัลทั้งระบบ"**

## serializer ของคลาสเขียนอะไรบ้าง (นับได้ครบ ไม่มีเศษ)

`0x00729E10` (ตัวนอก):
- `0B <presence>` จาก `[this+0x14] != 0` (`setne`) — **หนึ่งไบต์แท็กเดียว** แล้ว
- ถ้า presence = 0 → `ret 8` ทันที · ถ้า = 1 → เรียก `0x00726C20` ด้วย `ecx = [this+0x14]`

`0x00726C20` (ตัวใน — เขียน body ทั้งหมด ตามลำดับนี้เป๊ะ):

| ลำดับ | ที่มา | TAG | ขนาด | VA ที่เขียน |
|---|---|---|---|---|
| 1 | `child+0x10` | `0x14` | 4 | `0x00726C3B` |
| 2 | `child+0x14` | `0x14` | 4 | `0x00726C55` |
| 3 | `child+0x18` | `0x0B` | 1 | `0x00726C6F` |
| 4 | `child+0x1C` | string | - | `0x00726C85` (`call 0x89A810`) |
| 5 | `child+0x38` | string | - | `0x00726C9B` (`call 0x89A810`) |

ตรงกับ `RE-283` FINAL คำต่อคำ · **ไม่มีฟิลด์ที่หก** ⇒ ทั้ง 5 ฟิลด์ + presence กินไบต์พอดี

## ตรวจกับไบต์จริงทั้งสามเฟรม (R322B)

เฟรมที่ 1 `0B 00 | 0B 01 | 14 01000000 | 14 00000000 | 0B 01 | 48 00000000 | 48 00000000`

| ไบต์ | ผู้เขียน | ความหมาย |
|---|---|---|
| `0B 00` | ซองจดหมาย `0x005F3993` | **`vital_version` = 0** |
| `0B 01` | คลาส `0x00729E37` | presence ของ `child` = มี |
| `14 01000000` | `0x00726C3B` | `child+0x10` = **1** (บิตฟังก์ชัน) |
| `14 00000000` | `0x00726C55` | `child+0x14` = 0 |
| `0B 01` | `0x00726C6F` | `child+0x18` = 1 (แฟล็ก) |
| `48 00000000` | `0x00726C85` | สตริงว่าง |
| `48 00000000` | `0x00726C9B` | สตริงว่าง |

รวม 26 ไบต์ = ตรงกับที่ decoder รายงานว่า "อ่าน 2 ไบต์แล้วเหลือ 24" เป๊ะ
เฟรม 2 ต่างที่ไบต์เดียว (`0B 01`→`0B 00` ที่ฟิลด์ 3) และเฟรม 3 ต่างที่ `14 00100000` (=0x1000)
กับสตริงแรก `48 02000000 3000` — **ทั้งสองความต่างตกในฟิลด์ที่ตารางข้างบนทำนายไว้ ไม่มีไบต์เกิน**

## nonclaims

1. **ไม่อ้างว่า decoder ผิด** — ตามคำสั่งของเจ้าของใบ · อ้างเฉพาะว่า **pin เริ่มนับผิดหนึ่งฟิลด์

2. **ไม่อ้างว่า `vital_version` ของทุกคลาสเท่ากับ 0** — วัดได้ว่าค่าถูกอ่านจาก `vital+0x10`

4. **ไม่ได้ใช้ linear disassembler เป็นหลักฐานผลลบ** — ทุกข้ออ้างข้างบนเป็นผลบวก อ่านจาก
