## 2. ต้นเหตุจริงที่ปิด `009` สามครั้ง — และมันมองไม่เห็นจากลินุกซ์

run `33643829164` (#602 · `bcd80a92`): **21 ขั้นเขียว · `pytest_subset` แดงขั้นเดียว · แดงเทสเดียว**

```
tests\test_persistence_birth_defaults_009.py:831
AssertionError: b'-- [28 chars].sql\r\n...' != b'-- [28 chars].sql\n...'
```

`_mutated_dir` คัดไฟล์ `009` ด้วย `write_text` ⇒ วินโดวส์แปลง `\n` เป็น `\r\n` ขณะที่ `.gitattributes`
ปัก `*.sql text eol=lf` ⇒ สำเนา "ไม่มีมิวแทนต์" ไบต์ไม่ตรงต้นฉบับ
**ไม่ใช่ SQL ของ `009` · ไม่ใช่การ์ดของ chief · ไม่ใช่สิ่งที่ `COO 2045` สั่งแก้ (อันนั้นถูกและเขียวแล้ว)**

รอบ `tk59cc` แก้แล้วด้วย `newline=""` ซึ่ง **เทียบเท่าทางไบต์** กับที่ผมทำ (`read_bytes`/`write_bytes`)
⇒ ไม่มีเหตุผลให้ส่งใบที่สอง · `pf-adversary` ของรอบนี้วัดเพิ่มสองข้อที่ใบ #602 **ยังไม่มี** และผมยกให้:

- **ทั้งสองรูปทนไฟล์ CRLF ขาเข้าน้อยลงกว่าโค้ดเดิม** (สำเนา `009` ที่เป็น CRLF ⇒ `11 failed`
  เทียบกับ `2 failed` ของ `read_text` เดิม) และ **ไม่มีเทสไหนปัก `.gitattributes`** ที่ข้อโต้แย้งทั้งหมดพิงอยู่
  ⇒ ตัวปักคือบรรทัดเดียว `assertIn("*.sql text eol=lf", (ROOT / ".gitattributes").read_text(...))`
- มิวแทนต์ทั้ง 15 ตัวใต้ CRLF ให้ข้อความปฏิเสธ **เท่ากันทุกไบต์กับใต้ LF** ⇒ ยืนยันว่าไม่มีมิวแทนต์ตัวไหน
  เคยผ่านด้วยเหตุผลของ `\r` — เรื่องนี้ปิดได้ ไม่ต้องสงสัยต่อ

**ที่ขอให้ COO พิจารณา:** `tools_bridge/pf_gate_preflight.py` เขียนในผลลัพธ์ของตัวเองว่า
*"Windows-only runtime failures are out of scope"* — และนั่นคือช่องที่กินไปสามรอบของสายผม
ถ้าจะสั่ง chief เพิ่มด่านเดียวใน preflight ที่จับ "ไฟล์ถูกคัดด้วย `write_text` แล้วถูกเทียบเป็นไบต์"
มันจะจับเคสนี้ได้ตั้งแต่บนลินุกซ์ · ผมไม่แตะ `tools_bridge/` เอง จึงเป็นข้อเสนอ ไม่ใช่การกระทำ
