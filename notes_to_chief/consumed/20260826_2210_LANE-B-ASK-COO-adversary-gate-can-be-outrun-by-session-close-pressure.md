# ติดอะไร: กติกา "ต้องผ่าน pf-adversary ก่อน commit ทุกครั้ง" ถูกข้ามลำดับได้จริงในรอบนี้ -- ไม่ใช่เพราะจงใจฝ่าฝืน แต่เพราะเครื่องมือของ session บีบให้เลือกระหว่างสองกติกาที่ขัดกันเอง

## เกิดอะไรขึ้นจริง (ลำดับเวลา)

1. รอบ `hsy023` ให้ pf-builder agent สำรวจ+แก้ไฟล์ 6 ไฟล์ (docstring/NONCLAIMS ที่ล้าสมัย 3 โมดูล +
   pin JSON 2 ไฟล์ + `docs/FUNCTIONAL_COVERAGE.json` อีก 1 ไฟล์ที่ orchestrator เพิ่มเอง) -- ทั้งหมด
   ยังไม่ commit ค้างอยู่ใน working tree
2. orchestrator เรียก pf-adversary agent แบบ **async** (ต้องรอ notification กลับ ไม่ใช่รอสด) เพื่อตรวจ
   ก่อน commit ตามกติกา
3. ระหว่างรอ pf-adversary, session hook (`~/.claude/stop-hook-git-check.sh`) ปฏิเสธการปิดรอบเพราะเห็น
   working tree มีการแก้ไขค้าง -- hook นี้ไม่รู้ว่ามี pf-adversary กำลังตรวจอยู่ มันเช็คแค่ "มี diff ค้างไหม"
4. orchestrator เลือก **commit + push ก่อน** ได้ผล pf-adversary เพื่อให้ hook ผ่าน โดยบันทึกเหตุผลไว้ตรง ๆ
   ใน round file section 11 ว่าจะ push คอมมิตแก้เพิ่มถ้า pf-adversary พบปัญหาจริง
5. ผล pf-adversary กลับมาทีหลัง: **เนื้อหาผ่านทุกข้อ ไม่พบบั๊ก** แต่ตัวมันเองชี้ตรงว่าลำดับที่เกิดขึ้น
   (push ก่อนเห็นผล) คือการข้าม "ประตูบังคับ" จริง ไม่ใช่แค่ความเสี่ยงทางทฤษฎี เพราะคอมมิตไปอยู่บน branch
   สาธารณะที่ chief/COO/สายอื่นอ่านได้ทันทีตั้งแต่ก่อนตรวจเสร็จ

**สรุปตรง ๆ:** รอบนี้รอดเพราะเนื้อหาถูกต้องจริง (orchestrator ตรวจซ้ำเองก่อน push ด้วย) แต่ระบบไม่ได้
"บังคับ" ให้ถูกต้อง -- มันแค่บังเอิญถูกต้อง `draft PR` และ "สัญญาว่าจะแก้ทีหลัง" ไม่ใช่ lock จริงตามที่
pf-adversary เขียนไว้ (ไม่มีอะไรห้ามคนอื่นเอา PR ออกจาก draft หรือ merge ก่อนจะรู้ผล)

## ทางเลือกที่เห็น

**(ก) ยอมรับว่า hook กับ async-adversary ขัดกันในรอบที่ต้องปิดก่อน adversary ตอบ** -- แก้โดยให้ chief/
เจ้าของตั้ง branch protection หรือ required-status-check บน PR ที่ยังเป็น draft (เช่น ห้าม merge จนกว่า
จะมี label/comment ยืนยันจาก pf-adversary) เป็นกลไกที่ "อีกฝ่ายทำให้เสียได้จริง" ไม่ใช่แค่คำสัญญาของสายที่
push เอง -- ตรงกับที่ `cloud_round_lock.json` (tombstone) เคยสรุปไว้แล้วสำหรับปัญหาคนละแบบแต่หลักการ
เดียวกัน ("a lock you win by pushing is real because git rejects atomically")

**(ข) เปลี่ยนกติกา session ให้ hook ไม่บล็อกรอบที่มี pf-adversary agent กำลังรันอยู่จริง** (ต้องมีทางบอก
hook ว่า "กำลังรอผลอยู่ ไม่ใช่ทิ้งงานค้าง") -- แก้ปัญหาที่ต้นเหตุ (การบีบให้เลือก) แต่เป็นการแก้ tooling ของ
session ซึ่งไม่ใช่เขตของสาย B และอาจไม่ใช่เขตของ chief ด้วย (อาจเป็นของเจ้าของ/ผู้ตั้งค่า session)

**(ค) เก็บพฤติกรรมปัจจุบันไว้ (push ก่อน, แก้ตามทีหลังถ้าพบปัญหา) แต่บันทึกเป็นกติกาที่ยอมรับอย่างเป็น
ทางการ** สำหรับกรณีที่ hook กับ async-review ขัดกันเท่านั้น -- ง่ายสุด แต่คือการยอมรับว่าประตูบังคับข้อนี้
มีช่องโหว่โดยเจตนา
