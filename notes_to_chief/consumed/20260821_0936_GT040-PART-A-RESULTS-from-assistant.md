# 1) `0x5E2960` — derived bit `0x04` · object `+0x24`

รูปแบบเป็นฟังก์ชันเดียวสองทาง: `cmp BYTE PTR [esp+0xC],0` -> ไม่ใช่ศูนย์ = **เขียน** (เรียก `0x89A600`) · ศูนย์ = **อ่าน** (เรียก `0x89A640`)
ลำดับ tag เหมือนกันเป๊ะทั้งสองทาง ⇒ ตารางเดียวใช้ได้ทั้งขาไปขากลับ

**ลายเซ็นของ primitive ที่ใช้ตลอดทั้งสองฟังก์ชัน:** `thiscall(stream) (int tag, void* p, int len)` — อาร์กิวเมนต์ push จากขวาไปซ้าย (`len` ก่อน, `tag` หลังสุด)

### ส่วนหัวของ object `+0x24`

| ลำดับ | tag | ที่มา/ปลายทางในอ็อบเจกต์ | len |
|---|---|---|---|
| 1 | `0x14` | `+0x10` | 4 |
| 2 | `0x0B` | `+0x14` (ขาเขียนตัดเหลือ 1 ไบต์ · ขาอ่าน `movzx` กลับเป็น dword) | 1 |
| 3 | `0x0B` | `+0x18` (เหมือนกัน) | 1 |
| 4 | `0x12` | จำนวนสมาชิก = `([+0x2C]-[+0x28])/4` ตัดเป็น `uint16` | 2 |

### ต่อด้วยลูปสมาชิก (จำนวนตามข้อ 4)

| tag | ฟิลด์ในสมาชิก | len |
|---|---|---|
| `0x0B` | `elem+0x10` | 1 |
| `0x2A` | `elem+0x14` | 4 |

### สมาชิกคืออะไร (วัดจาก allocator ไม่ได้เดา)

ขาอ่านสร้างสมาชิกด้วย `mov ecx,0x1031324 ; push 0xF0A90C ; push 0 ; call 0x5E2630`
(`0xF0A90C` = สตริง `"file"` ท้ายพาธ `e:\projects\big\source\shareproj\essential\PcRecycleBlock.h` ⇒ เป็นแท็ก **pool allocator** ไม่ใช่ชื่อคลาส)

ใน `0x5E2630`: `push 0x18 ; call 0x88D020` ⇒ **ขนาดสมาชิก = `0x18` ไบต์** แล้วเซ็ต
`[esi] = 0xF86D6C` (คลาสฐาน) แล้วทับด้วย `[esi] = 0xF2FF14` (คลาสลูก) และ `movss [esi+0x14], 0.0f`

- `0xF86D6C` แก้ RTTI ได้ = **`.?AVPcRefObject@@`** ⇒ สมาชิกสืบทอดจาก `PcRefObject`
- `0xF2FF14` **ไม่มี RTTI** (`[vt-4] = 0`) และ **ไม่มี runtime name literal** — ทั้งอิมเมจอ้างเลขนี้แค่ **3 จุด** (`0x5E25D5`, `0x5E2682`, `0x5E26F9`) ซึ่งอยู่ในย่านตัวเองทั้งหมด
  🔴 **จึงไม่มีชื่อคลาสให้รายงาน และผมจะไม่เดา** (วินัย `pf-static-re`)
- `movss` ที่ `+0x14` ยืนยันว่า **tag `0x2A` = float 4 ไบต์** (สอดคล้องกับข้อ 3 ของท่อน B ด้านล่าง)

ขาอ่านผลักสมาชิกเข้า container ที่ `+0x1C` (`lea ecx,[esi+0x1C] ; call 0x64F2D0`)
ส่วนขาเขียนเดิน vector ที่ `[+0x28]..[+0x2C]`
🟡 **ความไม่สมมาตรนี้เป็นข้อเท็จจริงที่วัดได้ ไม่ใช่ข้อสรุป** — ยังไม่ได้พิสูจน์ว่า `+0x1C` กับ `+0x28` เป็นตัวเดียวกันหรือคนละตัว

# 2) `0x5F85B0` — derived bit `0x08` · object `+0x20`
### (ตัวที่ใบสั่งบอกว่า "ยังไม่ decode เลยแม้แต่บรรทัดเดียว")

โครงเดียวกัน (เขียน `0x89A600` / อ่าน `0x89A640`) แต่ **เป็นลิสต์ที่เข้ารหัสแบบ dirty-mask ต่อสมาชิก**

### ส่วนหัว

| ลำดับ | tag | ที่มา | len |
|---|---|---|---|
| 1 | `0x12` | `[obj+0x2C]` เป็น `uint16` = จำนวนสมาชิก | 2 |

จากนั้นเดินลิสต์จาก `[obj+0x28]` (โหนดมี `next` ที่ `[node+0x00]`, payload ที่ `[node+0x10]`)

### ต่อสมาชิกหนึ่งตัว

| เงื่อนไข | tag | ฟิลด์ใน payload | len |
|---|---|---|---|
| เสมอ | `0x14` | `+0x10` (id) | 4 |
| เสมอ | `0x0B` | `+0x28` = **ไบต์ mask** | 1 |
| mask `0x02` | `0x14` | `+0x14` | 4 |
| mask `0x04` | `0x0F` | `+0x18` | 2 |
| mask `0x08` | `0x05` | `+0x1B` | 1 |
| mask `0x10` | `0x2A` x3 | `+0x1C`, `+0x20`, `+0x24` = **สามฟลोट** (ผ่าน `0x5F3490` ขาเขียน / `0x5F34D0` ขาอ่าน) | 4+4+4 |
| mask `0x20` | `0x08` | `+0x1A` | 1 |

🔴 **ถ้า mask เป็นศูนย์ ข้ามทุกฟิลด์ที่มีเงื่อนไข** (`mov al,[edi] ; test al,al ; je`)
🔴 **บิต `0x01`, `0x40`, `0x80` ไม่เคยถูกทดสอบเลยทั้งขาเขียนและขาอ่าน** — สามบิตนี้ว่าง (หรือถูกใช้ที่อื่นนอกฟังก์ชันนี้ ซึ่งใบนี้ไม่ได้ตรวจ)
✅ **ขาอ่าน (`0x5F8719`+) สะท้อนตารางนี้เป๊ะทุกแถว ทุก tag ทุก len** — ตรวจแล้วทีละบรรทัด

### สมาชิกคืออะไร

`mov ecx,0x1031570 ; push 0xF0A90C ; call 0x5F82C0` (pool คนละตัวกับข้อ 1)
ใน `0x5F82C0`: `push 0x2C` ⇒ **ขนาดสมาชิก = `0x2C` ไบต์** · `[esi]=0xF86D6C` แล้วทับด้วย `[esi]=0xF313C4`
ค่าเริ่มต้นที่คอนสตรัคเตอร์เซ็ต: `+0x1C/+0x20/+0x24 = 0.0f` (สาม `movss`) · `+0x1A = 1` · `+0x28 = 0xFF` · `+0x10/+0x14 = 0` · `+0x1B = 0`

- ฐานเดียวกัน: `PcRefObject`
- `0xF313C4` เป็น vtable 4 ช่อง `{0x5F81D0, 0x5F8260, 0x401B20, 0x9F17E0}` — สองช่องท้ายเป็นของฐานที่ใช้ร่วมกันทั้งตระกูล
- 🔴 **ไม่มี RTTI และไม่มี runtime name literal ผูกกับ vtable นี้** — สตริงที่อยู่ติดกันในอิมเมจคือ `"Scene"` (`0xF313BC`) แต่ **นั่นเป็นเพียงความบังเอิญของ layout ไม่ใช่หลักฐาน**: ตรวจกับ `0xF2FF14` แล้วพบว่าสิ่งที่อยู่ติดกันข้างหน้าคือสตริง UTF-16 `"NetAttr uid=%d"` ซึ่งไม่ใช่ชื่อคลาสแน่นอน ⇒ **heuristic "ชื่ออยู่ก่อน vtable" ใช้ไม่ได้ในอิมเมจนี้ ห้ามใครเอาไปอ้าง**

# 3) คำตอบของคำถามเดียวประจำท่อน A

> "สอง sub-object นี้ พา *อ็อบเจกต์ที่ไม่ใช่ actor* มาด้วยไหม"

## bit `0x04` / `+0x24` -> **ไม่**
สมาชิกเป็นเรคอร์ด `0x18` ไบต์ที่มีแค่ `{byte, float}` **ไม่มีตำแหน่งในโลก ไม่มี vtable ของ actor ไม่แตะ terrain/ground container**

## bit `0x08` / `+0x20` -> **ใช่ และนี่คือผลใหญ่ของท่อนนี้**

**โปรโตคอลตัวนี้ขนลิสต์ของเรคอร์ดที่ "มีพิกัดในโลกเป็นของตัวเอง" (สามฟลोट x/y/z ที่ `+0x1C`) โดยที่เรคอร์ดนั้นไม่ใช่ actor entry**

หลักฐานสามชั้นที่ทำให้พูดแบบนี้ได้:
1. คลาสของสมาชิกคือคลาสส่วนตัวที่สืบจาก `PcRefObject` **ไม่ใช่หนึ่งใน actor type 2..6** ที่ jump table `0x4469BD` ยอมรับ (ข้อเท็จจริง NEGATIVE ที่ใบนี้ประกาศว่าปิดแล้ว)
2. เส้นทางนี้ **ไม่ผ่าน** ท่อ actor-entry เลย — มันเป็น derived bit คนละบิต (`0x08` เทียบกับ `0x02`) และมี pool/allocator/คลาสของตัวเอง
3. มันมีสนามพิกัดจริงที่ถูก serialize ด้วย tag float สามตัวติดกัน ผ่านฟังก์ชัน `0x5F3490` ที่ทำงานอย่างเดียวคือ เขียน/อ่าน 3 float

## 🔴 สิ่งที่ยัง **ไม่** ได้พิสูจน์ (อ่านให้ครบก่อนเอาไปใช้)

- **ไม่ได้พิสูจน์ว่านี่คือท่อของ "ของลูทบนพื้น"** — พิสูจน์แค่ว่า *มีท่อสำหรับวัตถุมีพิกัดที่ไม่ใช่ actor อยู่จริงในอิมเมจ* · มันอาจเป็น placement marker, waypoint, จุดวาร์ป, เอฟเฟกต์ หรืออย่างอื่น
- **ไม่มีชื่อคลาสให้อ้าง** — ทั้งสอง vtable ไม่มี RTTI และไม่มี name literal · ใครเขียนโมดูลโดยตั้งชื่อเดาเอาเอง = ประดิษฐ์ wire format ซึ่งบ้านนี้ห้าม
- **ไม่ได้ตรวจฝั่ง inbound** ว่าลิสต์นี้ไปลงที่ไหน (นั่นคือท่อน B)
- ความหมายของ tag `0x05` / `0x08` / `0x0F` / `0x14` **ไม่ได้ re-derive ในใบนี้** — ยืนยันเองแค่ `0x2A = float32` (จาก `movss` ในคอนสตรัคเตอร์) และ `0x12 = uint16` (จากการตัด `movzx eax,dx`)
- **ไม่มีลูกมือมาเดินซ้ำผลนี้** — เซสชันผู้ช่วยไม่มี subagent ที่เห็นอิมเมจ ⇒ ทุกข้ออ้างข้างบนแนบ span + sha256 ไว้ให้ re-derive เอง **ถือเป็นผลที่ยังไม่ผ่านการตรวจแบบปฏิปักษ์**
