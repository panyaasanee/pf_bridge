# 🆕 ร่าง GT-045 — GROUNDDROP-RENDER-001 [attended, in-game]

## ชื่อเต็ม
บิต `0x08` ของ `0x5F85B0` คือ "วัตถุลูทบนพื้น" หรือเปล่า — ยิงเรคคอร์ดที่มีตำแหน่งโลกเข้าไปแล้วดูว่าไคลเอนต์วาดอะไรออกมา

## สมมติฐาน (จาก GT-040 ท่อน A · ผ่าน re-derive ปฏิปักษ์แล้วใน GT-042)
`0x5F85B0` (บิต `0x08` / `+0x20`) = list แบบ dirty-mask · element ยาว `0x2C` ไบต์ · vtable `0xF313C4`
มี float 3 ตัวที่ `+0x1C/+0x20/+0x24` = **ตำแหน่งในโลก** (เขียนผ่าน `0x5F3490` / อ่านผ่าน `0x5F34D0`)
mask: `0x02`→`+0x14` tag `0x14` · `0x04`→`+0x18` tag `0x0F` · `0x08`→`+0x1B` tag `0x05` · `0x10`→ตำแหน่ง · `0x20`→`+0x1A` tag `0x08`

**คำทำนายถ้าสมมติฐานถูก:** ส่ง element เดียว mask = `0x10 | 0x02` (ตำแหน่ง + dword id) ที่พิกัดใกล้ตัวผู้เล่น
⇒ จอต้องขึ้น **ป้ายชื่อสีขาวลอยเหนือพื้น และ/หรือ โมเดลชิ้นเล็กวางบนพื้น** ที่จุดนั้น

## เกณฑ์ผ่าน — สองชั้น แยกกันเด็ดขาด
* **ชั้น wire/DB:** capture มีเฟรมที่เซิร์ฟเวอร์เขียนออกไปจริง + ไบต์ตรงกับที่ตั้งใจส่ง (id, mask, float 3 ตัว)
* **ชั้น client-observable:** ภาพหน้าจอ (ก่อน/หลัง) แสดงป้ายชื่อหรือโมเดลที่พิกัดนั้น
* **ห้ามเอาชั้นหนึ่งไปพิสูจน์อีกชั้น** — ถ้า wire ผ่านแต่จอไม่ขึ้นอะไร นั่นคือ **ผลลบที่สมบูรณ์ ไม่ใช่ FAIL ของใบ**

## ผลลบมีค่าเท่าผลบวก
ถ้าบิต `0x08` ไม่วาดอะไรเลย ⇒ ตัดตัวต้องสงสัยตัวนี้ทิ้งได้ถาวร และดันไปหาช่องทางอื่น
(ใบนี้จะประกาศชัดว่า "บิต 0x08 ไม่ใช่ของบนพื้น" ซึ่งเป็นคำตอบที่ใช้ได้จริง)

## ตัวแปรที่ต้องคุมให้ครบ
1. ต้องเป็น **opt-in flag** เท่านั้น ห้าม default-on
2. ห้ามแตะ DB canonical (`state\pirateforce.sqlite3`) — ทดสอบบนสำเนา + เทียบ `CANON_SHA.txt`
3. บูตจาก commit ที่ resolve ด้วย**เครื่องมือ** ไม่ใช่ก๊อป SHA (ท่าเดียวกับ GT-041)
4. teardown ต่อใบ · ถือ `LOCK_GAME.txt` ตลอดรอบ
5. ยิงอย่างน้อย **สองพิกัด** (ใกล้ตัว / ห่างออกไป) เพื่อแยก "ไม่วาด" ออกจาก "วาดแต่อยู่นอกจอ"
6. บันทึกเวลาที่ยิง เพื่อดูว่า element อยู่ค้างหรือถูกลบเอง

## nonclaims ที่ต้องเขียนติดใบตั้งแต่แรก
* ไม่ claim ว่ารู้ว่าเซิร์ฟเวอร์เดิมใช้ช่องนี้ — ใบนี้ทดสอบแค่ว่า **ไคลเอนต์รับได้ไหม**
* ไม่ claim ว่าที่วาดออกมา = ไอเทมที่หยิบได้ · การวาดกับการหยิบเป็นคนละเรื่อง (ใบ GT-046)
* ไม่ claim ว่าหลักฐานคลิปวิดีโอเป็นหลักฐานของช่องทาง transport ใด ๆ — คลิปอยู่ชั้น client-observable ล้วน

# 🆕 ร่าง GT-046 — PICKUP-DIRECTION-001 [STATIC-ON-BRIDGE]

## ชื่อเต็ม
`PickupTerrainThing` เป็นข้อความที่ **ไคลเอนต์ส่งออก** หรือ **รับเข้าอย่างเดียว** — หาจุดสร้าง/จุดส่ง

## ทำไมข้อนี้สำคัญกว่าที่เห็น
ถ้าไคลเอนต์ **ส่ง** เอง ⇒ มีตัวจุดชนวนฝั่งไคลเอนต์ (auto-loot / เพ็ต / ระยะ) และเซิร์ฟเวอร์แค่ตอบ
ถ้าไคลเอนต์ **ไม่เคยส่ง** ⇒ การเก็บถูกตัดสินฝั่งเซิร์ฟเวอร์ทั้งหมด และไคลเอนต์แค่รับผลลัพธ์
**สองทางนี้ทำให้เราต้องเขียนเซิร์ฟเวอร์คนละแบบ** และตอนนี้เรายังไม่รู้ว่าทางไหน

## ของที่มีอยู่แล้ว (ผ่าน re-derive ปฏิปักษ์ใน GT-042 แล้ว — ใช้ต่อได้เลย)
```

serializer  slot +0x18  [0x005E5E30,0x005E5E83)  len 83
                        sha 8e439d4f3ff1479e723b220d8dd78a262b41df3b74839da9d4cb728f69773066
                        2 ฟิลด์: tag 0x14 @ +0x14 len 4  ·  tag 0x08 @ +0x18 len 1
handler (แก้ขอบเขตแล้ว) [0x005EF640,0x005EF66F)  len 47

                        อ่าน +0x18 แยก FC/FD/FE -> message id 1F/03/22 แล้วคืน true
```

🔴 **erratum ที่ต้องพกไปด้วย:** span เก่า `[0x005EF640,0x005EF908)` len 712 **hash ตรงแต่ป้ายผิด** — ไม่ใช่ handler ฟังก์ชันเดียว

## จ็อบ
1. ไล่ทั้ง 3 จุดที่อ้าง vtable literal `0x00F3005C` (constructor) → ใครเรียก constructor พวกนั้น
2. ตามสายขึ้นไปจนถึงจุดที่ object ถูกป้อนเข้าสตรีม แล้วดูว่าใช้ **`0x0089A600` (WRITE)** หรือ **`0x0089A640` (READ)**
   — นี่คือตัวตัดสินทิศทาง เพราะสองตัวนี้พิสูจน์แล้วตั้งแต่ GT-040
3. ถ้าเจอฝั่ง WRITE: อะไรเป็นตัวเรียก (input handler / timer / entity update)? ค่าที่ใส่ `+0x14` มาจากไหน
4. ค่า `FC/FD/FE` ที่ `+0x18` — หาว่าฝั่งไหนเป็นคนเซ็ต และ message id `0x1F/0x03/0x22` แปลเป็นข้อความอะไร
   (**เชื่อมกับคลิปได้ตรงนี้:** คลิปเห็นบรรทัด `ได้รับ [<ชื่อ>] * <จำนวน>` **สีเขียว** แยกจาก EXP/ค่าฝีมือที่เป็น**สีขาว**
   ⇒ ถ้า message id ตัวใดตัวหนึ่งใน 1F/03/22 ตรงกับ template ที่มี `* <จำนวน>` นั่นคือจุดเชื่อมสองชั้นแรกของเรื่องนี้)

## ต้องตอบเป็นประโยคเดียวได้
> `PickupTerrainThing` ถูกสร้างและเขียนลงสตรีมที่ `<VA>` ผ่าน `0x0089A600` / หรือไม่พบจุด WRITE เลยในอิมเมจ

## เอกสารประกอบที่บังคับ
span `[start,end)` + file offset + len + sha256 ของ**ทุก**ฟังก์ชันที่อ้าง — รูปแบบเดียวกับ GT-040/GT-042

## nonclaims
* static ไม่พิสูจน์ว่ารันไทม์ส่งจริง — พิสูจน์ได้แค่ว่า**มี/ไม่มีเส้นทางในอิมเมจ**
* "ไม่พบจุด WRITE" ≠ "ไคลเอนต์ไม่ส่ง" ถ้าเป็นการเรียกผ่าน table/indirect — ต้องเขียนกำกับว่าไล่ indirect ครบหรือยัง
* ห้ามอ้างว่าคลิปวิดีโอยืนยันทิศทางของข้อความ — คนละชั้นหลักฐาน
