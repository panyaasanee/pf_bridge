# LANE-Q-REPORT — `pf-adversary` เจาะ sandbox ของ Lua host ได้จริง (RCE `uid=0`) · แก้แล้วในรอบเดียวกัน · เสนอเป็นกฎบ้านหนึ่งบรรทัด

## เกิดอะไรขึ้น (วัดแล้ว ไม่ใช่ทฤษฎี)
รอบ `s2fxf6` สร้าง Lua host ให้สคริปต์ต้นฉบับของเกม 616 ไฟล์รันบนเซิร์ฟเวอร์ · sandbox ปิด `io`/`os`/`require`/`load` ตาม charter · ระหว่างรอบผมเจอเองว่า `lupa` ยัดตาราง `python` (มี `eval`/`builtins`) เข้าทุก Lua state จึงปิดเพิ่ม แล้ว **เขียนลงไฟล์รอบว่า "แก้แล้ว"**

`pf-adversary` เจาะบนคอมมิตนั้น — คอมมิตที่ตั้งใจปิดรูโดยเฉพาะ — **แล้วทะลุ**:
```lua
Quest.GetQuestFlag.__globals__["__builtins__"]["__import__"]("os")
```
ได้ `__import__` จริง `os.system` รันในสิทธิ์โปรเซสเซิร์ฟเวอร์ วัดได้ `uid=0(root)` · ทางนี้ **ไม่แตะตาราง `python` และไม่แตะ global ที่บล็อกไว้เลยสักตัว**

ต้นเหตุ: เรายื่น **อ็อบเจกต์ Python ที่มีชีวิต** (namespace `Quest`/`Player`/…) เข้าไปใน Lua state และ `lupa` ปล่อยให้ Lua `getattr` อ็อบเจกต์ Python ตัวไหนก็ได้ที่มองเห็น · เมธอดที่ namespace คืนกลับมาคือ closure ของ Python ธรรมดา ⇒ `__globals__` เปิดโล่ง
แก้แล้ว (คอมมิต `d97bb06`): `attribute_filter` แบบปฏิเสธทุกอย่าง (ทั้งอ่านและเขียน) — ดีไซน์นี้ไม่ต้องใช้ attribute access จาก Lua เลย

## สิ่งที่ผมอยากให้ COO เห็นมากกว่าตัวบั๊ก
**เทสสามใบที่ผมเขียนพร้อมกับการแก้ครั้งแรก เขียวหมด ในขณะที่ root shell เปิดอยู่** — เพราะมันปักที่ attribute ของ **ตัว namespace** (ซึ่ง `__getitem__` ดักไว้และตอบ `0`) ไม่ใช่ที่ attribute ของ **ค่าที่ namespace คืนกลับมา** · นี่คือรูปเดียวกับที่กฎ WIRED v2 (`0947`) พูดถึง: การ์ดที่ปักผิดชั้นให้ความมั่นใจผิด ๆ ที่แพงกว่าไม่มีการ์ด
ถ้ารอบนี้ไม่ได้สั่ง adversary สิ่งที่ขึ้น PR คือ **sandbox ที่เปิดอยู่ พร้อมเอกสารและเทสที่ยืนยันว่าปิดแล้ว**

## เสนอเป็นกฎบ้าน (COO เคาะ — ผมไม่เขียน `AGENTS.md` เอง)
> **ยื่นอ็อบเจกต์ Python เข้าไปในตัวแปลภาษา/สคริปต์เอนจินอื่นเมื่อไหร่ ต้องปิด attribute access ที่ระดับ runtime (ไม่ใช่ blocklist ชื่อ) และเทสต้องปักที่ *ค่าที่ถูกคืนกลับมา* ไม่ใช่แค่ที่ตัวอ็อบเจกต์ที่ยื่นเข้าไป**
