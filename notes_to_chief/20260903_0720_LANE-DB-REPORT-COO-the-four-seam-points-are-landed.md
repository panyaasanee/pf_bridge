## 2. ข้อที่ผมตัดสินเองในรอบนี้ ให้ท่านค้านได้

**การเทียบว่า apply ลงหรือไม่ ใช้ `is` ไม่ใช่ `==`** — `Character` เป็น frozen dataclass ที่เทียบตามฟิลด์
⇒ `==` จะอ่าน "apply สำเร็จบนตัวละครที่ถือเลขนั้นอยู่แล้ว" เป็น "ถูกปฏิเสธ" แล้วพิมพ์ `REFUSED`
ทับล็อกอินที่ถูกต้อง และนั่นคือ **ตัวละครเกิดใหม่ทุกตัวบนดาต้าเบสสด รวมของเจ้าของ**
(กับดัก `COO 0054` ในรูปกลับด้าน) ปักด้วยมิวแทนต์ M9

## 3. สิ่งที่วัดได้แล้วและอยากให้ท่านรู้ ก่อนใครถามว่า "แถวเสียทำอะไรกับล็อกอิน"

`level` แพ็ก `<H` และ HP แพ็ก `<I` **โดยไม่มียามที่ตัวประกอบ** — แต่แถวที่ทำให้ `struct.error`
หลุดเข้าเธรดผู้ฟัง **มีไม่ได้**: `migrations/006` ใส่ทั้งช่วงและชนิดไว้ใน **schema**
(`CHECK(... typeof(level)='integer' AND level BETWEEN 0 AND 65535)`) ⇒ SQLite เองปฏิเสธ
ไม่ใช่ validator ของ store ที่ raw SQL ของสายอื่นเดินอ้อมได้ · ปักไว้ใน
`test_no_row_this_login_can_read_is_unencodable` ซึ่งจะ **แดง** ถ้าวันหนึ่ง migration ไหน
rebuild `characters` แล้วทำ CHECK ตกหาย — วันนั้นตัวประกอบต้องมียามของตัวเองก่อน migration นั้นลง

🔴 **และข้อที่ผมเดาผิดแล้วเทสหักให้เอง**: ร่างแรกคาดว่า CHECK ปฏิเสธ **สตริง** — ไม่จริง
คอลัมน์มี INTEGER affinity ⇒ SQLite แปลง `"250"` เป็นจำนวนเต็ม **ก่อน** ประเมิน constraint
แถวจึงถือ 250 จริง (ผลถูก แต่คำยืนยันว่า "ปฏิเสธ" เป็นเท็จ) ⇒ แยกเป็นสองข้อ:
สตริงที่ไม่ใช่ตัวเลขถูกปฏิเสธ · `"250"` ถูกแปลง และปักด้วย `typeof`
