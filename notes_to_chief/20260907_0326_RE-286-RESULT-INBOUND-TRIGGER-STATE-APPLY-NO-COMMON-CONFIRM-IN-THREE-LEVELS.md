## ข้อ 1 — ทิศทางจริง: **inbound (server→client)**

หลักฐานสี่ชั้น อิสระต่อกัน:

**(ก) โครง vtable ของคลาส** `0x00F31738`: `+0x10` = id getter `0x006008C0` · `+0x18` = serializer `0x00600960` · **`+0x1C` = handler `0x006018A0`** — ทั้งสามที่อยู่นี้ถูกอ้างถึง **ที่เดียวในทั้งอิมเมจ** คือสล็อตของ vtable นี้เอง (ตรวจด้วย pointer-xref ทั้งไฟล์) ⇒ handler เป็นของคลาสนี้คลาสเดียวจริงตามที่ใบอ้าง

**(ข) handler อ่านค่าที่มาจากสาย แล้วเอาไปแก้สถานะเกม** — นี่คือพฤติกรรมของฝั่ง "รับ" เท่านั้น:
```
0x006018A0  mov eax,[0x1093198]        ; global game context
0x006018A9  mov ecx,[eax+0x2C0]        ; -> scene/trigger holder
0x006018AF  mov esi,[ecx+0x0C]
0x006018DF  push 0x00F0F5EC            ; "TriggerModule_C..."  <- ขอ module ตามชื่อ
0x006018EA  call 0x005F9B40            ; GetModule(name)
0x00601902  cmp word ptr [edi+0x3C],0  ; edi = อ็อบเจ็กต์ข้อความที่รับมา  <- ฟิลด์บนสาย
0x00601909  cmp byte ptr [edi+0x3F],0  ;                                  <- ฟิลด์บนสาย
0x0060190F  call 0x005FF030            ; ทั้งคู่ = 0
0x0060191C  push edi / call 0x005FEE40 ; อย่างใดอย่างหนึ่ง != 0
```
ปลายทางจริงที่ `0x005FEE40` ใช้ค่าจากเฟรมเต็ม ๆ:

## ข้อ 2 — ไม่เชื่อมกับ `Common_Confirm` (ผลลบแบบมีขอบเขต 3 ชั้น)

- **ชั้น 1** — handler `0x006018A0` เอง: ไม่อ้าง `0x00F19F44` / `0x00F2BE9C` / `0x005AB5F0`
- **ชั้น 2** — สองสาขาปลายทาง `0x005FF030` (90 คำสั่ง) และ `0x005FEE40` (127 คำสั่ง): **ไม่มีทั้งสามอย่าง**
- **ชั้น 3** — ทุกฟังก์ชันที่สองตัวนั้นเรียก (`0x005FBED0`, `0x005FCBA0`, `0x005FDA60`, `0x005FE250`, `0x005FCD70` + ปลายทางย่อยอีก 10 ตัว): **ไม่มีทั้งสามอย่าง**

⇒ **`TriggerResult` ไม่ใช่ candidate ของกล่อง "รายงานกัปตัน"** · ขอบเขตของผลลบ = caller-graph 3 ชั้นจาก handler (ไม่ใช่ image-wide) และไม่ครอบคลุมเส้นทางที่ผ่าน function pointer/vtable ที่ resolve ไม่ได้แบบ static

🔴 **สิ่งที่ใบเดาไว้แล้วไม่ตรง:** `UNTAGGED_WSTRING16LE_LEN32LE` ที่ `+0x20` มีจริง แต่ **เส้นทางรับไม่แตะมันเลย** — ข้อความ UTF-16 นั้นไม่ได้ถูกเอาไปแสดงในเส้นทางที่ handler เดิน (อาจถูกใช้ในทิศส่ง หรือค้างเป็นฟิลด์ที่ไคลเอนต์บิลด์นี้ไม่ใช้)

## ข้อ 3 — `+0x18` คืออะไร

- ctor `0x00600830` ตั้ง `[esi+0x18]=0` และ `[esi+0x1C]=0` (`0x00600897`/`0x0060089A`) ⇒ ค่าเริ่มต้น qword = 0
- **เส้นทางรับไม่อ่าน `+0x18` เลย** (apply อ่านแค่ `+0x3C/+0x3E/+0x3F/+0x5C`)
- ทั้งโมดูลของคลาส (`0x00600830..0x00601930`) อ่าน `[esi+0x18]` **จุดเดียว** ที่ `0x0060185B` ในฟังก์ชันที่สร้างอ็อบเจ็กต์ 0x38 ไบต์ แล้วส่ง `([esi+0x18], (int16)[esi+0x14], 0,0,0)` เข้า `0x00452FF0` ก่อนผลักเข้าคิวของ global `0x01032EC4` — คู่ (dword, u16) แบบนี้เป็นรูป **record/queue entry** ไม่ใช่การใช้เชิงเกมเพลย์ที่ระบุชนิด identity ได้
- ⇒ **ตอบเชิงเปรียบเทียบตามที่ใบถาม:** ตัวที่ทำหน้าที่แบบ `AddSurveyData +0x12` (trigger/dock id) **คือ `+0x3C` ไม่ใช่ `+0x18`** · และ **ไม่พบฟิลด์ที่ทำหน้าที่แบบ `+0x14` (คีย์ `SAILING_RESULT`) ใน `TriggerResult` เลย** — ผลลบแบบมีขอบเขต (ขอบเขต = เส้นทาง apply + ทุกการอ้าง `+0x18` ในโมดูลของคลาส)
- ชนิดของ `+0x18` จึง **ยังไม่ถูกพิสูจน์** — ห้ามเขียนว่าเป็น entity id

## nonclaims

1. ไม่อ้างว่า `TriggerResult` เกี่ยวกับ "รายงานกัปตัน" — ผลรอบนี้ตัดมันออกจากรายชื่อ candidate (ภายในขอบเขต 3 ชั้น)
2. ไม่อ้างชนิดของ `+0x18` และไม่อ้างว่า wstring `+0x20` ไม่มีผู้ใช้เลยในอิมเมจ — อ้างแค่ว่า **เส้นทางรับไม่แตะ**
3. ไม่อ้างว่า "unique handler ⇒ inbound" เป็นกฎทั่วไป — `ForcePos` เป็นตัวอย่างค้าน รายงานไว้แล้ว
4. ไม่ได้ไล่ primitive `0x0089A6D0` (ฟิลด์ `+0x40`) ว่าเข้ารหัสอะไร — ไม่ได้ถาม และไม่กระทบคำตอบสามข้อ
5. ไม่ได้ยิงเฟรมทดลองใด ๆ · read-only ล้วน · ไม่ได้แตะ `GameClient/`, `external/`, `gamedata/`, `SERVER/` หรือไฟล์คิว
