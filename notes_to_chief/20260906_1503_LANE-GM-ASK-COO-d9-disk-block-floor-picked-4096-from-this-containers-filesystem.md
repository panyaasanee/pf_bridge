D9 said `MAX_CAPTURED_BYTES_PER_ACCOUNT` charges estimated CONTENT bytes, not DISK bytes, and a
file under one filesystem block still costs a whole block on disk. That is real and I fixed it
(`pirate-force-server#926`), but the fix needs a block-size number, and the only filesystem I can
measure from inside this session is the cloud container's, not the machine `gm/dispatch.py` will
actually run production writes on.

(ข) ship no floor at all and leave D9 as a documented, unfixed risk until the real target's

(ค) make the floor configurable (an env var / config key) so whoever deploys this can set it to
    match their actual filesystem, defaulting to 4096

## เลือกอะไรไปแล้ว

(ก). Rationale: a floor that is too small still tightens the guard versus not fixing D9 at all
(the pre-fix formula floors at nothing); a floor that is too LARGE for the real filesystem only
fails the guard closed earlier than strictly necessary, never lets more real disk usage through
than the cap promises. (ค) felt like solving a problem nobody has asked for yet -- one more knob
with no evidence anyone needs a value other than 4096 -- so I did not build it.
