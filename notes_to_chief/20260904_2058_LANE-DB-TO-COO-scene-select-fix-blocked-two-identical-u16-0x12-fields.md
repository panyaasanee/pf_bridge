`characters.actor_wire` **ไม่ใช่**บล็อบที่ประกอบผ่าน `player_wire.py` เลย (`legacy_bridge.py`,
`lifecycle.py:138` `build()`, `actor_wire.bind_actor_and_avatar_identity`) — มันคือ `CreateActorDataEx`
ที่ไคลเอนต์ส่งมาตอนสร้างตัวจริง ๆ ถูกแก้แค่ identity/selector เท่านั้น การอ้างอิงบรรทัด `223`/`306` ของ
`player_wire._make_actor_attr_with_name(_and_class)` ในใบ `1947` เป็นคนละโครงสร้าง คนละ serializer กับ
`actor_wire` นี้ (บทเรียนเดียวกับกับดัก tag `0x19` ที่ `persistence_class_id.py` เคยเจอมาแล้ว — tag ชนกัน
คนละฟิลด์คนละออฟเซ็ต)

เดินโครงสร้างจริงของ `actor_wire` preset ตัวเดียวกับที่เทสทั้งหมดในรีโปใช้ (`test01`):

```
identity(8B) selector(u8) name(wstr="test01")
  appearance/create(u8,u8=1,1)
  u32 tag 0x19 = 1   <- "class_id" ตามสมมติฐาน (COO-DECISION 20260903_1943: ห้ามใช้เป็นความจริง)
  u16 tag 0x12 = 1   <- ฟิลด์ A
  u16 tag 0x12 = 1   <- ฟิลด์ B
  astr(33B, hex-like GUID) wstr("test001")
  ... (เหลือ AvatarAttr ที่ embedded ต่อ)
```

**ปัญหา**: มี `u16 tag 0x12` สองตัวติดกัน ค่าเป็น `1` เท่ากันทั้งคู่ในตัวอย่างเดียวที่มี (สร้างตัวละครใหม่
เกิดที่ Port Royal เสมอ = scene_id คาดว่าเป็น 1 เสมอทุกการจับจริง ไม่มีทางแยกด้วยตัวอย่างเดียวว่าอันไหนคือ
scene_id กับอันไหนเป็นฟิลด์อื่นที่บังเอิญเป็น 1 เหมือนกัน — ไม่มี second sample ให้ไขว้)

## ทำไมไม่เดาแล้วส่ง
ใบ `1947` ข้อ 4 สั่งห้ามเดา offset ชัดเจน และประวัติของสายนี้เจอกับดักทำนองเดียวกันมาแล้วจริง (tag `0x19`
ชนกันคนละฟิลด์คนละ struct) เขียนทับผิดตัว = ส่งบิตขยะเข้าฟิลด์ที่ไม่รู้จักไปทุกเฟรมรายชื่อตัวละครของทุกคน
เงียบ ๆ (ค่าที่แก้ผิดจะยังอ่านเป็น 1 เหมือนเดิมในเทสเดียวที่มี ไม่มีทางจับได้จากเทสเลยถ้าเดาผิด) —ตรงเงื่อนไข
"ทางเลือกที่ไม่มีทางพิสูจน์ถูกด้วยหลักฐานที่มี ต้องเขียนใบถึง COO ก่อนตัดสินเอง"

## ขอตัดสินใจ
1. มี capture จริงที่ตัวละครไม่ได้อยู่ฉาก 1 ตอนสร้าง (ไม่น่ามี — สร้างที่ Port Royal เสมอ) หรือ capture คู่ที่
   ต่างกันแค่ฟิลด์เดียวไหม ถ้ามีให้ COO ชี้มา จะไขว้ให้ทันที
2. ถ้าไม่มี — ขออนุมัติเปิด RE ใบแคบ (ข้อยกเว้นจากข้อห้าม "ห้ามเปิด RE ก่อน" ในใบ `1947` เพราะเจอเงื่อนไข
   ที่ทำให้ GT ไม่ใช่ตัวตัดสินที่ปลอดภัยอีกต่อไป — เขียนผิดตัวจะไม่มีอะไรบอกว่าผิด) แคบสุด: จับสองเฟรม
   `CreateActorVital` จากตัวละครสองตัวที่ scene ตอนสร้างต่างกันไม่ได้ (เพราะสร้างที่ Port Royal เสมอ) →
   ทางเดียวที่ไขว้ได้คือจับเฟรมจากไคลเอนต์ที่แก้ appearance/relook เพื่อดูว่าฟิลด์ไหน "คงที่ข้ามการรีบิลด์
   แถวเดิม" กับฟิลด์ไหนเปลี่ยนตามการกระทำอื่น หรือ RE แบบ static หาว่า serializer `0x5DFF60` (ตัวเดียวกับ
   `SelectActorVital`/`CreateActorVital` ตามคอมเมนต์ `get_preset_actor_wire`) เขียนสอง field นี้จากตัวแปร
   ชื่ออะไรใน client image
3. ทางเลือกที่ไม่เสี่ยง (เสนอ ไม่ตัดสินเอง): เขียนทับ **ทั้งสองฟิลด์** เป็น `scene_id` เดียวกัน — ถ้าฟิลด์ที่
   ไม่ใช่ scene_id บังเอิญมีความหมายอื่นที่ผู้เล่นเห็นผลจริง (เช่นสีอวาตาร์/แฟล็ก) การเขียนทับสองอันจะพังฟิลด์
   นั้นแทน ไม่ปลอดภัยกว่าเดาตัวเดียวจริง ๆ **ไม่แนะนำ**
