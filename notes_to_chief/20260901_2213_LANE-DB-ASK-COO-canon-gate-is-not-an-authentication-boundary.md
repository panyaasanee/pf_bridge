# ASK-COO — `canon_gate` ลงแล้วตามที่สั่ง · แต่มันกันคนตั้งใจโกงไม่ได้ และผมไม่ปิดข้อนี้เอง

## ทำตามคำสั่งแล้ว (แผน ก)

ใบ `2149` สั่งว่า "รอบถัดไปหลัง GM-B merge ทำ `canon_gate` ห้ามเลื่อนเป็นรอบที่สาม" — รอบนี้ทำแล้ว
`src/pirateforce_foundation/persistence_canon_gate.py` สามผลตามที่อนุมัติเป๊ะ ไม่เปลี่ยนรูป
(`UNCHANGED` / `EXPLAINED_BY_MIGRATION` / `UNEXPLAINED`) เทส 149 ตัวเขียว (ไม่มี skip ใหม่) mutation 42 แบบถูกจับหมด
เรียก pf-adversary **สองรอบ** ก่อน commit ตามกฎ ได้ข้อบกพร่องรวม 24 ข้อ แก้ครบทุกข้อในรอบนี้

## เรื่องที่ต้องให้ COO ตัดสิน ไม่ใช่ผม

pf-adversary ตรวจก่อน commit แล้ว **ทำสำเร็จจริง** (ไม่ใช่ทักท้วง — เขารันแล้ววัดผล):
เอาฐานข้อมูลที่ถูกแก้ด้วยมือ (`INSERT` เพิ่มบัญชีเอง) + เขียนไฟล์ `MANIFEST.json` หกบรรทัดด้วยมือ
วางในโฟลเดอร์ `db_backups/` แล้ว **ด่านตอบ `EXPLAINED_BY_MIGRATION` พร้อมพิมพ์ค่า sha ใหม่ให้หมุน**

ผมปิดช่องนั้นไปสองชั้นในรอบนี้ (ทั้งสองชั้นวัดแล้วว่ากันของเดิมได้):
1. **`POSTSTATE.json`** — บันทึก sha ที่ migration *ผลิตออกมา* เขียนโดยบูตจริงหลัง migrate เสร็จ
   ⇒ ใครแตะฐานข้อมูลหลังจากนั้นแม้แถวเดียว ด่านกลับเป็น `UNEXPLAINED` ทันที
   (ก่อนมีชั้นนี้: migration ถูกต้องครั้งเดียว = เบิกทางให้ทุกสภาพของไฟล์ตลอดกาล ผู้ตรวจวัดถึงขั้น
   ลบบัญชีทิ้งทั้งตาราง แล้วด่านยังตอบ "explained, หมุนได้")
2. **อ่าน ledger ในตัวสำเนาเอง** — สำเนาที่อ้างว่าถ่ายก่อน migration N ต้อง *ไม่มี* N อยู่ข้างใน

🔴 **แต่ผมไม่กล้าบอกว่ามันปลอดภัยแล้ว และนี่คือทั้งเหตุผลของใบนี้:**
หลักฐานทุกชิ้นของด่านนี้เป็น **ไฟล์ในโฟลเดอร์ `db_backups/`** ใครเขียนโฟลเดอร์นั้นได้ ก็เขียนหลักฐาน
ได้ทุกชิ้น และ "เลขเดียวที่การปลอมต้องใช้" คือ canonical sha ซึ่ง **เผยแพร่อยู่ใน `CANON_SHA.txt`
ของรีโปที่ด่านนี้เฝ้าอยู่เอง** สองชั้นข้างบนแค่ทำให้ปลอมยากขึ้น (ต้องปลอม sha สามค่าให้ตรงกัน
และต้องผลิตฐานข้อมูลที่ไม่มี migration นั้นจริง ๆ) **ไม่ได้ทำให้ปลอมไม่ได้**
ไม่มีการจัดเรียงไฟล์แบบใดในโฟลเดอร์ที่ผู้โจมตีเขียนได้ ที่จะตอบคำถามนี้ได้เลย

⇒ ผมเขียนไว้ในหัวโมดูลตรง ๆ ว่า **ด่านนี้แยก "ไฟล์เปลี่ยนเพราะอะไรไม่รู้" ออกจาก "migration ที่มีบันทึก"
ไม่ใช่ด่านพิสูจน์ตัวตน** และห้ามใครอ้างมันเป็นอย่างหลัง

## เรื่องที่สอง (สำคัญกว่าที่ผมคิดตอนเริ่มเขียนใบนี้): ด่านเคยตอบผิด **ทั้งสองทาง**

pf-adversary ตรวจรอบที่สองหลังผมแก้ และเจอของที่ใหญ่กว่าเดิม — **ไม่ต้องเขียน `db_backups/` เลย**
ต้นเหตุคือประโยคเดียว: **SQLite เก็บธุรกรรมที่ commit แล้วไว้ใน `-wal` ได้ทั้งก้อน โดยไฟล์หลักไม่ขยับ**
⇒ "hash ของไฟล์" กับ "เนื้อของฐานข้อมูล" เป็นคนละเรื่องกันในจังหวะนั้น เขาวัดได้สองทาง:

1. **โลกถูกลบทิ้ง แต่ด่านบอกว่าเขียว** — `DELETE FROM accounts` แล้ว commit แล้วปิดโปรแกรมทิ้ง
   (โปรแกรมค้าง/ปิดหน้าต่าง) ไฟล์หลักยัง hash เท่าเดิมเป๊ะ ⇒ ด่านตอบ `EXPLAINED_BY_MIGRATION`
   **พร้อมสั่งให้หมุน `CANON_SHA.txt`** ทั้งที่ตารางบัญชีว่างเปล่า
   🔴 เงื่อนไขที่ต้องใช้ **น้อยกว่า** ข้อจำกัดที่ผมประกาศไว้ข้างบนมาก — แค่เขียนฐานข้อมูลได้
   ซึ่งทุกเส้นทางของเกมก็ทำได้อยู่แล้ว ไม่ต้องแตะโฟลเดอร์สำรองเลย
2. **migrate จริงแต่ด่านบอกว่า "ไม่มีอะไรเปลี่ยน"** — ถ้ามี connection อื่นเปิดค้างตอน migrate
   (เครื่องมือมอนิเตอร์ · เซิร์ฟเวอร์ค้าง · บูตสองตัวพร้อมกัน) migration ไม่ลงไฟล์หลัก
   ⇒ ด่านตอบ `UNCHANGED` **exit 0** ทั้งที่เพิ่ง migrate และพอมีอะไรมา checkpoint ทีหลัง
   ก็กลายเป็น `13` ค้างถาวร

**แก้แล้วรอบนี้**: ด่าน **ปฏิเสธที่จะตอบ** ถ้ามี `-wal` ไม่ว่างอยู่ข้างฐานข้อมูล (ตอบ `13`
พร้อมบอกให้หยุดตัวที่เขียนอยู่แล้วรันใหม่) และบูตจะ **ไม่เขียนบันทึก** ถ้า `-wal` ยังไม่ว่าง
มีเทสสำหรับทั้งสองทางแล้ว ทั้งคู่แดงจริงบนโค้ดเก่า
🔴 **ผลข้างเคียงที่ COO ควรรู้**: จุดใดที่รันด่านนี้ตอนเซิร์ฟเวอร์ยังขึ้นอยู่ จะได้ `13`
ซึ่งด่าน sha วันนี้ไม่แดง — แจ้ง chief แล้วในใบสเปก ให้เลือกจุดต่อสายที่เซิร์ฟเวอร์หยุดแล้ว

ผู้ตรวจรอบสองยังเจออีกสามข้อที่ทำให้ **บูตจริงของเจ้าของ** ได้ `13` แบบกู้ไม่ได้ (สำเนาที่ถูกใช้ซ้ำ ·
ฐานข้อมูลที่ ledger ยังไม่มีคอลัมน์ checksum ซึ่ง**คือรูปของ canonical ของเจ้าของพอดี** ·
สองบูตแข่งกันเขียนบันทึก) แก้ครบทั้งสามพร้อมเทสแล้วรอบนี้ รายละเอียดอยู่ในไฟล์รอบ

## เรื่องที่สาม: ผมเปลี่ยน exit code จาก 20 เป็น 75 — วัดแล้วว่า 20 ชนของเดิม

ใบ `1515` ผมเสนอ `20` ให้ chief ไว้ ผู้ตรวจจับได้ว่า **20 มีความหมายตรงข้ามอยู่แล้วในบริดจ์**
ผมวัดซ้ำเองแล้ว: `staged/TEMPLATE_teardown_generic.ps1:520-521` = `THIS ROUND IS DEGRADED,
NOT GREEN (exit 20)` และ `staged/072_gt001_boot.ps1:72` = `ABORT: no server PID`
⇒ ถ้าใครห่อ "20 = LANE-DB ผ่าน" ในอนาคต รอบ teardown ที่ล้มจะกลายเป็นเขียว
เปลี่ยนเป็น **75** (ไม่มี `exit 75` ในทุกสคริปต์ `staged/` วัดรอบนี้) · `13` คงเดิมโดยตั้งใจ
ยังไม่มีใครต่อสาย (grep = ศูนย์ผู้เรียก) การเปลี่ยนตอนนี้จึงไม่กระทบใคร แจ้ง chief ในใบแยกแล้ว
