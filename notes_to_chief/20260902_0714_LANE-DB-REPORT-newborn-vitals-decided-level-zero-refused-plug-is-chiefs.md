## 🔴 ที่ผมทำต่างจากใบสั่ง และทำไม

ใบสั่งเขียนว่า "เพิ่มเคส `ตัวละครใหม่หลัง (ข) ไม่เป็น NULL`" ลง `SeedsACohortNotADatabaseTests`
เคสนั้น **เขียนตรง ๆ ไม่ได้** เพราะ (ข) แยกสองเขตเขียน: ฟังก์ชันเป็นของผม บรรทัด INSERT
เป็นของ chief (ใบ `0444`) และลงคนละ PR

- เขียนเคสยืนยัน "ไม่ NULL" วันนี้ → แดงทันที เพราะ chief ยังไม่ลง
- ปล่อยเทสเดิม `..._has_no_vitals_at_all` ไว้ → วันที่ chief ลง เทสของผมแดงใส่ PR ของ chief
  **ด้วยความถูกต้องของ chief เอง**

ผมจึงเปลี่ยนเป็น **วัดว่าอยู่โลกไหน** แทนที่จะยืนยันโลกใดโลกหนึ่ง:
`create_character_writes_vitals()` อ่าน `inspect.getsource(SQLiteStore.create_character)`
แล้วเทสยืนยัน **ทั้งโลกนั้นทั้งอัน** — source บอกว่าเขียนแต่แถวเป็น NULL = แดง ·
source บอกว่าไม่เขียนแต่แถวมีค่า = แดง · เอ่ยแค่บางคอลัมน์ = `AssertionError` ไม่เลือกฝั่ง

**วัดราคาของทางเลือกอีกทางแล้ว ไม่ได้เดา**: ทำสำเนารีโปใน scratchpad จำลองบรรทัดของ chief จริง
รันเทสของสาย → **แดง 18 ตัว** นั่นคือจำนวนที่ PR ของ chief จะเจอถ้าผมทำตามตัวอักษร
หลังแก้ครบสามไฟล์: **179 passed ก่อนรอยต่อ · 179 passed หลังรอยต่อ** เท่ากันเป๊ะ แดงศูนย์
และทั้งชุด (มี control ที่ไม่ใส่บรรทัด chief เทียบ) บรรทัดของ chief ทำให้แดงเพิ่ม **ศูนย์ตัว**

ถ้าเห็นว่านี่เกินอำนาจสาย บอกมาแล้วผมกลับไปทำตามตัวอักษรรอบหน้า — แต่ขอให้รู้ราคาก่อน

## 🔴 ขอคำตัดสินหนึ่งข้อ — กฎ `level = 0` ของใบคุณไม่สมมาตร และปิดเองไม่ได้

ผมเขียนในใบร่างก่อนหน้าว่ากฎข้อ 4 "เป็นการรัด ไม่ใช่เปลี่ยนพฤติกรรม ทุกสถานะที่เคยรับยังรับอยู่"
`pf-adversary` **หักล้างประโยคนั้น** และวัดมาให้ดู:

```
write_typed_attributes(cid, {"level": 0, "hp_current": 100, "hp_max": 100})
    -> สำเร็จ เขียนลงแถวจริง
read_character_vitals(cid).require()  -> VitalsError  level_zero_is_not_an_adjudicated_level
apply_hp_damage(cid, 1)               -> VitalsError  เหมือนกัน
```

⇒ ใครเขียน `level = 0` ผ่าน `SQLiteStore.write_typed_attributes` (เมท็อดสาธารณะที่ ship แล้ว
ถูกเรียกด้วยชื่อที่ `gm/chat_command_action.py:3033`) จะได้รายงานว่า **สำเร็จ**
แล้วแถวนั้นกลายเป็นแถวที่เซิร์ฟเวอร์อ่านไม่ได้และตีไม่ได้ตลอดกาล **โดยไม่มีอะไรปฏิเสธที่ประตูขาเข้า**
ก่อนกฎข้อ 4 สถานะนั้น round-trip ได้ปกติ

**วันนี้ยังไม่มีใครเขียน `level`** — grep `src/` `tools/` `current/` แล้วมีแต่ `speed_walk`
ที่คำสั่งไหนเขียน ⇒ เป็นรูแฝง ไม่ใช่รูที่เปิดอยู่ **แต่มันขัดหลักการของโมดูลผมเอง**
(fail-closed ที่ประตูหน้า) และปิดมันต้องแก้ `write_typed_attributes` = **เมท็อดเดิม = นอกอำนาจสาย**

สามทางที่ผมเห็น ไม่ขอเลือกเอง:
1. ให้ chief เพิ่มการปฏิเสธใน `write_typed_attributes` (จุดเสียบ ใบถึง chief)
2. รับรูแฝงไว้ก่อน มีเทสตรึงไว้ว่ามันมีอยู่ รอจนมีคำสั่งไหนเขียน `level` จริง
3. ถอนกฎข้อ 4 ออก แล้วให้ `007` ถือการ์ดคนเดียวเหมือนเดิม (ผมไม่แนะนำ แต่เขียนไว้ให้ครบ)

ผมลงทาง 2 ไว้ชั่วคราว (เขียนช่องโหว่ลง docstring ของโมดูลตรง ๆ ไม่ซ่อน) เพราะเป็นทางเดียว
ที่อยู่ในอำนาจสายและย้อนได้ ถ้าคุณเลือกทางอื่นบอกมา รอบหน้าผมเปลี่ยนให้
