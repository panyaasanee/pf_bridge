## คำตอบ (ค): เสนอรูปประตู — ยังไม่สร้าง

รูปเดียวกับที่ท่านขอ (ตาราง + ฟังก์ชัน store + อ่านกลับหลังเขียน + บรรทัดคอนโซล) แต่มีสามคำถามที่ต้องให้
ท่านตัดสินก่อนผมจะเริ่มสร้างจริง:

1. **ใครเขียน**: ข้อมูลที่จะเขียนมาจาก `mob_loot.DropLedgerCell`/`GroundDrop` ของสาย B (ผมห้ามแตะ) เขต
   เขียนของผมคือตาราง+`store.py` method ใหม่เท่านั้น — เหมือนแบบที่มีอยู่แล้วสำหรับกระเป๋า
   (`mob_pickup_persist.pickup_and_persist` ของสาย B เรียก `store.commit_acquired_backpack_item` ของ
   ผม) เสนอให้ใช้แบบเดียวกัน: LANE-DB สร้างตาราง+method ใหม่ (`commit_ground_drop`/
   `list_ground_drops_for_scene` เป็นต้น) ส่วนจุดเรียก (เมื่อของตกจริง) เป็นของสาย B หรือจุดเสียบที่ chief
   สร้างให้ ตามชาร์เตอร์เดิม (`20260901_1100`)
2. **คีย์ชนกันข้ามเซสชัน**: `DROP_KEY_BASE`/`DROP_KEY_LIMIT` (`mob_loot.py:686-687`) เป็นค่าคงที่ระดับ
   โมดูล ทุกเซสชันเริ่มออกเลขจาก `DROP_KEY_BASE` เหมือนกันหมด (เพราะแต่ละเซสชันมี ledger แยกกันวันนี้
   จึงไม่ชนกัน) ถ้าย้ายไปตาราง (ที่ต้องมี PK เดียวรวมทุกเซสชัน) สองผู้เล่นฆ่ามอนพร้อมกันคนละเซสชันจะขอ
   `drop_key` เดียวกัน (`0x00100000`) ทันที ⇒ ต้องมีตัวออกเลขระดับเซิร์ฟเวอร์ตัวใหม่ ไม่ใช่แค่ย้ายตารางเฉย ๆ
   นี่เป็นคำถามออกแบบจริง ไม่ใช่แค่ backup — เสนอไว้ในจดหมาย ไม่ได้ตัดสินเอง
3. **ขอบเขตของประตูรอบแรก**: เสนอให้ทำแค่ "เขียนตอนตกของ + อ่านกลับ" ก่อน (แบบเดียวกับที่ `0951` วัดแค่
   เขียน-อ่านของกระเป๋า ไม่รวมวงจรทั้งหมด) ส่วนการลบแถวตอนถูกเก็บ/หมดอายุ (`DropLedgerCell` มี expiry
   ในหน่วยความจำอยู่แล้ว) เป็นคิวถัดไป **ห้ามลบแถวจนกว่าจะมีตัว publisher ลบจริง** (`0253`) ตรงกับที่
   `DropLedger` เองก็ยึดหลักเดียวกัน (ไม่ลบจนกว่าจะมี removal publisher — คอมเมนต์ `mob_loot.py:2244-2251`)

**backup**: การ์ดของท่าน (`20260901_1112` ข้อ 3) บังคับ backup อัตโนมัติเฉพาะ migration ที่แตะ**แถวเดิม**
(backfill/UPDATE/rebuild) — migration สร้างตารางใหม่เปล่า (CREATE TABLE เฉย ๆ ไม่แตะแถวเดิม) จึงไม่เข้า
เงื่อนไขนั้นโดยตรง แต่ถ้าท่านต้องการให้ทุก migration มี backup เสมอ กลไกมีพร้อมแล้ว
(`store.migrate_with_backup`, `store.py:327` — ของ LANE-DB เองจากรอบก่อน) แค่เปลี่ยน chief ให้เรียก
เมธอดนี้แทน `migrate()` เฉย ๆ ตอน boot

## pf-adversary — พบสามจุดจริง แก้ครบในคอมมิตเดียวกัน

1. เทสโครงสร้างของ constructor เดิมใช้ `co_varnames[:co_argcount]` ซึ่งมองไม่เห็น `**kwargs` — สาธิตจริง
   ในเวิร์กทรีแยก (แพตช์ให้แอบรับ `store=` ผ่าน `**kwargs` แล้วเทสเดิมยังเขียว) ⇒ แก้เป็น
   `inspect.signature` + เช็ค `VAR_POSITIONAL`/`VAR_KEYWORD` แยก
2. เทส grep ตาราง migration เดิมเช็คทีละบรรทัดด้วย `startswith` — สาธิตจริง: เขียน `CREATE TABLE` กับชื่อ
   ตารางคนละบรรทัด (SQL ใช้ได้จริง) หลบผ่านได้ ⇒ แก้เป็น regex ข้ามทั้งไฟล์
3. การสแกนด้วยชื่อ (ground/drop/loot) หลบได้เสมอด้วยชื่อไม่เกี่ยวข้อง (เช่น `floor_items`) — ไม่มีทางปิด
   ช่องนี้ได้สนิทด้วยการสแกนชื่ออย่างเดียว ไม่พบว่าถูกใช้จริงใน `migrations/*.sql` วันนี้ ⇒ เพิ่มหลักฐาน
   อิสระชั้นที่สอง (ข้อ 6 ข้างบน) แทนการสแกนซ้ำรูปแบบเดิม และเขียนไว้ตรง ๆ ในดอกสตริงว่าการสแกนชื่อพิสูจน์
   ได้แค่ "ไม่มีตารางภายใต้ชื่อแบบนี้" ไม่ใช่ "เป็นไปไม่ได้ภายใต้ชื่อใดก็ตาม"

ทั้งสามจุดแก้แล้ว ทวนมิวเทชันซ้ำเองหลังแก้ — จับได้ทั้งคู่ (สอง จุดแรก) ยืนยันด้วย `git status` ว่าไม่มีไฟล์
อื่นถูกแตะระหว่างทดลอง (migration ที่ผมแก้ทดสอบชั่วคราวคืนสภาพเดิมแล้วทุกครั้ง)
