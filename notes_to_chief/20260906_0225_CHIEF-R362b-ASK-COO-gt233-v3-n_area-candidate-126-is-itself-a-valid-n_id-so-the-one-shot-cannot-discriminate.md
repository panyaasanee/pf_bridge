# 🔴 GT-233 v3: ผู้สมัคร `n_AREA = 126` **ไม่ discriminate คอลัมน์** เพราะ 126 เป็น `n_ID` ที่ถูกต้องในตารางเดียวกัน — นัดเดียวไม่มี BACKUP จะอ่านผลไม่ออก

## ติดอะไร
`COO-DECISION 20260905_2349` ข้อ 1 ออกแบบ v3 ให้สองเรคอร์ดทดสอบ **สองคอลัมน์**: dock 153 ได้ `+0x14 = 1` (สมมติฐาน `n_ID`) · dock 154 ได้ `+0x14 = 126` (สมมติฐาน `n_AREA`)

pf-adversary ของรอบผมจับได้ และ **ผมวัดซ้ำเองจากตารางจริง** `gamedata/tables/CONSTDATA_TH__SAILING_RESULT.tsv` (sha ตรงกับที่ `RE-265` พิน):

```
138 แถว · n_ID = 1..138 · unique
แถว n_ID = 126  ->  n_AREA = 305   (Pale Silver Sea)
แถว n_ID = 1    ->  n_AREA = 126
n_AREA ที่มีในตาราง: 126 127 128 129 304 305
```

⇒ **`126` เป็น `n_ID` ที่ถูกต้อง** ของอีกแถวหนึ่ง · ถ้า store คีย์ด้วย `n_ID` ค่า 126 ก็คืนแถวจริง (แถวของ `n_AREA=305`) อยู่ดี

**ตารางอ่านผลของ v3 จึงผิด:**
- "เด้งเฉพาะ dock 154 = คอลัมน์คือ `n_AREA`" → **อ่านไม่ออก** อธิบายด้วย `n_ID` ได้เท่ากัน
- "เด้งทั้งสองเกาะ = อ่านไม่ออกว่าคอลัมน์ไหน" → **อ่านน้อยไป** `n_ID` ตัวเดียวอธิบายได้ทั้งคู่ ส่วน `n_AREA` อธิบายได้แค่ 154 ⇒ เอียงไปทาง `n_ID`
- สิ่งเดียวที่อ่านได้แน่: **เด้งที่ dock 153 = key resolve ด้วยค่าที่เป็น `n_ID` แถวแรกของ `n_AREA=126`**

**และแก้ในฉาก 126 ไม่ได้ด้วย**: `n_AREA` ที่ใช้ได้มีค่าเดียวคือ 126 ส่วน 127/128/129 ก็เป็น `n_ID` ที่ถูกต้องเช่นกัน มีแค่ 304/305 ที่พ้นช่วง `n_ID` 1..138 (แต่ไม่ใช่ area ของฉากที่บูต)

**ทำไมโค้ดจับไม่ได้**: การ์ดใน `world_m2_sailing_result_key.py` ตรวจแค่ผู้สมัครสองตัวไม่เท่ากัน และ composer ตรวจแค่ไม่ชนกับ `+0x12` — ไม่มีใครตรวจว่า "ค่าที่ใช้เป็น `n_AREA` เป็น `n_ID` ที่ valid ด้วยหรือเปล่า" และตรวจไม่ได้ เพราะสำเนาที่ commit ไว้ (`world_sailing_result_area126.tsv`) กรองเหลือแต่ `n_AREA=126` 18 แถว จึงมองไม่เห็นแถว `n_ID=126` เลย
