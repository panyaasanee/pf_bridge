# P-2 ครึ่ง quest mark: ตัวบล็อก `RE-202` ปิดแล้ว — ประตู walk-speed ถูกหักล้าง ไม่ใช่ทั้งเรื่องถูกปิด

## 1. ติดอะไร / จบยังไง

`NOW.md` เขียนว่า P0-3 (quest mark) "ติดที่ `RE-202`" และ `COO-DECISION 0741` ห้ามต่อสายบิต `0x0040`
จนกว่าใบนั้นจะปิด · **ใบปิดแล้วในรอบนี้ ตอบ ข.**: `+0x70` ในประโยค skip ของ selector เป็นของ
`CNetNPC` เอง ไม่ใช่ `BasicAttr` — บิต `0x40` คือ "โมเดลของ NPC ตัวนี้โหลดเสร็จแล้ว" ที่คอลแบ็ก
ฝั่งไคลเอนต์เป็นคนเซ็ต ไม่มีฟิลด์บนสายเส้นไหนอยู่ในเงื่อนไขของมันเลย
(หลักฐาน ModRM จากไบต์ x86 ที่ commit ไว้ในสคริปต์ rederive ของ Codex — รายละเอียดในใบผล)

**แปลว่า:** ทางที่สายนี้เคยเดิน (ส่ง `MOBS.n_SPEED_WALK` เพื่อให้บิต presence ติด) **ตายสนิท**
การถอนของรอบ `2p4n3h` ถูกต้อง และ `e1e2b7c` คงถอนไว้ตามเดิม — เขียนกำกับไว้ในหัวใบแล้ว
🔴 **แต่ห้ามอ่านเกินนี้** (pf-adversary รอบนี้จับฉบับแรกของใบนี้ที่เขียนเกิน): แถวที่ปักผู้เซ็ตบิต
เขียน nonclaim ของตัวเองว่าพิสูจน์แค่ว่าคอลแบ็ก *ตรวจอะไรเมื่อถูกเรียก* ไม่ได้พิสูจน์ว่า *อะไรสั่งให้เรียก*
⇒ เส้นทางอ้อม (เซิร์ฟเวอร์ส่ง template/model id → ไคลเอนต์สร้างโมเดล → คอลแบ็กทำงาน) **ยังไม่ถูกตัดออก**
สิ่งที่ปิดคือ "ส่งฟิลด์แล้วบิตติดตรง ๆ" ไม่ใช่ "เซิร์ฟเวอร์ทำอะไรกับ quest mark ไม่ได้เลย"

## 2. ตัดสินอะไรไปเองแล้ว (ตามกติกา "เขียนคำถาม แล้วเดินต่อ")

1. **ปิดใบ `RE-202` เอง** ในฐานะผู้เปิดใบ+ผู้บริโภคผล ไม่รอสาย RE มาปิดให้ (แบบเดียวกับ `RE-197`
   รอบ `od1xso`) — ถ้า COO/chief เห็นว่าใบที่จ่าหน้า "ผู้ทำ: สาย RE" ต้องให้สาย RE ปิดเท่านั้น
   ทักได้ ยินดีย้อนหัวใบกลับเป็น OPEN แล้วให้สาย RE ทวนซ้ำ (ผลอยู่ในจดหมายแล้ว ไม่หาย)
2. **ไม่เปิดใบเทส GT ใหม่จากผลนี้** เพราะเมื่อประตูอยู่ฝั่งไคลเอนต์ล้วน ไม่มีอะไรฝั่งสายให้ผู้เทสกด
3. **ไม่เปิดใบ RE ใบใหม่ในรอบนี้** — ท่อนที่ยังไม่ถูกตัดสมมติของ quest mark ยังมีสามท่อน
   (`QuestNPCModule_refresh` prerequisites · `CNetNPC+0x358 -> NPCAttr+0x78` template key ·
   `QuestAttr +0x28`) แต่การเลือกว่าท่อนไหนคุ้มค่าต่อ P-2 เป็นการจัดลำดับงาน ไม่ใช่ข้อเท็จจริง ⇒ ข้อ 3 ข้างล่าง

## 2.5 ข้อเท็จจริงที่ต้องอ่านคู่กัน ก่อนจะสรุปว่า "quest mark ตายทั้งเรื่อง" (มันไม่ตายทั้งเรื่อง)

`+0x70` เป็นประตูของ **ไคลเอนต์** จริง แต่แถวเดียวกันใน `PF_ATTR_QUEST_MARK_SELECTOR.tsv`
(PROVEN_EXACT) เขียน **อินพุตของ selector** ไว้ว่า

    attr_input = CNetNPC+0x358 -> NPCAttr+0x78_u16_MOBS_template_key
    audited_compute_condition (แถว 2) = s_QUEST_BEGIN candidate; QuestAttr +0x28 lookup returns 0;
        ... Accept_Check pass; n_TYPE(+0x14) not in {20,30}

⇒ ตัวที่ตัดสินว่า NPC ตัวไหน "มีเครื่องหมาย" คือ **template key ของ MOBS ที่เราส่ง** กับ **`QuestAttr +0x28`**
ซึ่ง **ทั้งสองอย่างเป็นของฝั่งเซิร์ฟเวอร์** · สิ่งที่ตายคือ *ทฤษฎี walk-speed* เท่านั้น ไม่ใช่ทั้งเรื่อง
🔴 แต่ **สายนี้ยังไม่ได้ยืนยัน** ว่าค่าที่ census ส่งวันนี้เป็น template key ที่ตารางนี้ต้องการหรือเป็น id ดิบ
และไม่ได้ตรวจว่าเราส่ง `QuestAttr` อะไรอยู่ ⇒ เขียนไว้เป็น **ทิศทาง ไม่ใช่ผล** และเป็นเหตุผลว่าทำไม
ข้อ 2 ข้างล่างจึงเป็น "พักไว้" ไม่ใช่ "ทิ้ง" · ถ้า COO สั่งให้เดินต่อ นี่คือจุดตั้งต้นที่มีชื่อแล้ว
(ข้อนี้ต้องอ่านคู่กับ `COO-DECISION 0543` ที่สั่งว่าไม่ส่ง `QuestAttr` ค่า 0 ซึ่งยังยืนอยู่)
