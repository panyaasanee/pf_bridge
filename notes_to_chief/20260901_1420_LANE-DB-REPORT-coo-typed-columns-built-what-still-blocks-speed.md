## ทำตามข้อ 1 ของใบ 1325 แล้ว วัดได้

`migrations/006_character_typed_attribute_columns.sql` เพิ่ม 21 คอลัมน์ที่ยังขาดลงตาราง
`characters` (level · hp/mp ปัจจุบันและสูงสุด · **speed_walk** · class · แต้ม · 5 สแตท ·
5 โบนัส · exp · เงิน) ⇒ ครบ 22 ฟิลด์ที่ใบ `1100`/`1325` ให้ DB ถือ

ตัวเลขเดียวกับที่ผมรายงานไปในใบ `1335` รันซ้ำหลังลง migration (`unlock_report()`):

```
ก่อนรอบนี้ (55 ฟิลด์ ประกอบไม่ได้ทั้งหมด)      หลังรอบนี้ (ยังประกอบไม่ได้ทั้ง 55 เหมือนเดิม)
 21 server_owned_column_not_built        ->    0   ปิดหมดแล้ว ทั้งชั้น
  1 server_owned_value_not_supplied      ->   22   คอลัมน์มีแล้ว แต่ยังไม่มีใครเขียนค่าลงไป
 25 client_default_not_adjudicated       ->   25   เท่าเดิม (ของ COO ตัดสิน ไม่ใช่ของผม)
  7 no_proven_source                     ->    7   เท่าเดิม
  1 refused_sensitive                    ->    1   เท่าเดิม (x=30 ปฏิเสธถาวร)
```

อ่านให้ตรง: **"มีคอลัมน์" ไม่เท่ากับ "มีค่า"** 006 เพิ่มคอลัมน์อย่างเดียว ไม่เขียนแถวใดเลย
ทุกคอลัมน์เป็น NULL บนตัวละครทุกตัว และ NULL ถูก **ตัดทิ้ง** จากสิ่งที่ `read_typed_attributes`
คืนมา ไม่ถูกแปลงเป็น 0 — นั่นคือกฎของเจ้าของ (ใบ `1059`) เขียนลงไปในสคีมา ไม่ใช่คำสัญญา
ถ้ารอบไหนเขียนค่าครบทั้ง 21 คอลัมน์ ช่องว่างจะเหลือ 34 (เทสยืนยันเลขนี้จริง) ไม่ใช่ 0

**ทำไมไม่ seed ให้เลย** สองเหตุผล ไม่ใช่หนึ่ง:

1. seed = เขียนทับแถวข้อมูลจริง = ต้องมี snapshot ก่อน apply ตามใบ `1112` ข้อ 3 และ
   `CORE-REQUEST-DB-001` (จุดเสียบ boot ให้เรียก `migrate_with_backup`) **ยังไม่มีคำตอบ
   ทวนไปครั้งที่ 2 รอบนี้** ⇒ 006 ถูกบังคับให้เป็น `ADD COLUMN` ล้วน ห้ามมี UPDATE แม้แต่บรรทัดเดียว
   (มีเทสพาร์ซไฟล์ .sql ทีละคำสั่งเพื่อพิสูจน์ข้อนี้ ไม่ใช่คำรับรอง)
2. 🔴 **ยังไม่ชัดว่าจะ seed ด้วยเลขไหน — และนี่คือของที่ผมเพิ่งจับได้รอบนี้ ต้องแก้คำที่ผมเคยเขียนเอง**
   pf-adversary ชี้ว่าผมอ้างอิงหลักฐานแค่ครึ่งเดียว ตรวจซ้ำเองแล้ว **ผู้ตรวจถูก**:
   - `docs/FUNCTIONAL_COVERAGE.json` ให้เกรด `npc_locomotion_presentation` = **`runtime_pass`**
     บน **บิตเดียวกัน** ("the decoded MOBS walk-speed value carried in BasicAttr bit **0x0040**")
   - `tests/test_npc_gait_wire.py:59` ปักหมุด **`PROVEN_WALK_SPEED = 150.0`** ที่บิต/ออฟเซ็ตนั้น
     พร้อมเทส `test_walk_speed_sets_exactly_bit_0x0040_in_the_basic_mask`
   ⇒ ออฟเซ็ตนี้ **ไม่ได้ไม่มีชื่อ** อย่างที่ผมเขียนไปในใบก่อน มันมีชื่อแล้ว **ในชั้น NPC/ภาพ** และ
   ยังไม่มีใครทดสอบกับ **ตัวผู้เล่น** (แถวเดียวกันนั้นเขียนเองว่า Foundation population path
   ไม่เคยขอค่าความเร็ว) · และสองชั้นถือ **เลขคนละตัว** สำหรับออฟเซ็ตเดียวกัน:
   **150.0** (พิสูจน์บนสาย สำหรับ NPC) กับ **400.0** (default ตอน client สร้างวัตถุของผู้เล่น)
   สายผมไม่มีอำนาจตัดสินว่าอันไหนใช้กับผู้เล่น — **ขอ COO สั่ง RE หนึ่งใบเพื่อปิดข้อนี้**
   ถ้า seed ผิดเลข ตัวละครทุกตัวจะได้ความเร็วผิดพร้อมกันโดยที่ไม่มีอะไรจับได้

## ข้อ 3 ของใบ 1325 (เทส omit-bit ด้วย speed) — ผมยังร่างใบขอ GT ไม่ได้อย่างซื่อสัตย์ และนี่คือเหตุผลที่นับได้

ใบ `1325` สั่งให้ผม "ร่างขอ GT entry ผ่าน chief รอบถัดไป" ผมตรวจแล้วว่าจะร่างเป็นใบที่ผู้เทส
**รันไม่ได้** เพราะวันนี้ยังไม่มีเส้นทางส่งเฟรม `UpdateAttrVital` ออกไปหาไคลเอนต์เลยแม้ทางเดียว
ขาดสามชิ้น ไม่มีชิ้นไหนอยู่ในเขตเขียนของสาย DB:

| # | สิ่งที่ขาด | หลักฐาน | ของใคร |
| --- | --- | --- | --- |
| 1 | ไม่มี call site ใดเรียก encoder เลย | `grep -rn "build_named_field_update" src/` เจอแต่ในไฟล์ของสาย GM กับเทส | chief (`runtime.py`) |
| 2 | ประตูส่งของสาย GM ยังปิด | `gm/attr_wire.py:UPDATE_ATTR_VITAL_VERSION_CONFIRMED = None` | LANE-GM |
| 3 | ไม่มีคำสั่ง `/speed` ในเกม | ไม่มี handler ที่ไหน | chief + LANE-GM |

ผมทำชิ้นที่ 4 (ที่เก็บค่า) เสร็จรอบนี้ และผมเขียนสามชิ้นบนไม่ได้ตามกติกาเขตเขียน
**ขอ COO ตัดสินทางเดียวในสองทางนี้** (ผมไม่ตัดสินเอง):

- **(ก)** COO สั่ง chief เปิดจุดเสียบ + สั่ง LANE-GM เรื่องประตูส่ง แล้วผมค่อยร่างใบขอ GT entry
  ในรอบที่ของทั้งสามชิ้นมีจริง — ใบขอ GT จะรันได้จริง
- **(ข)** ผมร่างใบขอ GT entry รอบหน้าเลยโดยเขียนเงื่อนไข "ใบนี้รันได้ต่อเมื่อสามชิ้นข้างบนลงครบ"
  ไว้บนหัวใบ — ได้ใบเร็วขึ้น แต่มันจะไปนอนในคิวจนกว่าสามชิ้นจะเสร็จอยู่ดี

ผมเสนอ **(ก)** เพราะใบที่รันไม่ได้ในคิวเทสคือของที่กินรอบ attended ของเจ้าของไปเปล่า ๆ ซึ่งเป็น
สิ่งที่ `NOW.md` เตือนไว้เองในข้อ UI-A
