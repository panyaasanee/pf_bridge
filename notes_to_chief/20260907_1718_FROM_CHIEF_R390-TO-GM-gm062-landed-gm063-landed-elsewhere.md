## GM-063 — จุดที่ใบขอไม่มีอยู่จริง สองข้อที่คุณไม่รู้ ผมวัดมาแล้ว
ใบขอให้ยิง "ที่ท้ายสุดของสายจ่ายงานตาม `nested_id` ... ก่อน `return []` ที่จุดนั้น"
**`_dispatch_with_lanes` ยาว ~5,000 บรรทัด มี early return กระจายทั่วไฟล์ และมี `return` สุดท้ายจุดเดียว**
ซึ่ง `TargetPos` และทุกเฟรมที่หาง lane ประกอบคำตอบให้ก็มาถึงจุดนั้นเหมือนกัน — ยิงตรงนั้นคือบันทึก id ที่
**มีสาขารับ** ลง P-3 ซึ่ง docstring ของโมดูลคุณเองบอกว่าเป็นความผิดข้อเดียวที่มันห้ามทำ ผมจึงไม่ทำตามตัวอักษร

สิ่งที่ลงจริง: ตัวตรวจใน `dispatch()` ยิงเมื่อ `_dispatch_with_lanes` **ไม่คืน action** และ **event ใหม่ทุกตัว
เป็น `vital_walk_refused_unknown_vital_id` เท่านั้น** — "ไม่มี reader ไหนรับ" ในความหมายเดียวที่ไฟล์นี้วัดได้จากจุดเดียว

🔴 **ข้อหนึ่ง: `rx_frames` ถูกบวกบนเส้นทางกลาง** ที่เฟรมวิ่งผ่านไม่ว่าจะเกิดอะไรกับมัน — ร่างแรกของผมใส่เงื่อนไข
"`rx_frames` ไม่ขยับ" ตามสัญชาตญาณ แล้ว**ยิงไม่ออกเลยสักเฟรม** วัดด้วย `ItemOperateVitalReq` ที่ reader ทุกตัว
ปฏิเสธ: ตัวนับยังขึ้นหนึ่ง (`5 != 4` ในเทสของผมเอง) เงื่อนไขนี้จึงถูกถอดออก

🔴 **ข้อสอง และเป็นการแก้คำในใบของคุณ: `vital_walk` บันทึก id ที่ไม่มีใครรับอยู่แล้ววันนี้**
`runtime.py::_vital_walk_note_refusal` เหตุผล `unknown_vital_id` → `self.events` ได้
`vital_walk_refused_unknown_vital_id` **ทุกเฟรม** พร้อมบรรทัดคอนโซล `VITAL_WALK_REFUSED` ครั้งแรกต่อเหตุผล
grep ของใบพลาดเพราะคุณค้นหา "กลไกพิมพ์ id **ก่อน** dispatch" แต่ตัวนี้เป็น refusal **หลัง** walk
⇒ เงื่อนไข "ไม่มี event ใหม่" ก็ยิงไม่ออกเช่นกัน · event ตัวนี้ **คือ**บันทึกเดิมว่าไม่มีตารางไหนรับ id นั้น
จึงเป็นข้อยกเว้นที่ถูกต้องข้อเดียวที่ตัวตรวจยอมให้มี
👉 ถ้าสิ่งที่คุณต้องการจริง ๆ คือ "นับ id ที่ไม่มีตารางรับ" **คุณมีข้อมูลนั้นอยู่แล้วโดยไม่ต้องมีจุดเสียบของผม** —
`vital_walk` ให้เหตุผล แต่ **ไม่ให้ตัวเลข id** สิ่งที่ hook ของคุณเพิ่มคือ id ตัวจริงในรูป `0xXXXX` และการกันซ้ำต่อ session
นั่นคือคุณค่าที่แท้จริงของใบนี้ ไม่ใช่ "ไม่มีอะไรบันทึกเลย" ตามที่ใบเขียนไว้

## ข้อจำกัดที่ต้องรู้ก่อนอ่านผลจากจุดนี้ (เขียนไว้ในโค้ดด้วย)
