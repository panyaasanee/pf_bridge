# ข้อ 3 บรรทัดสุดท้าย "write/flush ห้ามยกข้อยกเว้นไม่ว่ากรณีใด" — ผมตีความแคบไว้ก่อน ขอคำยืนยัน

## ผมทำอะไรไปแล้ว (ไม่ได้รอ)
จ่ายใบ `1441` ครบทั้งห้าข้อในคอมมิตเดียว และตีความบรรทัดนี้ว่า **ครอบคลุมเส้นทางหลังถอด (detached) เท่านั้น**
ติดป้าย `[สมมติของสาย LANE-E - รอ COO ยืนยัน]` ไว้ในไฟล์รอบแล้ว

## ทางเลือกที่มี
- (ก) **แคบ — ที่ผมเลือก**: หลังถอด `write`/`flush` ไม่ยกข้อยกเว้นเลย (forward + warn อยู่ใน try/except Exception ทั้งคู่)
  เส้นทางปกติ (ยังไม่ถอด) คงพฤติกรรมเดิม: sink พังแล้วข้อยกเว้นทะลุออกไปหาผู้เรียก
- (ข) **กว้าง**: `write`/`flush` กลืนทุกข้อยกเว้นตลอดอายุมิเรอร์ รวมเส้นทางปกติ

## ทำไมผมเลือก (ก)
1. เหตุผลที่ใบเขียนกำกับคือ "diagnostic ห้ามเปลี่ยน dispatch" — diagnostic ในใบนี้คือคำเตือนและ property
   `encoding`/`errors` ทั้งคู่อยู่หลังถอดหรืออยู่นอกเส้นทางเขียนจริง
2. (ข) ทำให้ไฟล์ retained ที่เขียนไม่ลง **เงียบสนิท** บนเส้นทางปกติ ซึ่งเป็นความเสียหายรูปเดียวกับ (ก) drop ที่ใบนี้เพิ่งปฏิเสธ
3. adversary รอบ `axmac6` ชี้ไว้แล้วว่ารากของ `qq0i9u`/D1 คือ **`write()` ไม่ atomic ข้ามสอง sink**
   (sink เดียว raise ทำให้สำเนาของอีก sink หายด้วย) — นั่นคือใบของตัวเอง ไม่ใช่ของใบนี้ และการกลืนเงียบทำให้มันแก้ยากขึ้น

## ถ้าผมผิดต้องย้อนอะไร
แก้สองเมธอดในไฟล์เดียว (`_Mirror.write` / `_Mirror.flush`) + เพิ่มเทสหนึ่งตัว — ย้อนได้ในรอบเดียว ไม่มีอะไรค้างบน main ที่ต้องรื้อ

## nonclaims
ไม่ได้อ้างว่าเส้นทางปกติของ `write()` atomic แล้ว (ไม่ atomic · ยังไม่แก้รอบนี้ · เป็นงานคนละใบ)
ไม่ได้วัดพฤติกรรมนี้บนเครื่องเจ้าของ วัดบนโคลนคลาวด์ (Linux) และซ้อมด้วย CPython 3.14 ผ่าน `uv`
