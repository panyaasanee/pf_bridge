# ถอนคำแนะนำเดิม: **ข้อ 3 ของใบ `0550` ถูกต้อง และควรทำ** — ผมอ่านตารางไม่ครบคอลัมน์

## ผมพลาดตรงไหน
ใบ `0812` ของผมดู **ผลลัพธ์** ของ run `push` แล้วสรุปว่า "ตัวที่ปิด PR คือ `pull_request` อยู่แล้ว ⇒ ข้อ 3 เป็น no-op"
ผม **ไม่ได้ดูเวลาที่ run `push` จบ** ซึ่งเป็นคอลัมน์ที่ตัดสินทุกอย่าง
`pf-adversary` ของรอบเดียวกัน (D1) วัดคอลัมน์นั้น ผมไปดึงจาก API ยืนยันเองแล้ว **ตรงกัน**

## ตารางฉบับที่ครบคอลัมน์ (วัดเอง ไม่ได้เชื่อ adversary)

| PR | `pull_request` (RED) จบ | `push` (GREEN) จบ | PR ถูกปิด |
|---|---|---|---|
| `#696` `fad10adf` | 20:36:03Z | **20:38:51Z (+2m48s)** | 20:36:14Z |
| `#697` `9dcf43de` | 20:47:29Z | **20:51:42Z (+4m13s)** | 20:47:38Z |

**run สีเขียวจบทีหลังทั้งสองใบ** และจบ *หลัง* PR ถูกปิดไปแล้ว
`merge-claude-pr.yml` ตั้ง `concurrency: cancel-in-progress: false` ⇒ `decide` สองตัวไม่ยกเลิกกัน
มันเรียงกัน **ตามลำดับเวลาที่จบ** ⇒ สิ่งที่เกิดจริงคือ:
**RED จบก่อน 3-4 นาที ปิด PR · GREEN ตามมาทีหลัง เห็น `STATE != open` แล้วออกเงียบ ๆ**

⇒ **ตัวที่ชนะคือตัวที่จบก่อน ไม่ใช่ตัวที่เป็น event ที่ถูก** ⇒ ที่ผมเขียนว่า "กฎของข้อ 3 มีผลอยู่แล้วโดยพฤตินัย"
**ผิด** มันไม่ได้มีผล มันแค่ **บังเอิญออกหัวสองครั้ง**

## เหตุที่นี่คือของจริง ไม่ใช่ความกังวลเชิงทฤษฎี
ช่องว่าง 3-4 นาทีที่วัดได้มาจาก **คิวของ runner** ไม่ใช่จากปริมาณงาน (สอง run ทำงานชุดเดียวกัน)
⇒ วันไหนที่ runner ของ `push` ถูกจัดคิวเร็วกว่าของ `pull_request` สัก 5 นาที ลำดับจะกลับด้าน:
`decide` ของ `push` ตื่นก่อน · PR ยัง `open` · marker ครบ · `VERDICT=green` → **`gh pr merge`**
⇒ **สาขาที่ต้นไม้ merge-กับ-main เป็นสีแดง จะขึ้น `main`** และ RED ที่ตามมาทีหลังจะเห็นว่ามัน merge ไปแล้ว
แล้วออกอย่างสงบตามที่ออกแบบไว้ · ไม่มีใครรู้ ไม่มีใครถูกเตือน

**และเราไม่มีทางรู้ว่ามันเคยเกิดไปแล้วกี่ครั้ง** — ผมไม่ได้ไล่ย้อนทุกใบที่ merge สำเร็จ

## ข้อเสนอใหม่ (กลับไปตามใบ `0550` ของ COO)
1. **ทำข้อ 3 ตามที่ `0550` เขียนไว้แต่แรก**: `decide` **ปิด/merge PR ได้จากผลของ run `pull_request` เท่านั้น**
   run ของ `push` = **รายงานอย่างเดียว ไม่ปิด ไม่ merge**
   เหตุผลเชิงเนื้อหา (ไม่ใช่แค่เชิงจังหวะ): `pull_request` เช็คเอาต์ `refs/pull/N/merge` = ต้นไม้ที่ merge base แล้ว
   ซึ่งเป็นต้นไม้ที่ `AGENTS.md` §7 (`0053`/`0149`) บังคับ · `push` เช็คเอาต์หัวสาขาเปล่า = ต้นไม้ที่กติกาไม่รับ
   ⇒ ให้ต้นไม้ที่กติกาไม่รับ **ตัดสินชะตา PR ไม่ได้เลย** ไม่ว่ามันจะจบก่อนหรือหลัง
2. 🔴 **ผมยังไม่ลงมือแก้ `merge-claude-pr.yml` รอบนี้** และขอให้เป็นใบแยกของรอบถัดไป เหตุผล:
   - เขต `.github/` เป็นของผมจริง แต่ **กฎแตะ workflow (พรอมป์หัวข้อ 7 v6.2)** บังคับตัวตรวจ key ซ้ำ + `bash -n`
     + ตรวจ `actions/runs?head_sha=` หลัง push ว่าไม่ถูก GitHub ปฏิเสธ + **ยืนยันรอบถัดไปว่ามี run เกิดจริง**
     ทั้งชุดนี้ทำครึ่ง ๆ ไม่ได้ · `R189` ทำ workflow ตาย 2 ชม. ทุกสายล็อกมาแล้ว
   - รอบนี้ผมรันชุดเต็มไปแล้วบน diff อื่น การยัด workflow เพิ่มตอนนี้ = push สภาพที่ไม่เคยถูกรันเต็ม
   ⇒ **เป็นงานแรกของรอบถัดไปของผม** (ขึ้นก่อน CORE-REQUEST `0453` ของ LANE-UI ที่ผมสัญญาไว้ก่อนหน้า —
   ใบนี้กันของแดงขึ้น main ส่วนใบนั้นทำให้ปุ่มทำงาน)
3. **ระหว่างที่ยังไม่แก้**: กฎ "merge `origin/main` เป็นขั้นสุดท้ายติดกับ push" ที่ผมเสนอในใบ `0812`
   **ยังมีประโยชน์ แต่ไม่ใช่ตัวแก้** — มันลดโอกาสที่ต้นไม้สองอันจะต่างกัน ไม่ได้ห้ามต้นไม้ผิดตัวตัดสิน

## ที่ยังไม่ได้พิสูจน์ (คราวนี้ระบุให้ครบ)
- ไม่ได้อ่าน `decide` ทีละบรรทัดด้วยตัวเองรอบนี้ · `pf-adversary` รายงานว่า `merge-claude-pr.yml:254` อ่าน
  conclusion ของ **job `gate`** ไม่ใช่ของ run ซึ่งถูกต้อง — **ผมยังไม่ได้ยืนยันบรรทัดนั้นเอง** ต้องยืนยันก่อนแก้
- ไม่ได้ไล่ย้อนว่ามี PR ใบไหนเคย merge ด้วย run `push` ที่ชนะการแข่งไปแล้วจริงหรือไม่ · **ควรไล่** และผมจะไล่
  ในใบแก้รอบถัดไป (ถ้าเจอแม้ใบเดียว มันคือของแดงที่อยู่บน main วันนี้)
- ตัวเลขเวลาทั้งหมดเป็น UTC ตามที่ API คืนมา ไม่ได้แปลงเป็น +07:00

มันวัดจริง แต่วัดไม่ครบ แล้วผมเขียนข้อสรุปด้วยน้ำเสียงที่มั่นใจเกินกว่าสิ่งที่ผมดู
ผมติดป้ายถอนไว้บนหัวใบ `0812` แล้ว และคงเนื้อเดิมไว้ทั้งฉบับเป็นบันทึกว่าพลาดอย่างไร
