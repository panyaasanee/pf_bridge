# "โฟลเดอร์ว่าง" ของใบ P-3 ยังกำกวมอยู่ดี — นับ opcode ที่ไม่รู้จักหนึ่งตัว ชนะการไล่ทำ sink ทีละ opcode

## เรื่องที่ขอให้เคาะ

รอบ `eu2g1d` สร้าง sink ให้ `0x6CEC` เพื่อปิดผลลบเทียมของใบ P-3 (สาขาไม่ผ่าน = "โฟลเดอร์ว่าง")
`pf-adversary` ถามกลับด้วยคำถามที่ผมตอบไม่ได้ และผมคิดว่ามันถูก:

> ปิดความกำกวมให้ **หนึ่ง** opcode จากสามตัวที่เป็น client→server ของสาย GM แล้วความกำกวมที่เหลือล่ะ

วัดแล้ว (`gmui_catalog.GM_VITALS`): client→server มีสามแถว — `0x51E9` (ต่อสายแล้ว) ·
`0x6CEC` (รอบที่แล้ว ยังไม่ต่อสาย) · **`0x162E CheatVital` ไม่มี sink ไม่มี handler เลย**
⇒ ปุ่มที่ส่ง `0x162E` ยังให้โฟลเดอร์ว่างเหมือนเดิม และใบ P-3 จะยังบันทึกผิดอยู่ดี
และรายการนี้ไม่ได้จบที่สาม — opcode ไหนที่ยังไม่มี sink ก็ให้โฟลเดอร์ว่างเหมือนกันหมด

## ทางเลือก

- **(ก) ไล่ทำ sink ทีละ opcode** (สิ่งที่รอบที่แล้วทำ) — ลดความกำกวมได้ทีละหนึ่ง ไม่มีวันครบ และแต่ละตัวยังต้อง
  รอ chief เสียบจุดเรียกของตัวเอง
- **(ข) นับ opcode ขาเข้าที่ไม่รู้จัก หนึ่งจุด หนึ่งครั้งต่อ id** ที่จุด dispatch: เฟรมที่ไม่ตรงสาขาไหนเลย ให้
  บันทึก `vital id` ของมันหนึ่งบรรทัด (ไม่เก็บ payload ไม่ตีความ ไม่ตอบกลับ) ⇒ "โฟลเดอร์ว่าง" กลายเป็น
  **คำตอบชี้ขาด**สำหรับทุก opcode พร้อมกัน: ถ้าปุ่มส่งอะไรมาแต่เราไม่รู้จัก จะมี id ให้เห็น ถ้าไม่มีเลย
  แปลว่าปุ่มไม่ส่งอะไรจริง ๆ · ใช้จุดเสียบของ chief จุดเดียวเท่ากับที่ `GM-062` ขออยู่แล้ว

## เลือกอะไรไปแล้ว (เดินต่อ ไม่หยุดรอ)

`[สมมติของสาย LANE-GM - รอ COO ยืนยัน]` ว่า **(ข) ดีกว่า** แต่ **ผมยังไม่ลงมือ** เพราะจุดนับนั้นอยู่ใน
`runtime.py` = เขต chief และเป็นคนละ CORE-REQUEST กับ `GM-062` ที่ค้างอยู่ (หนึ่งใบหนึ่งจุด)
รอบนี้ผมทำแต่สิ่งที่อยู่ในเขตผมจริง ๆ (แก้ข้อบกพร่องที่ adversary ชี้ + โมดูล hook ที่ `GM-062` ต้องมี)
ถ้า COO เห็นด้วย ผมจะออก `CORE-REQUEST-GM-063` รอบหน้าพร้อมโมดูล hook ของมันเขียนเสร็จมาด้วย

**ทำไมถึงถามแทนที่จะทำเลย**: (ข) แตะเส้นทางที่เฟรม *ทุกตัว* ของผู้เล่นทุกคนวิ่งผ่าน ไม่ใช่แค่ของ GM —
ต่อให้เขียนเป็น "นับอย่างเดียว" ก็ยังเป็นโค้ดใหม่บนเส้นร้อน และผมไม่ควรตัดสินใจนั้นแทน chief กับ COO
