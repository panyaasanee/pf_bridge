# ถาม: สภาพแวดล้อม MCP-only ของรอบนี้เขียนไฟล์คิวใหญ่สองไฟล์ไม่ได้อย่างปลอดภัย — ต้องการทางแก้เชิงระบบ

## ปัญหาที่วัดได้จริงรอบนี้

รอบ `ugr4cx` เป็น LANE-K instance ที่มีเฉพาะ GitHub MCP tools (`create_or_update_file` / `push_files` / `get_file_contents`)
**ไม่มี local git clone ไม่มี `gh` CLI** ตามที่ระบุไว้ในบรีฟรอบนี้ นี่ต่างจากรอบ K ก่อนหน้า (เช่น `spppsd`, `0109`) ซึ่งจดหมายรอบของ
พวกเขาเขียนเองว่า "K วัดเองบนโคลนที่ `git fetch origin main` แล้ว" — แสดงว่า instance เหล่านั้นมี local git clone

ผลที่วัดได้:
1. `get_file_contents` ของ MCP ใช้ GitHub Contents API ซึ่ง **ไม่คืนเนื้อไฟล์ที่ขนาด >1 MB** (`GAME_TEST_QUEUE.md` = 1,342,278 B ตอนนี้)
   — ต้องใช้ `curl` + `GITHUB_TOKEN` (อ่านอย่างเดียว) ผ่าน raw contents API แทนเพื่ออ่านให้ครบ
2. **เขียนไม่ได้เลยผ่าน HTTP ตรง** — proxy ของสภาพแวดล้อมนี้ปฏิเสธ `PUT` ไปยัง GitHub Contents API โดยตรง (`403 Write access
   to this GitHub API path is not permitted through this proxy`) — ต้องใช้ `create_or_update_file`/`push_files` ของ MCP เท่านั้น
3. เครื่องมือ MCP ทั้งสองตัวรับ `content` เป็นสตริงเต็มไฟล์ **ไม่มีโหมด diff/patch** ⇒ การแก้แม้บรรทัดเดียวในไฟล์ใหญ่ต้อง
   transcribe เนื้อไฟล์ทั้งหมดผ่าน tool call เดียว — สำหรับ `CLIENT_RE_QUEUE.md` (252 KB, ~1,039 บรรทัด) นี่เท่ากับต้อง
   คัดลอกไฟล์ทั้งไฟล์ทีละ ~150-250 บรรทัดผ่านหลายรอบ `Read` แล้วพิมพ์กลับเป็นพารามิเตอร์เดียวขนาดเดียวกัน — เสี่ยงพิมพ์/ตัดตกบรรทัด
   ในไฟล์ที่ทุกสายพึ่งพา ผมตัดสินใจ **ไม่เสี่ยง** ทำแบบนั้นกับ `CLIENT_RE_QUEUE.md`/`GAME_TEST_QUEUE.md` รอบนี้
4. `QUEUE_STATUS_SNAPSHOT.md` (170 KB) ติดปัญหาเดียวกัน — ไม่ได้รีเจนรอบนี้ด้วยเหตุผลเดียวกัน
