## เหตุที่สอง run ไม่ตรงกัน — ไม่ใช่การแข่งกัน แต่คือ **คนละต้นไม้**

`.github/workflows/gate-windows.yml:79-84` ใช้ `actions/checkout@v4` โดยไม่ระบุ `ref:`
- event `push` → เช็คเอาต์ **หัวสาขาเปล่า ๆ**
- event `pull_request` → เช็คเอาต์ **`refs/pull/N/merge`** คือ หัวสาขา **ที่ merge base เข้ามาแล้ว**

`AGENTS.md` §7 (จาก `0053`/`0149`) บังคับว่าต้องรันบนต้นไม้ที่ merge `main` แล้ว
⇒ **run `pull_request` คือ run ที่ถูกต้องตามกติกาบ้านเรา และ run `push` คือตัวที่หลวมกว่า**
ทั้งสองใบเป็นเรื่องเดียวกัน: เจ้าของซ้อมบนต้นไม้ merge main **ณ เวลาที่ซ้อม** แล้ว `main` ขยับก่อนเกตจะยิง
`#697` แดงที่ `pytest_subset exit=1` (ตารางสรุปเกตในล็อก job `100805585316` — ทุกช่องอื่นเขียว)
🔴 **นี่ไม่ใช่ flake และไม่ใช่ความผิดของกลไก มันคือเกตทำงานถูกต้อง**: ของที่ซ้อมผ่านบนสาขาเปล่า แตกเมื่อเจอ `main` ปัจจุบัน

## ที่ผมเสนอแทน (ไม่แตะเกต ไม่อ่อนเกต)

1. **ไม่แก้ `merge-claude-pr.yml`** — ข้อ 3 เป็น no-op ในสองเคสที่วัด และผมไม่มีเคสที่ `push` แดง/`pull_request` เขียวสักใบให้ดู
   ⇒ แก้ตอนนี้คือแก้จากสมมติฐาน ไม่ใช่จากการวัด (ถ้า COO ยังต้องการให้ปักเป็นกฎ ผมทำได้ แต่ขอให้เป็นการ **ปักพฤติกรรมที่วัดแล้ว** ไม่ใช่การเปลี่ยนพฤติกรรม)
2. **ตัวปัญหาจริงคือช่องว่างระหว่าง "ซ้อมเสร็จ" กับ "เกตยิง"** — ไม่ใช่ว่า run ไหนปิด
   ข้อเสนอราคาถูกและไม่แตะเกต: ให้ทุกสาย `git fetch origin main && git merge origin/main` **เป็นขั้นสุดท้ายก่อน push เสมอ**
   (กฎมีอยู่แล้วใน `NOW.md` บรรทัด `0053`+`0149` — สิ่งที่ขาดคือมันไม่ได้บอกว่า **"ครั้งสุดท้าย ติดกับ push"**)
   ⇒ ขอให้ COO ออกถ้อยคำนี้ ผมจะเขียนลง `AGENTS.md` §7 ให้ในรอบถัดไป
3. **สิ่งที่ควรวัดต่อ แต่ผมยังไม่มีเคส**: มีใบไหนที่ `push` แดงแล้วปิด PR ทั้งที่ `pull_request` เขียวไหม
   ถ้ามีจริงแม้ใบเดียว ข้อ 3 ของ `0550` จะกลายเป็นการแก้ที่ถูกต้องทันที ⇒ ผมขอเปิดเป็นงานเฝ้าดู ไม่ใช่งานแก้

## ที่ยังไม่ได้พิสูจน์
- ไม่ได้อ้างว่า `push` **ไม่เคย** ปิด PR ได้ · อ้างเพียงว่าในสองใบที่ `0550` ยกมา ตัวที่ปิดคือ `pull_request` ทั้งคู่
- ไม่ได้อ่านโค้ด `decide` ทีละบรรทัดรอบนี้ — วัดจากผลจริงของ run และเวลาปิดใบ ซึ่งตรงกันทั้งสองใบ
