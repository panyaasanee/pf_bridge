## คลังคำเจ็ดคำ (ปิดตาย สายนี้เขียนเองทุกคำ) — **แกนคือ "วิธีแก้" ไม่ใช่ "จุดคืนค่า"**

🔴 ฉบับแรกของสายนี้ตัดแกนผิด และ pf-adversary วัดออกมาว่าได้อะไร: **ไม่ได้อะไรเลย**
หกในเจ็ดโทเคนยิงเฉพาะตอนคอนฟิกเปลี่ยนใต้ล็อกอินกลางคัน · ส่วนโทเคนที่เจ็ด ซึ่งเป็นตัวเดียวที่คอนฟิกเสียแบบปกติ
ทำให้เกิด **ตอบคำเดียวกันให้ทั้งสองวิธีแก้ที่คุณบอกว่าไม่เหมือนกัน** — และยังเรียกแฟ้มที่อ่านได้ปกติว่า `unreadable`
ซึ่งเป็นเคสปกติหลัง `#264` ⇒ เจ้าของ grep แฟ้มแล้วไม่เจออะไรผิด แล้วเลิกเชื่อบรรทัดนั้น
**ตัดใหม่แล้วตามแกนที่เจ้าของหน้าคอนโซลลงมือต่างกันจริง:**

| token | เกิดอะไร | เจ้าของทำอะไร |
|---|---|---|
| `config_unreadable` | ไบต์เสียจริง JSON พัง/อ่านไม่ได้ | **แก้แฟ้มคอนฟิก** |
| `registry_refused_entry` | ไบต์**ปกติดี** แต่ registry ที่โปรเซสนี้ถืออยู่ไม่รับแถวนั้น | **รีสตาร์ทเซิร์ฟเวอร์ หรือแก้ registry ของสาย A** |
| `gm_accounts_unreadable` | `gm_accounts.json` อ่านไม่ได้หลัง lookup ผ่าน | ดูแฟ้มบัญชี |
| `gm_map_unreadable` | `gm_login_scene.json` อ่านไม่ได้ | ดูแฟ้ม override |
| `standalone_map_unreadable` | แผนที่ standalone อ่านไม่ได้ | ดูแฟ้ม standalone |
| `claim_raised` | ตัวลบระเบิด — ชะตาใบบนดิสก์ **ไม่รู้** | ดูดิสก์/สิทธิ์ แล้วดูว่าใบยังอยู่ไหม |
| `entry_survived_claim` | ลบไม่สำเร็จ — **รู้แน่**ว่าใบยังอยู่ | ลบใบด้วยมือ |

**สองแถวแรกคือเหตุผลทั้งหมดที่ฟีเจอร์นี้คุ้มจะพิมพ์** ถือด้วย
`login_scene_override.LoginSceneRefusedError` ซึ่งเป็น **subclass ของ `ValueError`**
⇒ ผู้เรียกเดิมทุกตัวที่จับ `except (OSError, ValueError)` ทำงานเหมือนเดิมทุกไบต์ ไม่มีใครต้องรับชนิดใหม่
subclass มีไว้ให้เฉพาะคนที่**อยาก**แยกเท่านั้น

🔴 **สิ่งที่จงใจไม่แยก** (เขียนไว้กันคนมา "คืนค่า" ให้): read ล้ม**ก่อน**หรือ**หลัง** claim
ฉบับแรกแยกไว้ แล้ว adversary ชี้ว่า read ของ standalone มีสองจังหวะเดียวกันเป๊ะแต่ได้โทเคนเดียว
⇒ แกนนั้นไม่ได้ถูกใช้อย่างสม่ำเสมอด้วยซ้ำ และเจ้าของก็ไม่ได้ทำอะไรต่างกันระหว่างสองจังหวะ
`claim_raised` กับ `entry_survived_claim` อยู่ต่อ เพราะคู่**นั้น**เป็นการแยกตามวิธีแก้จริง

## สัญญาที่ทำให้ปลอดภัยพอจะพิมพ์ (ข้อนี้สำคัญกว่าข้ออื่นทั้งหมด)

D1 ของรอบ `9wy444`: ไบต์จาก client ห้ามถึงคอนโซลของเจ้าของ · `cause` กำลังจะไปอยู่บนคอนโซลนั้น
ถ้าสร้างจาก `str(exc)` มันจะพา**เนื้อในแฟ้มคอนฟิก**ไปด้วย (JSON parse error อ้างบรรทัดที่ผิดตรง ๆ)
โดยสวมโทเคนของสายนี้เป็นตราประทับว่าเชื่อได้

- ทุกคำเป็น literal เขียนไว้**ก่อน**ไคลเอนต์ต่อเข้ามา · ข้อความ exception ไม่เป็น cause แม้บางส่วน
- เซตปิด `ConsumeResult` **ปฏิเสธ** คำนอกเซต ⇒ **ไม่ใช่ตัวกรอง แต่คือไม่มีทางเดินให้กรอง**
- ทุกคำผ่าน **cp874** และ ASCII · ไม่มีช่องว่าง `=` `\n` `\r` ⇒ ปลอมฟิลด์ที่สองหรือบรรทัดที่สอง
  บนบรรทัด `key=value` ของคุณไม่ได้ (พินด้วยเทส)
- ผูกสองทาง: `CONSUME_FAILED` **ต้อง**มี cause · ผลสำเร็จ**ห้าม**มี (`CAUSE_NONE` เสมอ)
  ⇒ บรรทัดของคุณจะไม่มีวันตั้งชื่อความผิดให้ล็อกอินที่สำเร็จ

**การ raise ไม่กินล็อกอิน [วัดแล้ว]:** `runtime.py` จับ `(ValueError, OSError, TypeError)` รอบจุดเรียก
consume อยู่แล้ว ⇒ cause ที่สายนี้เขียนผิดเสีย **override** ไม่ใช่ล็อกอิน · พินเป็นเทสฝั่งสายนี้
เพราะเหตุผลทั้งหมดของการเลือก raise แทนการกลืน วางอยู่บนมัน
