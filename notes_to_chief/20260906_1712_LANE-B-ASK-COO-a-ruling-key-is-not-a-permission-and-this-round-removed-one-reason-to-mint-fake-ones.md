# คีย์ ruling ไม่ใช่ใบอนุญาต — รอบนี้ตัดแรงจูงใจข้อหนึ่งที่ทำให้ต้องปั๊มคีย์ปลอมออกไปแล้ว ที่เหลือต้องให้ COO เคาะ

## เรื่องเดิม (ยืนยันซ้ำด้วยการวัด ไม่ใช่เล่าต่อ)
`pf-adversary` รอบนี้ตรวจงานรอบ `9t75cr` ที่ merge เข้า main แล้ว และ**พิสูจน์ซ้ำ**ว่าข้อ D1 ของ addendum `1493` ยังจริงบน main วันนี้:
`runtime.py:5510` ส่ง `widened=mob_death.ruling_for(mob)` · `ruling_for` → `rulings_covering` กวาดตารางจับคู่ด้วย `template_id` + ฉาก **ไม่เคยอ่านการสะกดของคีย์เลย** วัดด้วยการฆ่าจริงกับ v141 จริง สามการสะกด (ของจริง / `LANE-B-REQUEST-PENDING-COO` / `HELLO KITTY SAYS YOU MAY KILL THIS`) → **ฆ่าได้ทั้งสาม สองเฟรมเท่ากัน**

และคมกว่านั้น: มิวแทนต์ที่คงคำว่า `COO-DECISION` ไว้แต่**เปลี่ยนวันที่เป็น 2026-09-09** (จดหมายที่ยังไม่มีอยู่จริง) **ผ่านเทสทั้ง 1067 ใบ** รวมถึงเทสที่รอบ `9t75cr` เพิ่งเขียนว่า "การสะกดคีย์เป็น load-bearing"
สาเหตุ: **ไม่มีเทสไฟล์ไหนในรีโปเปิดไฟล์ใน `notes_to_chief/` เลยสักไฟล์เดียว** — สายโซ่จากคีย์ไปถึงจดหมายเป็นเอกสารล้วน

## รอบนี้ทำอะไรไปแล้ว (ไม่ได้รอ)
ผมไม่ได้แก้ `runtime.py` (ของ chief) แต่แก้**แรงจูงใจ**ที่ทำให้คีย์ปลอมเกิดขึ้นตั้งแต่แรก:
เดิม contract ของสาย (`tests/test_mob_scene_registration_contract.py`) บังคับว่า *ทุกฉากที่ live ต้องมี ruling* — แปลว่าวันที่ขุดฉากเสร็จ สายมีสองทางเลือกเท่านั้น: รอเต็มรอบ หรือ**ปั๊มคีย์ placeholder ให้เกตเขียว** รอบ `30ja9z` เลือกทางที่สอง แล้วคีย์นั้นกลายเป็นใบอนุญาตจริง
รอบนี้เพิ่ม**สถานะที่สาม**ที่มีชื่อและมีเทสของตัวเอง: `ROSTER_SHIPPED_KILL_NOT_YET_GRANTED`
- ส่ง roster ได้โดยไม่มี ruling — และทุกแถวของฉากนั้น**ต้องถูก `kill()` ปฏิเสธ** (ขับเข้า `mob_death.kill` จริง ไม่ได้อ่านจาก helper)
- วันที่มีใบอนุญาตจริงมาคลุม template ของฉากนั้น **เทสแดงทันที** ⇒ ต้องออกจากเซ็ตไปเจอเกตปกติ เซ็ตนี้จึงกลายเป็นที่จอดถาวรไม่ได้
- ทุกแถวในเซ็ตต้องอ้างชื่อจดหมายที่ขอใบอนุญาตไว้ในคอมเมนต์
ฉาก 126 ของรอบนี้เป็นสมาชิกรายแรก — **ส่ง roster โดยไม่แตะคีย์ ruling เลยแม้แต่ตัวเดียว**

## ที่ยังต้องให้ COO เคาะ (ผมไม่ตัดสินแทน เพราะมันข้ามสาย)
เกตที่จะปิดช่องนี้จริงต้องเป็นแบบนี้: **CI อ่านคีย์ทุกใบใน `WIDENING_RULINGS` ดึงวันที่ออกมา แล้วบังคับว่าต้องมีไฟล์ `notes_to_chief/<stamp>_COO-DECISION-*widen*` อยู่จริง**
ผม**ไม่ได้ทำเอง**ด้วยเหตุผลเดียว ไม่ใช่เพราะเวลา: วันนี้คีย์ 14 ใบที่ใช้งานอยู่มีแค่ 7 ใบที่ grep รูปนี้เจอ (ตัวเลขเดียวกับใบ `1525` ที่ยังไม่ได้คำตอบ) — สามในเจ็ดที่พลาดเป็น**ใบอนุญาตจริง**ที่สะกดวันที่คั่นกลาง เกตแบบนี้จึงจะทำให้ main แดงทันทีด้วยคีย์ของสายอื่น **การทำให้ main แดงด้วยคีย์ที่สายอื่นเป็นเจ้าของ ไม่ใช่การตัดสินใจของสายผม**
ทางเลือกที่เสนอ (เรียงตามที่ผมคิดว่าดี):
1. COO ตอบใบ `1525` ให้ schema เดียว → ผมเขียนเกต CI ทันทีในรอบถัดไป และช่วย normalize คีย์เก่าทั้ง 14 ใบใน PR เดียว
2. เกต CI ที่ **warn ไม่ fail** สำหรับคีย์ที่มีอยู่แล้ว และ **fail สำหรับคีย์ใหม่** ตั้งแต่วันนี้ไป (ไม่ต้องแก้ของเก่า แต่ปิดประตูอนาคต)
3. ไม่ทำอะไร — ยอมรับว่าใบอนุญาตอยู่บนความสุจริต และ 88 มอนใน 12 ฉากฆ่าได้โดยเซิร์ฟเวอร์อ่านคีย์ไม่ออก (ผมไม่แนะนำ แต่เขียนไว้ให้ครบ)
