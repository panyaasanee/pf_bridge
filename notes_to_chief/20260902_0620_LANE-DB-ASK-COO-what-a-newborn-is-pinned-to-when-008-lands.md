# สี่ข้อที่เกินอำนาจสาย เจอจาก pf-adversary สามรอบตอนตรวจงานรอบนี้ ขอคำตัดสิน

ทั้งสองข้อ **ไม่ใช่บั๊กที่มีอยู่ตอนนี้** เป็นทางเลือกที่ต้องเลือกก่อนจะเจอเข้าจริง
ผมไม่ตัดสินเอง และไม่รอข้ามรอบ ตามวินัยของสาย

## ข้อ 1 — วันที่ RE ตอบค่าจริง ตัวละครใหม่ยึดกับอะไร

ใบ `0443` ให้เหตุผลว่าทาง ข ดีกว่าทาง ก เพราะ "วันที่ RE พบค่าจริงจะต้อง rebuild อีกรอบ /
ทาง ข แก้ที่เดียวบรรทัดเดียว" — **บรรทัดเดียวนั้นยังไม่มีอยู่จริง** วัดแล้ว:
แก้ `NEW_CHARACTER_HP` ค่าเดียว → เทสแดง **5 ตัว** เพราะเทส
`test_the_values_are_the_ones_007_wrote` ตรึงค่าคงที่ไว้กับ **ข้อความของ `migrations/007`**
ซึ่งใบ `0250` ข้อ 3 ห้ามแก้ตลอดกาล ⇒ ทางออกตอนนี้คือแก้ไฟล์ที่ห้ามแก้ หรือแก้เทส

การตรึงนั้น **ถูกต้องและผมยังไม่ถอด** เพราะมันคือสิ่งเดียวที่กันไม่ให้ตัวละครสองรุ่น
(รุ่นที่ `007` seed กับรุ่นที่เกิดหลังจุดเสียบ) ถือเลขต่างกัน แต่มันตอบคำถามนี้ไม่ได้:

**ถ้าวันหนึ่งมี `008` เขียนเลขใหม่ที่ RE ยืนยันแล้ว:**
- (ก) ตัวละครใหม่ยึดกับ **migration seed ใบล่าสุด** (`008`) แล้วตัวละครที่ `007` seed ไว้ค้างที่เลขเก่า
  ⇒ มีสองรุ่นถาวร ต้องมี migration ตามไปแก้ไหม (แตะแถวเดิม = ต้องมี backup ตามกฎ `1112` ข้อ 3)
- (ข) ตัวละครใหม่ยึดกับ **`007` เสมอ** ⇒ `008` ไม่มีความหมายกับตัวละครใหม่ ซึ่งขัดกับเหตุผลของใบ `0443`
- (ค) `008` เขียนทับทั้งสองรุ่นให้เท่ากัน แล้วค่าคงที่ในโค้ดตรึงกับ `008` แทน
  ⇒ กลับมาที่คำถามเดิมอีกรอบตอน `009` แต่ทุกครั้งจะมีคำตอบเดียวคือ "ใบล่าสุด"

ผมเอียงไปทาง **(ค)** เพราะมันทำให้กฎเป็นประโยคเดียวที่ไม่ต้องตัดสินใหม่ทุกครั้ง
("ตัวละครทุกตัวถือค่าของ migration seed ใบล่าสุดเสมอ") และ `007` ไม่ต้องถูกแก้เลย
แต่มันแปลว่า **ทุก `00X` ที่แก้เลข = migration ที่แตะแถวเดิม = ต้องมี backup ทุกครั้ง**
ซึ่งเป็นราคาที่เจ้าของต้องรู้ ไม่ใช่ผมเลือกให้

รอบนี้ผมเขียนข้อจำกัดนี้ลงใน docstring ของโมดูลตรง ๆ แล้ว (ไม่ปล่อยให้เหตุผลของใบ `0443`
ยืนอยู่ทั้งที่วัดแล้วว่ายังไม่จริง) และตรึงไว้กับ `007` ต่อไปจนกว่าจะมีคำตัดสิน

## ข้อ 2 — กฎ `level = 0` ปิดประตูอ่าน แต่ประตูเขียนยังเปิด

ตามใบ `0443` ข้อ 4 ผมใส่กฎปฏิเสธ `level = 0` ในทางอ่านแล้ว วัดผลข้างเคียงได้ดังนี้บน DB จริง:
```
store.write_typed_attributes(cid, {"level":0,"hp_current":100,"hp_max":100})  -> ผ่าน
store.read_character_vitals(cid).require()   -> VitalsError
store.apply_hp_damage(cid, 1)                -> VitalsError
```
⇒ ตัวละครที่มี HP 100/100 ครบดี **จะตีไม่ได้เลย** ถ้ามีใครเขียน `level = 0` ลงไป
ก่อนรอบนี้แถวนั้นตีได้ กฎใหม่ทำให้ตีไม่ได้ — นี่คือผลของกฎที่ใบสั่งมาเอง ผมไม่ได้คัดค้าน
แต่ต้องรายงานเพราะ **ประตูที่สร้างสภาพนี้ได้จริงคือ `write_typed_attributes` ซึ่งยังไม่มีใครกัน**

**ตอนนี้ยังไม่เกิดขึ้นจริง** (latent ไม่ใช่ live): ทางเขียน typed attr ที่ shipped อยู่มีทางเดียวคือ
`/speed` เขียน `speed_walk` และไม่มีอะไรในรีโปเขียน `level` เลยแม้แต่ที่เดียว

**ผมปิดเองไม่ได้** เพราะ `write_typed_attributes` เป็นเมท็อดเดิม และ charter ใบ `1100`
ห้ามเปลี่ยนพฤติกรรมของเมท็อดเดิม ทางเลือก:
- (ก) COO อนุมัติให้สายนี้เพิ่มการปฏิเสธ `level = 0` ใน `write_typed_attributes`
  (เป็นการปิดให้แน่นขึ้นเหมือนข้อ 4 แต่กระทบเมท็อดเดิม จึงต้องขออนุมัติ)
- (ข) ปล่อยไว้ latent แล้วรอจนมีคนเขียน `level` จริง ค่อยมาปิด
- (ค) เพิ่มเมท็อดใหม่ที่กันครบ แล้วให้คนใหม่ ๆ ใช้ตัวนั้น (ของเดิมไม่แตะ)

ผมเอียงไปทาง **(ก)** เพราะ (ข) แปลว่าประตูจะถูกปิดหลังจากมีแถวเสียแล้ว และ (ค) คือมีสองประตู
ที่กฎไม่เท่ากันในโมดูลเดียวกัน ซึ่งเป็นรูปเดียวกับที่ pf-adversary จับได้รอบนี้

## ข้อ 3 — ตัวละครที่พยายามจะเกิด "ระหว่าง" python ของ 008 ลง กับ SQL ของ 008 รัน

pf-adversary รอบสองตั้งคำถามนี้ และผมตอบเองไม่ได้เพราะมันอยู่ใน `runtime.py` ซึ่งเป็นของ chief

พอจุดเสียบลง `create_character` จะ **ต้องการสคีมาล่าสุด และปฏิเสธทุกสคีมาที่เก่ากว่า**
ผมทำให้การปฏิเสธนั้นมีชื่อแล้ว (`SchemaDriftError` บอกชื่อคอลัมน์ที่ขาด แทน error ดิบ)
**แต่ชื่อนั้นหายไปที่ชั้นถัดขึ้นไป** — `runtime.py:6178-6186` จับ `except Exception`
แล้วยัดทุกอย่างลงคีย์ `decode_error` + `foundation_create_rejected_no_reply`
⇒ ความผิดพลาดเรื่อง **สคีมา** ถูกติดป้ายเป็นความผิดพลาดเรื่อง **ถอดรหัสไวร์** แล้วเงียบไป
ผู้เล่นเห็นแค่ "สร้างตัวละครไม่ได้" โดยไม่มีใครรู้ว่าเพราะอะไร

**คำถาม:** ถ้าฐานข้อมูลตามหลังโค้ดอยู่ เซิร์ฟเวอร์ควรทำอะไร — หยุด boot ไปเลย ·
ปฏิเสธเฉพาะการสร้างตัวละคร · หรือบอกผู้เล่นตรง ๆ  และใครเป็นเจ้าของคำตัดสินนี้
(ผมเดาว่าในทางปฏิบัติจะไม่เกิด เพราะ migration รันตอน boot ก่อนรับ connection
แต่ "ในทางปฏิบัติจะไม่เกิด" ไม่ใช่คำตอบที่ผมมีสิทธิ์ให้แทนเจ้าของ)
ผมไม่แตะ `runtime.py` และไม่เสนอโค้ด แค่ยกขึ้นมาให้ตัดสิน

## ข้อ 4 — ไม่มีอะไรในรีโปแยก `hp_current` ออกจาก `hp_max` บนสาย

pf-adversary รอบสามตั้งคำถามนี้ และผมยืนยันว่าเป็นจริง วัดจากโค้ดที่มีอยู่

คู่ HP ในเฟรมล็อกอินคือ `legacy.u32tag(0x14, 100)` **สองตัวติดกัน** และเทสของสายนี้เอง
(`WireEqualityTests`) พิสูจน์ว่า `encode(x=3, 100) + encode(x=4, 100)` เท่ากับสองตัวนั้น
**ไบต์ต่อไบต์** ⇒ ทั้งสอง encoding เหมือนกันทุกประการตราบใดที่ค่าเท่ากัน

**แปลว่า:** สิ่งที่พิสูจน์ว่าตัวที่สองคือ `hp_max` (ไม่ใช่แค่สมาชิกตัวถัดไปของแถวที่ไม่มีใครแยกออก)
คือ **ลำดับตำแหน่ง** อย่างเดียว และตัวผูกนั้นจะสลายทันทีที่ `hp_current != hp_max`
ซึ่งคือ **นาทีแรกที่ M4 ทำงานจริง** (ตีแล้วเลือดลด) — พอดีกับตอนที่เราต้องการมันที่สุด

- ตอนนี้ยังไม่พัง เพราะค่าทั้งคู่เป็น 100 และไม่มีอะไรเขียน HP ลงแถวเลย
- แต่วันที่ LANE-B ต่อสาย damage เข้าจริง ถ้าสองฟิลด์นี้สลับกัน **จะไม่มีเทสไหนแดง**
  ผลที่ผู้เล่นเห็นคือหลอดเลือดเต็มตลอด หรือเพดานเลือดลดลงเรื่อย ๆ แทนที่จะเป็นเลือดปัจจุบัน

**สิ่งที่ผมทำได้และทำแล้วรอบนี้:** ตัวผูกฝั่ง source ตอนนี้เป็น "หน้าต่างที่มีชื่อขนาบสองข้าง"
(ระหว่างแท็ก `level` กับแท็ก movement speed) ⇒ ถ้ามีใครเปลี่ยนค่าใดค่าหนึ่งหรือแทรกแท็กเข้ามาในแถว
เทสแดงทันที (วัดแล้วสามแบบ) **แต่มันยังแยกไม่ได้ว่าตัวไหนคือตัวไหน** เพราะข้อมูลนั้นไม่มีในรีโป

**สิ่งที่ผมทำเองไม่ได้:** ยืนยันว่า x=3 คือ `hp_current` และ x=4 คือ `hp_max` จริงตามที่ client อ่าน
นั่นคือคำถาม RE (`BasicAttr+0x044` กับ `+0x048` ตาม `gm/attr_wire.FIELDS`) ไม่ใช่คำถามที่เทสตอบได้
**ขอเปิดใบ RE** ผ่าน chief: ให้ยืนยันว่า client อ่าน offset ไหนเป็นเลือดปัจจุบัน offset ไหนเป็นเพดาน
เกณฑ์ผ่านง่ายมาก — ขอแค่ค่าที่ **ไม่เท่ากัน** หนึ่งคู่ (เช่น 80/100) แล้วดูว่าหลอดเลือดบนจอแสดงอะไร
อันนี้เป็น GT ใบเดียวจบ ไม่ต้อง RE binary ก็ได้ ถ้าเจ้าของสะดวกเปิดเกม
