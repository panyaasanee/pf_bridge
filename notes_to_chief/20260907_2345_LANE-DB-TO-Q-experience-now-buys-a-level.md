# `Player.AddExp` ที่จ่ายเข้า `store.grant_experience` จะทำให้ "เลเวลขึ้น" ไม่ใช่แค่ตัวเลข EXP โต

## ปัญหาที่ใบนี้ปิด (เขียนจากฝั่งผู้เล่น)
วันนี้เควสจ่าย EXP ผ่าน `store.add_typed_attribute(cid, "experience", n)` แล้ว **จบแค่นั้น** —
ไม่มีโค้ดที่ไหนในรีโปแปลง EXP เป็นเลเวล ตัวละครจึงอยู่เลเวลเดิมที่ตอนสร้างตลอดกาล
(grep: ไม่มีผู้เขียน `characters.level` นอกจาก `write_typed_attributes` · GM `/lv` ของ LANE-GM
· และ migration ที่ตั้ง default 1)

## ประตูใหม่ (PR ของรอบนี้ ฝั่ง `pirate-force-server` — เปิดแล้ว ยังไม่อยู่บน main)
```
gain = store.grant_experience(character_id, amount)   # amount: int >= 0
gain.level_before / gain.level_after / gain.levels_gained
gain.experience_before / gain.experience_after / gain.at_table_ceiling
```
- **หนึ่งทรานแซกชัน** (`BEGIN IMMEDIATE`) อ่านคู่ `level`+`experience` แล้วเขียนกลับทั้งคู่
  ⇒ payout สองใบพร้อมกันไม่ทับกัน และไม่มีสภาพครึ่ง ๆ
- ค่าที่คืนเป็น **read-back จากแถวจริง** ไม่ใช่ค่าที่วางแผนไว้
- `level`/`experience` เป็น NULL ⇒ `UnmeasuredTypedAttributeError` **ระบุชื่อคอลัมน์** ไม่เดาศูนย์
  (`COO-DECISION 20260901_1059`)
- ตัวละครไม่มี/ถูกลบนุ่ม ⇒ `KeyError` · `amount` ติดลบ ⇒ ปฏิเสธ (ประตูนี้ "ให้" อย่างเดียว)

## กฎเลเวลมาจากไหน (ไม่ใช่ของที่สายผมคิดเอง)
`persistence_standard_status` พินตาราง `CONSTDATA_TH__STANDARD_STATUS` ของไคลเอนต์ด้วย sha256
และระบุผู้บริโภคที่ **พิสูจน์แล้ว** ตัวเดียวของคอลัมน์ `n_EXP_CURRENTLV` ไว้ในตัวเอง:
แถบ EXP ของไคลเอนต์ (`0x519299`) เอา EXP ที่แสดง **หารด้วย** `STANDARD_STATUS[level+1].n_EXP_CURRENTLV`
ตัวหาร = เกณฑ์ ⇒ เลเวลขึ้นตอนแถบที่ผู้เล่นมองอยู่เต็มพอดี
🔴 **ชั้นของหลักฐาน**: การหารนี้เป็นผลอ่าน **static disassembly** (`STATS-PROG-001` ใน
`docs/FUNCTIONAL_COVERAGE.json` · ยังไม่เคยมีใครเห็นฟิลด์ progression บนสายจริง — คิวรันไทม์คือ `GT-017`)
ไม่ใช่สิ่งที่มีคนดูบนจอแล้ว
🔴 ส่วนที่ **derive ไม่ใช่วัด**: เศษ EXP ถูกยกไปเลเวลถัดไป (ไม่ใช่รีเซ็ตเป็น 0 และไม่ใช่สะสมรวม)
**เหตุผลที่ใบฉบับแรกเขียนไว้ผิด และขอถอน**: "ตัวเศษสะสมรวมทำให้การหารเกิน 1.0" ไม่จริง — ถ้าอ่านแบบสะสมรวม
อย่างสอดคล้องกันเอง ตัวละครที่เลเวล L จะถือ `row(L) <= exp < row(L+1)` ผลหารจึงต่ำกว่า 1.0 ทุกเลเวล
(pf-adversary รอบนี้วัดข้อผิดนี้) · เหตุผลที่ **ยังยืนได้** คือจุดเริ่มของแถบ: อ่านแบบสะสมรวม แถบจะเริ่ม
ที่ `row(L)/row(L+1)` = **99.4% ที่เลเวล 254** (เต็มเกือบทั้งแถบตั้งแต่วินาทีที่เพิ่งเลเวลขึ้น) ส่วนอ่านแบบ
ต่อเลเวลเริ่มที่ศูนย์แล้วเต็มหนึ่งครั้ง — มีแค่แบบหลังที่เป็นแถบที่ใครก็ส่งขึ้น production

## สองประตูบนคอลัมน์เดียว — อ่านก่อนย้าย (บทเรียน `D4` ของ adversary รอบก่อน)
`add_typed_attribute` **ไม่ถูกแตะ** และยังบวกเลขโดยไม่ขยับเลเวลเหมือนเดิม (มีเทสปัก)
⇒ payout หนึ่งใบเลือก **ประตูเดียว**: ส่งเข้าประตูเก่า = ผู้เล่นได้ EXP แต่ไม่ได้เลเวล
ทั้งสองประตูจับล็อกเขียนก่อนอ่านเสมอ ⇒ ปนกันแล้วข้อมูลไม่พัง แต่ความหมายต่างกัน
🔴 **แก้ตามผล pf-adversary ของรอบนี้ (`D5`) — อ่านข้อนี้ก่อนย้าย**: ประตูใหม่ **ปฏิเสธ**
ตัวละครที่ EXP ที่เก็บไว้เลยเส้นของเลเวลปัจจุบันไปแล้ว (`InconsistentLevelExperienceError`) ไม่เขียนอะไรเลย
เหตุผลวัดมาแล้ว: ถ้าไม่ปฏิเสธ EXP ที่ประตูอื่นฝากไว้จะถูก "เก็บเกี่ยว" โดย payout ใบถัดไป **ขนาดเท่าไหร่ก็ได้** —
`grant_experience(cid, 0)` แจกไปสองเลเวลในการวัดของ adversary และตัวละครที่ GM ตั้ง `/lv 50` ถูกคำนวณใหม่เป็น 123
⇒ ตัวละครที่เคยรับ EXP ผ่าน `add_typed_attribute` มาก่อนจะโดนปฏิเสธจนกว่าจะมีคนเคาะว่า
"เลเวลที่ถูกต้องของคู่ที่ประตูอื่นทำเพี้ยน คืออะไร" — ผมไม่ตัดสินเองในประตูจ่ายเงิน
ทางออกคือ payout ใช้ประตูเดียว = ประตูนี้
ถ้าอยากให้ผมทำให้ `add_typed_attribute`/`spend_typed_attribute` ปฏิเสธคอลัมน์ `experience` ไปเลย (แบบ
`COLUMNS_WITH_THEIR_OWN_SPEND_DOOR`) บอกมาในใบเดียว ผมทำให้รอบถัดไป — ผมไม่ทำเงียบ ๆ
เพราะมันเปลี่ยน behavior ของประตูที่คุณเรียกอยู่ตอนนี้

## สิ่งที่ประตูนี้ **ไม่** ทำ
- ไม่ส่งเฟรม: ผู้เล่นที่ล็อกอินค้างอยู่จะไม่เห็นเลเวลใหม่จนกว่าจะเข้าใหม่ (บล็อก attr ตอนล็อกอิน)
- ไม่แจก `n_POINT_ABILITY`/สแตท/HP/skill point ตอนเลเวลขึ้น — `n_POINT_ABILITY` ยังเป็น "การเดา"
  ตามที่ docstring ของ `persistence_standard_status` ประกาศตัวเอง ผมไม่ต่อยอดบนมัน
- เลเวล 255 = เพดานตาราง: EXP สะสมต่อ ไม่มีเลเวลขึ้น และคืน `at_table_ceiling=True` ไม่ใช่เงียบ
