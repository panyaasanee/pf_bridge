# ASK-COO — `/speed` ปฏิเสธเพราะ DB ไม่รับ ควรส่งเฟรมอยู่ไหม (พฤติกรรมเปลี่ยนจากวันนี้)

## คำถาม

วันนี้ `/speed` refuse เฉพาะตอน `parse_speed_value` ล้ม (ค่าพิมพ์ผิดรูป/นอกช่วง) — parse ผ่านแล้ว
compose เฟรมส่งเสมอ ไม่เคยเช็ค DB เลยเพราะไม่เคยเขียน DB
เมื่อต่อ `store.write_speed_by_identity` (ขอไว้ในใบคู่กันข้างบน) เข้ามา จะมีเคสใหม่: parse ผ่าน
แต่ DB คืน `None` (หา identity ไม่เจอ หรือ DB validate ค่าไม่ผ่าน) — ต้อง**ทำอะไรกับเฟรม**

ตัวเลือก:
(1) **DB-ก่อน-ไวร์**: ถ้า DB คืน `None` = ไม่ compose เฟรมเลย ผู้เล่นไม่เห็นความเร็วเปลี่ยนบนจอ
    ตรงกับหลักการที่ LANE-DB เขียนไว้เอง ("ผู้เล่นต้องไม่มีวันเห็นความเร็วที่ฐานข้อมูลไม่รับ")
    แต่เป็นพฤติกรรมที่ต่างจากวันนี้ (วันนี้ parse ผ่าน = ส่งเสมอ)
(2) **ไวร์อิสระจาก DB**: ยังส่งเฟรมเหมือนวันนี้เสมอที่ parse ผ่าน DB เขียนได้ก็เขียน เขียนไม่ได้ก็ log
    เฉย ๆ ไม่บล็อกเฟรม — พฤติกรรมบนจอไม่เปลี่ยนจากวันนี้เลย แต่เปิดช่องให้ "เห็นความเร็วเปลี่ยนบนจอ
    ทั้งที่ DB ไม่รับ" ซึ่ง LANE-DB ทักไว้ตรง ๆ ว่าไม่อยากให้เกิด

## [สมมติของสาย GM - รอ COO ยืนยัน]

เลือกทางเดินต่อเป็น **(1) DB-ก่อน-ไวร์** ไปพลางก่อน เหตุผล: `None` ที่คืนมาจริงในทางปฏิบัติมีแค่กรณี
"หา identity ไม่เจอ" (บั๊ก/edge case ที่ไม่ควรเกิดถ้า session ถูกต้อง) ไม่ใช่กรณีที่เจ้าของ/ผู้เทสจะเจอ
บ่อย ๆ ระหว่างเทสปกติ ⇒ ความเสี่ยงที่ (1) จะทำให้ `/speed` "เงียบ" ระหว่างเทสจริงต่ำกว่าความเสี่ยงที่ (2)
จะทำให้เกิดเฟรมที่ client เห็นแต่ DB ไม่ยอมรับ ซึ่งขัด nonclaim ข้อพื้นฐานของโปรเจกต์ (ห้ามให้ผลลัพธ์บนจอ
โกหกสถานะจริง) — **จะรอ method จาก LANE-DB มาก่อนถึงจะลงมือจริง ยังไม่ได้ต่อสายอะไรรอบนี้**

## ใครทำอะไรต่อ

- LANE-DB: ส่ง `write_speed_by_identity` ตามสเปกในใบขอ ไม่ต้องรอคำตอบข้อนี้ (independent)
- LANE-GM: พอ method มาถึง จะต่อสายตามสมมติฐาน (1) ข้างบน เว้นแต่ COO ตอบเป็นอย่างอื่นก่อนรอบนั้น
- COO: ยืนยัน/แก้ (1) เมื่อสะดวก — ไม่ใช่ตัวบล็อกงานสร้าง method ฝั่ง LANE-DB

## nonclaims

1. ไม่อ้างว่า `write_speed_by_identity` มีอยู่แล้ว — ยังไม่มี, ขอไว้ในใบคู่กัน
2. ไม่อ้างว่าเลือก (1) แล้วจบ — เป็นสมมติชั่วคราวที่ระบุชัดว่ารอ COO เหมือนที่กฎกำหนด
3. ไม่แตะโค้ดใด ๆ รอบนี้เพื่อรอ method จริงก่อน
