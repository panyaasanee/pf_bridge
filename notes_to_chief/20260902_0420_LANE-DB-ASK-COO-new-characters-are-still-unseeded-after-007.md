## 2. census ที่ขอในข้อ 2 — และคำเตือนหนึ่งบรรทัดที่ต้องอ่านคู่กัน
🔴 **นี่ไม่ใช่ canonical DB ของเจ้าของ** — คอนเทนเนอร์ของรอบนี้ไม่มีไฟล์ `.db` ของเจ้าของเลย
(`find . -name "*.sqlite3" -o -name "*.db"` = ศูนย์) ตัวเลขข้างล่างนับจากฐานข้อมูลที่รอบนี้สร้างเอง
ด้วย `migrations/` **จริง** ผ่าน `migrate_with_backup` **จริง** — เป็นหลักฐานว่า `007` ทำอะไรกับแถวแบบไหน
ไม่ใช่รายงานสภาพเครื่องเจ้าของ ตัวเลขของเครื่องเจ้าของต้องนับตอนบูตจริงเท่านั้น

สร้างสามตัวละคร: หนึ่งตัวเปล่า · หนึ่งตัว "เคยเล่นแล้ว" (`level=9, hp 50/60`) · หนึ่งตัวคู่ HP ครึ่งใบ (`hp_max=50` เดียว) แล้วลบอ่อน

| key | ก่อน `007` | หลัง `007` |
| --- | --- | --- |
| `characters_any` / `characters_live` | 3 / 2 | 3 / 2 |
| `level_seeded_any` / `_live` | 1 / 1 | **3 / 2** |
| `hp_current_seeded_any` / `_live` | 1 / 1 | **2 / 2** |
| `hp_max_seeded_any` / `_live` | 2 / 1 | **3 / 2** |
| `hp_pair_mixed_any` / `_live` | 1 / 0 | **1 / 0** (ไม่ขยับ = แถวคู่ครึ่งใบไม่ถูกแตะ) |

แถวจริงหลัง `007`: `(1, level=1, hp 100/100)` · `(2, level=9, hp 50/60 — ไม่ถูกแตะ)` · `(3, level=1, hp_current=NULL, hp_max=50 — คู่ HP ไม่ถูกเดาให้ครบ)`
`migrate_with_backup` ถ่ายสำเนาก่อน apply จริง (เทสเปิดสำเนาแล้วยืนยันว่ายังเป็น NULL ทั้งสามช่อง)

**หนึ่งจุดที่ผมอ่านใบแคบกว่าตัวอักษร และขอให้ตรวจ:** ใบเขียน "`WHERE ... IS NULL` ทั้งสามคอลัมน์"
ผมทำ `level` แยกอิสระ แต่ `hp_current`/`hp_max` **เป็นคู่** (`WHERE hp_current IS NULL AND hp_max IS NULL`)
เพราะถ้าเดาเติมทีละช่อง แถวที่มี `hp_max=50` อยู่ก่อนจะได้ `hp_current=100` = `REASON_HP_ABOVE_MAX`
กฎของเซิร์ฟเวอร์เองปฏิเสธทันที **ซ่อมแล้วพัง** · บนฐานข้อมูลวันนี้สองการอ่านนี้ให้ผลเท่ากันทุกแถว
(ยังไม่มีอะไรเขียนคอลัมน์เหล่านี้) ถ้าคุณต้องการตัวอักษรเป๊ะ สั่งได้ ผมออก `008` ให้ (แต่แนะนำว่าอย่า)

## 3. 🔴 รูที่ `007` ปิดไม่ได้ — และทำไมมันสำคัญกว่าตัว `007` เอง
วัดแล้ว ไม่ใช่ทฤษฎี (`test_a_character_created_after_007_is_still_unseeded`): สร้างตัวละครใหม่หลัง `007`
→ `level/hp_current/hp_max` = `NULL, NULL, NULL` → `apply_hp_damage` **ปฏิเสธ**
⇒ ถ้าเจ้าของสร้างตัวละครใหม่หลังบูตหน้า **M4 ยังปิดสำหรับตัวนั้น** ทั้งที่ `007` "ผ่าน" แล้ว

สองทางที่ปิดได้ ทั้งคู่เกินอำนาจสายนี้:

- **(ก) `008` rebuild ตาราง `characters` ให้สามคอลัมน์มี `DEFAULT 1/100/100`**
  ได้ผลกับ **ผู้เขียนทุกราย** รวมคนที่ไม่ผ่าน store · แบบอย่างมีแล้ว (`004` rebuild มาก่อน)
  ราคา: rebuild คือ migration รูปแบบหนักที่สุด ต้องถอดทุกคอลัมน์/ทุก CHECK/ทุก index ออกมาเขียนใหม่ให้ครบ
  พลาดหนึ่งบรรทัด = ข้อมูลจริงเสีย · ต้องไปกับ `migrate_with_backup` (มีแล้ว) และต้องอนุมัติเป็นใบใหม่
- **(ข) เขียนค่าตอนสร้างตัวละคร** — ต้องแก้พฤติกรรม `store.create_character` ซึ่ง **charter `1100` ห้ามตรง ๆ**
  ทางอ้อมคือ method ใหม่ + ให้ chief ต่อ call site (ใบขอจุดเสียบ) = สองสาย สองรอบ และช่วงกลางยังมีตัวละครไม่มีค่า

**สายนี้เอนไป (ก)** เพราะมันปิดที่ระดับ schema — ไม่ต้องรอสายอื่น ไม่มีช่องว่างระหว่างทาง และไม่ต้องมี
"ผู้เขียนที่ต้องจำ" · แต่ (ก) แตะแถวข้อมูลจริงและ rebuild ตาราง ⇒ **ไม่ทำจนกว่าจะมีใบอนุมัติ**
🔴 ระหว่างรอ ตัวละครใหม่ทุกตัวยังตีไม่ได้ตายไม่ได้ — จดไว้ตรง ๆ ไม่กลบ

## 4. คำถามที่สองที่ผู้ตรวจ (pf-adversary) ทิ้งไว้ และผมตอบเองไม่ได้ — ขอให้ตัดสินคู่กับข้อ 3

กติกาของ `007` เรื่อง "แถวไหนเขียนได้" คือ **"แถวที่มีอยู่ ณ วันที่ `007` วิ่ง"** เท่านั้น
ไม่มีที่ไหนเขียนกติกาสำหรับแถวถัดไป และ `007` **แก้ย้อนหลังไม่ได้ตลอดกาล** (checksum อยู่ใน ledger)

⇒ วันที่ RE ตอบกลับมาว่า HP เริ่มต้นจริงไม่ใช่ `100` บนดิสก์ของเจ้าของจะมี **สามประชากรปนกัน**:
1. แถวที่ `007` seed เป็น `1/100/100`
2. แถวที่สร้างหลัง `007` — ว่างทั้งสามช่อง (ข้อ 3 ข้างบน)
3. คู่ HP ครึ่งใบที่ `007` ปฏิเสธอย่างตั้งใจ

และ `vitals_seeding_census` **แยกไม่ออกว่าค่าหนึ่ง ๆ มาจากใคร** — docstring ของมันเขียนไว้เอง
("มันตอบว่ามีอะไรถูกเขียนแล้วหรือยัง ไม่เคยตอบว่าสิ่งที่ถูกเขียนได้รับอนุญาตไหม")

**คำถาม:** `008` (หรือใบใดก็ตามที่มาแก้ค่าเริ่มต้นทีหลัง) **เขียนทับประชากรไหนได้บ้าง**
และอยากให้มีอะไรบนดิสก์ที่ยังแยกทั้งสามออกจากกันได้ ณ วันนั้น
(ทางที่สายนี้ทำได้ถ้าสั่ง: คอลัมน์ `vitals_seeded_by` เก็บเลข migration ที่เขียนค่านั้น — **แต่มันคือ
คอลัมน์ใหม่บนตารางจริง = migration อีกใบ** จึงไม่ทำเองโดยไม่มีใบ) 🔴 **ไม่ตัดสินเอง**

รอบนี้ผู้ตรวจยังยืนยันของเดิมที่ไม่ใช่ของสายนี้ไว้ด้วย จดไว้ให้ครบ: สี่เธรดเรียก `migrate()` พร้อมกัน
ข้อมูลไม่เสียและ ledger ถูก แต่ผู้แพ้ตายด้วย `IntegrityError: UNIQUE constraint failed:
schema_migrations.version` ซึ่งไม่ได้บอกว่า "มีอีกโปรเซสหนึ่ง migrate ไปแล้ว" · `007` เป็นใบแรกที่ผู้แพ้
**ถ่ายสำเนาไปแล้วก่อนตาย** · `migrate()` อยู่นอกเขตเขียนของสายนี้ (charter `1100`) ⇒ แจ้ง ไม่แก้
