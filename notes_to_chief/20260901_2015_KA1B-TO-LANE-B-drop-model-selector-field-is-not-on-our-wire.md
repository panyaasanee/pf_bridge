## ① ของใหม่จาก Codex — ตัวเลือกโมเดลปิดแล้วแบบ exact

`n_DROPMODEL_TYPE` ถูกรับ **โดยตรงเฉพาะช่วง 0..12 ไม่มีการลบหรือ remap** แล้วใช้เป็นดัชนีของตารางโทเคนนี้เป๊ะ:

```
0=item  1=weapon  2=armor  3=fittings  4=money  5=buff  6=pandora
7=crystal_r  8=crystal_b  9=crystal_g  10=DROP_ENERGY  11=DROP_LIFE  12=holloween01
```

client ประกอบเป็น `.\Data\GC\F\<token>.nif` → เรียก resource-open + type filter → เก็บผลที่ `DropThingGameObj+0x84`

🔴 **`Type 0 เป็นค่าที่ใช้ได้จริง แปลว่าขอ item.nif ไม่ได้แปลว่า "ไม่มีโมเดล"`** (Codex เขียนย้ำเองในใบ)

เส้นทางขาเข้า: `GSCN_RunTimeProtocolRes` (`0x6E9D`) ฟิลด์ทางเลือก `+0x20` เลือกด้วย presence-mask bit `0x08` เป็น `TerrainThingPool*`
client เก็บของบนพื้นใน module map ที่ `+0x18` คีย์ด้วย `TerrainThing+0x10` (u32) — คีย์ใหม่สร้าง `DropThingGameObj` คีย์ซ้ำอัปเดตทับ

## ② สิ่งที่ผมเทียบกับโค้ดที่รันอยู่แล้วเจอ

`mob_loot.py:97-100` เขียนรูปร่างของ element ไว้เองว่า:

| bit ใน dirty mask | ฟิลด์ที่ตามมา |
|---|---|
| `0x02` | tag 0x14 u32 (+0x14) |
| `0x04` | tag 0x0F u16 (+0x18) |
| `0x08` | tag 0x05 u8 (+0x1B) |
| `0x10` | tag 0x2A f32 สามตัว (+0x1C, +0x20, +0x24) |
| `0x20` | tag 0x08 u8 (+0x1A) |

และบรรทัดถัดมาเขียนว่า **"This lane emits mask `0x12`"** = `0x10 + 0x02` เท่านั้น
⇒ **เราส่งแค่พิกัดสามตัวกับ u32 ที่ +0x14 · ไม่เคยส่ง `0x04`, `0x08` หรือ `0x20` เลยสักครั้ง**

ตัวเลือกโมเดลเป็นจำนวนเต็มเล็ก 0..12 ⇒ ผู้สมัครมีแค่สามช่องนั้น (u16 +0x18 หรือ u8 +0x1B หรือ u8 +0x1A) **และทั้งสามช่องเราไม่ส่ง**

## ③ [สมมติฐาน] ที่ตามมา และทำไมมันเข้ากับผลลบเดิมของสาย B

**[สมมติฐาน — ผมประกอบเอง ยังไม่มีใครพิสูจน์]** โมเดลไม่ขึ้นเพราะ element ของเราไม่เคยพก
ฟิลด์ที่ตัวเลือกโมเดลอ่าน ไม่ใช่เพราะไอเทมนั้นไม่มีโมเดล

ข้อนี้**ไม่ขัด**กับที่สาย B วัดไว้ที่ `mob_loot.py:68` ว่า `n_DROPMODEL_TYPE = 1` ไม่พอ — **มันอธิบายได้พอดี**:
GT-045 เปลี่ยน **ไอดีไอเทมในตาราง DATA** ส่วนตัวเลือกที่ Codex ปิดได้อ่าน **ฟิลด์บนสาย/รันไทม์**
⇒ ถ้าเราไม่เคยส่งฟิลด์นั้น การสลับไอดีในตารางจะช่วยไม่ได้เลยไม่ว่าจะสลับกี่ครั้ง
บันทึกของสายที่ว่า "not sufficient is not not-the-switch" ยังถูกทุกตัวอักษร ใบนี้แค่เติมว่าสวิตช์อยู่คนละชั้น

**สิ่งที่ผมไม่ได้อ้าง:** ผมไม่รู้ว่าในสามช่องนั้นช่องไหนคือตัวเลือกโมเดล Codex ปิดฝั่ง client ว่า
"อ่าน `n_DROPMODEL_TYPE` 0..12" แต่**ไม่ได้ผูก**ว่ามันมาถึงด้วย tag/offset ไหนบนสายของเรา
และผมไม่ได้พิสูจน์ว่า `TerrainThingPool*` ที่ `+0x20` ของ `0x6E9D` คือก้อนเดียวกับที่ lane นี้ส่งอยู่

## ④ วิธีพิสูจน์ผิด ราคาถูก

ส่ง element เดิมแต่เพิ่มทีละ bit พร้อมค่าโทเคนที่รู้ผลแน่ (เช่น `1` = `weapon.nif` ซึ่ง `.nif` มีอยู่จริง)

1. `mask 0x16` (เพิ่ม `0x04`) → u16 ที่ +0x18 = 1
2. ถ้าไม่ขึ้น `mask 0x1A` (เพิ่ม `0x08`) → u8 ที่ +0x1B = 1
3. ถ้าไม่ขึ้น `mask 0x32` (เพิ่ม `0x20`) → u8 ที่ +0x1A = 1

**ทำนาย:** มีหนึ่งใน 3 ที่ทำให้โมเดลอาวุธโผล่บนพื้น
**ถ้าครบสามแล้วยังเห็นแต่ label กับฝุ่นเหมือนเดิม** ⇒ สมมติฐานนี้ผิด ตัวเลือกไม่ได้มาจาก element นี้
และคำถามย้ายไปที่ว่า `TerrainThingPool*` ของเราไปถึง handler ตัวที่ Codex ปิดหรือเปล่า — ตีกลับได้ทันที

รอบเดียวจบทั้งสามได้ เพราะเป็นการเพิ่ม bit ในก้อนเดิม ไม่ต้องบูตใหม่ต่อข้อ
