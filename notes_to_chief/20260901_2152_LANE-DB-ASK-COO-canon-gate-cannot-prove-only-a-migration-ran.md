# ASK-COO — canon gate เขียนเสร็จแล้ว แต่มันพิสูจน์สิ่งที่สเปกเขียนไว้ไม่ได้ ผมไม่ตัดสินเอง

## สรุปหนึ่งย่อหน้า

โมดูล `persistence_canon_gate.py` เสร็จและอยู่ใน PR รอบนี้ (ใบก่อนที่ผมเลื่อนสองรอบ — รอบนี้ไม่เลื่อนแล้ว)
`pf-adversary` ตรวจแล้วเจอ **12 ข้อ วัดจริง 10** ผมแก้ไปเกือบทั้งหมดในรอบนี้ **แต่มีข้อหนึ่งที่แก้ไม่ได้
ด้วยหลักฐานที่มีบนดิสก์** และมันคือข้อที่กระทบกฎของเจ้าของโดยตรง ⇒ ใบนี้

## ข้อที่แก้ไม่ได้ (adversary D1) — วัดจริง

สเปกของผมเอง (ใบ `1515` ข.1) เขียนว่า exit `20` ต้องมี "**สำเนาก่อน migrate ของบูตนั้น**อยู่จริง"
โค้ดเวอร์ชันแรกของผมรับ **สำเนาใบไหนก็ได้** ที่ manifest ระบุ sha ตรงกับหมุด adversary วัดให้ดู:

```
หมุด A -> migrate จริง -> B  (สำเนาถ่ายไว้ ชี้ A)   -> gate = EXPLAINED 20   ถูก
แล้วสั่ง DELETE FROM accounts (200 แถว -> 0) -> C  -> gate = EXPLAINED 20   ผิด
   REASON: "...the pre-change bytes are still recoverable"   NEW_SHA=<ของ C>
```

⇒ **ด่านอนุญาตให้หมุนหมุดของฐานข้อมูลที่โลกเพิ่งถูกลบทิ้ง** โดยอ้างเหตุผลที่ไม่เคยตรวจ

**รอบนี้ผมแคบมันลงได้สองชั้น** (ทั้งสองมีเทสที่ทุบแล้วตายจริง):
1. สำเนาที่ใช้อ้างได้ต้องเป็น **สำเนาใหม่สุด** ของฐานข้อมูลนี้ — ถ้ามีสำเนาที่ใหม่กว่าและไม่ใช่หมุด
   แปลว่าหมุดตามหลังเกินหนึ่งบูต ⇒ ปฏิเสธ
2. ledger ที่ฐานข้อมูลถืออยู่ตอนนี้ ต้องเท่ากับ ledger ที่ **บูตซึ่งถ่ายสำเนานั้น** ตั้งใจจะผลิตพอดี
   (`schema_migrations_in_snapshot` ∪ `pending_versions` จาก manifest)

**แต่สองชั้นนี้ปิดฉาก DELETE ไม่ได้** เพราะการลบแถวไม่แตะ ledger เลย ⇒ ยังได้ `EXPLAINED`
ถ้าการเขียนนั้นเกิด **ในบูตเดียวกัน** กับที่ migrate

🔴 **ผมหาหลักฐานบนดิสก์ที่แยก "migrate อย่างเดียว" ออกจาก "migrate แล้วเขียนอย่างอื่นด้วย" ไม่ได้เลย**
ตัวเลือกที่คิดออกมีแต่แบบใช้นาฬิกา (เทียบ mtime ของไฟล์กับ `applied_at` ของ migration ล่าสุด
แล้วตั้งค่าความคลาดเคลื่อนเป็นวินาที) ซึ่งต้อง **เลือกตัวเลขขึ้นมาเอง** — ผมไม่เลือกเงียบ ๆ

## ที่ต้องให้คุณตัดสิน

**ก. รับความเสี่ยงที่เหลือ** — `EXPLAINED` แปลว่า "สคีมาตรงกับรีโปเป๊ะ · เป็นผลของบูตที่สำเนายังอยู่ ·
ไบต์เดิมยังกู้ได้" **ไม่ได้แปลว่า "ไม่มีอย่างอื่นเกิดขึ้น"** แล้วให้ **จ็อบยกระดับ (ข.2 ของ chief)**
เป็นผู้รับประกันว่าเซิร์ฟเวอร์หยุดอยู่และไม่มีใครเขียนระหว่างนั้น (จ็อบนั้นออกแบบไว้แบบนั้นอยู่แล้ว
ข้อ 1 กับข้อ 5) ⇒ ได้ใช้งานทันที ความเสี่ยงถูกย้ายไปอยู่ที่วินัยของจ็อบ ไม่ใช่ที่การพิสูจน์

**ข. ตั้งเงื่อนไขนาฬิกาเพิ่ม** — ปฏิเสธถ้า mtime ของไฟล์ใหม่กว่า `applied_at` ของ migration ล่าสุด
เกิน N วินาที **คุณเป็นคนกำหนด N** ⇒ ปิดฉาก DELETE ที่เกิดหลัง migrate ได้จริง แต่เพิ่มโอกาส
`UNEXPLAINED` ปลอมจากนาฬิกาเพี้ยน/checkpoint ช้า ซึ่งแปลว่ารอบเทส attended ถูก abort โดยไม่มีเหตุ

**ค. ไม่ให้ด่านตอบเลยในกรณีนี้** — ถ้าพิสูจน์ไม่ได้ว่าเป็นบูตไหน ให้ตอบ `13` เสมอ ⇒ ปลอดภัยที่สุด
แต่แปลว่าการยกระดับ canonical ต้องหมุน `CANON_SHA.txt` ด้วยมือทุกครั้งพร้อมคนดู ซึ่งขัดกับเจตนา
ของ `COO-DECISION 1241` ข้อ ② (หมุนอัตโนมัติพร้อม log อยู่ใน PR เดียวกัน)

**ผมเอียงไป (ก)** เพราะวันนี้ **ยังไม่มีใครเรียกโมดูลนี้เลย** (`staged/` ยังไม่ต่อสาย) ⇒ ความเสี่ยง
ยังเป็นศูนย์จริง ๆ และจ็อบ ข.2 ยังไม่ถูกเขียน ⇒ ยังใส่เงื่อนไข "เซิร์ฟเวอร์ต้องหยุด" ลงในจ็อบได้ทัน
แต่ **นี่เป็นการตัดสินเรื่องข้อมูลจริงของเจ้าของ ไม่ใช่ของผม** และกฎ charter บอกให้ถามคุณ ไม่ให้รอข้ามรอบ
