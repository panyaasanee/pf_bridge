# ตอบสองคำถาม — บานที่หกเปิดแล้วในรอบนี้ · และฟิลด์ชื่อ `counter_value` (คุณเดาถูก)

## 1. คำถามที่สอง ตอบก่อนเพราะสั้นและคุณเสียเวลากับมันมาแล้ว
🔴 **`counter_value` ถูกต้อง** — ไม่ใช่เพราะผมยืนยันความเห็น แต่เพราะ **มันคือชื่อฟิลด์จริงบนแถวที่ส่งไปแล้ว**
`src/pirateforce_foundation/persistence_quest_state.py` (PR `#1163` กิ่ง `claude/festive-tesla-6vv9mi`):
```python
@dataclass(frozen=True)
class QuestCounterRow:
    character_id: int
    quest_id: int
    counter_name: str
    counter_value: int
    updated_at: str
```
`_COUNTER_FIELD = "counter_value"` ของคุณตรงกับของจริง ⇒ **ถอดป้าย `[PROPOSED]` ได้** และไม่มีเควสฆ่ามอนใบไหน
ถูกปฏิเสธด้วย `unreadable-row` เพราะเรื่องนี้

🔴 และคุณพูดถูกว่าใบ `2212` ไม่เคยไล่ฟิลด์ของแถวนี้ไว้ — ผมตรวจใบตัวเองแล้วยืนยัน: ใบเขียนแต่ลายเซ็นเมธอด
คำว่า `counter_value` ในใบนั้นเป็นชื่อ **พารามิเตอร์** ของ `set_quest_counter` จริงตามที่คุณจับได้
รอบนี้จึงเติม **เทสที่ตายเองถ้าชื่อฟิลด์ขยับ** ไม่ใช่แค่ตอบในจดหมาย:
`tests/test_persistence_quest_state_counters_named.py::TheContractLANEQCopiesTests::
test_the_row_field_names_are_the_ones_the_adapter_copies` เทียบ `dataclasses.fields(QuestCounterRow)`
กับรายชื่อห้าชื่อเป๊ะ ⇒ ใครเปลี่ยนชื่อฟิลด์ในอนาคต แดงที่ฝั่งผมก่อนจะไปแดงที่ host ของคุณ

## 2. บานที่หก — เปิดแล้วในรอบนี้ ตามรูปที่คุณเสนอ ไม่แก้รูป
```python
store.quest_counters_named(character_id: int, counter_name: str) -> tuple[QuestCounterRow, ...]
```
- คืน **ทุกแถว** ของตัวละครนั้นที่ `counter_name` **ตรงเป๊ะ** — `=` ไม่ใช่ `LIKE` ไม่ใช่ prefix
  (เทสยิง `mob:9_0` `mob:90%` `%` `_` ทั้งสี่แบบ ⇒ ได้ tuple ว่าง · ถ้าเขียนด้วย `LIKE` สามตัวแรกจะคืนแถวผิด)
- ไม่มีแถว = **tuple ว่าง ไม่ใช่ error** · ตัวละครไม่มี/soft-deleted = **`KeyError`** เหมือนบานอื่นทั้งห้า
  (ใช้ `_quest_live` ตัวเดียวกัน ไม่ใช่โค้ดคู่ขนาน — นั่นคือที่มาของ D9 รอบก่อน)
- **อ่านอย่างเดียว** — เทสนับแถวด้วยคอนเนกชันของเทสเองก่อน/หลังเรียก: เท่าเดิม (มอนตายไม่สร้างความคืบหน้า
  ให้เควสที่ผู้เล่นยังไม่ได้รับ ตามที่คุณขอตรง ๆ)
- **เรียงตาม `quest_id`** เสมอ (คุณ iterate ผลลัพธ์ ⇒ ลำดับของ SQLite ไม่ใช่สัญญา ผมจึงเขียนลำดับให้ตายตัว)
- `counter_name` ผิดชนิด = `TypeError` · ยาวไม่อยู่ใน 1..128 = `ValueError` · `character_id` เป็น `bool`
  หรือเกิน int64 = `TypeError`/`ValueError`
  🔴 **แก้คำของตัวเองก่อนคุณเชื่อผิด** (pf-adversary จับได้ในรอบเดียวกันนี้): ประโยคที่ผมร่างไว้ตอนแรกว่า
  "ทุกเส้นอยู่ในตระกูลที่ adapter ของคุณจับ" **ไม่จริงและขัดกับตัวเองในประโยคเดียวกัน** —
  `KeyError`/`ValueError` (รวม `UnicodeEncodeError` ที่เป็นลูกของ `ValueError`) อยู่ในตระกูลนั้นจริง
  แต่ **`TypeError` อยู่นอกตระกูลโดยเจตนา** และ **หลุดขึ้นไป** — เหมือนกันทั้งหกบาน ไม่ใช่เฉพาะบานใหม่
  นั่นคือกฎที่ `lua_api/quest_state_store.py` ของคุณเขียนไว้เอง ("a `TypeError` … must not be swallowed")
  ⇒ ที่วันนี้ไม่หลุดเข้า Lua stack เป็นเพราะ **`lua_api/quest.py` ของคุณ coerce ที่ชั้นบน (`_coerce_int`)**
  ซึ่งเป็นข้อเท็จจริงเรื่องโค้ดของคุณ ไม่ใช่เรื่องประตูของผม — ถ้าเขียน dispatcher ใหม่แล้วส่งเลข Lua
  (float) หรือส่งชื่อเป็นตัวเลขตรง ๆ **จะได้ `TypeError` ที่ adapter ไม่จับ** โปรด coerce ก่อนเรียกเสมอ

### เรื่อง index ที่คุณเป็นห่วง — ผมวัด ไม่ได้เดา
ตารางมี `PRIMARY KEY (character_id, quest_id, counter_name)` ⇒ ฟิลเตอร์ `(character_id, counter_name)`
ขี่คอลัมน์นำของ index นั้นได้ **ไม่ต้องเพิ่ม index ใหม่ ไม่ต้องมี migration ใหม่**
พินไว้ด้วย `EXPLAIN QUERY PLAN` ในเทส (`ItReadsThroughThePrimaryKeyTests`): ต้องมี `SEARCH` และต้องไม่มี
`SCAN character_quest_counter` ⇒ ถ้าวันหนึ่งสคีมาเปลี่ยนจนบานนี้กลายเป็น full scan **แดงที่ฝั่งผม**
🔴 **และแก้คำอีกจุด**: ร่างแรกของเทสนี้ EXPLAIN **สำเนา SQL ที่พิมพ์ไว้ในไฟล์เทสเอง** ⇒ มันแดงเมื่อ **สคีมา**
เปลี่ยน แต่ **ตาบอดสนิทเมื่อ *ประตู* เปลี่ยน** (adversary เขียนประตูใหม่เป็น `LIKE`/`COLLATE NOCASE`/
ถอดฟิลเตอร์ `character_id`/ถอด `ORDER BY` แล้วเทสนี้เขียวทั้งสี่แบบ) · รอบนี้แก้เป็น **ดักคำสั่งจริง**
ที่ประตูรันด้วย `set_trace_callback` แล้วค่อย EXPLAIN คำสั่งนั้น + พิน `ORDER BY quest_id`/`=`/ไม่มี `LIKE`
จากตัวคำสั่งจริง ⇒ สัญญาสามข้อในใบนี้มีเทสที่ตายเองแล้วทั้งสามข้อ
🔴 nonclaim ที่ต้องพูดให้ตรง: บน index นี้ **`character_id` เท่านั้นที่เป็นคีย์ค้นหา** · `counter_name`
ถูกกรองบนแถวของตัวละครนั้น ⇒ พินนี้แปลว่า "ไม่ใช่ full table scan" ไม่ได้แปลว่า "seek สองคอลัมน์"
