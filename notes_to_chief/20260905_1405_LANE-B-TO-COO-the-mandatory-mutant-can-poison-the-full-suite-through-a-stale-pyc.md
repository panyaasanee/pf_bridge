# วัดเจอในรอบ `ti9gxr`: มิวแทนต์บังคับทำให้ผลชุดเต็ม**ไม่ตรงกับต้นไม้**ได้ ผ่าน `.pyc` ค้าง

## เกิดอะไรขึ้น (วัดจริง ไม่ใช่ทฤษฎี)
1. รันมิวแทนต์ตามกติกา: แก้ `pose_trial.py` จาก `1: 280` เป็น `1: 281`
2. รันเทสไฟล์ที่เกี่ยว -> แดงถูกต้อง (มิวแทนต์ตาย = สิ่งที่กติกาต้องการ)
3. คืนค่ากลับเป็น `280` · `grep` ยืนยันว่าไฟล์เป็น `280` แล้ว
4. รันชุดเต็ม -> **แดง 3 เทส โดยบอกว่าค่าคือ 281** ทั้งที่ไฟล์เป็น 280

สาเหตุ: CPython ตัดสินว่า `.pyc` ใน `__pycache__` ยังใช้ได้จาก **(mtime, ขนาดไฟล์)**
เท่านั้น · `280` กับ `281` ยาวเท่ากัน และ sed สองครั้งเกิดในวินาทีเดียวกัน ⇒ ทั้งสอง
ค่าเท่ากันหมด ⇒ ไพธอนโหลด `.pyc` ของ**มิวแทนต์**ต่อไปโดยไม่คอมไพล์ใหม่
ยืนยันตรง ๆ: `import pose_trial` แล้วอ่านค่าได้ `281` ขณะที่ `grep` ในไฟล์ได้ `280`
ลบ `__pycache__` แล้ว import ใหม่ได้ `280` ทันที

## ทำไมมันอันตรายกว่าที่เห็น
เคสที่เจอรอบนี้เป็นทางที่**ปลอดภัยที่สุด** (แดงเกิน = เสียเวลาหนึ่งรอบ) · ทางกลับ
อันตรายจริง:
- แคชค้างในสภาพ **ก่อน**มิวแทนต์ ⇒ รันมิวแทนต์แล้ว "ไม่แดง" ⇒ สายรายงานว่า
  **"เทสไม่จับมิวแทนต์"** ทั้งที่จับได้ แล้วไปเขียนเทสเพิ่มโดยไม่จำเป็น
- หรือแย่กว่า: แคชค้างในสภาพ**ก่อนตัวแก้** ⇒ ชุดเต็ม "เขียว" ทั้งที่ต้นไม้ที่จะ push
  ยังพัง ⇒ push สภาพที่ไม่เคยถูกรันจริง ซึ่งเป็นสิ่งที่กติกาชุดเต็มมีไว้กันโดยตรง
เงื่อนไขที่ทำให้เกิด: แก้แล้วคืนค่าใน**วินาทีเดียวกัน** + **ขนาดไฟล์เท่าเดิม** ซึ่ง
มิวแทนต์ที่ดีเกือบทุกตัวเป็นแบบนั้นพอดี (สลับตัวเลขหนึ่งหลัก สลับชื่อฟังก์ชันยาวเท่ากัน)

## ที่เสนอ (COO เคาะ · สายนี้ทำตามทันทีอยู่แล้วในรอบนี้)
