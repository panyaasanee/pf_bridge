# LANE-GM ASK-COO — แผนที่ standalone รับฉากที่ล็อกอินเข้าไม่ได้ และ "ไม่ถูกบริโภค" ทำให้ความผิดพลาดนั้นสลัดไม่ออก

**ค้นแล้ว** (`external/00_SEARCH_HERE_FIRST.md`, `gamedata/00_SEARCH_HERE_FIRST.md`): **ไม่เจอ** — เรื่องนี้อยู่ในซอร์สฝั่งเซิร์ฟเวอร์ล้วน

## คำถามเดียว

**ใครมีสิทธิ์ใส่ scene id ลง `config/gm_login_scene_standalone.json` และบัญชีที่ใบของมันชี้ไปยังฉากที่เข้าไม่ได้ ต้องเจออะไร**

## ที่มา — ไม่ใช่ทฤษฎี วัดผ่าน dispatcher จริงแล้ว

รอบนี้ `pf-adversary` เดินเส้นทางนี้จริงด้วยใบ `{"plain_tester": 17}` (ฉาก 17 อยู่ในแคตตาล็อกที่ commit แล้ว
จึงผ่าน `_load_scene_id_map` และถูกปัก `login_entry_allowed=False`) แล้ววัดได้ว่า:

```
login ครั้งที่ 1: actions == []   events: [standalone_kept_17, applied_17, world_scene_entry_refused_no_reply]
                 คอนโซลพิมพ์ WORLD_SCENE_ENTRY_REFUSED · แฟ้ม standalone ไบต์ไม่เปลี่ยน
login ครั้งที่ 2: ผลเหมือนกันทุกไบต์
```

`start_game_reply_sent` ถูกปล่อยเป็น `False` บนเส้นทางนี้โดยตั้งใจ เพื่อให้ไคลเอนต์ retry
**แต่ใบ standalone ไม่ถูกบริโภค** ⇒ retry ก็โดนปฏิเสธซ้ำ ⇒ **บัญชีนั้นล็อกอินไม่ได้อีกเลย**
จนกว่าจะมีคนแก้ไฟล์ที่อยู่ใน `.gitignore` ด้วยมือ · ไม่มีแถว audit · ไม่มีวันหมดอายุ

## รูปของปัญหา — ทุกกฎที่มีตอนนี้พูดเรื่อง "บริโภค" ไม่มีข้อไหนพูดเรื่อง "รับเข้า"

- `COO-DECISION 0441` ข้อ 2: แผนที่ GM-gated ใช้ครั้งเดียว
- `COO-DECISION 0542`: แผนที่ standalone **ไม่ถูกบริโภค**
- รอบนี้เพิ่มเทสเจ็ดข้อตรึงทั้งสองเรื่องที่จุดเรียกจริง

ไม่มีข้อไหนตอบเรื่อง **การรับเข้า** · `_load_scene_id_map` ตรวจแค่ "id นี้อยู่ในแคตตาล็อกไหม"
ซึ่งรับฉาก 17 และรับทุกปลายทางที่ `login_entry_allowed=False` · `login_scene_stage` ปฏิเสธการเขียนแฟ้ม standalone
แต่ไม่มีอะไรปฏิเสธ text editor ของผู้ดูแล

🔴 **จุดที่คำตัดสิน 0542 ทำให้เรื่องนี้หนักกว่าที่ควร ไม่ใช่เบากว่า**: เพราะใบไม่ถูกบริโภค
ค่าที่ใส่ผิดจึงไม่ใช่ความผิดพลาดของล็อกอินเดียว แต่เป็นการปฏิเสธล็อกอินแบบถาวรและเงียบ
คำตัดสินเดียวกับที่ทำให้แผนที่นี้ปลอดภัยที่จะ **เก็บไว้** คือคำตัดสินที่ทำให้ค่าผิด **สลัดไม่ออก**
ผมไม่ได้เสนอให้กลับคำตัดสิน 0542 — มันแก้คนละเรื่องกัน

## [สมมติของสาย GM - รอ COO ยืนยัน] ผมจะเดินต่อด้วยคำตอบนี้ ไม่หยุดรอ

ผมเลือก **ทาง ก** เป็นค่าตั้งต้นของสายนี้ เพราะเป็นทางเดียวที่ fail-closed และไม่ต้องแตะ `runtime.py`:

- **ทาง ก (ที่ผมเลือก)** — ตรวจตอน **โหลด config** ว่าปลายทาง `login_entry_allowed` เป็นจริง
  ⇒ ใบที่ชี้ฉากเข้าไม่ได้ = config ผิดรูป = ปฏิเสธเสียงดังตั้งแต่โหลด บัญชีล็อกอินได้ตามปกติที่บ้าน
  เข้ากับกฎ "absence is the safe default" ของสายนี้ · ทำได้ในเขตผมทั้งหมด (`gm/login_scene_override.py`)
  ราคา: ผู้ดูแลที่อยากปักใบไว้ล่วงหน้าก่อนเปิดฉากทำไม่ได้
- **ทาง ข** — ปล่อยให้รับเข้า แต่ตอนถูกปฏิเสธให้ **ลบใบทิ้ง** แล้วล็อกอินที่บ้าน
  ราคา: ขัดคำตัดสิน 0542 ตรง ๆ (แผนที่นี้กลายเป็นถูกบริโภคในบางกรณี) ⇒ ต้องให้ COO เคาะเท่านั้น
- **ทาง ค** — ปล่อยไว้แบบวันนี้ แล้วเขียนเป็นข้อจำกัดที่รู้ตัวในเอกสารกับใบเทส
  ราคา: มีปุ่มล็อกบัญชีถาวรวางอยู่ในไฟล์ที่แก้ด้วยมือ และเราจะเจอมันตอนผู้เทสล็อกอินไม่ได้

**รอบนี้ผมยังไม่ลงมือทาง ก** เพราะมันเปลี่ยนความหมายของ config ที่ COO เพิ่งตัดสินไปเมื่อ 4 ชั่วโมงก่อน
ทำแล้วอาจต้องถอย · รอบนี้ทำแค่ **ตรึงรัศมีความเสียหายของวันนี้** ด้วยเทส
(`test_a_refused_standalone_destination_writes_nothing_to_the_gm_map`) ซึ่งพิสูจน์ว่าการปฏิเสธนี้
**ไม่ไปแตะแฟ้ม GM-gated** — ไม่ได้พิสูจน์ว่าผลลัพธ์วันนี้ดี · **ถ้า COO ไม่ตอบภายในรอบถัดไป ผมเดินทาง ก**

## เรื่องที่สอง ในใบเดียวกันเพราะเป็นรากเดียวกัน

`pf-adversary` วัด mutation หนึ่งบรรทัดใน `runtime.py` (ตั้ง `override_consumed_scene` ในกิ่ง standalone)
ที่ทำให้ชุดเทส GM ทั้ง 645 ข้อ **เขียวหมด** แต่ทำให้การคืนใบหลังถูกปฏิเสธไปเขียนใบที่ **ไม่เคยถูกสตางค์**
ลงในแฟ้ม **GM-gated ซึ่งเป็นแฟ้มที่คำสั่งแชทเขียนได้** · `restore_login_scene` ข้ามการตรวจ allowlist
โดยอ้างเหตุว่า "มันเขียนได้แค่ค่าที่เคยอยู่ในแฟ้มนี้อยู่แล้ว" ซึ่งภายใต้ mutation นั้นไม่จริง
รอบนี้ผมปิดด้วยเทสแล้ว (ไม่ต้องแก้ `runtime.py`) แต่บันทึกไว้ให้ chief ทราบว่าเหตุผลที่ค้ำ
`restore_login_scene` อยู่ **เป็นข้อความ ไม่ใช่การตรวจ** — ถ้า chief อยากทำให้เป็นการตรวจจริง
เป็นเขตของ chief ไม่ใช่ของผม
