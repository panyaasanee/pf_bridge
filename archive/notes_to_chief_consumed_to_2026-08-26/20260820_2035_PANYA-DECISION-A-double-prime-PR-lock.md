## คำตัดสิน — Panya เคาะทั้งสองข้อ

### ① การรวมงาน = **A″** (PR แทน fast-forward)
chief push ขึ้น branch ของเซสชันตัวเอง → **เปิด PR** → Actions รัน gate → **merge อัตโนมัติเมื่อเขียว**
- 🔴 **ตัว merge ต้องทำฝั่ง GitHub** (Actions / auto-merge) **ไม่ใช่ให้ Panya กด** — เธอปฏิเสธการเป็นสายพานมือแล้วสองครั้ง
- ✅ `main` ยังไม่มีวันแดง เพราะ merge ต่อเมื่อเขียว

### ② การ์ดกันรอบซ้อน = **ใช้ PR ที่ยังไม่ merge เป็นล็อก**
ต้นรอบ ก่อนทำอะไรทั้งสิ้น: **ถาม API ว่ามี PR เปิดค้างจาก `claude/*` ไหม**
- **มี** ⇒ 🔴 **จบรอบทันที** เขียนบรรทัดเดียวว่าติด PR หมายเลขอะไร · **ห้ามทำงาน ห้ามเปิด PR ใหม่**
- **ไม่มี** ⇒ ทำงานได้ตามปกติ
⇒ ใช้ของที่ **เพิ่งพิสูจน์แล้วทั้งสองอย่าง** (อ่าน API ได้ · เปิด PR ได้) ไม่พึ่งอะไรที่ยังไม่เคยทดสอบ

## 🔴 สี่ข้อที่ต้องตอบให้ได้ — อย่าเพิ่งเขียน prompt ก่อนตอบครบ

**① PR แดงจะกลายเป็นล็อกที่ไม่มีวันปลด**
ถ้า PR เปิดค้างแล้ว gate แดง ⇒ ล็อกไม่ปลด ⇒ **ทุกรอบต่อจากนั้นจบทันทีตลอดกาล**
และ **รอบใหม่แก้ PR เก่าไม่ได้ด้วย** เพราะ push ได้เฉพาะ branch ของเซสชันตัวเอง
⇒ **ต้องมีทางออกที่ทำได้จริง** — เช่น รอบใหม่ **ปิด PR แดงทิ้ง** (ยืนยันก่อนว่า API ปิด PR ได้ไหม)
แล้วทำงานใหม่บน branch ของตัวเอง · **ถ้าปิดไม่ได้ ต้องออกแบบใหม่ อย่าเขียนกฎที่ทำตามไม่ได้**

**② กลไก auto-merge ต้องยืนยันว่ามีจริง ไม่ใช่สมมติ**
GitHub auto-merge ต้องเปิดในตั้งค่า repo และมักต้องมี branch protection + required checks
**repo เป็น private และแผนของ Panya คือ Max (บัญชีบุคคล ไม่ใช่ org)**
⇒ **ตรวจก่อนว่าใช้ได้ไหม** ถ้าไม่ได้ ให้ใช้ **workflow ที่ merge เองเมื่อ gate เขียว** แทน
🔴 **ห้ามเขียนว่า "เปิด auto-merge" แล้วจบ — ต้องบอกวิธีที่พิสูจน์ได้บน repo นี้**

**③ `CHIEF_CONTINUATION.md` แทรกที่บรรทัด 3 เสมอ**
คุณวัดเองไว้แล้ว (`@@ -2,0 +3,86 @@`) ⇒ **PR สองใบที่ทับช่วงเดียวกัน merge ใบที่สองจะชนแน่นอน**
การ์ด PR ข้อ ② กันได้ **ก็ต่อเมื่อบังคับให้มี PR เปิดได้ทีละใบจริง ๆ** — ยืนยันว่าตรรกะครอบเคสนี้

**④ ของค้างตอนนี้: PR #1 (รอบ 110) และ PR #2 (รอบ 111)**
ทั้งคู่แตะไฟล์เดียวกัน ⇒ **เสนอมาว่าจะจัดการยังไง** (merge ใบไหนก่อน · ปิดใบไหน · หรือให้ Panya ปิดทั้งคู่แล้วเริ่มใหม่)
