> *"เหมือนจริงใช้จริง ทำครั้งเดียวจบ > ง่ายวันนี้แต่รื้อทีหลัง"*

(**ยังไม่เคยมีใคร push `main` จาก Routine**) ที่ใบสั่งมองข้าม คือเหตุผลที่งานนี้ยังต้องผ่านคุณ

## งานรอบนี้: apply แพตช์ทาง D
แพตช์อยู่ในข้อ 3 ของ `FINDINGS_R108_A_PRIME_HOW_TO_READ_ACTIONS.md` แล้ว — **apply · gate · commit**
(แตะ `.github/workflows/gate-windows.yml` ⇒ ต้องผ่าน gate เต็ม · Panya push เอง)

### 🔴 สี่ข้อที่ต้องตอบให้ได้ก่อน commit — ทุกข้อคือจุดที่มันพังได้เงียบ ๆ

**① สถานะต้องผูกกับ commit SHA**
ไฟล์สถานะบน `ci-status` **ต้องระบุ SHA ของ commit ที่มันพูดถึง**
⇒ chief ต้องเทียบ SHA ก่อนเชื่อ · **ห้ามอ่านแค่คำว่า `success`**
🔴 ถ้าไม่มีข้อนี้ chief อาจอ่านสถานะเก่าค้าง แล้ว **merge commit ที่ยังไม่ผ่านหรือที่แดง** เข้า `main`
นี่คือความผิดพลาดที่แพงที่สุดที่ดีไซน์นี้ทำได้ — และมันจะเงียบสนิท

**② ห้ามเกิดลูป**
workflow ตั้ง `push: branches: ['**']` ⇒ **`ci-status` ก็เข้าเงื่อนไข**
GitHub ไม่ยิง workflow จาก push ที่ใช้ `GITHUB_TOKEN` **แต่ห้ามพึ่งข้อนั้นอย่างเดียว**
⇒ **กัน `ci-status` ออกจาก trigger ให้ชัดในไฟล์ workflow ด้วย** (เข็มขัดสองเส้น)

**③ `ci-status` ต้องไม่ไปปนกับตรรกะ merge ของ A′**
A′ สแกนหา branch ค้างที่ขึ้นต้น `claude/` ⇒ `ci-status` ไม่ควรถูกนับ **ยืนยันว่าไม่นับ**
และมันควรเป็น **orphan branch** ไม่ลากประวัติ repo ตามไปด้วย

**④ ต้องมีทางออกเมื่อยังไม่มีสถานะ**
รอบแรก ๆ `ci-status` อาจยังว่าง หรือ workflow ยังรันไม่จบ
⇒ **"ไม่มีสถานะ" ต้องแปลว่า "ยังไม่ merge" เสมอ ห้ามแปลว่า "น่าจะเขียว"**
เขียนให้ชัดใน prompt v3

### เกณฑ์รับงาน
- gate เขียว · commit เดียว · Panya push แล้ว **Actions รันแล้วมี branch `ci-status` โผล่จริงพร้อมสถานะของ commit นั้น**
- 🔴 **จนกว่าจะเห็น `ci-status` เกิดขึ้นจริงบน GitHub ห้ามนับว่าทาง D ใช้ได้** — เอกสารไม่ใช่หลักฐาน

## ที่ต้องคงไว้ ไม่เปลี่ยน
- **probe รอบแรกของ cloud chief (ข้อ 5 ของ FINDINGS R108) ยังต้องทำเป็นอย่างแรกก่อนงานอื่นทั้งสิ้น**

  (เช่น หยุดที่ `claude/*` แล้วรายงานให้ Panya merge เอง จนกว่าจะแก้ได้) **อย่าให้รอบแรกไปงงหน้างาน**
- การ์ดกันรอบซ้อน (`cloud_round_lock.json`) — ทำเสร็จแล้ว ไม่ต้องแตะ
