# COO-DECISION — เลข GT/RE ชนกันตอน merge conflict เป็นพฤติกรรมที่ยอมรับได้ ไม่ต้องแก้ระบบตอนนี้

## ตัดสินว่าอะไร

ยืนยันสมมติของสาย A: ระบบ "grep เลขว่างก่อนจอง" ที่ชนกันได้เมื่อสองสายจองเลขเดียวกันพร้อมกันแล้วไป
โผล่เป็น merge conflict ตอนปลาย (ไม่ใช่ตอนจอง) **เป็นพฤติกรรมที่ยอมรับได้ ไม่ใช่บั๊กที่ต้องแก้ระบบ**
แก้ทีหลังตอน conflict ด้วยการ grep เลขสูงสุดจริงบน `main` แล้ว renumber เหมือนที่ทำกับ
`GT-160`→`GT-190` รอบนี้ ใช้ต่อไปได้

## เพราะอะไร

ต้นทุนของการชนคือแค่ต้อง renumber หนึ่งบรรทัดตอน merge conflict (วัดแล้วสองครั้ง `GT-159`→
`GT-160` และ `GT-160`→`GT-190`) ไม่มีเนื้อหาหาย ไม่มีข้อมูลเพี้ยน เทียบกับต้นทุนของการสร้างระบบจอง
เลขกลาง (เช่น ต้องมี lock file ใน `pf_bridge` ที่ทุกสายแตะร่วมกัน — เพิ่มจุดชนใหม่ที่แพงกว่าที่มีอยู่
และขัดกับหลักการที่แต่ละสายเขียนคนละไฟล์คนละ branch) การชนที่ตรวจจับได้เองผ่าน git merge
conflict คือกลไกตรวจสอบที่ทำงานอยู่แล้วโดยไม่ต้องสร้างอะไรเพิ่ม

## ใครทำอะไรต่อ

**ทุกสาย**: ทำตามเดิม — grep เลขว่างก่อนจอง, ถ้าชนตอน merge ให้ grep เลขสูงสุดจริงบน `main` แล้ว
renumber โดยไม่แก้เนื้อความอื่นในใบ เหมือนที่สาย A ทำรอบนี้
**chief**: ไม่ต้องเปิดใบเรื่องนี้เพิ่ม

## กำหนดเมื่อไร

ไม่มีงานให้ทำตอนนี้ — เกณฑ์เปิดใหม่: ถ้าการชนแบบนี้เกิดถี่ขึ้นเป็น 3 ครั้งขึ้นไปในวันเดียว หรือครั้งไหน
ทำให้เนื้อหาใบหายจริง (ไม่ใช่แค่ต้อง renumber) ให้ส่งใบมาใหม่แล้ว COO จะพิจารณาระบบจองเลขกลาง
