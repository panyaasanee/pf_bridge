# หมายเหตุกระบวนการ -- session นี้ไม่มีเครื่องมือ GitHub MCP ให้เรียก ปลด draft เองไม่ได้ตามขั้นตอนที่กำหนด

## สิ่งที่เกิด

session ของสายนี้รอบ `bdcmkf` ไม่มีฟังก์ชัน `mcp__github__*` (เช่น `update_pull_request`,
`pull_request_read`) อยู่ในชุดเครื่องมือที่เรียกได้จริงเลย (ตรวจแล้ว: มีแค่ Read/Grep/Glob/Bash/Edit/
Write) มีแค่ `git` (push ได้ปกติ ผ่าน proxy) กับ `curl` REST API ของ GitHub (อ่าน/สร้าง/แก้ title-body
ได้ปกติผ่าน `$GITHUB_TOKEN`)

ทำตามขั้นตอนได้ครบสองข้อแรก: (1) push งานครบทั้งสองรีโป (2) แก้หัวข้อ + body ของทั้งสอง PR ให้มี
`PF-AUTOMERGE: v4` แล้วยืนยันด้วย GET สดว่า marker อยู่จริง -- **ทำไม่ได้เฉพาะข้อ 3 (ปลด draft)**
เพราะไม่มีเครื่องมือ MCP ให้เรียก `update_pull_request(draft=false)` ตามที่กำหนด และกฎของสายนี้เอง
ห้ามใช้ raw REST PATCH `{"draft": false}` เป็นทางสำรอง (บันทึกไว้ว่าคืน 200 แต่ไม่เปลี่ยนค่าจริง) และ
ห้ามใช้ GraphQL `markPullRequestReadyForReview` เช่นกัน (proxy ปฏิเสธเสมอ) -- ไม่มีทางเลือกที่กฎอนุญาต
เหลือให้ session นี้ทำ

## หมายเหตุเพิ่ม -- ทำไมไม่ push wake-gate commit เปล่ารอบนี้ (ฝั่ง pirate-force-server)

ขั้น "wake gate" เดิมต้องทำ **หลัง** ปลด draft สำเร็จ เพราะ `decide` job ตื่นจาก `workflow_run` ของ
`gate-windows` เท่านั้น และการปลด draft เองไม่ยิง push ให้ gate รันใหม่ รอบนี้ยังไม่ได้ปลด draft เลย
(ข้างบน) ดังนั้น push commit เปล่าตอนนี้จะยิง gate-windows ซึ่งจะจบแล้ว `decide` เห็น draft=true
แล้วข้ามอยู่ดี ไม่ช่วยอะไร -- **แต่มีความเสี่ยงต่อเนื่อง**: ถ้า reaper ปลด draft ให้เองที่ ~6 ชม.
(pirate-force-server) โดยไม่มี push ใหม่ตามหลัง `decide` จะไม่มีวันตื่นเพื่อเห็นสถานะ ready+เขียวเลย
(เหมือนเคสจริง `server#415` แต่รอบนี้จุดพังคือ "ปลด draft ไม่ได้เลย" ไม่ใช่ "ปลดแล้วแต่ลืม wake")
**session/รอบถัดไปของสายนี้ที่ปลด draft สำเร็จ (หรือกู้คืนงานนี้) ต้อง push wake-gate commit เปล่าเอง
หลังปลด draft** ตามขั้นตอนเดิม -- อย่าเข้าใจว่าขั้นนี้ทำไปแล้วเพราะรอบนี้ไม่ได้ทำ
