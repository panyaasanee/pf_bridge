## ส่วนที่ 1 — แก้คำตัวเองก่อน

ใบ `20260901_1210` ของผม ข้อ 4 เขียนว่า *"ห้ามเปิด canonical DB ... ถ้าสาย DB แตะไฟล์นั้น
รอบเทส attended ทุกใบจะ abort ที่ด่าน sha"* — **ข้อนั้นถูกยกเลิกแล้ว** โดยเจตนาของเจ้าของเอง
(เธอบอก COO ตรง ๆ ว่า canonical ต้องพัฒนาเป็น DB มาตรฐาน) และโดยใบ `1112`

ผมยกกฎบ้านของ **เซสชันเทส** มาใช้เป็นกฎของทั้งโปรเจกต์ ซึ่งไม่ใช่สิ่งเดียวกัน กฎ "ห้ามเปิด
canonical" คือกฎของคนที่ถือ `LOCK_GAME` ระหว่างบูตเกม ไม่ใช่ข้อห้ามถาวรของทุกสาย
**chief: ถ้าลงทะเบียนใบ 1210 ไปแล้ว ให้ตัดข้อ 4 ทิ้ง ใบ 1112 มีผลแทน** ข้อ 1-3 และ 5-6
ของใบนั้นยังใช้ได้ตามเดิม

## ส่วนที่ 2 — ข้อค้นพบ: charter ข้อ 1 อธิบายสิ่งที่โค้ดวันนี้ยังไม่ทำ

ใบ `1112` ข้อ 1 เขียนว่า canonical DB *"ถูกยกระดับผ่านไฟล์ migration ของ LANE-DB
โดยอัตโนมัติตอน server boot (runner ใน store.py)"*

ผมวัดเส้นทางบูตทุกเส้นแล้ว **ไม่มีเส้นไหนชี้ `--db` ไปที่ canonical เลยสักเส้น**:

| เส้นทาง | `--db` ชี้ไปที่ | canonical โดน migration ไหม |
|---|---|---|
| บูตเทส attended (`1404_..._boot.ps1:19,40`) | `state\run_gt182_<stamp>.sqlite3` = **สำเนา** | ไม่ |
| บูตเล่นเองของเจ้าของ (`9001_play_boot.ps1:37,39,60`) | `state\play.sqlite3` = **สำเนา** | ไม่ |

`store.py:25-26` รับ path เข้ามาแล้ว apply migration ลงไฟล์นั้น — มันทำงานถูกต้องทุกครั้ง
แต่ไฟล์นั้นไม่เคยเป็น canonical

**ผลที่จะเกิดถ้าไม่ทำอะไร:** สาย DB ลง migration 006 ได้สำเร็จ pytest เขียว pf-adversary ผ่าน
PR merge ทุกอย่างดูปกติหมด — แล้ว canonical ก็ยังค้างอยู่ที่ 005 ตลอดไป โดยไม่มีอะไรเตือน
เพราะทุกบูตยัง "ทำงานได้" ปกติ **นี่คือปัญหาเงียบชนิดที่เจ้าของสั่งห้ามไว้ตรง ๆ**
และมันจะเงียบนานเท่าที่ไม่มีใครไปเปิดไฟล์ canonical ดู `schema_migrations` ด้วยมือ

ที่สำคัญกว่า: คำสัญญาของ charter คือ *"DB มาตรฐานที่ทุกฝ่ายเริ่มและยึดจากตรงนี้"* —
ถ้า canonical ไม่ขยับ ทุกสำเนาที่ทุกฝ่ายเริ่มจากมันก็จะเริ่มจาก schema เก่าเสมอ แล้วไป
apply migration เอาเองตอน boot ซึ่งได้ผลลัพธ์เหมือนกันก็จริง **แต่ canonical จะไม่ใช่
"มาตรฐาน" มันจะเป็นแค่จุดตั้งต้นที่เก่าที่สุดในระบบ**

## ส่วนที่ 3 — สิ่งที่ต้องตัดสินคู่กัน ถ้าจะทำให้ charter ข้อ 1 เป็นจริง

🔴 **วันที่มีอะไรสักอย่างชี้บูตไปที่ canonical จริง `CANON_SHA.txt` จะล้าสมัยทันที**
แล้วรอบ attended ถัดไปจะ **abort ที่ `1404_..._boot.ps1:18` ด้วย exit 16 'canonical mismatch'**
และบูตเล่นเองก็ตายที่ `9001_play_boot.ps1:32-34` เหมือนกัน

ข้อความ abort อ่านแล้วเหมือน DB โดนทำพัง ซึ่งเป็นคำเตือนแบบที่คนจะแก้ด้วยการ **ปลดด่านทิ้ง** —
แล้วเราจะเสียตัวจับ corruption ตัวเดียวที่มีอยู่

ดังนั้นการเดินสาย migration เข้า canonical **ต้องมาพร้อมกฎหมุน `CANON_SHA.txt` ในการเปลี่ยน
ครั้งเดียวกัน** ข้อเสนอ (ไม่ใช่ข้อสั่ง — เขตนี้เป็นของ COO/chief):
1. ด่านต้องแยกให้ออกระหว่าง **"sha เปลี่ยนเพราะ migration N ลงไป (คาดหมายได้)"** กับ
   **"sha เปลี่ยนเพราะอย่างอื่น (abort)"** — อ่าน `schema_migrations` เทียบ checksum
   ถ้าต่างกันเฉพาะเวอร์ชันที่คาดไว้ = หมุนค่าใหม่ลง `CANON_SHA.txt` พร้อม log ดัง ๆ
   นอกนั้น abort เหมือนเดิม
2. PR ที่ลง migration ต้องมีขั้นหมุน `CANON_SHA.txt` อยู่ในใบเดียวกัน ไม่งั้นรอบ attended
   ใบถัดไปตายทันที
3. ตัดสินให้ชัดว่า **ใครเป็นคนบูตครั้งที่ยก canonical** — วันนี้ไม่มีเส้นทางไหนทำเลย
   ต้องสร้างขึ้นมา (จ็อบเฉพาะ หรือแก้ `9001` ให้ชี้ canonical) ไม่ใช่จะเกิดเอง
