# ASK-COO — ทรง "ทั้งพื้นในหนึ่ง generation ต่อคิล" ชนกับ *ONE ANNOUNCEMENT PER DROP* หรือไม่

## 1. ติดอะไร

PANYA-ORDER 27/29 ส.ค. สั่งสาย B ว่า *"ไปทำให้ของมันค้างอยู่นาน ๆ ก่อน"* (ผ่านใบ chief 2105)
ทางเดียวที่ทำได้ในเขตสายนี้คือทรงที่หัวไฟล์ `mob_loot.py` เขียนไว้เองเป็น **WIRING ข้อ 4b**:
เก็บแถวไว้ แล้วส่ง `cell.frames(legacy)` = **ทั้งพื้นที่ยังมีชีวิต เป็นหนึ่ง generation ต่อคิล**

แต่หัวไฟล์เดียวกันนั้น ข้อ 5 เขียนว่า:

> **ONE ANNOUNCEMENT PER DROP** — each drop announced ONCE and never re-announced.
> It is a CADENCE rule, not a frame-count rule.
> (คำปฏิเสธของ COO 2026-08-26 07:45: `DROP_REFRESH_MS` ห้ามอยู่บนเส้น production
> เพราะ 12.5 เฟรมต่อวินาทีต่อแถวแพงเกินไปสำหรับกลไกที่ยังไม่มีใครวัด)

ทรง 4b **ประกาศแถวเก่าซ้ำ** ทุกครั้งที่มีคิลใหม่ ⇒ ตัวอักษรของข้อ 5 ชน

## 3. เลือกอันไหนไปแล้ว

**เลือก (ก) ทำไปแล้ว ลงในรอบนี้** ด้วยเหตุผลสี่ข้อ ที่อ้างเอกสารของโปรเจกต์เอง ไม่ใช่ความสะดวก:

1. ข้อความที่ชนนิยามตัวเองว่าเป็น **cadence rule** และสิ่งที่ COO ปฏิเสธคือ **ON A TIMER**
   ทรง (ก) ไม่มี timer ไม่มีเธรด ไม่มี interval — จำนวนการส่งเท่ากับจำนวนคิลเป๊ะ
   ต่อให้พื้นมีของสิบชิ้น หนึ่งคิลก็ยังเป็น **หนึ่งเฟรม** เท่าเดิม (frames=1 พินไว้ในเทส)
2. ข้อ 4b **เขียนไว้เองในไฟล์** ว่า *"That is a shape change, not a cadence change, so the
   COO's 2026-08-26 refusal in step 5 does not cover it"* — สายนี้ไม่ได้ตีความใหม่ ทำตามที่เขียนไว้
3. เงื่อนไขเดียวที่ 4b ตั้งไว้คือ *"what it does need is an expiry or a pickup"* — **expiry ลงแล้ว**
   ในรอบ `0n9inw` ตาม COO-DECISION 2026-08-29T12:41 (ต่อแถว lazy ไม่มี timer)
4. ทางเลือก (ข) ไม่ทำตามคำสั่งเจ้าของ: RE-130 วัดแล้วว่า generation ที่ไม่ว่างลบทุกคีย์ที่มันไม่มี
   ⇒ คงทรงเดิมแปลว่าคิลที่สองลบของคิลแรกทิ้ง "ค้าง" จึงเป็นไปไม่ได้ตามนิยาม

ราคาที่จ่ายจริง วัดแล้ว: generation กว้างขึ้นตามจำนวนแถวที่ยังมีชีวิต — สองแถว = 82 ไบต์
(แถวเดียว = 54 ไบต์ เท่าเดิมเป๊ะ) เพดานสองชั้น: อายุ 120 s ต่อแถว และ trim ที่ `sustain_a_kill`
ทำเองถ้าพื้นกว้างเกินหนึ่งเฟรม (2426 elements ซึ่งวันนี้ไปไม่ถึง)

ติดป้าย `[สมมติของสาย B - รอ COO ยืนยัน]` ไว้ในหัวโมดูล `mob_drop_presence.py` และในใบ CORE-REQUEST

## 4. ถ้าผิดต้องย้อนอะไรบ้าง

จุดย้อนสั้นและอยู่ที่เดียว: **สามบรรทัดในใบ CORE-REQUEST 2246 ที่ chief ยังไม่ได้วาง**
- ถ้า COO ตีตกก่อน chief วาง: ไม่ต้องย้อนอะไรเลย โมดูลลง main แล้วไม่มีใครเรียก (ราคาศูนย์)
- ถ้าตีตกหลัง chief วาง: เปลี่ยน `step.frames` กลับเป็น `mob_loot.drop_frames(legacy, drops)`
  หนึ่งบรรทัด · เก็บการลบลูป `take` ไว้ (ข้อนั้นไม่มีใครเถียง คลิกต้องเจอแถว) · ถ้าต้องการเพดาน
  แบบเดิมกลับมา ใส่ `cell.prune_previous_kills()` หนึ่งบรรทัด
- ไม่มี migration ไม่มี DB ไม่มี state ที่ค้างข้ามบูต ไม่มีสายอื่นพึ่งโมดูลนี้
