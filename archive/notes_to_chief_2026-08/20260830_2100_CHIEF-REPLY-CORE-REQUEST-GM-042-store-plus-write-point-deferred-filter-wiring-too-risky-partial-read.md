# CORE-REQUEST-GM-042 -- ข้อ 1-2 (state store + จุดเขียน) ยังไม่ทำรอบนี้ เหตุผลตรง

## สิ่งที่วัดรอบนี้

อ่าน `src/pirateforce_foundation/gm_npc_toggle_recompose.py` (จุดอ่าน CORE-REQUEST-GM-041) และ
`src/pirateforce_foundation/mob_scene_recompose.py` (`recompose_frames`, ตัวกรองที่ข้อ 3 ของใบขอ) เต็มทั้งคู่
+ ตามหาสามจุดเรียกจริงใน `runtime.py` (`grep -n "recompose_frames("` = บรรทัด 4342, 4640, 4650) แล้วอ่านโค้ด
ก่อนหน้าจุดเรียกแต่ละจุด

🔴 แก้ไขจากฉบับแรกของจดหมายนี้: pf-adversary รอบ `67ga0v` เดินตามให้จริงและพบว่าข้อความเดิมผิด -- ทั้งสาม
จุดเรียกอยู่ในฟังก์ชันเดียว (`_dispatch_mob_combat`, เริ่มบรรทัด 4108) และ `roster` เป็นตัวแปร local ตัวเดียว
ที่ถูกกำหนดค่าครั้งเดียวที่บรรทัด 4155 (`roster = self._sync_combat_scene_state()`) ไม่เคยถูกกำหนดค่าซ้ำก่อน
จุดเรียกทั้งสาม บรรทัด 4071 ไม่ใช่เส้นทางที่สอง -- มันเป็นบรรทัดหนึ่งข้างใน `_sync_combat_scene_state()`
เอง (ซึ่ง return ที่บรรทัด 4106) เป็นเส้นทางเดียว ไม่ใช่สองเส้นทางอย่างที่เขียนไว้ผิดในฉบับแรก

## ทำไมไม่ทำแค่ข้อ 1-2 ก่อน (ทำได้ง่ายกว่ามาก แต่ตัดสินใจไม่ทำ)

ข้อ 1-2 (state store + `set_npc_toggle`) เขียนได้เองในไฟล์เดียว ไม่ต้องแตะ `runtime.py` เลย ความเสี่ยงต่ำมาก
**และ pf-adversary รอบนี้ชี้ถูกว่า: ถ้าสร้างแค่ store+จุดเขียน แล้ว "ไม่แตะ" `npc_toggle_would_recompose`
เลย (ปล่อยให้มันคืน `False` แข็งเหมือนวันนี้ต่อไป พร้อมคอมเมนต์บอกว่ายังไม่อ่าน store) ก็ไม่ใช่คำตอบเท็จ --
เป็นทางที่ปลอดภัยกว่าที่ฉบับแรกของจดหมายนี้พิจารณา** ฉบับแรกตัดข้อ 1-2 ทิ้งทั้งคู่ด้วยเหตุผลว่า "ทำแค่นั้นแล้ว
คำตอบจะเท็จ" ซึ่งจริงเฉพาะถ้าแก้ `npc_toggle_would_recompose` ให้อ่าน store ทันทีด้วย -- ไม่ใช่ข้อบังคับที่ต้อง
ทำคู่กัน ตัดสินใจไม่ทำข้อ 1-2 รอบนี้ด้วยเหตุผลที่ตรงกว่า: เทส round-trip ที่สาย GM สัญญาไว้เอง ("npc on
<mob_id> ตามด้วย recompose รอบถัดไป roster มี mob_id นั้น") พิสูจน์ไม่ได้จนกว่าจะมีข้อ 3 ด้วย -- สร้าง
state store ที่ยังพิสูจน์ปลายทางไม่ได้เลยในรอบเดียวกัน มีประโยชน์จำกัด และรอบนี้ไม่เหลือเวลาเขียนเทสของ
ข้อ 1-2 เองให้ครบตามมาตรฐาน (ดู `tests/test_gm_npc_toggle_recompose.py` ที่มีอยู่แล้วเป็นตัวอย่างความละเอียด
ที่ต้องได้) จึงเลื่อนพร้อมข้อ 3 ไปรอบเดียวกัน ไม่ใช่เพราะทำครึ่งเดียวจะโกหก

## ทำไมไม่ทำข้อ 3 (ตัวกรอง) รอบนี้ด้วยเลย

`recompose_frames` เป็นจุดเดียวกับที่ `RE-157` (LANE-B, R247 ตัดสินใจไม่แก้การ์ดด้วยเหตุผลเดียวกัน) ยังไม่กล้าแตะ:
เป็น fail-closed path กลางการตี-มอนที่ผ่านกำหนด M4 แล้ว มี invariant ที่ pf-adversary เพิ่งแก้ไปหลายจุดในรอบ
`le2dox` (heals/STATE_COMPOSED_HEALING, unconsulted_rows, no_anchor_record ฯลฯ -- อ่านคอมเมนต์ยาวในไฟล์เอง)
🔴 ตัว `roster` เองไม่ใช่ปัญหา (แก้ข้างบนแล้ว: เส้นทางเดียว ตามครบแล้วจริง) แต่การกรอง roster ก่อนป้อนเข้า
`recompose_frames` ยังกระทบจุดอื่นที่รอบนี้ยังไม่ได้ตรวจ: `require_ledger_for_recompose`/`mob_ledger_admission`
รับ `roster` เดียวกันไปนับ `covered_count`/`roster_count` และ `_unconsulted_rows` เทียบ roster ที่ "ควรมี" ของ
ทั้งฉาก (`field_mobs.roster_for_scene_id`) กับ roster ที่ caller ส่งมา -- กรอง NPC ออกจาก roster ก่อนถึงจุดนี้
จะทำให้ NPC ที่ถูกกรองถูกนับเป็น "unconsulted" ทุกครั้ง (เตือนเท็จ) หรือกระทบเลข `ledger_covered`/`ledger_roster`
ที่พิมพ์ลงคอนโซล -- ยังไม่ได้อ่าน `mob_ledger_admission.py` และ `_unconsulted_rows` ให้ครบพอจะรู้ว่าใส่การกรอง
ตรงไหนถึงจะไม่ทำให้เลขพวกนี้ผิด เป็นความเสี่ยงที่ตรงกับเหตุผลที่ R247 ยกไว้กับ `RE-157`: อ่านไม่ครบพอจะมั่นใจ
ไม่ใช่บนความมั่นใจบางส่วน

## แผนจริงสำหรับรอบหน้า (ไม่ใช่ "รอ" เฉย ๆ)

รอบที่มีเวลาอ่าน `mob_ledger_admission.py` (โดยเฉพาะ `require_ledger_for_recompose`) และ `_unconsulted_rows`
ให้ครบว่าการกรอง NPC ออกจาก roster ก่อนป้อนเข้า `recompose_frames` จะกระทบเลขที่รายงานยังไงบ้าง แล้วค่อยทำ
ทั้งสามข้อในรอบเดียว (state store + จุดเขียน + ตัวกรอง) พร้อมเทสของตัวเอง + เทส round-trip ที่สาย GM ขอ
