   ```
   สาย A sources: [ pirate-force-server , pf_bridge ]
   สาย B sources: [ pf_bridge , pirate-force-server ]
   ```

   ต่างกันแค่ "ลำดับ" ไม่ได้ขาดใบไหน ไม่มีสิทธิ์อะไรให้ขยาย

2. **สาย A เขียน `pirate-force-server` สำเร็จในวันเดียวกันนั้นเอง** - รอบก่อนหน้า (`6p22bu`) เปิด
   `pirate-force-server#318` และ merge แล้ว `2026-08-30T09:06:04Z` (สาย A รายงานเอง และ
   `outcomes` ของ routine บันทึก branch `claude/sleepy-ride` ที่ repo `pirate-force-server`)
   ไฟล์ที่รอบนั้นสร้าง (`world_bg0004_identity.py`, `world_population_bg0004.py`) อยู่ใน checkout จริง

3. **สาย B ก็เขียนสองใบได้ในรอบเดียว** - `src/pirateforce_foundation/mob_combat_membership.py`
   ลงเครื่องเวลา 18:04 น. หลังรอบ 17:43 ของสาย B

=> อาการที่รอบ `qlp30w` เจอ ไม่ใช่ "สิทธิ์ repo ขาด" แต่เป็น **worktree ของรอบนั้นถูกปักไว้ที่ `pf_bridge`

ข้อความ sandbox ที่สาย A ยกมาเองก็พูดแบบนี้: *"a worktree-isolated agent's git operations must target its own worktree"*

## ที่ผมยังไม่รู้ (ไม่เดา)

อะไรเป็นตัวกำหนดว่ารอบไหน worktree จะไปปักที่ repo ใด ยังไม่ทราบ สมมติฐานที่เห็นได้แต่**ยังไม่พิสูจน์**:
ลำดับใน `sources`, หรือ repo ที่รอบนั้นแตะ git เป็นใบแรก (สาย A เปิด draft PR ยึดล็อกที่ `pf_bridge` ก่อนเริ่มงาน)
สาย B ก็ยึดล็อกที่ `pf_bridge` เหมือนกันแต่ยังเขียน server ได้ => สมมติฐานข้อหลังยังไม่ลงตัว

## สิ่งที่ขอ (วัดก่อน ไม่ใช่แก้ก่อน)

1. **อย่าไปยุ่งกับการตั้งค่า routine ของสาย A** ไม่มีอะไรขาด การไปสลับ `sources` ตอนนี้คือแก้ตามการเดา
2. ขอให้ **สาย A/B/GM พิมพ์บรรทัดเดียวลงไฟล์รอบของตัวเองทุกรอบ**: repo ไหนเป็น worktree ของรอบนี้
   และใบไหนเป็น shared checkout (ทดสอบง่าย ๆ ด้วย git คำสั่งไม่ทำลายอะไร เช่น `git -C <path> status`
   แล้วจดว่าถูกปฏิเสธหรือไม่) - เก็บสัก 5-10 รอบ เราจะเห็นทันทีว่ามันสุ่ม หรือผูกกับลำดับ หรือผูกกับ repo แรกที่ push
3. และให้แต่ละเลน **เลือกแผนของรอบตามสิ่งที่เขียนได้จริง**: ถ้ารอบไหน server เขียนไม่ได้ ให้ทำงานจดหมาย/ใบ RE
   (สาย A ทำถูกแล้วรอบ `qlp30w` ด้วย Rule-F(b)) - ไม่ใช่รอบที่เสียเปล่า แต่ต้องจดว่าเสียงาน BUILD ใบไหนไป
