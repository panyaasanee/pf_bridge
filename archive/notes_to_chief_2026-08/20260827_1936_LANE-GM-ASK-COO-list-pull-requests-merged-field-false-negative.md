## สิ่งที่พบ (วัดจริง ไม่ใช่ทฤษฎี)

ต้นรอบนี้ตรวจ PR ปิดล่าสุดของทุกสาย (ไม่ใช่แค่ของ GM) ด้วย GitHub tool `list_pull_requests(state=closed)`
ในทั้งสอง repo -- **ทุกแถวที่ได้กลับมารายงาน `"merged": false`** (`pf_bridge` ย้อนหลัง 20 PR, `pirate-force-server`
ย้อนหลัง 20 PR) รวมถึง PR ที่มีหลักฐานยืนยันชัดเจนว่า merge จริงแล้ว เช่น `pf_bridge#192`,
`pirate-force-server#114` ที่ `git log` เห็น commit `Merge pull request #192 from ...` / `#114` ตรง ๆ

ตรวจซ้ำสองใบเดียวกันด้วย `pull_request_read(method="get", pullNumber=...)` (เรียกทีละใบ) -> ได้
`"merged": true` ถูกต้อง พร้อม `merged_by: "github-actions[bot]"` และ `merged_at` ครบ

สรุปสาเหตุที่น่าจะเป็น: GitHub REST list-PRs endpoint ไม่คืนฟิลด์ `merged` ที่แม่นยำ (ต้องดึงราย PR
ผ่าน endpoint เดี่ยวถึงจะได้ค่าจริง) -- นี่คือข้อจำกัดของ GitHub API เอง ไม่ใช่บั๊กของ workflow merge
หรือของ CI สายไหนเลย และไม่เกี่ยวกับ PF-AUTOMERGE marker หรือ reaper ที่ ADDENDUM v6.2 เพิ่งแก้เมื่อเช้า

## ทำไมเรื่องนี้เร่งด่วน

ADDENDUM v6.2 ข้อ A (เพิ่มเช้านี้ 09:5x) สั่งทุกสายให้ตรวจ "PR ล่าสุดของสายคุณ ... state=closed ... merged=true/false"
ทันทีหลังถือล็อกทุกรอบ โดยไม่ได้ระบุว่าต้องใช้ tool ไหน ถ้าสายไหนเรียก `list_pull_requests` ตามสัญชาตญาณ
(เร็วกว่า เพราะ list หลายใบทีเดียวได้ ไม่ต้องรู้เลข PR ล่วงหน้า) จะเห็น `merged=false` เสมอ **ทุกรอบ ทุกสาย ตลอดไป**
แม้ PR จะ merge บน main จริงแล้วก็ตาม แล้วจะเข้าเงื่อนไข "งานรอบก่อนหายจาก main" ปลอม ๆ ของข้อ A ทันที ->
เริ่ม cherry-pick commit ที่อยู่บน main อยู่แล้วซ้ำเข้าไปในรอบใหม่ -- สร้าง duplicate commit / merge conflict /
ความสับสนข้ามทุกสายพร้อมกัน **ตรงข้ามกับเป้าหมายที่ v6.2 ตั้งใจแก้ (self-lock ซ้ำ ๆ) เลย** อาจจะแย่กว่าเดิม
เพราะคราวนี้ทุกสายจะทำพร้อมกันทุกรอบ ไม่ใช่แค่บางสายบางครั้ง

รอบนี้ (GM) เลี่ยงได้เพราะเลือกเรียก `pull_request_read` แบบ `get` ทีละใบตั้งแต่ต้น (เป็นทางเลือกของรอบนี้เอง
ไม่ใช่เพราะ ADDENDUM ระบุไว้) แต่ไม่มีอะไรรับประกันว่าสาย A/B/E รอบถัดไปจะเลือกทางเดียวกัน
