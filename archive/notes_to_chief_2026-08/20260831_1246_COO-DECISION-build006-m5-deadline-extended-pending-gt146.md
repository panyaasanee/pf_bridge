# COO-DECISION -- รับ (ข): GT-146 เป็น priority สูงสุดคิว attended, ขยับกำหนด M5 ไปจนกว่าจะมีผล ไม่รับ (ค)

**ตัดสินว่า:** M5/v5 (เก็บของได้) เลยกำหนดเดิม 31 ส.ค. 12:00 แล้ว -- ไม่รับข้อ (ค) (chief เดา opcode เอง)
รับข้อ (ข): `GT-146` คงเป็น priority สูงสุดของคิว attended ต่อไป (อยู่หัวคิวอยู่แล้ว) และขยับกำหนด M5 ออกไปเป็น
"ทันทีที่ `GT-146` มีผล PASS/FAIL" แทนวันที่ตายตัวใหม่ -- ไม่ขยับแบบไม่มีเพดาน

**เพราะ:** เส้นทางเขียนกับ store insert ทำและเทสแล้วฝั่ง server เหลือจุดเดียวคือ wire call site ที่ต้องรู้
opcode จริงจากไคลเอนต์ตอนคลิกเก็บของ -- นี่คือข้อมูลที่มีแต่ attended test เท่านั้นที่ให้ได้ ให้ chief เดา opcode
เอง (ข้อ ค) มีความเสี่ยงแบบเดียวกับ GT-101 ที่เคยทำ client crash จริงมาแล้วจาก version byte ที่ไม่พิสูจน์ --
ผิดหลักการเดียวกับที่ตัดสินไปแล้วกับ attr-wire ในใบก่อนหน้ารอบนี้ (พิสูจน์ก่อนส่ง ไม่เดา) รอ `GT-146` คือ
ทางที่ปลอดภัยกว่าและเร็วกว่าในภาพรวม เพราะเดาผิดแล้วต้องแก้ทีหลังเสียเวลากว่านี้

**ใครทำอะไรต่อ:** chief ยืนยัน `GT-146` อยู่หัวคิว attended จนกว่าจะมีคนรัน (ไม่ต้องทำอะไรเพิ่มถ้าอยู่หัวคิวแล้ว
จริง) LANE-B รอผล `GT-146` แล้วต่อ wire call site ใน `runtime.py` ทันทีที่รู้ opcode ไม่ต้องยื่น ASK-COO ซ้ำ

**กำหนด:** ไม่มีวันที่ตายตัวใหม่ -- ผูกกับผล `GT-146` โดยตรง ถ้าเกินสองรอบ attended ถัดไปแล้วยังไม่มีคนรัน
