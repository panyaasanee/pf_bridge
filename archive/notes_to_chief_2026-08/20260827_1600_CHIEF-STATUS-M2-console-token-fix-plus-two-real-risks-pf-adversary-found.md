## แก้แล้ว: token ไม่เคยขึ้นคอนโซลจริง (บั๊กจริง ไม่ใช่แค่ทฤษฎี)
`pf-adversary` พบว่าจุดเรียก `dispatch_columbus_quest3021` ใน `runtime.py` ส่ง `emit=self.events.append`
เฉยๆ (ต่างจากจุด login ที่ใช้ `emit=print` โดย default) — แปลว่า `SCENE_ENTRY .../COLUMBUS_QUEST3021_NO_
VEHICLE_DISPATCH` **ไม่เคยขึ้นคอนโซลจริงเลย** เว้นแต่บูตด้วย `--export-events` ทั้งที่ `GT-106`'s เอง
ต้องการเห็นบรรทัดนี้ก่อนเชื่อจอ แก้แล้ว (พิมพ์ + บันทึก event พร้อมกัน ตามรูปแบบเดิมของ `PLAYER_FACTION`
line) มีเทสยืนยัน stdout จริง (`test_the_scene_entry_and_no_vehicle_tokens_actually_reach_stdout`)

## ความเสี่ยงที่ยังแก้ไม่ได้วันนี้ — ต้องรู้ก่อนลองจริง ไม่ใช่ปิดบัง

**① ประตู FSM ฝั่งไคลเอนต์ที่ `RE-077` T3 เคยพินไว้ อาจปฏิเสธ TeleportVital เงียบ ๆ**
`RE-077` (ที่ chief อ้างเป็นหลักฐานว่า TeleportVital ใช้กับตัวละครที่ live อยู่แล้วได้) ตัวมันเองพินไว้ด้วยว่า
handler `0x005F14B0` **ยอมรับเฉพาะตอนไคลเอนต์อยู่ state `StateRunTime`/`StateNavigation`** — ทุกจุดที่โปรเจกต์
นี้เคยใช้ `make_login_teleport` มาก่อนอยู่หลัง `StartGameRes` เสมอ (state นั้นแน่นอน) จุดใหม่นี้ยิงทันทีหลัง
เลือกตัวเลือกบทสนทนา ซึ่งไม่มีใครวัดว่าไคลเอนต์อยู่ state ไหนตอนนั้น — ถ้าไม่ใช่ 2 state นั้น ไคลเอนต์อาจ
เพิกเฉยเงียบ ๆ (ไม่มี NAK ที่โปรเจกต์นี้เคยเห็น) เซิร์ฟเวอร์จะคิดว่าสำเร็จ (ไม่มี refusal event) ทั้งที่ผู้เล่น
ไม่ขยับ

**② ยิงได้แค่ครั้งเดียวต่อ connection ไม่มี retry ถ้าพลาด**
`columbus_quest3021_dispatch_attempted` ล็อกถาวรตั้งแต่ครั้งแรกที่ลอง (สำเร็จหรือไม่ก็ตาม) — เดิมไม่มีผล
เพราะ dispatch ปฏิเสธเสมออยู่แล้ว ตอนนี้ถ้าเฟรมเดียวที่ส่งจริงหายไปกลางทาง (แพ็กเก็ตหลุด หรือชน ① ข้างบน)
ผู้เล่นจะติดอยู่ที่เดิมถาวรจนกว่าจะ disconnect/reconnect ใหม่ — ไม่มี event บอกด้วยซ้ำ (เงียบสนิท)

**③ ชิ้น quest-gate-skip (จดหมาย 1545) อาจทำให้ทุกอย่างข้างบนไม่ถูกแตะเลยคืนนี้**
