# 1) ตารางฟิลด์ของ `0x005E5E30` (ทั้งฟังก์ชันยาว 83 ไบต์ ไม่มีสาขาอื่น)

รูปแบบเดียวกับทุกตัวในตระกูลนี้: `cmp BYTE PTR [esp+0x8],0` -> ไม่ศูนย์ = เขียน (`0x89A600`) · ศูนย์ = อ่าน (`0x89A640`)
**สองทางมีฟิลด์เหมือนกันเป๊ะ ลำดับเดียวกัน tag เดียวกัน len เดียวกัน**

| ลำดับ | tag | ฟิลด์ในอ็อบเจกต์ | len |
|---|---|---|---|
| 1 | `0x14` | `+0x14` | 4 |
| 2 | `0x08` | `+0x18` | 1 |

**จบแค่นี้ — ไม่มีฟิลด์ที่สาม ไม่มีลิสต์ ไม่มี sub-serializer ไม่มี mask**

# 2) โซ่หลักฐานที่ทำให้ชี้ vtable ตัวนี้ได้ (ทุกขั้นเป็น census ไม่ใช่การเดา)

**ขั้น 1 — จากชื่อไปยัง id global**
`0x00BEE5E0` (24 ไบต์): `push 0xF3093C` -> `call 0x89C080` -> `mov ecx,eax` -> `call 0x89BD00` -> `mov ds:0x0108202C, ax`
dword sweep ทั้งไฟล์: **`0x0108202C` ถูกอ้าง 2 จุดเท่านั้น** — `0xBEE5F3` (เขียน จุดเดียว) และ `0x5E46A2` (อ่าน จุดเดียว)

**ขั้น 2 — จาก id global ไปยัง getter**
`0x005E46A0` = `mov ax, ds:0x0108202C` + `ret` — **ยาว 7 ไบต์ ทั้งฟังก์ชัน** = virtual `GetId()` ของคลาสนี้

**ขั้น 3 — จาก getter ไปยัง vtable**
dword sweep ทั้งไฟล์หา `0x005E46A0`: **พบจุดเดียวคือ `.rdata:0x00F3006C`**

**ขั้น 4 — จัดเรียง vtable ด้วย marker ที่ยืนยันแล้วสามครั้ง**
vtable ของตระกูลโปรโตคอลนี้ยาว 8 ช่อง และมีฟังก์ชันร่วม `0x00401B20` อยู่ที่ **+0x08 เสมอ**
ยืนยันกับตัวที่เอกสารเดิมรู้จักอยู่แล้ว — `GSCN_RunTimeProtocolRes` vtable `0xF2FFC0`:

| slot | ค่า | เอกสารเดิมเรียกว่าอะไร |
|---|---|---|
| +0x08 | `0x401B20` | (ช่องร่วม) |
| +0x10 | `0x5E37C0` | getter สั้น |
| +0x18 | `0x5E3EE0` | **Serialize** ตรงกับใบสั่ง |
| +0x1C | `0x5E4060` | **inbound handler** ตรงกับใบสั่ง |

ในย่านของเรา `0x401B20` อยู่ที่ `0xF30064` ⇒ ฐาน vtable = `0xF30064 - 8` = **`0x00F3005C`**
และ `0x5E46A0` ตกที่ **+0x10** = ช่องเดียวกับ getter ของ Res เป๊ะ ✅

| slot | ค่า | ความหมาย |
|---|---|---|
| +0x00 | `0x005E4690` | getter ตัวชี้ (`mov eax,0x1081E64 ; ret`) |
| +0x04 | `0x005E7D80` | |
| +0x08 | `0x00401B20` | ช่องร่วม (marker) |
| +0x0C | `0x00716010` | |
| +0x10 | `0x005E46A0` | **GetId -> `ds:0x0108202C`** |
| +0x14 | `0x005EB0D0` | |
| +0x18 | `0x005E5E30` | **Serialize** |
| +0x1C | `0x005EF640` | **inbound handler** |

🟡 **ยืนยันความถูกต้องของการจัดเรียงอีกชั้น:** vtable ถัดไปที่ `0x00F30080` มี `0x401B20` ที่ `0xF30088` (+0x08 ✅)
และคู่ getter ของมันคือ `0x5E4740` (+0x00) กับ `0x5E4750` (+0x10) — ห่างกัน 0x10 เหมือนคู่ `0x5E4690`/`0x5E46A0` ของเรา

# 3) 🔴 handler ไม่ใช่ stub — vital ตัวนี้เดินสองทาง

`0x005EF640` เริ่มด้วย:

```
5ef640:  mov  al, BYTE PTR [ecx+0x18]     ; ฟิลด์ที่สองของ serializer
5ef643:  cmp  al, 0xfc  -> je  ... push 0x1f
5ef647:  cmp  al, 0xfd  -> je  ... push 0x03
5ef64b:  cmp  al, 0xfe  -> jne (ทางอื่น) / push 0x22
5ef659:  mov  ecx, DWORD PTR ds:0x01093198
```

⇒ **ไบต์ที่ `+0x18` เป็นรหัสผล/เหตุผลที่ฝั่งเซิร์ฟเวอร์ตอบกลับมา** และ client แปลค่า `0xFC`/`0xFD`/`0xFE` เป็นข้อความคนละใบ
⇒ `PickupTerrainThing` **ไม่ใช่ใบ request ทางเดียว** มันถูกใช้ทั้งขาส่งและขาตอบ

**คนที่สร้างอ็อบเจกต์คลาสนี้** (dword sweep หา vtable `0x00F3005C`): 3 จุด — `0x005E8FE8`, `0x005E905D`, `0x005EE612`

# 5) 🔴 nonclaims

- **ไม่ยืนยัน derived id `0x4543`** ที่เอกสารเดิมคำนวณจากแฮชชื่อ — id ตัวจริงมาจาก `0x89BD00` ตอนรันไทม์แล้วเก็บใน `ds:0x0108202C` ซึ่ง `.data` เป็นศูนย์ในไฟล์ ⇒ **static พิสูจน์เลข id ไม่ได้เลย ไม่ว่าจะพยายามแค่ไหน** · ใครอยากได้เลขจริงต้องอ่านตอนรัน
- **ไม่รู้ความหมายของ tag `0x14` และ `0x08`** — ใบนี้ยืนยันได้แค่ **len 4 กับ len 1** เท่านั้น
- **ไม่รู้ว่า `0xFC`/`0xFD`/`0xFE` แปลว่าอะไร** — รู้แค่ว่าแต่ละค่าไปหยิบข้อความคนละใบ (`0x1F`/`0x03`/`0x22`) จาก singleton `0x01093198`
- **vtable ระบุด้วยการจัดเรียงตาม marker ไม่ใช่ด้วย RTTI** — คลาสนี้ไม่มี RTTI · marker ถูกตรวจซ้ำสามครั้งอิสระ (Res ที่เอกสารเดิมรู้จัก + vtable ก่อนหน้า + vtable ถัดไป) แต่ **มันยังเป็นการอนุมานเชิงโครงสร้าง ไม่ใช่การอ่านป้ายชื่อ**
- **ไม่ได้พิสูจน์ว่า field `+0x14` คือ id ของวัตถุบนพื้น** — พิสูจน์แค่ว่ามันเป็น dword ที่เดินทางไปกับ vital ใบนี้
- ผลทั้งใบเป็น **ชั้น wire/static ล้วน** ห้ามอ้างเป็นหลักฐานชั้น client-observable
- **ไม่มีลูกมือมาเดินซ้ำ** — ทุกข้ออ้างแนบ span + sha256 ให้ re-derive เอง ถือว่ายังไม่ผ่านการตรวจแบบปฏิปักษ์
