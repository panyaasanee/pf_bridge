# ❓ คำถามระดับทิศทาง — **"เซิร์ฟเวอร์ของเรา" เป็นของเราจริงกี่เปอร์เซ็นต์**

🔴 **ใบนี้ไม่ใช่คำตัดสิน** เป็นคำถามที่ต้องขึ้นถึงเจ้าของตามกฎข้อ (ก) เปลี่ยนทิศทางปลายทางของโปรเจกต์
เจ้าของถามเองว่า *"v141 ห้ามแตะตลอดกาล แปลว่ามันศักดิ์สิทธิ์ หรือแปลว่ามันคือผลทดลองเก่าที่ยังไม่พิสูจน์ ห้ามเอาเป็นฐานของเวอร์ชันแรกของเราเอง"*
**คำถามนี้เปิดของที่กฎปัจจุบันยังไม่ครอบ**

---

## ① ตอบตามเอกสาร — ไม่ใช่ของศักดิ์สิทธิ์ และเราเขียนไว้เองแล้ว

`AGENTS.md` และ prompt ของ chief เขียนตรงกันว่า artifact มีสามชั้น:
1. **หลักฐานจริง** `GameClient.local.bin` + capture corpus — อ่านอย่างเดียวตลอดกาล
2. **`v141`** = **สมุดทดลองของ Codex** (AI ตัวก่อน) · *"เป็นงาน derive เหมือน `src/` ของเรา ต่างแค่เป็นสภาพ ณ จุดส่งมอบ"* · 🔴 **"ห้ามเรียกว่า original server"**
3. **งานปัจจุบัน** `src/` `tools/` `tests/` — แก้ได้ตามกติกา gate

> *"`v141 immutable` ยังอยู่ แต่เหตุผลคือ**เสถียรภาพของตัวเทียบ** ไม่ใช่**ความศักดิ์สิทธิ์ของหลักฐาน**"*

**ไม้บรรทัดที่งอได้ไม่ใช่ไม้บรรทัด** — คืน 25 ส.ค. เจอตัวอย่างจริง: `v141:6098 / 6107 / 6239` มี self-test ยืนยัน `population_indices == V112_TEST_INDICES` และ `len(population_pc) == 504` ⇒ ถ้าสาย A ไป "แก้" `v141` ให้ส่ง 115 เราจะ**เสียความสามารถในการพูดว่า "เฟรม 3 ตัวของเราตรงไบต์กับของที่เคยรันได้จริง"** ไปตลอดกาล

## ② 🔴 แต่คำถามของเจ้าของเปิดของที่ใหญ่กว่านั้น — **`v141` ไม่ได้วางอยู่เฉย ๆ มันคือเซิร์ฟเวอร์ที่กำลังรันอยู่**

ผมไปเปิดโค้ดจริงมา ไม่ได้ตอบจากความจำ:

```
src/pirateforce_foundation/app.py:675
    legacy = load_legacy(root/'current/pf_login_game_server_v141.py')

tests/test_foundation_legacy_seam.py หัวไฟล์ เขียนไว้เองว่า
    "The Foundation server is not an alternative to the frozen V141 scenario runner.
     app.py loads current/pf_login_game_server_v141.py and runtime.make_state_class
     returns a subclass of legacy.GameSessionState that calls super().dispatch()
     for everything it does not override."
```

⇒ **`src/` ของเราเป็น subclass ที่ override ไม่กี่จุด · ที่เหลือ `super().dispatch()` ตกไปให้ `v141` ทำ · `v141` มี 8,014 บรรทัด**
⇒ **"เวอร์ชัน 1 ของเรา" วันนี้ = `v141` + override ไม่กี่จุด ไม่ใช่เซิร์ฟเวอร์ของเราเอง**

🔴 และเทสของเราเองเตือนไว้ตรง ๆ แล้ว:
> *"A `runtime_pass` produced by a Foundation process therefore **does not imply that Foundation code produced the behavior**."*
> **เขียวไม่ได้แปลว่าโค้ดของเราเป็นคนทำ**

## ③ อันตรายที่ตามมา และมันไม่ใช่เรื่องทฤษฎี

`v141` มีสองชนิดปนกันอยู่ และไม่มีใครติดป้ายแยก:
- ส่วนที่ **data-backed** — พิกัด placement, แถวจาก `MOBS`, ค่าที่ derive จาก `MARKER1`
- ส่วนที่เป็น **composition ที่ Codex เดา** — เอาของที่พิสูจน์แยกกันสองชิ้นมาต่อกัน โดยไม่มีหลักฐานว่าเซิร์ฟเวอร์ต้นฉบับต่อแบบนั้น

**อย่างหลังคือ 9 ใบ `expired_pending_decision` ที่ COO เพิ่งปิดไปเมื่อ 01:45 พอดี** — chief สรุปรูปแบบร่วมของทั้ง 9 ใบไว้เองว่า *"ต่อของที่พิสูจน์แยกกันสองชิ้นเข้าด้วยกัน แล้วขาดชิ้นเดียวกันหมดคือหลักฐานว่าเซิร์ฟเวอร์ต้นฉบับทำแบบนั้นจริง"*

⇒ **การพึ่ง `v141` โดยไม่ติดป้าย = การนำเข้าสมมติฐานของ Codex มาเป็นข้อเท็จจริงของเรา** และเราจะไม่รู้ตัว เพราะมันอยู่ใต้ `super().dispatch()` ที่ไม่มีใครอ่าน

## ④ ช่องว่างในกฎ พูดให้ตรง

กฎปัจจุบันเขียนว่า **"ห้ามแก้ `v141`"** — แต่**ไม่เคยเขียนว่า "ห้ามพึ่ง `v141`"**
สองอย่างนี้ต่างกันมาก และตอนนี้เรา **พึ่งมันเต็มตัว** โดยที่กฎไม่ได้ห้าม และไม่มีใครวัด

## ⑤ 🔴 สิ่งที่ผมขอให้เจ้าของเคาะ — ผมไม่ตัดสินเอง

**ผมไม่เสนอให้เลิกใช้ `v141`** การรื้อ 8,014 บรรทัดตอนที่ `M1` ยังไม่ลง คือการฆ่าโครงการเพื่อความบริสุทธิ์
**ผมเสนอให้เริ่มวัดมัน** — เพราะของที่ไม่ถูกวัด จะไม่มีวันถูกทวงคืน

> **ตัวชี้วัดใหม่ `OWN_BEHAVIOR_RATIO`** — สัดส่วนพฤติกรรมที่ **โค้ดของเราเป็นคนทำ** เทียบกับที่ **ตกไปให้ `v141` ทำ**
> วัดจาก: จำนวน dispatch path ที่ `runtime.make_state_class` override จริง หารด้วยจำนวน path ทั้งหมดที่ `legacy.GameSessionState` มี
> รายงานเป็นตัวเลขในรอบผู้บริหารทุกวัน **ข้าง ๆ `production_allowed 9/53`**

**ทางเลือกที่ผมเห็น สามทาง — เจ้าของเลือก:**

| ทาง | ความหมาย | ราคา |
|---|---|---|
| **ก** เก็บ `v141` เป็นรากถาวร override ไปเรื่อย ๆ | เร็วที่สุด ได้ `M1`–`M6` ตามกำหนด | **"เซิร์ฟเวอร์ของเรา" จะไม่มีวันเป็นของเราเกิน ~20%** และสมมติฐานของ Codex ฝังอยู่ตลอดไป |
| **ข** เก็บไว้ แต่**วัดและทวงคืนทีละ path** | ได้ไมล์สโตนตามกำหนด และตัวเลขขยับขึ้นทุกสัปดาห์ | ต้องมีคนทำงาน "ย้าย path" ควบคู่ไปกับงานฟีเจอร์ · **ผมเชียร์ทางนี้** |
| **ค** รื้อออกก่อนปล่อย `v1` | `v1` เป็นของเราจริง 100% | **`M1`–`M6` เลื่อนหมด** และผมคัดค้าน เพราะยังไม่มีใครรู้ว่า 8,014 บรรทัดนั้นทำอะไรบ้าง |

🔴 **ไม่ว่าจะเลือกทางไหน มีอย่างหนึ่งที่ต้องทำทันทีและไม่ขึ้นกับการเลือก:**
**`SERVER_VERSIONS.md` ทุกเวอร์ชันต้องมีบรรทัดที่บอกว่า "ฟีเจอร์นี้โค้ดเราทำ" หรือ "ฟีเจอร์นี้ `v141` ทำ"**
ไม่งั้นเราจะประกาศ `v1` โดยไม่รู้ว่ากำลังประกาศงานของใคร

## ⑥ nonclaims
- ผม **ไม่ได้อ้างว่า `v141` ผิด** — อ้างว่ามันเป็นงาน derive ชั้นเดียวกับเรา จึงไม่มีอำนาจเป็นหลักฐาน
- ผม **ไม่ได้วัด `OWN_BEHAVIOR_RATIO` จริง** ในใบนี้ — ตัวเลข ~20% ในตาราง ⑤ เป็น **`[เสนอ]` ไม่ใช่ `[วัดแล้ว]`** มาจากการที่ `runtime.py` override ไม่กี่จุดเทียบกับ 8,014 บรรทัด · **ต้องวัดจริงก่อนใช้อ้างอิง**
- คำว่า "เคยรันได้จริง" ที่ผมใช้กับ `v141` มาจากการที่มันเป็น **สภาพ ณ จุดส่งมอบของ Codex** ไม่ใช่จากการที่ผมเห็นมันรันสำเร็จเอง
