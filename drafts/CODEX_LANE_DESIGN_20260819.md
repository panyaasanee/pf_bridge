# 🏭 ข้อเสนอ: ให้ Codex เป็น "เลนโรงงานหลักฐาน" แทนการสลับกะ

**สถานะ:** ข้อเสนอรอ Panya เคาะ · เขียน 2026-08-19 ~12:0x โดยเซสชันหลัก (มือเขียนแทน)
**โจทย์จาก Panya:** ไม่อยากสลับกะเพราะกลัวงานไม่ต่อเนื่อง / เดินกันคนละแบบ / ต้องมานั่งจูนกลับ ·
Codex Pro x20 รันได้ 24 ชม. × 3 วัน/สัปดาห์ · ช่วงนั้นตรงกับตอนที่ **Claude หมดโควตารายสัปดาห์ (นิ่งสนิท)**
**การเข้าถึงที่เคาะแล้ว:** **Codex CLI บนเครื่อง Panya** (แตะไบนารีได้ ไม่ต้องอัปโหลดอะไรขึ้นคลาวด์)

---

## 1) หลักคิด: แบ่งงานตาม **ชนิดงาน** ไม่ใช่แบ่งตาม **เวลา**

การสลับกะล้มเหลวเพราะทั้งสองฝ่ายแตะ **"บันทึกของโปรเจกต์"** (ledger / matrix / CHIEF_CONTINUATION /
คิวเทส) ซึ่งเป็นที่อยู่ของ *ความต่อเนื่อง* — พอสองสมองตีความบันทึกเดียวกันคนละแบบ ก็ต้องมาจูนกัน

**ข้อเสนอ: Codex ไม่ใช่ "ผู้บันทึก" แต่เป็น "ผู้ผลิตหลักฐาน"**

| | chief (Claude) | **Codex** | ผู้เทส attended (Claude) |
|---|---|---|---|
| ตัดสินใจ/ตีความ/เล่าเรื่อง | ✅ เจ้าของ | ❌ **ห้าม** | ❌ |
| เปิด hypothesis · flip matrix · เขียน ledger | ✅ เจ้าของ | ❌ **ห้าม** | ❌ |
| เขียน CHIEF_CONTINUATION / GAME_TEST_QUEUE | ✅ เจ้าของเดียว | ❌ **ห้าม** | ❌ (ใช้กล่องจดหมาย) |
| **กวาดไบนารี / สร้าง byte guards / เขียนเครื่องมือ + เทส** | ทำได้ | ⭐ **เจ้าของ** | ❌ |
| รัน gate ซ้ำ ๆ / soak / headless replay ทุก scenario | ทำได้ | ⭐ **เจ้าของ** | ❌ |
| ขับ UI เกมจริง | ❌ | ❌ **ห้าม** | ⭐ เจ้าของ |

⇒ Codex ได้งานที่ **ยาว น่าเบื่อ ตรวจด้วยเครื่องได้ และไม่ต้องอ่านประวัติศาสตร์ของโปรเจกต์**
ซึ่งพอดีกับ 24 ชั่วโมงที่มันรันได้ และพอดีกับสิ่งที่กินเวลา/คอนเท็กซ์ของ chief มากที่สุดตอนนี้

## 2) กลไกกัน drift 6 ชั้น (นี่คือหัวใจที่ตอบความกลัวของ Panya)

1. **Order แบบจบในตัว** — Codex อ่าน *ใบสั่งงานใบเดียว* ไม่ต้องอ่าน continuation 64KB
   ⇒ มันไม่มีโอกาสตีความประวัติศาสตร์ผิด เพราะมันไม่ได้อ่านประวัติศาสตร์เลย
2. **ห้ามแตะบันทึก** — เขียนได้เฉพาะ `tools/` `tests/` `reports/` ของงานตัวเอง + `HANDBACK.md`
3. **ต้องทวนคำตอบที่รู้อยู่แล้วก่อน** (กฎเดิมของโปรเจกต์) — เครื่องมือที่ยังไม่เคยถูกเช็คกับคำตอบที่รู้
   = เครื่องผลิตข้อความน่าเชื่อ · ทุก order ระบุ "known answers" ที่ต้อง reproduce ให้ตรง
4. **ต้องมี trap test** — เทสที่พิสูจน์ว่า guard แดงได้จริงเมื่อของผิด
5. **แยก branch** `codex/ORD-xxx` — ห้าม commit ลง main · chief เป็นคน merge ⇒ **main ยังเป็นเส้นเดียว**
6. **คำศัพท์ล็อกไว้** — 3 ชั้นของ artifact / สองชั้นหลักฐาน / ต้องมี nonclaims / **ห้ามใช้คำว่า
   "original server"** — เขียนไว้ในสัญญาที่ Codex อ่านทุกครั้ง

## 3) 🔴 ปัญหาที่ต้องแก้ก่อนปล่อย Codex เข้ามา (เจอตอนตรวจวันนี้)

**`Pirate Force ServerProject\AGENTS.md` = ไฟล์ที่ Codex CLI อ่านอัตโนมัติทุกครั้งที่เริ่ม —
และตอนนี้มันล้าสมัยหนัก** ยังชี้ให้อ่าน `STATUS.md` + `docs/EXPERIMENT_LEDGER.md` (เอกสารยุค Codex)
ยังเขียนว่า **"V140 คือ checkpoint ล่าสุด"** และยังพูดถึงระบบ lease `docs/AI_WORKSPACE_LEASE.json`
ที่เราเลิกใช้ไปแล้ว (เราใช้ `LOCK_GAME.txt` / `LOCK_GIT.txt`)

⇒ **ถ้าปล่อย Codex ตอนนี้ มันจะ drift ตั้งแต่วินาทีแรกโดยไม่ใช่ความผิดมัน**
⇒ งานแรกสุดของเลนนี้คือ **เขียนหัว AGENTS.md ใหม่** ให้ชี้มาที่ระบบปัจจุบัน + ระบบใบสั่งงาน
(ผู้เทสร่างให้แล้วใน `pf_bridge\codex_orders\README.md` — ให้ chief เป็นคน commit ทับ AGENTS.md)

## 4) ระบบใบสั่งงาน (พร้อมใช้แล้ว)

```
pf_bridge\codex_orders\
├── README.md          <- สัญญา + template (Codex อ่านไฟล์นี้ก่อนทุกครั้ง)
├── READY\             <- ใบสั่งที่ chief เตรียมไว้ Codex หยิบเรียงตามเลข
├── DOING\             <- Codex ย้ายมาที่นี่ตอนเริ่ม (= สัญญาณชีพ)
├── DONE\              <- Codex ย้ายมาพร้อม HANDBACK.md
└── DIGEST.md          <- append-only บรรทัดเดียวต่อ order (Claude กลับมาอ่านไฟล์เดียวจบ)
```

**กติกาเติมคิว:** chief ต้องรักษา `READY\` ให้มี **≥ 6 ใบเสมอ** (≈ 24 ชม.ของ Codex) และ
**ก่อนโควตา Claude จะหมด ต้องเติมให้เต็ม 12–18 ใบ** (≈ 3 วัน) — นี่คือการเปลี่ยนแปลงเชิงปฏิบัติข้อเดียว
ที่ต้องเพิ่มใน prompt ของ chief ถ้า Panya เอาแผนนี้

## 5) ตอน Claude กลับมา (ต้นทุนการ "จูนกลับ" ที่ตั้งใจให้เกือบเป็นศูนย์)

1. chief อ่าน **`DIGEST.md` ไฟล์เดียว** (บรรทัดละ order: id · verdict · ไฟล์ · เทสที่เพิ่ม · ธงแดง)
2. chief review + merge branch `codex/*` ทีละใบ → **แล้วค่อยเป็นคนตัดสินว่าจะเปิด hypothesis /
   flip matrix / เข้าคิวเทสไหม** ⇒ การตีความยังอยู่ในมือเดียวตลอด
3. ถ้า order ไหน Codex ทำผิดทาง → ทิ้ง branch นั้น เสียแค่ใบเดียว ไม่กระทบ main

## 8) ความเสี่ยงที่เหลือ (พูดตรง ๆ)

1. **Codex อาจ "ทำเสร็จ" แบบผ่านเทสแต่ตอบผิดคำถาม** — กันด้วยข้อ "ต้อง reproduce known answers"
   แต่กันได้ไม่ 100% ⇒ chief ต้อง review ก่อน merge เสมอ (นี่คือค่าใช้จ่ายที่ยอมจ่าย)
2. **72 ชั่วโมงไม่มีใครดู** — ถ้ามันติดใบเดียวแล้ววนซ้ำ จะเสียทั้งวินโดว์
   ⇒ กันด้วยกฎ **"ติดเกิน 2 ชั่วโมงต่อ order ให้เขียน BLOCKED ใน HANDBACK แล้วข้ามไปใบถัดไป"**
3. **ยังไม่มี backup นอกเครื่อง** — ถ้าอยากปล่อย Codex รันยาว 3 วัน **ควรมี remote/backup ก่อน**
   (ข้อนี้ค้างมาตั้งแต่ก่อนแล้ว และเป็นความเสี่ยงที่ใหญ่ขึ้นเมื่อมีตัวเขียนงานเพิ่ม)
