  `SkillGrantStore`, `_GRANT_SOURCE`) ตัดคำว่า "ยังไม่จริง"/"not-yet-real" ออกทั้งหมด ให้ตรงกับความจริงว่า
  `store.grant_learned_skill` อยู่บน main แล้ว โค้ดฟังก์ชันไม่ต้องแก้อะไรเลย (arity ตรงกันมาตั้งแต่ `#866`)

## pf-adversary — เจอจริง แก้แล้ว

สั่งต้นรอบด้วย `Agent` tool (`subagent_type: pf-adversary`) ตรวจ diff ใน worktree แยก (`mktemp -d`, ไม่แตะ
ของจริง) — **เจอข้อบกพร่องจริงหนึ่งจุด**: เทส `test_regranting_dedups_on_the_real_grant_door_only` เวอร์ชัน
แรกเช็คแค่ "จำนวนแถวยังเป็น 1" หลัง regrant ซึ่งพิสูจน์ไม่ได้ว่า `INSERT OR IGNORE` ทำงานจริง — `INSERT OR
REPLACE` (บั๊กสมมติ) ก็ให้แถวเดียวเหมือนกันแต่จะเปลี่ยน `id`/`granted_at` แบบเงียบ ๆ (บั๊กชนิดเดียวกับที่
`grant_starting_skills`'s docstring เตือนไว้เอง และมีเทสกันไว้แล้วสำหรับประตูนั้น แต่ `grant_learned_skill`
ยังไม่มี) adversary พิสูจน์ด้วยการสลับ `OR IGNORE` เป็น `OR REPLACE` ใน `store.py` จริง แล้วเทสเดิมผ่านทั้งหมด
ไม่จับ

แก้แล้ว: เพิ่ม assertion เทียบ `(id, granted_at)` ก่อน/หลัง regrant ต้องเท่ากันเป๊ะ ทดสอบซ้ำด้วย mutation
เดียวกัน (`OR IGNORE` → `OR REPLACE`) ยืนยันว่าเทสที่แก้แล้ว **จับได้จริง** (`AssertionError: (1, ...) !=
(2, ...)`) แล้วคืน `store.py` กลับที่เดิม (`git diff --stat src/pirateforce_foundation/store.py` = ว่าง
หลังคืน) — โค้ดจริงที่ merge แล้ว (`INSERT OR IGNORE`) ถูกต้องอยู่แล้ว จุดอ่อนอยู่ที่ "ความแข็งของเทส" ไม่ใช่
บั๊กใน production

adversary ตรวจอีก 5 ข้อที่สั่งไป (real path ถูกเรียกจริง / schema ตรง / persistence ข้าม reopen ไม่ได้แชร์
connection / ไม่มี docstring ค้าง / ไม่มี side effect จาก `import sqlite3`) — สะอาดทุกข้อ พิสูจน์ด้วย mutation
(สลับ argument order, เปลี่ยนค่า source) จับได้ทั้งคู่

**ไม่มี `ADVERSARY_PENDING`** — ผลคืนก่อน push รอบสอง (คอมมิตแรก push ไปก่อนตามกฎ stop-hook ของเครื่องมือ ผล
adversary กลับมาทีหลัง แก้แล้ว push commit ที่สอง)
