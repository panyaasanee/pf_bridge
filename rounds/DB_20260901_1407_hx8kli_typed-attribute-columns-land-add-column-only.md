## ทำอะไรรอบนี้

### 1. `migrations/006_character_typed_attribute_columns.sql` — 21 คอลัมน์ ไม่มี UPDATE แม้บรรทัดเดียว

เพิ่ม typed column ลง `characters`: `level` `hp_current` `hp_max` `mp_current` `mp_max`
**`speed_walk`** `class_id` `skill_points` `unspent_points` `stat_str/con/dex/int/per`
`experience` `cash` `bonus_str/con/dex/int/per` ⇒ ครบ 22 ฟิลด์ที่ใบ `1100`/`1325` ให้ DB ถือ
(`name` มีอยู่แล้วตั้งแต่ `001_initial.sql`)

สามข้อที่ตั้งใจออกแบบให้เป็นแบบนี้ ไม่ใช่บังเอิญ:

- **`ADD COLUMN` ล้วน** ไม่มี UPDATE/DELETE/INSERT/DROP/rebuild — เพราะ `CORE-REQUEST-DB-001`
  ยังไม่มีคำตอบ ⇒ ยังไม่มี boot path ไหนเรียก `migrate_with_backup` ⇒ บน canonical DB ของเจ้าของ
  ไฟล์นี้วิ่งผ่าน `migrate()` ที่ไม่มี snapshot ⇒ ข้อห้ามของเจ้าของ (ใบ `1112` ข้อ 3) บังคับให้
  migration นี้ห้ามแตะแถวเดิม **มีเทสพาร์ซไฟล์ .sql ทีละคำสั่งเพื่อพิสูจน์ข้อนี้** ไม่ใช่คำรับรอง
- **ทุกคอลัมน์ nullable ไม่มี DEFAULT** — `NOT NULL` ต้องมีค่าคงที่ และบนตัวละครจริงค่าคงที่นั้นคือ
  ค่าที่เซิร์ฟเวอร์แต่งขึ้นซึ่งอ่านกลับมาแล้วแยกไม่ออกจากค่าที่วัดมา NULL แยกออก
- **NULL ถูกตัดทิ้ง ไม่ถูกแปลงเป็น 0** — `read_typed_attributes` ไม่คืนคอลัมน์ที่เป็น NULL เลย
  ⇒ ฟิลด์ที่ยังไม่มีค่าไปถึงประตู `persistence_attr_compose` ในสภาพ "ไม่มี" แล้วมันปฏิเสธเอง
  ตามกฎของมันเอง กฎ "ห้ามเดาเป็นศูนย์" ของเจ้าของ (ใบ `1059`) จึงเป็นสมบัติของสคีมา ไม่ใช่วินัย

**การแคบลงสองข้อที่พูดออกมาตรง ๆ ไม่ซุกไว้**: (ก) ฟิลด์ u64 (`experience` `cash`) ถูก CHECK ไว้ที่
2^63-1 ไม่ใช่ 2^64-1 เพราะ INTEGER ของ SQLite เป็น signed 64-bit ไม่มีที่ให้ครึ่งบน — เป็นสมบัติของ
เครื่องมือ ไม่ใช่ทางเลือก (ข) `speed_walk` เก็บใน REAL 8 ไบต์ CHECK ไว้ที่ช่วง float32 จริง
แต่ double ในช่วงนั้นยังละเอียดกว่า f32 บนสาย — encoder เป็นคนปัด

### 2. `persistence_typed_attrs.py` + สอง method ใหม่ใน `store.py`

โมดูลใหม่ถือคำอธิบายคอลัมน์ชุดเดียวในฝั่ง python (คอลัมน์ไหนรับใช้ฟิลด์ x ไหน · ช่วงค่าของ wire

### 4. pf-adversary 11 ข้อบกพร่อง — แก้ 9 ตอบ/ติดป้าย 2

เรียก pf-adversary ก่อน commit ตามกติกา ผู้ตรวจ **วัดมาแสดงทุกข้อ** (รันเทสในเวิร์กทรีทิ้ง) ไม่ใช่ทักท้วง
สี่ข้อที่หนักที่สุด:

1. 🔴 **เทสที่ปักช่วงค่าของ CHECK เป็นละคร — และผู้ตรวจพิสูจน์ด้วยการทำจริง** เทสเดิมใช้
   `assertIn(str(bound), statement)` คือหา **สตริงย่อย** ผู้ตรวจแก้ `stat_str BETWEEN 0 AND 65535`
   เป็น `BETWEEN -1000 AND 65535` (คำว่า `"0"` อยู่ใน `"-1000"`) และ `bonus_per` เป็น
   `AND 655350` (`"65535"` อยู่ใน `"655350"`) แล้วรัน suite เต็ม → **เขียวเป๊ะเท่าเดิมทุกตัวเลข**
   17 จาก 21 คอลัมน์ไม่มีอะไรคุ้มครองเลย **แก้แล้ว**: พาร์ซตัวเลขออกมาจาก `BETWEEN ... AND ...`
   แล้วเทียบเป็น **จำนวน** ไม่ใช่สตริง · **วัดหลังแก้: รัน mutation สองอันเดิมของผู้ตรวจ → แดงทั้งคู่**
2. 🔴 **คำอ้าง "ค่าที่รอดสายไม่ได้ เก็บไม่ได้" ผิด และผิดในทิศที่ระบบนี้ตั้งมาเพื่อกันโดยเฉพาะ**
   ผู้ตรวจวัด: `speed_walk = 1e-300` ผ่าน `validate` ผ่าน CHECK อ่านกลับมาได้ `1e-300` แต่
   `struct.pack("<f", ...)` (บรรทัดที่ `gm/attr_wire.py:288` ใช้จริง) ให้ **`0.0` เป๊ะ** และบนสายนี้
   `0.0` คือ *ค่า* ไม่ใช่ *ความว่าง* (`tests/test_npc_gait_wire.py` มีเทสชื่อ
   `test_zero_speed_is_still_serialized_because_only_none_means_absent`) ⇒ ศูนย์ต้องห้ามของเจ้าของ
   เดินเข้ามาทางเลขคณิต แทนที่จะเข้ามาทาง `.get(x, 0)` **แก้แล้วสองชั้น**: (ก) `validate` ปัดค่า f32
   ผ่าน `struct` ก่อนเก็บ ⇒ เลขใน DB กับเลขบนสายเป็นเลขเดียวกันโดยโครงสร้าง (`400.1` เก็บเป็น
   `400.1000061035156`) (ข) ค่าที่ไม่ใช่ศูนย์แต่ underflow เป็น `0.0` ถูก **ปฏิเสธ** ที่การเขียน
   *(ข้อนี้ตอบ "คำถามเดียวที่ดีไซน์ยังไม่ตอบ" ของผู้ตรวจด้วย: ตอนนี้ค่าที่เก็บ = ค่าที่ส่ง)*
3. 🔴 **`write_typed_attributes` commit สำเร็จแล้วโยน `KeyError` ได้** เพราะอ่านสถานะกลับบน
   คอนเนกชันใหม่ *หลัง* transaction ปิดไปแล้ว ผู้ตรวจแทรก soft-delete เข้าไปในช่องนั้นแล้ววัดได้ว่า
   เมธอดเขียนลงดิสก์จริง (`level=42`) แล้วโยน `KeyError` — ผู้เรียกที่จับ `KeyError` จะรายงานว่า
   "ไม่มีตัวละครนี้" ทั้งที่แถวเปลี่ยนไปแล้ว · และค่าที่คืนมาอาจเป็นค่าของ **คนอื่น** ที่เขียนแทรกเข้ามา
   **แก้แล้ว**: อ่านกลับ **ในทรานแซกชันเดียวกัน** บนคอนเนกชันเดิม + เทสที่ทำให้เส้นทางเดิมระเบิด
