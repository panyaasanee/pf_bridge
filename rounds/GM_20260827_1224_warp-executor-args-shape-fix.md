# รอบ nzt815 -- LANE-GM: ปิดช่อง args-shape ของ `gm/warp_executor.py` (2026-08-27 12:1x-12:2x +07:00)

## บริบท

รอบ 1600 (say-wire frame builder) ทิ้งรายการ "ค้าง (ตั้งใจ ไม่บล็อก)" ไว้หนึ่งข้อที่ทำได้ทันทีในเขตเขียนของสายนี้เอง
โดยไม่ต้องรอ RE/chief/COO: `gm/warp_executor.py` มีช่องโหว่แบบเดียวกับที่ `gm/say_wire.py` เพิ่งแก้ไปในรอบเดียวกัน --
`command.args` ถูกวัดขนาด/index ด้วย `len()`/`[0]`/`[1]`/`[2]` เปล่า ๆ ซึ่งจะโยน `TypeError`/`KeyError`/`IndexError`
ดิบ ๆ แทนที่จะเป็น `WarpExecutorError` ของโมดูลเอง เมื่อ `args` มี "รูปร่าง" ผิด (`None`, `set`, `dict`) ไม่ใช่แค่
"ค่า" ผิด

## ทำอะไรไปบ้าง

1. **แก้ตามที่ค้างไว้**: ห่อ `len(command.args)` และการ index สามตำแหน่งด้วย try/except ให้แปลงเป็น
   `WarpExecutorError` เหมือน `say_wire.py`
2. **ส่งให้ pf-adversary ตรวจก่อน commit** (ตามกติกาที่ไม่เปลี่ยน) -- เจอสองช่องที่ pattern แบบ
   `say_wire.py` (catch สามชนิดเจาะจง) เองก็ยังเปิดอยู่ พิสูจน์ได้จริงด้วยการรันสด:
   - object ที่ `__len__`/`__getitem__` โยน exception นอกเหนือจากสามชนิดนั้น (เช่น `AttributeError`,
     `ValueError`) ยังหลุดผ่าน `WarpExecutorError` ไปได้ -- ขัดกับคำมั่นในตัว docstring เอง
   - `str`/`bytes` ความยาว 3 (เช่น `"123"`) ไม่ crash เลย เพราะ `len()==3` และ index ได้ตามปกติ ->
     ถูกอ่านเป็น `(scene_id, x, y)` จริงอย่างเงียบ ๆ ทั้งที่ไม่ใช่รูปร่างที่ตั้งใจรับ
3. **แก้ทั้งสองช่องภายในรอบเดียวกัน** (ไม่ทิ้งเป็นค้างอีก เพราะราคาถูกและอยู่ในเขตเขียนของตัวเองอยู่แล้ว):
   - เปลี่ยน catch เป็น `except Exception` ทั้งสองจุด (กว้างขึ้นโดยตั้งใจ เพราะ `args` เป็นของที่ผู้เรียก
     ควบคุมได้เต็มที่ตามนโยบาย "รับ `GmCommand` ไม่ว่าจะมาจากไหน" ที่ `docs/GM_LANE.md` ประกาศไว้เอง)
   - เพิ่ม `isinstance(args, (str, bytes))` ปฏิเสธตั้งแต่ต้น ก่อนถึง try/except ใด ๆ
4. เพิ่มเทส 4 ข้อใหม่ใน `tests/test_gm_warp_executor.py` ครอบทั้งสี่กรณีที่ pf-adversary เจอ
5. บันทึกไว้ใน `docs/GM_LANE.md` ว่า `gm/say_wire.py` มีช่องเดียวกันสองข้อนี้เหมือนกัน แต่ไม่ได้แก้รอบนี้
   (นอกเขตของ diff รอบนี้ -- ไม่ได้แตะ `say_wire.py` เลย) ติดป้ายเป็นค้างสำหรับรอบถัดไป
