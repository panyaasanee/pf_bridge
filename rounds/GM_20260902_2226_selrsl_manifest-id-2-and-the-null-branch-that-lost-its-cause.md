## 3. งานที่ 1 — `plugin_image_check` รัดเป็น RT_MANIFEST id 2 (`COO 2147` ข้อ 2)

**สิ่งที่พังก่อนหน้านี้:** ฟังก์ชันตอบว่า "มี RT_MANIFEST อยู่ใน resource directory ชั้นบนสุดไหม"
แต่ activation context ของ **DLL** สร้างจาก resource id **2** (`ISOLATIONAWARE_MANIFEST_RESOURCE_ID`) เท่านั้น
⇒ manifest ที่ฝังมือไว้ที่ id 1 (id ของ EXE ซึ่งคือสิ่งที่ `mt.exe -outputresource:GameMaster.dll;1` เขียน)
เคยได้ `image_ok` แล้วยังโดน loader ตอบ **14001** อยู่ดี — ไฟเขียวบนไฟล์ที่รันไม่ได้ คือรูปที่แย่ที่สุดที่โมดูลนี้ผลิตได้

**สิ่งที่ทำ:**
- `_manifest_resource_ids()` เดินลง subdirectory ของ type entry 24 แล้วคืน "ทุก id ที่อยู่ใต้ RT_MANIFEST"
- `_resource_entries()` อ่านตารางเดียวแบบมีขอบ (บนสุดและชั้น id ใช้ตัวเดียวกัน ไม่มี recursion ไม่มีทางวน)
- `has_embedded_manifest` = `2 in ids` · `PeFacts.manifest_resource_ids` เก็บ id ไว้ให้ข้อความบนจอแยกสองรูปได้
- ข้อความ FAIL แยกสองทาง: "ไม่มี manifest เลย → rebuild ด้วย revision 5" กับ "มี manifest ที่ id 1 → ฝังใหม่ที่ `;#2`" พร้อมคำสั่งเต็ม
- โทเคนคอนโซล: `embedded_manifest=no manifest_ids=1` ⇒ **แยกสองรูปได้จาก log อย่างเดียว ไม่ต้องมีไฟล์ในมือ**
- type entry ที่ชี้ตรงไปยัง data (ไม่มีชั้น id) = ไม่นับเป็น manifest — `mt.exe` ผลิตรูปนั้นไม่ได้ และ loader ไม่มีอะไรให้จับคู่กับ id 2

**ทำไมนี่ไม่ใช่ false red ตัวใหม่ (สำคัญกว่าตัวโค้ด):** DLL ตัวเดียวที่ **มีคนวัดว่าโหลดได้จริง** บนเครื่องเจ้าของ
(ka1-A, attended `GT-207` build 1) ถูกฝังด้วย `-outputresource:GameMaster.dll;#2` = **id 2**
และ `build_vs2008.bat` revision 5 ฝังที่ `;#2` และอ่านกลับที่ `;#2` ⇒ ทุกเส้นทางที่มีคนเดินจริงยังเขียวเหมือนเดิม
ที่กลายเป็นแดงคือ hand-embed ผิด id ซึ่ง**แดงอยู่แล้วตอนโหลด** เราแค่เลิกโกหกว่ามันเขียว

**nonclaim:** อ่าน resource **tree** ไม่ได้อ่าน **เนื้อ XML** ของ manifest · entry ที่ id 2 แต่ประกาศเวอร์ชัน assembly ผิด
ยังนับว่า "มี" ที่นี่ — ไม่มีใครวัดรูปนั้น จึงไม่มี verdict ไหนอ้างถึงมัน · และโมดูลนี้ยังไม่เคยถูกรันกับ `GameMaster.dll` จริงในโคลนนี้

## 4. งานที่ 2 — `find_mt.bat` ข้อความ FAIL ต้องบอกทางออกจริง (`COO 2147` ข้อ 2)

เดิมจบด้วย "ถ้าของคุณอยู่ที่อื่น เอาโฟลเดอร์ใส่ PATH แล้วรันใหม่" ซึ่ง **ใช้ไม่ได้ถ้าเครื่องไม่มี `mt.exe` เลย**
เพิ่มบล็อก `NEXT STEP` สองทางเลือกที่ทำได้จริง:
- **A.** มีในเครื่องแต่ค้นไม่เจอ → `set "PATH=%PATH%;<โฟลเดอร์ที่มี mt.exe>"` ในหน้าต่างนี้ (บอกด้วยว่าค่าตายพร้อมหน้าต่าง) แล้วรันใหม่
- **B.** ไม่มีในเครื่อง → รันตัวติดตั้ง Visual Studio 2008 แล้วติ๊กคอมโพเนนต์ Windows SDK — และ**บอกตรง ๆ ว่ารีโปนี้แจก `mt.exe` ให้ไม่ได้** (เป็นเครื่องมือของ Microsoft)

**nonclaim:** ไฟล์นี้เป็น batch ของ Windows · โคลนนี้ไม่มี cmd ⇒ **ยังไม่เคยถูกรัน** สิ่งที่อ้างคือ "ข้อความบอกทางออกแล้ว" ไม่ใช่ "รันผ่าน"

## 5. งานที่ 3 — กิ่ง NULL ของ `_speed_undo` เสียต้นเหตุหลัก (ใบ LANE-DB `2140`)

- docstring: **ขีดฆ่าประโยคเดิม ไม่ลบ** แล้วเขียนเหตุใหม่ พร้อมรายการ "แหล่งที่ยังเดินถึงกิ่งนี้ได้จริง" สี่ทาง
  (store ไม่มี `read_typed_attributes` · read โยน exception · แถวบนไฟล์ที่ไม่เคยรัน `009` · store ที่ไม่ใช่ `SQLiteStore`)
  เพื่อกันคนรุ่นถัดไปลบกิ่งทิ้งด้วยเหตุผล "009 ทำให้มันไปไม่ถึง" — `009` ปิดไปหนึ่งในสี่ ไม่ใช่ทั้งหมด
- เทส: `test_a_first_ever_speed_reports_not_reverted_rather_than_lying` **ชื่อมันโกหกไปแล้ว** ⇒ เปลี่ยนเป็น
  `test_a_store_with_no_prior_value_...` และเขียนในตัวเทสว่าชื่อเดิมคืออะไร ทำไมถึงเปลี่ยน
- เทสใหม่ `test_an_unreadable_prior_value_reports_not_reverted_too` เดินแหล่งที่ `009` **ไม่ได้** ปิด (read โยน exception)
  ⇒ กิ่งนี้ไม่ได้ยืนบนรูปที่ฐานข้อมูลจริงผลิตไม่ได้อีกต่อไป ซึ่งคือสิ่งที่ LANE-DB เตือนพอดี
