### 1ข. pf-adversary สองรอบ 12 ข้อบกพร่อง แก้ครบก่อน commit

เรียก pf-adversary สองครั้งก่อน commit ตามกติกา ได้ข้อบกพร่อง 12 ข้อ แก้ทั้งหมดใน PR นี้
สี่ข้อที่หนักที่สุด (ทั้งสี่ผู้ตรวจวัดมาแสดง ไม่ได้แค่ทักท้วง):

1. 🔴 **ตัวสำรองเองทำลายของจริง** — `_copy_consistent` เปิด DB ต้นทางแบบ read-write ตอนปิด
   connection สุดท้าย SQLite checkpoint แล้ว **ลบ `-wal`/`-shm` ทิ้ง** = โมดูลที่ docstring เขียนว่า
   "สร้างอย่างเดียว" กลับเป็นตัวเดียวในระบบที่ทำสิ่งที่ย้อนไม่ได้กับไฟล์ของเจ้าของ ก่อนตรวจอะไรเลยด้วย
   แก้: เปิดผ่าน `mode=ro` URI ทุกจุด (วัดแล้วว่าไบต์ของ DB และ `-wal` ไม่ขยับเลย)
2. 🔴 **สำเนาที่ล้มกลางคัน หน้าตาเหมือนสำเนาที่ดี** — โฟลเดอร์ชื่อเดียวกัน มีไฟล์ชื่อเดียวกับ DB จริง
   ขนาด 0 ไบต์ เจ้าของที่เพิ่งถูกบอกว่าเซิร์ฟเวอร์ไม่ขึ้น อาจ copy กลับทับโลกจริง
   แก้: ประกอบในโฟลเดอร์ชื่อลงท้าย `.INCOMPLETE` แล้ว rename เป็นชื่อจริง **หลัง** ตรวจผ่านเท่านั้น
3. 🔴 **ประตูใช้สำเนาเดิมซ้ำ ส่งสำเนาที่พังกลับไปโดยไม่เปิดอ่าน** — เงื่อนไขเดิมคือ `is_file()`
   อย่างเดียว `verification.sha256` ใน manifest เขียนครั้งเดียวแล้วไม่เคยถูกเทียบกับไฟล์จริงอีกเลย
   สำเนาที่ถูกตัดขาดภายหลัง (bad sector / copy ค้าง / ดิสก์เต็ม) จะถูกส่งกลับให้ boot แล้ว migrate ต่อ
   แก้: re-hash + เปิด + `integrity_check` ใหม่ทุกครั้งก่อนยอมให้ใช้แทนสำเนาใหม่ (และไม่ลบของเดิมทิ้ง)
4. 🔴 **วิธีกู้ที่เขียนไว้ กู้ไม่ได้จริง** — ทำตาม `restore_hint` เดิมตรงตัวแล้ววัด: เซิร์ฟเวอร์ที่ปิดปกติ
   ทิ้ง `-wal` ร้อนไว้ข้าง DB ปลายทาง SQLite จึง replay มันทับสำเนาที่เพิ่ง copy กลับ = แถวหลัง snapshot
   กลับมา และ `integrity_check` ยังบอก `ok` แก้: hint บอกให้ย้าย `-wal`/`-shm` ของจริงออกก่อนเป็นขั้นที่ 1

อีกแปดข้อ: `mkdir` หลุดออกมาเป็น `OSError` ดิบแทน `BackupError` · DB ที่ยังไม่ใช่ WAL โดน
`connect()` เขียน header ทับโดยไม่มี backup · boot ที่ล้มซ้ำ ๆ ทำสำเนาเต็มใบทุกครั้ง (วัดได้ 10 ครั้ง
= 10 สำเนา) · `.INCOMPLETE` ที่ค้างสะสมจนดันโควตาพื้นที่ว่างจนเซิร์ฟเวอร์ไม่ยอมขึ้นถาวร ·
`stamp` ไม่ถูกตรวจ escape ออกนอกโฟลเดอร์ได้ · ชื่อไฟล์ที่อ่านจาก manifest ไม่ถูกตรวจ ·
docstring อ้างเกินจริงว่า probe ไม่แตะดิสก์เลย · คำอ้างในหัวไฟล์เทสที่กว้างเกินหลักฐาน

### 1ค. เทสที่ผ่านด้วยเหตุผลผิด — mutation testing 19 แบบ

รัน mutation กับโมดูลตัวเอง 19 แบบ รอบแรกมี **สี่แบบที่รอดทั้งที่ควรถูกจับ** = เทสผ่านด้วยเหตุผลผิด:

- เปลี่ยน online-backup API เป็น `shutil.copy` แล้วยังเขียว — เพราะเทสเปิดสำเนาในโฟลเดอร์ที่มี
  `-wal` ดิบวางอยู่ข้าง ๆ SQLite เลยกู้ธุรกรรมจากไฟล์นั้นให้ ไม่ว่าสำเนาหลักจะสมบูรณ์หรือไม่
  แก้: ย้ายสำเนาไปโฟลเดอร์ว่างก่อนเปิด + ย้าย `-wal` ดิบไปไว้ใน `raw_originals/`
- ลบการตรวจ `integrity_check` ทิ้งทั้งก้อนแล้ว hardcode `"ok"` ยังเขียว — เพราะเทส assert ค่าคงที่
  ที่โค้ดเขียนเองเสมอ แก้: เพิ่มเทสที่ทำ DB พังจริง + เทสที่บังคับสาขา "SQLite ตอบว่าไม่ ok"
- เปิดต้นทางแบบ read-write ยังเขียว — เพราะเทสเดิมมี connection ค้างไว้ SQLite เลย checkpoint ไม่ได้
  แก้: เพิ่มเทสที่จำลอง **เซิร์ฟเวอร์ถูก kill** ด้วย subprocess + `os._exit` แล้ววัดว่า `-wal` ไม่หาย
- ลบ probe ที่คุมเวลา lock ออก ยังเขียว — `Connection.backup` retry `SQLITE_BUSY` ไม่มีเพดานและ
  ไม่สน `busy_timeout` (ผู้ตรวจวัด: mutant รอ lock 20 วิแล้วสำเร็จ ของจริงล้มใน 5.0 วิ)
  แก้: เพิ่มเทสที่ให้ subprocess ถือ `BEGIN EXCLUSIVE` แล้ววัดว่าล้มภายในเวลาที่กำหนด

หลังแก้ **ทั้ง 19 แบบถูกจับหมด**
