### D6 — `except RuntimeError` โยนความผิดให้ migration 018 กับทุก RuntimeError ที่ store โยนออกมา
`grant_all` รับ `store: object` โดยเจตนา (อะไรก็ได้ที่มีประตู) แต่ดักด้วย**ชนิด**อย่างเดียวแล้วสรุปว่าทุก `RuntimeError` = "ประตูม้วนทรานแซกชันกลับเพราะฐานยังไม่ apply `migrations/018_character_skills_gm_grant_source.sql`" — ซึ่งจริงกับ `SQLiteStore` **วันนี้เท่านั้น** `RuntimeError` คือสิ่งที่ generator ที่ถูกเข้าซ้ำโยน ที่ `dict` ที่ถูกแก้ระหว่างวนโยน และที่ store ห่อชั้นใด ๆ โยนด้วยเหตุผลของตัวเอง ⇒ ความผิดพลาดที่ไม่เกี่ยวกันเลยจะพาผู้ปฏิบัติไปนั่งอ่าน `schema_migrations` ของฐานที่**ไม่ได้เสีย**

แก้: เพิ่มค่าคงที่ `GRANT_DOOR_ROLLBACK_SIGNATURE = "grant_gm_skills:"` — ข้อความ rollback ของ `SQLiteStore.grant_gm_skills` เซ็นชื่อตัวเองไว้ที่หัวข้อความ ⇒ **ข้อความคือหลักฐาน ไม่ใช่ชนิด** เฉพาะ `RuntimeError` ที่มีลายเซ็นนี้จึงได้เหตุผล `REFUSED_GRANT_ROLLED_BACK` ที่เหลือตกไปสาขาทั่วไปที่**บอกชนิดของ exception** แทนการเดาสาเหตุ · รวมสองสาขาที่พูดประโยคเดียวกันเป็นฟังก์ชันเดียว `_unnamed_store_failure` เพื่อไม่ให้สองสำเนาเพี้ยนจากกันในการแก้ครั้งหน้า

🔴 **ทำไมไม่ใช้คลาส exception ร่วม ซึ่งเป็นทางที่ถูกกว่า**: คลาสนั้นต้องประกาศใน `store.py` = **เขต LANE-DB ไม่ใช่ของสายนี้** ⇒ ใช้การผูกกับสตริงแทน

🔴 **หมุดของลายเซ็นเป็นเชิงพฤติกรรม ไม่ใช่การอ่าน source** (adversary D-A วัดแล้วว่าเวอร์ชันอ่าน source **ผ่านเขียวทั้งที่ coupling ขาด**: ย้ายลายเซ็นไปไว้ใน comment ท้าย `raise` แล้วยังเขียว และ `inspect.getsource` unwrap decorator ให้เอง จน wrapper ที่ raise ข้อความอื่นก็ยังเขียว) ⇒ `test_the_grant_door_really_signs_the_rollback_it_raises` **เปิดฐานที่หยุดที่ migration 017 เรียกประตูจริง แล้วอ่านข้อความที่มัน raise ออกมาจริง** · ทดลองซ้ำการทดลองของ adversary เองแล้ว: ย้ายลายเซ็นไป comment ⇒ **แดง**

### D9 — สาขา undo ที่ตายแล้ว
`chat_command_action._skill_action` เส้นปฏิเสธส่ง `(lambda: False) if result.granted else None` ตัวป้องกันนี้เป็นของ**ลูปต่อ id ที่รอบ `ve2zs4` ลบทิ้งไปแล้ว** — ประตูรวมเป็นทรานแซกชันเดียว การปฏิเสธจึงมาถึงโดยไม่มีแถวบนดิสก์ได้อย่างเดียว และ**ทุกการปฏิเสธที่ `grant_all` สร้างได้ถือ `granted=0`** ⇒ ครึ่ง `if result.granted` **ไปไม่ถึงตลอดกาล** บรรทัดอ่านเหมือนตัวป้องกันที่มีชีวิต ทั้งที่เลือกได้แค่ `None` เสมอ

แก้ **รอบแรกผิด และ adversary จับได้บนกิ่งนี้เอง**: ร่างแรกเขียน `None` ตรง ๆ ⇒ **เปิด `wv0fpe` D2 กลับมาจากอีกด้าน** (D-C) เพราะ `granted == 0` กำลังทำหน้าที่แทนประโยค "ไม่มีแถวบนดิสก์" ซึ่งจริงเฉพาะกับ store ที่ประตูเป็นทรานแซกชันเดียว**และ**อ่านกลับมาครบ — คือสมมติฐานที่ D6 เพิ่งถอดออกไปเองหนึ่งฟังก์ชันเหนือขึ้นไป · store ที่เขียนจริงแล้วรายงานต่ำกว่าจริงให้ `granted=0` พร้อม curriculum ทั้งชุดบนดิสก์ และการไม่มี undo ทำให้คอนโซลพิมพ์ *"anything it had in hand was dropped with it"* ทับแถวที่ยังอยู่

**แก้จริง**: `SkillGrant` ได้ฟิลด์ `door_was_called` = ข้อเท็จจริงที่สายนี้**ถืออยู่จริง** (เรียกประตูไปแล้วหรือยัง ไม่ใช่การเดาว่าประตูเขียนอะไร) · `_skill_action` แนบ undo แบบ always-`False` ("the effect was KEPT") ให้ **ทุกการปฏิเสธที่ผ่านประตูไปแล้ว** และเหลือ `None` เฉพาะการปฏิเสธที่คืนค่า**ก่อน**ถึงประตู (id ไม่ถูก · ไม่มีประตู · อ่านแถวไม่ได้ · curriculum ว่าง) ซึ่งประโยค "dropped" เป็นจริงโดยโครงสร้าง ⇒ **สาขาที่ตายหายไปจริง และที่มาแทนคือเงื่อนไขที่มีชีวิตและมีความหมาย**

🔴 **หมุดก็ผิดรอบแรกเหมือนกัน** (D-B): ร่างแรก assert `result.granted == 0` — **ตัวเลขที่ store ตัวที่กำลังถูกสงสัยเป็นคนผลิตเอง** · adversary แก้ fixture ให้เขียน 137 แถวแล้วรายงานศูนย์ ⇒ **ยังเขียวสนิท** · หมุดตอนนี้อ่าน `FakeStore.skills` = ตัวดิสก์จริง ไล่ **8 เส้นปฏิเสธ** (เพิ่มเส้น "ประตูเขียนแล้วรายงานต่ำกว่าจริง") และ assert คู่ที่ห้ามเกิดตรง ๆ: **มีแถวบนดิสก์ + บอก dispatcher ว่าไม่ต้อง undo** · และ (D-F) เลิกใช้ regex สแกน body ของ `grant_all` ซึ่งมองไม่เห็น `_unnamed_store_failure` ที่นิยามอยู่**เหนือ**มันทั้งที่สร้าง refusal เองด้วย
