## pf-adversary จับอะไรได้ และรอบนี้แก้อะไรไปแล้ว

รายงานมา **11 ข้อ** ทั้งหมดแก้ในรอบเดียวกัน ยกเว้นที่ระบุว่าเป็นของสายอื่น

**สองข้อที่เจ็บที่สุด — เทสที่แดงไม่ได้**
เทสวันหมดอายุที่ผมภูมิใจว่า "ทำให้ prose แดงได้" **แดงไม่ได้จริง** ทั้งสองครึ่ง

- ครึ่งสอง สแกนทีละบรรทัดหา `next_item_identity` คู่กับ `UPDATE`/`INSERT` ⇒ SQL ที่เขียนแบบที่
  `store.py` เขียนอยู่จริง (แยกเป็น string literal ติดกันหลายก้อน หรือยกเป็นค่าคงที่ระดับโมดูล)
  **ผ่านฉลุย** · และ `"UPDATE" in "UPDATED_AT"` ทำให้ SELECT ธรรมดา **แดงผิด**
- ครึ่งหนึ่ง หาโทเคน `MOB_PICKUP_ROW_DID_INSERT` ที่ **ไม่มีใครในโปรเจกต์เคยเขียน** ⇒ เติม
  `persist_pickup_row` ที่ INSERT จริงเข้าไป แล้วปล่อยโทเคน `WOULD` ไว้เฉย ๆ ก็ยังเขียว

แก้เป็นการอ่าน AST ของสตริงที่ **ถูกส่งเข้า `execute`/`executemany`** จริงเท่านั้น (prose ที่บรรยาย
INSERT ไม่นับ — ซึ่งสำคัญ เพราะ `mob_pickup` บรรยาย INSERT นั้นไว้ยาวมาก) และครึ่งหนึ่งเปลี่ยนเป็น
"ฟังก์ชันไหนบ้างที่ INSERT แถวกระเป๋าได้" ต้องเท่ากับ `{_insert_initial_backpack}` เท่านั้น

รัน mutation ของ pf-adversary ซ้ำหลังแก้: A3 (แยก literal) **แดง** · A5 (ค่าคงที่โมดูล) **แดง** ·
