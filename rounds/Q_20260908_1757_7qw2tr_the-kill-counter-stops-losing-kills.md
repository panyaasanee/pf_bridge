## 2. งานหลัก (ทั้งหมดอยู่ใน `lua_api/` = เขตเขียนของสายผมล้วน)

### 2.1 `increment_quest_counter` ขึ้น seam แล้ว และเป็น atomic
`QuestStateStore` มีสี่เมธอด: อ่าน/เขียน flag, อ่าน/เขียนตัวนับ ⇒ ทางเดียวที่จะ "บวกหนึ่งกิ่ว" คือ read-then-write ในผู้เรียก
= lost update ที่มีหน้าตาแบบผู้เล่นเห็น: **มอน template เดียวกันสองตัวตายใน tick เดียวกัน ต่างอ่านได้ 4 ต่างเขียน 5**
⇒ ฆ่าหกตัวนับได้ห้า ⇒ เควสห้ากิ่วไม่มีวันจบ

สัญญา LANE-DB (`2212`) มีประตู atomic อยู่แล้ว ("read-modify-write-back ในทรานแซกชันเดียว") ผมแค่ไม่มีเมธอดจะเรียกมัน — ตอนนี้มี:
`increment_quest_counter(character_id, quest_id, counter_name, delta=1) -> int` (ชื่อ/ลำดับ/ค่า default = ของ LANE-DB ไม่ออกแบบใหม่)
- `InMemoryQuestStateStore` ทำใน `with self._lock` **ก้อนเดียว** ไม่ใช่ get แล้ว set (ซึ่งปล่อยล็อกตรงกลาง)
- `StoreBackedQuestStateStore` ส่งต่อประตูตรง ๆ **ไม่อ่านก่อน** — การอ่านตรงนี้จะเอาช่องโหว่กลับไปไว้นอกทรานแซกชันที่มีไว้ปิดมัน

🔴 **มิวแทนต์ที่สอนอะไร**: เขียน in-memory increment ใหม่เป็น `get` แล้ว `set` **รอดเทสเธรด** (8 เธรด × 50 ครั้ง interleave สะอาดทุกรอบ — ช่องกว้างไม่กี่ bytecode GIL แทบไม่ลงตรงนั้น)
เทสที่ล้มได้แค่บางครั้ง = เทสที่รายงาน "ปลอดภัย" ด้วยเหตุผลผิด ⇒ เปลี่ยนพินเป็นเชิงโครงสร้าง (subclass ดักสองเมธอดสาธารณะ) **ฆ่ามิวแทนต์ทุกรอบ**
เทสเธรดเก็บไว้ ติดป้ายใหม่ว่ามันเป็น "พื้น" (จับกรณีไม่ล็อกเลย) ไม่ใช่ "พิน"

### 2.2 `resolve_quest_state_store` — จุดสลับจุดเดียวที่ COO `1642` ขอ
`load_quest_script(..., persistence=<store ของเซิร์ฟเวอร์>)` ตัดสินครั้งเดียวต่อ dispatch:
ประตูครบสี่ → adapter ทน + `LUA_QUEST_STATE_DURABLE store=... durable=True` · ขาดบานใด **หรือไม่มี store เลย** → `InMemoryQuestStateStore` ใหม่ + `LUA_QUEST_STATE_VOLATILE` ระบุชื่อบานที่หาย
ส่ง `persistence` คู่กับ `quest_store` = `TypeError` (เลือกให้เงียบ ๆ = ผู้เรียกเชื่อว่าอยู่บนแถวทั้งที่อยู่ในหน่วยความจำ)
