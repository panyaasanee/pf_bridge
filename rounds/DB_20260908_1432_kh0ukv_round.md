## 1. งานที่ส่ง — pickup เป็นธุรกรรมเดียว `store.commit_pickup_taking_the_drop_off_the_ground`

### 1.1 รูที่ปิด — และมันไม่ใช่รูที่ผมคิดเอง มันเขียนอยู่ในโค้ดของสาย B แล้ว
`src/pirateforce_foundation/mob_pickup.py` ข้อ 16 (โน้ตของสาย B เอง) เขียนไว้ว่า:

> `BagCell.commit_pickup` advances `_issued_through` in memory **after the drop leaves the ground**;
> `store.commit_acquired_backpack_item` is **a separate later call that can refuse**
> (lease taken over, database locked, disk full). ... There is no re-seed call and no
> compensating put-it-back. **The call site (GT-124) must decide what the player gets**; until it
> does, this lane does not claim a pickup is atomic - only that the DATABASE write is.

แปลว่า: ระหว่างสองธุรกรรมนั้น **ของหลุดจากพื้นไปแล้ว และยังไม่เข้ากระเป๋า** · ไม่มีอะไรเอากลับ —
`commit_ground_drop` เป็นตัวเขียนตารางนั้นตัวเดียว และ `taken_at` ไม่เคยถูก **un-set** โดยอะไรเลย
⇒ แถวที่ผู้เล่นเดินเหยียบหายจาก `list_ground_drops_still_on_the_ground` **ถาวร** ส่วนกระเป๋าไม่เคยได้
🔴 และเพราะทั้งสองครึ่งอยู่บนดิสก์ **ความเสียหายรอด relog** — ผู้เล่นล็อกอินใหม่แล้วของก็ยังไม่อยู่

### 1.2 สิ่งที่เพิ่ม (เขตงานผมทั้งหมด — `store.py` เพิ่ม method ใหม่ได้ ห้ามเปลี่ยน behavior ของเดิม)
| ชื่อ | เป็นอะไร |
|---|---|
| `_require_acquired_row(item)` (staticmethod) | ด่านก่อนเปิดธุรกรรมของ `commit_acquired_backpack_item` **ยกออกมาทั้งดุ้น ไม่แก้สักบรรทัด** |
| `_commit_acquired_backpack_item_locked(db, sid, character_id, item)` | ตัวธุรกรรมเดิม **ทุก statement เหมือนเดิม** แต่ใช้ `db` ที่ผู้เรียกเปิดมา |
| `_require_ground_drop_key(scene, drop_key)` (staticmethod) | ด่านของ `mark_ground_drop_taken` ยกออกมา |
| `_mark_ground_drop_taken_locked(db, scene, drop_key)` | ตัว UPDATE เดิม ใน `db` ของผู้เรียก · idempotent เหมือนเดิม |
| 🔴 `commit_pickup_taking_the_drop_off_the_ground(sid, character_id, item, scene, drop_key)` | **ของใหม่** — สองครึ่งใน `BEGIN IMMEDIATE` เดียว |

**public method เดิมสองตัวยังทำงานเหมือนเดิมเป๊ะ** — ตัวมันเองแค่เปิดธุรกรรมแล้วเรียก `_locked`
ของตัวเอง (เทสเดิม 159 ตัวของสี่ไฟล์ที่แตะประตูนี้เขียวหมดโดยไม่แก้เทสสักบรรทัด — ดูข้อ 3)

### 1.3 ลำดับในธุรกรรมเป็นเจตนา ไม่ใช่ความบังเอิญ
มาร์กพื้น **ก่อน** · ถ้า `_mark_ground_drop_taken_locked` คืน `False` (ฉากนี้ไม่เคยมี `drop_key` นี้)
⇒ ปฏิเสธทั้ง pickup **ไม่มินต์แถวกระเป๋าให้ของที่ไม่เคยมีอยู่จริง**
> "an item out of nothing is a worse bug than a refused pickup"

ส่วน drop ที่ **ถูกเก็บไปแล้ว** คืน `True` (ประตูนั้น idempotent โดยเจตนา เพราะจดหมาย LANE-B บอกว่า
pickup ส่งซ้ำได้) และ **ไม่ถูกปฏิเสธตรงนี้** — ตัวที่กันการเขียนซ้ำคือด่าน identity ในครึ่งกระเป๋า
ซึ่งปฏิเสธด้วยชื่อของมันเอง (พินไว้ในเทส `test_a_second_delivery_of_one_drop_does_not_write_a_second_row`)

### D1/D2 — ประตูนี้ **ไม่ใช่ exactly-once** และเทสของผมเขียวแบบหลอกตัวเอง
ผมเขียน docstring ว่า "drop ที่ถูกเก็บไปแล้ว ครึ่งกระเป๋าจะเป็นตัวปฏิเสธด้วยด่าน identity"
**ผิด** · adversary วัดมาสองทาง:
- **ตัวละครสองตัว** ส่ง `drop_key` เดียวกัน ⇒ **ได้ของทั้งคู่** · `BEGIN IMMEDIATE` เรียงคิวให้เรียบร้อย
  แล้ว**ทั้งคู่ชนะ** เพราะฝ่ายที่แพ้ไม่เคยถูกบอกว่าแพ้ (ครึ่งพื้นคืน `True` · ครึ่งกระเป๋ามองคนละ counter)
- **ตัวละครเดียว** ส่งซ้ำ ⇒ **ได้แถวที่สอง** ทันทีที่ re-mint ซึ่งคือสิ่งที่ re-delivery จริงทำ
  (`place_in_bag` อ่านกระเป๋าที่ขยับแล้ว หยิบ slot ถัดไป)
🔴 เทส `test_a_second_delivery_...` ของผม**เขียวเพราะส่ง `ItemAttrState` ตัวเดิมกลับไป** —
เขียวจาก **state delta ไม่ใช่จากประตู** · adversary บอกคำเดียวที่เปลี่ยนแล้วเทสแดง: `self._mint()`
**จ่ายแล้ว**: เทสตัวนั้นถูกเขียนใหม่ให้ **ยืนยันว่าแถวที่สองลงจริง** และเพิ่มเทสตัวละครสองตัว
⇒ ทั้งคู่ **assert ตัวบั๊กโดยเจตนา** วันไหนมีคนผูก bag row เข้ากับ drop เทสสองตัวนี้จะแดง
และ**นั่น**คือรอบที่มีสิทธิ์อ้าง exactly-once

**คำถามเดียวที่ดีไซน์นี้ยังตอบไม่ได้ (adversary เขียนเอง)**: อะไรผูก bag row เข้ากับ drop ที่มันมาจาก?
`character_backpack_items` ไม่มี `drop_key` · `ground_drops` ไม่มี "ส่งให้ใครแล้ว" ⇒ หลัง commit
**ไม่มีอะไรใน DB ตอบได้ว่า "drop นี้เข้ากระเป๋าใครไปหรือยัง"** · counter ต่อตัวละครตอบคำถามเกี่ยว drop ไม่ได้
⇒ สิ่งที่ผมสร้างจริงคือ **all-or-nothing ต่อความพยายามหนึ่งครั้ง** ไม่ใช่ exactly-once · เขียนลง docstring แล้ว
