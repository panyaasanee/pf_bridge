## 1. `new_character_vitals()` — ใบ `0443` ข้อ 1

`src/pirateforce_foundation/persistence_vitals.py` เพิ่มสามอย่าง:

- `NEW_CHARACTER_VITALS_LABEL` — สตริง ASCII เดียวกับป้ายบนหัว `007` เป๊ะ
- `_NEW_CHARACTER_VITALS` — ค่าจริง **private** เพื่อให้ผู้เรียกทำ dict ของโมดูลเปื้อนไม่ได้
- `new_character_vitals()` — คืน `{"level": 1, "hp_current": 100, "hp_max": 100}` **คีย์เป็นชื่อคอลัมน์**
  เพราะผู้บริโภคคือ INSERT ของ `create_character`

**ทำไมเป็นฟังก์ชัน ไม่ใช่ DEFAULT ในสคีมา** — ใบ `0443` ข้อ 2 ห้ามทาง ก ไว้ชัด: SQLite ใส่ DEFAULT
ให้คอลัมน์ที่มีอยู่แล้วไม่ได้ ต้อง rebuild ตาราง = ฝังเลขที่ตัวเองติดป้ายว่า OPEN ไว้ในสคีมาถาวร
แล้ววันที่ RE ตอบต้อง rebuild อีกรอบ ฟังก์ชันแก้ที่เดียวบรรทัดเดียว

**ทุกครั้งที่เรียก มัน validate ตัวเองผ่านประตูหน้าของโมดูลก่อนคืนค่า** (`resolve(...)` แล้วเช็ค gaps)
ไม่ใช่ท่าป้องกันเปล่า ๆ: ค่าตอนเกิดที่โมดูลตัวเองปฏิเสธ = ตัวละครที่เซิร์ฟเวอร์ประกอบเฟรมล็อกอินให้ไม่ได้
และความผิดจะโผล่เป็น "แถวนี้ผิด" ทั้งที่ไม่มีใครเขียนแถวนั้นด้วยมือ ราคาคือเช็คช่วงจำนวนเต็มสามตัว

## 2. กฎ `level = 0` — ใบ `0443` ข้อ 4

`REASON_LEVEL_ZERO` + กฎใน `_consistency_gaps` ⇒ `resolve(...).require()` ปฏิเสธแถวที่เก็บ `level = 0`

**ช่องที่มันปิด ไม่ใช่ทฤษฎี** — `007` เจอช่องนี้เองแล้วปิดจากฝั่ง migration (มี `AND (level IS NULL OR
level > 0)` ในคำสั่งของมัน) แต่การปิดนั้นครอบแค่ทางที่ผ่าน migration แถวที่ `level = 0` ถูกปฏิเสธวันนี้

ผู้ดูแล · migration อื่น) จะทำให้มันกลายเป็นแถวที่ `require()` **รับ** และ `apply_hp_damage` **รันได้**
รอบ ๆ เลเวลที่ไม่มีใครตัดสิน รอบนี้ปิดจากฝั่ง decision layer ซึ่งเป็นฝั่งที่ยังยืนเมื่อคนเติมไม่ใช่ migration
