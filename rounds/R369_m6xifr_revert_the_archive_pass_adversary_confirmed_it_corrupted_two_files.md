The fix from R368 landed as intended. (Noting this not to relitigate the adversary's work, but because a "measure twice" habit only works if I actually check disagreements against primary evidence instead of picking whichever version is more convenient.)

2. **"Systemic truncation" -- TRUE, confirmed directly.** R368's extraction cut each ticket's section at the *next markdown header of any level* (`##` or `###`), reasoning at the time that this was the *safer* (narrower) boundary than "next ticket header." That reasoning was backwards: this file's own convention uses `###` for a ticket's *own* internal subsections (`### steps`, `### pass criteria`, `### nonclaims`). Confirmed directly: `GT-026`'s stub at `GAME_TEST_QUEUE.md:626` in `694986a` is immediately followed, still in the live file with no parent header, by its own `### steps (สองท่อน แยกจ็อบ อย่ารวม)` / `### pass criteria (สองชั้น)` / `### nonclaims ที่ต้องเขียนติดผลเสมอ` sections -- real ticket content, orphaned, invisible to `pf_queue_status.py`'s own header-based scan going forward. The adversary's estimate is that this affected 16 of the 22 archiving targets and left roughly 214 KB of real ticket content stranded, headerless, in the live files (not lost -- still physically present -- but structurally broken and why the size reduction measured in R368 was much smaller than the archived tickets' true size).

3. **"An OPEN section archived as closed" -- TRUE, confirmed directly.** `CLIENT_RE_QUEUE.md` has two separate `## RE-234 ...` headers (a pre-existing structural duplicate in the file, not introduced by R368): one genuinely `DONE/MIXED` (original line 854), one genuinely `[OPEN -- ...]` (original line 862, its own header text says so). R368's script matched "RE-234" once, archived whichever occurrence it found, and got the **open** one -- `git show 694986a:CLIENT_RE_QUEUE.md` line 862 reads the OPEN header text with an "-- archived 20260906 (closed; ...)" suffix appended to it. This is a direct instance of the one rule this whole exercise exists to protect ("an open/untested ticket must survive byte-for-byte, in the same file, no matter how old") and it slipped past R368's own verification (`pf_queue_status.py`'s scan is a dict keyed by ticket id -- first occurrence wins -- so a duplicate id is structurally invisible to the "open count unchanged" check).

Root cause of both 2 and 3: the extraction script trusted the *same* regex-based header match for three different jobs at once -- classifying open/closed, finding section boundaries, and (implicitly) assuming ticket ids are unique -- without checking any of those three assumptions against what the file actually does.
