## 1. [MEDIUM] `mark_saturation_announced()` ติดครั้งเดียว**ตลอดชีวิตโปรเซส** ไม่ใช่ต่อเหตุการณ์

adversary วัด: ledger อยู่ใน `WeakKeyDictionary` ผูกกับ backing store ⇒ อยู่ยาวเท่าอายุโปรเซส · ไม่มีที่ไหน reset
`_saturated`/`_saturation_announced` แม้แถวที่ทำให้เต็มจะถูก `clear()` ไปแล้วและมีที่ว่างใหม่จริง ⇒ เหตุการณ์เต็มรอบที่สอง
(ตัวละครคนละคน สาเหตุคนละอย่าง) จะไม่มีเสียงอีกเลย

**ทำไมไม่ใช่ของเสียใหม่**: `saturated()` เดิม (ก่อนรอบนี้) ก็ "ติดครั้งเดียวตลอดชีวิต" อยู่แล้ว (ไม่มีโค้ดเดิมไหน reset
`_saturated` กลับ False) — `mark_saturation_announced()` ที่รอบนี้เพิ่มแค่ทำตามสัญญาเดิมของ flag ที่มันอ่าน ไม่ได้ทำให้
อะไรแย่ลงกว่าที่เป็นอยู่ (ก่อนรอบนี้ = ไม่มีเสียงเลยแม้ครั้งแรก · หลังรอบนี้ = มีเสียงครั้งแรก ไม่มีเสียงครั้งที่สอง) —
เป็นข้อจำกัดที่สืบทอดมา ไม่ใช่การถดถอย แต่เป็นข้อจำกัดจริงที่ควรแก้ ⇒ ยกไปรอบหน้า (ข้อ 2 ใน "รอบหน้า" ด้านล่าง)

## 2. [LOW-MEDIUM] "ไม่มีการเขียนใดสร้างเลขลบได้" ยืนด้วยธรรมเนียม ไม่ใช่ข้อบังคับชั้น DB

adversary grep ทุกจุดเรียก `.set_quest_flag(` ใน `src/` เจอ 3 จุด (สองปิดกั้นด้วย `_coerce_int(..., _MAX_FLAG_VALUE)` ·
หนึ่ง hardcode ค่าไม่ลบใน `trigger.py`) — วันนี้ปลอดภัยจริงตามที่ enumerate ได้ครบ แต่ `store.py`/migration `019`
**ไม่มี CHECK/enum ที่ชั้น DB** (ตั้งใจ ตาม `COO-DECISION 20260901_1059`) ⇒ เครื่องมือซ่อม/แอดมินในอนาคตที่เขียนตรงชั้น
store อาจชน `-1` โดยไม่รู้ตัว

**ทำไมไม่ใช่ของเสียใหม่**: ความไม่บังคับนี้มีอยู่ก่อนรอบนี้ (DB ไม่เคยเช็ค `flag_value` มาตั้งแต่ migration `019`) รอบนี้
แค่ทำให้ `-1` มีความหมายใหม่ที่โค้ดชั้น store ไม่รู้จัก — เขียนเป็นคำถาม COO/LANE-DB แยก (ข้อ 3 ใน "รอบหน้า")

## 4. [ข้อสงสัย ไม่ใช่ข้อสรุป] เลข "410"/"26" ใน docstring ของผมยกมาจากรอบก่อน ไม่ได้วัดซ้ำเอง
