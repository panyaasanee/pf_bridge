### 2 ต้นเหตุ

รอบก่อนเขียน `with sqlite3.connect(self.path) as db:` สองจุดในเทสนั้น
context manager ของ `sqlite3.Connection` **commit/rollback แต่ไม่ close** — handle ค้างจนกว่า GC
จะเก็บ ไฟล์เดียวกันนี้ใช้แพตเทิร์น `db = sqlite3.connect(...)` + `try/finally: db.close()` อยู่แล้ว
ทุกจุดที่เขียนไว้ก่อนหน้า (`:711`, `:790`) รอบก่อนคือจุดเดียวที่ออกนอกแพตเทิร์นของไฟล์ตัวเอง

วัดตรง ๆ บน Linux ว่ามันรั่วจริง ไม่ใช่เดาจาก traceback:

```
baseline                              : 0
after try/finally close, frame gone   : 0
after `with` form, frame gone         : 1   <- handle ค้างข้ามการจบฟังก์ชัน
after an explicit gc.collect()        : 0   <- อายุของมันขึ้นกับว่า GC วิ่งเมื่อไร
```

บรรทัดที่สามคือความผิด บรรทัดที่สี่คือเหตุผลที่ POSIX มองไม่เห็น: unlink ไฟล์ที่ยังเปิดอยู่สำเร็จเสมอ
บน Windows ไม่สำเร็จ

### 3 แก้

- สองจุดที่รั่ว → แพตเทิร์นเดิมของไฟล์ (`try/finally: db.close()`) ไม่ได้คิดแพตเทิร์นใหม่
- เพิ่มคลาส `NoLeakedSqliteHandleTests` สาม source pin กันไม่ให้กลับมาเงียบ ๆ บนเครื่อง POSIX:
  1. ห้ามมี `with sqlite3.connect(` ในไฟล์นี้
  2. ทุกจุดที่ `X = sqlite3.connect(...)` **ในเมธอดเดียวกัน**ต้องมี `X.close()` หรือ `return X`
     (กรณีหลังคือส่งหน้าที่ปิดให้ผู้เรียก — `_at_005_with_a_character` ทำแบบนั้นจริง กติกาแบบ
     "ต้องปิดภายใน N บรรทัด" จะรายงานมันผิดเป็นบวกลวง จึงไม่ใช้)
  3. พิสูจน์ว่าตัวจับยังจับบรรทัดรูปแบบที่ทำให้ PR #495 ตายได้จริง
