## 1. `migrations/007_character_vitals_seed.sql` — สิ่งที่ลงจริง

สองคำสั่ง ไม่มีอย่างอื่นเลย:

```sql
UPDATE characters SET level = 1 WHERE level IS NULL;
UPDATE characters SET hp_current = 100, hp_max = 100
    WHERE hp_current IS NULL AND hp_max IS NULL
      AND (level IS NULL OR level > 0);
```

เลขสามตัวมาจากไหน — แต่ละตัวพร้อมบรรทัดที่ส่งมันอยู่ **วันนี้**:

| คอลัมน์ | ค่า | บรรทัดที่ส่งอยู่แล้ว |
| --- | --- | --- |
| `level` | `1` | `player_wire.py:203` = `PLAYER_LOGIN_LEVEL` ที่ `:22` |
| `hp_current` | `100` | `player_wire.py:204` literal ในตัว |
| `hp_max` | `100` | `player_wire.py:205` literal ตัวที่สอง |

⇒ ไม่มีเลขใหม่เข้าโลก ไบต์บนไวร์ไม่ขยับสักไบต์ในวันที่มันรัน สิ่งที่เปลี่ยนคือเซิร์ฟเวอร์
**บอกได้ว่าทำไมถึงส่งเลขนั้น จากแถว ไม่ใช่จาก literal** และการเขียนทับทีหลังจะรอดข้าม logout

### จุดเดียวที่ **แคบกว่า** ใบสั่ง — รายงานไว้ตรงนี้ ไม่กลบ
ใบ `0250` เขียน `WHERE ... IS NULL` ทั้งสามคอลัมน์ ถ้าแปลตรงตัวเป็นสามคำสั่ง คำสั่งของ `hp_current`
จะยิงแถวที่ `hp_max = 50` อยู่แล้วแต่ `hp_current` เป็น NULL ⇒ ได้ `hp_current = 100 > hp_max = 50`
ซึ่ง `persistence_vitals.resolve(...).require()` **ปฏิเสธ** = migration ผลิตตัวละครที่ประกอบบล็อกไม่ได้
ด้วยมือของตัวเอง จึงรวมคู่ HP เป็นคำสั่งเดียว — **แตะแถวได้น้อยลงเท่านั้น ไม่มีทางมากขึ้น**
แจ้ง COO ในใบ `0330` แล้ว ถ้าสั่งกลับเป็นสามคำสั่ง แก้ได้ในรอบเดียว
