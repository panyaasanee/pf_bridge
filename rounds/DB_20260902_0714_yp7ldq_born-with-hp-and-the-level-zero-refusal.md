### 1 `new_character_vitals()` — ค่าที่ตัวละคร "เกิดมาพร้อม" (ใบ `0443` ข้อ 1)

`src/pirateforce_foundation/persistence_vitals.py` `new_character_vitals` (`:512` วันที่ลง) คืน `{"level": 1, "hp_current": 100,

ป้ายที่มา `NEW_CHARACTER_VITALS_PROVENANCE` (`:495`) เป็นสตริงเดียวกันเป๊ะกับหัว `007`

สองเรื่องที่ตั้งใจ ไม่ใช่ความสะดวก:

- **เป็นตัวเลขตรง ไม่ใช่ `import` จาก `player_wire`** — ถ้า import วันที่ใครแก้
  `PLAYER_LOGIN_LEVEL` ด้วยเหตุผลอื่น ตัวละครที่เกิดหลังจากนั้นจะต่างจากโคฮอร์ตที่ `007` ซีดไว้
  แบบเงียบ ๆ ไม่มีอะไรแดง ความเท่ากันจึงเป็น **ข้ออ้าง** และถูกให้คะแนนด้วยเทสที่ derive ใหม่
  จาก `player_wire.py` **และ** จาก SQL ของ `007` ที่ head ทั้งคู่ (ไม่ใช่เทียบกับค่าคงที่ในไฟล์เทสเอง)
- **ผ่านประตูหน้าของโมดูลตัวเองก่อนคืนค่า** — `resolve(born).require()` รันบนค่าที่จะคืน
  ⇒ ถ้าวันหน้าใครแก้ค่าคงที่สามตัวนั้นจนพัง มันจะ raise **ที่จุดเรียก** ไม่ใช่ไปโผล่เป็นแถวใน DB
- 🔴 **บวกกฎ "ห้ามเกิดมาตายแล้ว"** — `pf-adversary` ตั้ง `NEW_CHARACTER_HP_CURRENT = 0`
  แล้ว `resolve().require()` **ปล่อยผ่านสบาย** ทั้งที่ย่อหน้าแรกของโมดูลเขียนเองว่า 0 บนไวร์นี้
  ไม่ใช่ "ไม่รู้" แต่คือ **ตาย** · `resolve` ปฏิเสธไม่ได้และ**ต้องไม่ปฏิเสธ** เพราะศพที่ 0 HP
  คือสถานะที่ถูกต้องของแถวเดิม (มีเทสเดิมตรึงไว้) มันเป็นเรื่องไร้สาระ**เฉพาะตอนเกิด**
  กฎจึงอยู่ใน `new_character_vitals()` ที่เดียว ไม่ไปไหน

🔴 **มันไม่ได้เขียนฐานข้อมูล** — ไม่มี connection ไม่มี execute ไม่มี row มันคือ **คำตัดสิน**

### 2 กฎ `level = 0` ปฏิเสธ (ใบ `0443` ข้อ 4)

`persistence_vitals.py:429` `resolve(...).require()` ปฏิเสธ `level = 0` แบบเดียวกับที่ปฏิเสธ
`hp_max = 0` อยู่แล้ว รหัสเหตุผลใหม่ `REASON_LEVEL_ZERO` (`:191`)

วางไว้ **ก่อน** กฎคู่ HP โดยตั้งใจ: กฎคู่ HP `return` ทันทีเมื่อจุดติด แถวหนึ่งพังได้สองทางพร้อมกัน
