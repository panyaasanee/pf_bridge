## 🌿 กฎ commit / push (ท่อนที่เปลี่ยนมากที่สุด — Panya ต้องเคาะข้อ A/B ก่อนใช้)

**กฎเดิม "commit ต้องทำบน Windows bridge เท่านั้น" เกษียณแล้ว** — เหตุผลจริงของกฎนั้นคือ
*sandbox git index stale บน worktree ที่แชร์ผ่าน mount ⇒ phantom deletions* **ไม่ใช่คำว่า "Windows"**
ที่นี่ index มาจาก clone ของรอบนี้เอง ไม่มี mount ร่วมกับใคร ⇒ **commit ได้**

**เงื่อนไขที่ตรวจได้ (ต้องจริงทุกข้อก่อน commit):**
1. index มาจาก clone ของรอบนี้เอง · `git status` ต้นรอบสะอาด
2. **ห้าม `add -A`** — ใช้ `git add --` เฉพาะ path ที่ประกาศไว้ในจดหมายรอบนั้น แล้ว **นับจำนวน staged เทียบเลขที่ประกาศ**
3. **ปฏิเสธ deletion ที่ไม่ได้ประกาศ** (`git diff --cached --name-status | grep '^D'` ต้องว่างหรือตรงกับที่ประกาศ)
4. ยืนยัน HEAD ขยับจริงหลัง commit
5. **ห้าม `push --force` · ห้าม `reset` · ห้าม `clean` · ห้าม `stash` · ห้าม `checkout .`** ทุกกรณี ไม่มีข้อยกเว้น
6. `pull --rebase` ก่อนเริ่มงานเสมอ · ถ้า rebase ชน **ห้ามแก้ด้วยการทิ้งของฝั่งเขา** ให้หยุดแล้วรายงาน

**กติกา push ของ Routine (จากเอกสารของ Anthropic):**
- branch ที่ขึ้นต้น `claude/` — **รับเสมอ**
- branch อื่น — รับก็ต่อเมื่อ **ไม่ถูก protect · ไม่มี PR เปิดค้างจาก branch นั้น · ไม่มี commit ของคนอื่น**
- commit/PR จะขึ้นชื่อ GitHub ของ Panya (routine ผูกกับบัญชีเธอ)

2. หา branch ของรอบก่อน **ด้วยคำสั่งนี้เท่านั้น ห้ามไล่ดูด้วยตา:**

   🔴 **ทำไมต้องเป็น `refs/remotes/origin/claude/` ไม่ใช่ `git branch -r` แล้วค่อยกรอง:**

   แล้วอ่านผล gate ของ commit ปลาย branch นั้น (วิธีอ่าน = หัวข้อถัดไป)

   - 🟢 **เขียว** ⇒ **fast-forward `main` ไปหา branch นั้น** → push `main` → ลบ branch → **แล้วค่อยเริ่มงานใหม่**
   - 🔴 **แดง** ⇒ **ห้าม merge · ห้ามเริ่มงานใหม่** — **งานทั้งรอบคือทำให้มันเขียว** แล้ว push ทับ branch เดิม
   - ⏳ **ยังรันอยู่ / ไม่พบผล** ⇒ **ไม่ merge รอบนี้** · ทำงานใหม่บน branch ใหม่ได้ · **เขียนในจดหมายว่ามีกี่ branch ค้าง**
     🔴 **"ไม่พบผล" ไม่ใช่ "เขียว" เด็ดขาด** — ไม่มีข้อมูล แปลว่าไม่มีข้อมูล

**ข้อบังคับ (ทุกข้อมาจาก Panya โดยตรง):**
- 🔴 **fast-forward เท่านั้น** — ถ้า `main` ขยับจนไม่ ff ได้ **หยุดและรายงาน ห้าม force ห้าม merge commit**
- 🔴 ต้นรอบ **rebase branch งานใหม่บน `main` ล่าสุดเสมอ**
- 🔴 **branch ค้างยังไม่ merge ≥ 2 อัน ⇒ หยุดเปิดงานใหม่ ทั้งรอบใช้ไล่เคลียร์ของค้าง**
- **รอบแรกสุดไม่มี branch ก่อนหน้า (bootstrap)** ⇒ ข้ามขั้น 1-3 ไปทำงานได้เลย **และเขียนในจดหมายว่านี่คือรอบ bootstrap**

- ⚠️ **ราคาที่จ่าย: `main` ตามหลังงานล่าสุดหนึ่งรอบเสมอ** ⇒ ถ้ารายการในคิวเทสต้องใช้ commit ที่เพิ่งลง branch

🔴 **สี่กฎการอ่าน — ทุกข้อคือจุดที่มันพังเงียบ ๆ ได้ (ห้ามข้ามแม้ข้อเดียว):**

**① เทียบ `sha` ในไฟล์กับ SHA ที่จะ merge ก่อนเชื่อเสมอ — ห้ามอ่านแค่คำว่า `success`**

*(โดยดีไซน์ไฟล์ชื่อตาม SHA อยู่แล้ว การไม่ตรงจึงแปลว่ามีอะไรผิดปกติ ไม่ใช่เรื่องธรรมดา)*

**② เขียวคือคำว่า `success` คำเดียวเท่านั้น**
`needs.gate.result` เป็นได้สี่ค่า: `success` · `failure` · `cancelled` · `skipped`
🔴 **`skipped` และ `cancelled` ไม่ใช่เขียว และไม่ใช่แดง — เข้าเคส ⏳ (ไม่ merge)**

**③ ไม่มีไฟล์ = ไม่รู้ผล = ⏳ = ไม่ merge — ห้ามแปลว่า "น่าจะเขียว" เด็ดขาด**
`git show` จะออก **exit 128** พร้อมข้อความ `does not exist` เมื่อยังไม่มีคำตัดสินของ commit นั้น
กรณีที่เจอได้จริง: workflow ยังรันไม่จบ · runner ตายกลางคัน · job `publish-status` เองล้ม
**ทั้งสามกรณีมีคำตอบเดียวกัน: ไม่ merge รอบนี้ ทำงานใหม่บน branch ใหม่ได้ แล้วเขียนในจดหมายว่ามีกี่ branch ค้าง**

**④ ไม่มี `ci/latest.json` และจะไม่มีตลอดไป — นี่คือความตั้งใจ ไม่ใช่ของที่ลืมทำ**
ไฟล์ "ล่าสุด" ทำให้อ่านคำว่า `success` ของ commit อื่นแล้ว merge commit ที่ยังไม่ผ่าน **โดยไม่มีสัญญาณเตือนใด ๆ**
ถ้าอยากรู้แค่ว่า "กลไกยังมีชีวิตไหม" ให้ลิสต์ไดเรกทอรีแทน:
```
git ls-tree --name-only origin/ci-status ci/
```
